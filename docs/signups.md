# Anmeldung

Endnutzer-Sicht: siehe [guide-discord.md#anmeldung](guide-discord.md#anmeldung), [guide-web-admin.md#anmeldungen](guide-web-admin.md#anmeldungen).

> **Sprache im Discord:** Alles, was ein Raider im Discord rund um Events und Anmeldung liest, ist **standardmäßig Deutsch** und auf Englisch umschaltbar: öffentliche Nachrichten (Anmelder-Nachricht, Setup-Nachricht, Talk-Übersicht, Panels, Ankündigung, Discord-Event, Notiz im Orga-Kanal, öffentliche Event-Seite) in der Server-Sprache, alles Persönliche (Dialoge, Modals, Antworten, DMs, `/profil`, die Absage des Berechtigungs-Gates) in der eigenen Sprache des Raiders (`/language`, DE/EN-Schalter im Web), sonst der Server-Sprache. Wie das gebaut ist — `tr()`, Katalog, `serviceText`, `specLabel`, Sprachwechsel —: [bot-commands.md](bot-commands.md), „Sprache des Bots“. Datum/Uhrzeit im Discord sind immer **Discord-Timestamps** (`<t:…:F>` usw.); wo keiner rendert (Select-Optionen, Modal-Labels, öffentliche Seite) steht der Text in der Sprache in Serverzeit (Europe/Berlin). Gespeicherte Werte (Status-Keys, Spec-Keys) bleiben unverändert. Die englischen Beispiele in diesem Dokument („Saved for …“, „Late (1)“) sind die englische Fassung; auf Deutsch steht dort „Gespeichert für …“, „Spät (1)“.

## Anmeldung (Web) (`/signups`, `signup` area, #256)

The member's coming raids and their own signup. Menu entry *Anmeldungen* next to *Mein Profil*.

- **The rules live in `src/services/signups/signupService.js`**, UI-agnostic so the Discord signup (#258) uses it 1:1: `await submitSignup(eventId, userId, input, { byOrga, now, roleIds?, config? })` → `{ signup, event, waitlisted, locked, notice }` (#306) or `{ error, code }` (`httpStatusFor(code)`; **async** since it reads the member's roles). **Raider roles are checked on save, not only on the page:** a category with `categoryRoles` takes a *new* signup only from a holder of one (`checkRaiderRole`, `discord.memberRoleIds` on the event's server, `raider_role` → 403 „Für diesen Raid brauchst du eine Raider-Rolle.“); roles that cannot be read let it through, an existing own signup may still be changed or withdrawn, `byOrga` is exempt. **"Anmeldung nur für das Roster" (#658):** where the category's roster has `signupOnly`, the roster replaces the role rule inside `checkRaiderRole` (`rosterOnlyAccess`) — only members with status core (Stamm), trial (Probe) or bench (Ersatz) take a new signup, **paused members do not**; everyone else gets `roster_only` → 403 „Für diesen Raid melden sich nur Mitglieder des Rosters an (Stamm, Probe oder Ersatz). Frag die Raidleitung.“ (English through `botEnglish`/`serviceText`: "Only members of the roster (core, trial or bench) sign up for this raid. Ask the raid lead."). Same exemptions (orga, existing own signup); no Discord role is read then. Every Discord path (button, select, talk overview, several raids, status buttons) goes through `checkRaiderRole`, so the bot refuses with that sentence in the reader's language; the web row carries `rosterOnly: true` and the dialog shows the hint (`signups.dialog.rosterOnly`) with its button off, and words a `roster_only` refusal the same way (also in "Für alle gewählten"). Details: docs/roster-profile.md "Roster und der Rest des Tools". The rule itself — who may take a new signup — is `services/signups/signupAccess.js` (see „Which raids a member sees“ below), shared with the raider's lists of raids; `checkRaiderRole` only adds the exemptions (orga, existing own signup) and lets roles that cannot be read through. Only an own event (`raidhelper` otherwise), not after its start (`started`); the character must be in the raider's profile and the spec one of that character's profile specs (`character`/`spec`, then the rule set via `signupStore.normalizeSignup`). **After `signupDeadline` a member may only pick `absence` or `late`**, or keep the status and spec they already had (to edit the comment); `byOrga` (the orga **of that raid**, #727: the global orga with `raids` write, or a manager of the current roster of the raid's category — `web/events/raidOrgaAccess.js` `canOrgaRaid`, the rule of the `orgaScoped` gate, docs/permissions.md „Kategorie-Orga“; a raider role holding `raids` write without an orga rank is bound like everyone) is bound by neither, nor by a closed signup or the required message. **`offProfile`** (only together with `byOrga`, only the setup editor's „Anmeldung bearbeiten“, #521 — docs/setup.md) also takes a spec of the character's class the profile lacks, and keeps a character of the previous signup the raider has no profile entry for (its class read from the spec it was signed up with), and with a `className` in the character entry takes a new name the raider has no character for at all („Anderer Charakter …“: name through `validateCharacterName`, class from the version's rule set, the spec must belong to that class — „passt nicht zur Klasse von X“); the version rule (#543) stays; the profile itself is never changed. **Such a character stays the raider's without `offProfile`:** a character of the previous signup the profile lacks (e.g. one the orga entered) is kept on every raider path (status buttons, „Spät“, comment, web `PUT /api/signups`) with the spec it already has — another spec of it, or a new name with `className`, needs the orga or the profile (`characterFor`). The web signup page of an orga member stays bound to the profile. `canAlso` omitted = prefilled from the profile (`defaultCanAlso`: effective off-tank/heal switches plus the roles of the character's other specs, never the own role). `rosterCounts`/`roleCounts` are the one counting rule (signed + late take a seat) — `eventMessage.js` imports it. Saving goes through `signupStore.saveSignup`, so the event message and the talk overview update through `onSignupsChanged` with nothing extra.
- **Several characters (#293):** `submitSignup` takes `characters[]` and checks **each** against the profile (character and spec) — the first failing one names itself ("Brokk steht nicht in deinem Profil."); the same character twice counts once, more than the category allows are refused (`characters`, "Höchstens 5 Charaktere je Anmeldung in dieser Kategorie." — see „Charaktere je Anmeldung“ below). A request with only `character`/`spec` (the Discord status buttons, the comment modal) **keeps the stored alternates**, so no front end that knows one character drops them. After the deadline "unchanged" means same status and same character list. `submitSignups(userId, [{ eventId, characters, status }])` runs the full `submitSignup` per raid (role check, deadline, start — one refused raid never stops the others; the member's roles are read once per server) and first drops per raid what cannot go there (`fitCharactersToEvent`: a spec the event's game version does not have → "Klasse passt nicht zu diesem Raid", gear "none" → "laut Profil ohne brauchbares Gear"); beyond the raid's limit it keeps the first ones in priority order and skips the rest there with "mehr als N Charaktere je Anmeldung in dieser Kategorie"; a raid left without characters is `no_character`. Comment and "kann auch" of an existing signup are kept.
- **Charaktere je Anmeldung — per category (Oct 2026).** How many own characters one signup may name (the first counts, the others "kann auch mit") is a setting per raid category: `config.categorySignupCharacters` (`{ [categoryId]: 1..7 }`; no entry = **8**, the default and the most there is — 8 is never stored; normalised by `signupCharacters.normalizeCategorySignupCharacters`, merged by `configStore` like the other category maps, `PUT /api/settings` keeps an 8 in the patch so the merge drops the category again, a closed category leaves it, `categoryLifecycle.SETTINGS_KEYS`). Edited in Einstellungen › Kategorien › tab *Anmelde-Nachricht* › card „Charaktere je Anmeldung“ (− / + stepper, typed 1–8; the change list says „… · Charaktere je Anmeldung → 3“). **One resolver:** `signupCharacters.maxCharactersFor(eventOrCategoryId, config)` (pure; `signupService.maxCharactersFor` / `pickLimitFor` read the settings store when no config is handed in). Every path asks it: `validateSignup` (single signup, web and bot), `submitSignups` (per raid, see above), `eventManage.addRaider` (before anything lands in the profile), the Discord character picker after a button (`signupButtons.buildCharacterPicker` `max_values`, „Pick up to N characters“), the class way's „already signed up with N characters“ (`withAddedCharacter`), the multi-raid modal (`multiSignup.buildCharacterModal`: per raid its own `max_values`), the public select's „from your profile – up to N at once“ (`eventMessage.pickSelect`, part of the message hash, so a change redraws), and the web (`GET /api/signups` sends `maxCharacters` per own row; `SignupCharacterPicks` offers „+ Kann auch mit … (bis N)“ up to it and says „Höchstens N Charaktere …“ once reached; `BulkSignupDialog` takes the lowest limit of the chosen raids, `lib/signups/signupPicks.ts bulkMaxCharacters`, and says so when they differ). **Nothing is cut silently:** `exceedsCharacterLimit(entries, previous, max)` lets more than `max` through only when every requested character is already on the stored signup — a signup from before a lowered limit keeps its characters (a status button, a comment, reordering, removing all work), but adding or swapping in a new one beyond the limit is refused; the pickers offer as many as the stored signup has (`pickLimitFor`), the web dialog shows the lines with „Diese Kategorie nimmt jetzt höchstens N …“ and no „+“. Signing off is never refused. The store (`signupStore.normalizeSignup`) only guards the hard maximum of 8 — it does not read events. Bot texts: the refusal is German in the service and English through `botEnglish` („At most N characters per signup in this category.“). Tests: `test/services/signups/signupCharacters.test.js`, `signupService.test.js`, `test/commands/signup/signupMulti.test.js`, `eventButton.test.js`, `test/web/apiRoutes/system/settings.test.js`, `signups.test.js`, Vitest `SignupDialog.test.tsx`, `SignupsPage.test.tsx`, `CategoryMatrix.test.tsx`.
- **API** (`apiRoutes/events/signups.js`): `GET /api/signups` (area `signup`: upcoming events of both sources + own status + the profile's characters), `PUT /api/signups` (area `signup`, body `{ eventId, characters: [{ character, spec }], status, canAlso, comment }` — a single `character`/`spec` still works — **always the session's `user.id`**, a `userId` in the body is ignored), `POST /api/signups/bulk` (area `signup`, #293: `{ eventIds[], characters[], status }` → `results` per raid with `ok`, `error`/`code`, `skipped` and the fresh `counts`; again only the session's account). The orga's exemption (`byOrga`) is asked **per raid** in both writes (#727, `submitSignups` takes a boolean or `(event) => boolean`): a category's orga is exempt in its raids, not in the others'. **Managing other people's signups** (close/open, add/remove a raider, Anmelde-Aufruf, „Fehlende pingen“, „Invite callen“) is the orga's — the global one or the raid category's (docs/permissions.md „Kategorie-Orga“; a category orga's Anmelde-Aufruf goes into the raid's own channel and pings only the category's raider roles, else 400 `role_not_allowed`). Every signup of an own event, with Discord name, "kann auch" and comment, reaches the orga in the raid detail payload as `ownSignups`.
- **Which raids a member sees (Oct 2026)** — „Für dich“ on the dashboard and the „Anmeldungen“ page (`signupView.memberEventList`): the raids they **may sign up for**, plus the ones they **already signed up for**. For everybody, the orga included: both lists are personal, the orga sees every raid on the raid pages and in the dashboard's orga block. `raids` read is **no** reason to see more (raider roles like „Mo Raider“ hold it — that once put the Wednesday raid on a Monday raider's dashboard).
  - **One rule, `services/signups/signupAccess.js`** — `signupAccess(categoryId, { userId, roleIds, config, versionId })` → `{ rule, allowed, code }`, the very rule the save checks (`checkRaiderRole`), so „listed“ and „may sign up“ never drift apart. Per category and the raid's version (#739): *roster* (`roster.signupOnly`: status core, trial or bench — `roster_only` else), *roles* (`categoryRoles.expectedRoleIds`: holding one — `raider_role` else; roles not readable → `allowed: null`), *open* (neither: everyone may). `canSignUp()` adds the event categories (`config.categoryIds`, when set) and reads unknown roles as no. The orga's exemption and an existing own signup are the callers'.
  - **PuG:** an *open* category gets `openToAll: true` on every row (also `GET /api/raids/detail`), and the web shows a small badge **„PuG“** (tooltip „Offen für alle – keine Raider-Rolle nötig“, `components/signup/PugBadge.tsx`) in „Für dich“ (next raid and list), on „Anmeldungen“ and in the raid detail's head. Never guessed from a name.
  - **PuG raids on the web only for members of the raid's server (#907):** `PUT /api/signups` and the bulk route pass `memberOnly: true`; in an *open* category `submitSignup` asks `services/signups/pugMembership.js` `checkPugMember` (`discord.guildMembership` on the event's server) and refuses a non-member with `pug_members_only` → 403 „Nur für Mitglieder des PuG-Servers.“ / "Only for members of the PuG server.", the payload carrying `inviteUrl` (`pugInviteUrl(event)` = the server's general invite, `pugInvites.generalInviteUrl`, #905; `""` while none is made). Membership that cannot be read lets the signup through; the orga and an existing own signup are exempt; guild categories and Discord are untouched (the bot never passes `memberOnly`). The dialog (and a bulk result row) says so and shows „PuG-Server beitreten“ only when `inviteUrl` is filled.
    - **No way around it:** the attendance route (`availability.js`, `via === "web"`) passes `memberOnly` too. The exemption for an own signup holds only while that signup is not an absence (`holdsSignup`) — a signed-off non-member cannot sign up again on the web, also not in the bulk route. `guildMembership` has a time limit; running out counts as „cannot be read“.
    - **Known before the click:** `GET /api/signups` marks rows through `markMembersOnly` (only candidates are asked, once per server): `membersOnly: true` + `inviteUrl` for a non-member, `membershipUnknown: true` when Discord did not answer. The dialog then shows the notice instead of the form right away (a quiet line for `membershipUnknown`); the 403 on saving stays the authority.
    - **Links:** `inviteUrl` is only passed on as `https://…` (`safeInviteUrl`, server and client `lib/signups/pugMembers.ts`); anything else hides the join link and the text drops „tritt dem Server bei“.
- **Signing up without a character (#907):** when the profile has no character of the raid's version and the version's classes come with specs (`classesByVersion` → `specs: [{ key, label, icon, role }]`), the dialog asks class → spec → name like the bot (`components/signup/NewCharacterPick.tsx`, rules in `lib/signups/newCharacter.ts`; the name is prefilled with the Discord name, letters only, at most 12). `PUT /api/signups` sends `newCharacter: { name, spec }` with `characters: []`; `submitSignup` plans the character on a virtual profile first, runs every check (membership included) and only then stores it (`signupNewCharacter.addSignupCharacter`, `source: "manual"`) and signs it up — a refused signup leaves no character behind (a failing write of the signup itself may, accepted). The page reloads the profile afterwards. Absence needs no character.
  - **Roles that cannot be read** (bot offline, member not on the server): the roles come from `services/discord/roles/memberRoleMemory.js` — read live, the last read stands in for 15 minutes over a Discord hiccup; without one only open categories and own signups show, and the answer says so (`rolesUnknown` / `upcomingRolesUnknown`, only when a raid with a role was left out) → a quiet line „Deine Discord-Rollen konnten gerade nicht gelesen werden – evtl. fehlen Raids.“ The save stays lenient: unreadable roles let a signup through.
  - **„Ansicht als Rolle“** lists with the viewed roles (`web/signups/viewerRoles.js`, `user.viewAs.roleIds`), not the admin's own Discord roles; a roster-only category counts a holder of the roster's roles (`roleIds`, `trialRoleId`) as member (`rosterByRoles`), and the admin's own signups make no raid visible.

## Keine Grenze, Warteliste und Ankündigung (`src/services/signups/signupService.js`, `src/utils/signup/capacity.js`, `src/services/events/eventAnnounce.js`, #306, #516)

Seit #516 hat ein Raid **standardmäßig keine Grenze**: es dürfen sich so viele anmelden wie wollen, die 25 wählt die Orga erst im Setup. Warteliste und Ablehnen (#306) bleiben als bewusste Wahl, dazu die Ankündigung eines neuen Events.

- **Am Event** (`eventStore`, wie `fairness`/`wishes`, nicht im Plan validiert): `overflow` `"none"` (Voreinstellung, keine Grenze) | `"waitlist"` | `"refuse"` und `lockAtLimit` (aus). Beides steht auch in der **Raid-Vorlage** (`raidTemplates.normalizeTemplate`) und wird beim Anlegen kopiert (`eventCreate.templateDefaults`, `PLAN_KEYS`) — das Event behält seine eigene Kopie. Normalisiert wird an einer Stelle, `utils/signup/capacity.js` (`normalizeOverflow`, `normalizeLockAtLimit`); im Web ist es das Segment **„Bei voller Größe: keine Grenze · Warteliste · ablehnen“** (`OverflowField` in `RaidFields.tsx`) hinter „Mehr“ im Erstellen-Dialog und im Vorlagen-Editor.
- **Migration (#516, `settingsMigration.js`):** vor #516 hießen die Modi `"bench"` (Warteliste, damals Standard) und `"off"` (ablehnen). Der Start stellt jedes Event (`eventStore.migrateOverflowModes`) und jede Vorlage (`raidTemplateStore.migrateOverflowModes`) mit so einem Wert einmal auf `"none"` und `lockAtLimit: false` um und loggt es als `[settings] Migration: …`. Weil die neuen Modi andere Namen tragen, erkennt die Migration einen unberührten Altbestand ohne Marker — eine später bewusst gewählte Warteliste wird nie zurückgestellt; der Lesepfad liest einen Altwert ebenfalls als `"none"`. **Nicht zurückgesetzt** wird, was der alte Überlauf schon getan hat: Anmeldungen, die er auf die Bank gesetzt hat, bleiben Ersatz (die Orga entscheidet im Setup), und ein von `lockAtLimit` geschlossener Raid bleibt zu. Finden: Ersatz-Anmeldungen stehen im Roster-Tab als „n auf der Warteliste“ (Namen im Tooltip), ein automatisch geschlossener Raid hat im Event-Protokoll die Aktion `lock` („Raid voll (25/25)“).
- **Mit `"none"` greift nichts:** jede Anmeldung bleibt „Dabei“/„Spät“, kein Ersatz, keine Ablehnung, `waitlisted` ist nie gesetzt und `notice` leer — der Raider bekommt keine Warteliste-Zeile.
- **Die Zähler (#520) zeigen nur die Zahl der einzelnen Discord-Accounts, kein „/Größe“** (vorher, seit #516, „25/25 (+3)“): `capacity.accountCount(signups, statusOf)` zählt „Dabei“ + „Spät“, ein Account mit mehreren Charakteren (eine Anmeldung mit „kann auch mit“ oder bei Raid-Helper mehrere Einträge derselben `userId`) **einmal**, eine Anmeldung ohne `userId` als eigene; Vielleicht, Ersatz und Abmeldung zählen nicht. `rosterCounts`/`roleCounts` tragen es als `accounts` (`attending` bleibt die Platzzahl der Regeln oben), die Zeilen von `GET /api/signups` (beide Quellen) und `manageInfo` ebenfalls. Angezeigt als **„28 signed up“** (`capacity.signedUpText`) in der Anmelde-Nachricht (`**28** signed up`, ohne Label davor) und auf der öffentlichen Event-Seite („Signed up · 28“), als „28 angemeldet“ in der Übersicht von „Event verwalten“ im Bot und im Schritt *Anmeldung* der Raid-Detailseite, im Web über i18n `signups.attending` („28 angemeldet“ / „28 signed up“, `signedUpLabel` in `lib/signups/status.ts`) im Balken der Anmeldeseite und im Dialog-Kopf. Die Raid-Liste je Verknüpfung (#892, docs/discord-servers.md) zählt genauso, schreibt aber „28 signups“ / „28 Anmeldungen“ neben die Rollen-Zahlen („2 Tanks, 5 Heiler, 18 DD“) in der Agenda nach Tagen. Der Balken selbst füllt sich weiter gegen die Größe; die Rollen-Zähler (Tank/Heal/DD gegen den Plan) bleiben, wie sie sind. Nicht umgestellt sind die Orga-Übersichten mit Plätzen (Raids-Liste „12 / 25“, Dashboard-Dialog) — sie zählen `signupCount` (alle ohne Abmeldung) gegen die Größe.
- **Mit `"waitlist"`/`"refuse"` greift der Überlauf bei jeder *neuen* Anmeldung, die einen Platz belegt** (`applyOverflow`, aufgerufen zwischen `validateSignup` und `saveSignup`): ist `rosterCounts(...).attending` ohne die eigene Anmeldung ≥ `size`, wird aus der Anmeldung **Ersatz** (jeder Charakter auf `bench`) samt `notice` „Der Raid ist voll (25/25) – du stehst auf der Warteliste (Ersatz). …“, bei `"refuse"` wird sie mit `code: "full"` (409) abgelehnt. **Wer schon einen Platz hält** (`signed`/`late`, `holdsSeat`) behält ihn — auch beim Spec-Wechsel und beim Wechsel von „Dabei“ auf „Spät“ —, die Orga (`byOrga`) ist nicht gebunden, ein Event ohne `size` hat keine Grenze. ⚠️ **„Dabei“ und „Spät“ zählen beide** (`ATTENDING`): `rosterCounts` zählt sie gleich, also käme man an einer vollen Warteliste sonst einfach mit „Spät“ vorbei und die Nachricht stünde auf 3/2. „Vielleicht“, „Ersatz“ und eine Abmeldung belegen keinen Platz und werden nie angefasst.
- **Kein automatisches Nachrücken.** Meldet sich jemand ab, rückt niemand nach — das entscheidet die Orga im Setup. Der Roster-Tab der Raid-Detailseite sagt darum „3 auf der Warteliste“ (Badge neben „n abgemeldet“, Namen im Tooltip).
- **`lockAtLimit`** (`lockIfFull`, nach dem Speichern, zählt ebenfalls `attending` — eine „Spät“-Anmeldung, die den Raid voll macht, schließt ihn also auch): der volle Raid setzt `signupsClosed` wie „Anmeldung schließen“ (#288) und protokolliert es (`appendEventLog`, Aktion `lock`). **Nur zu, nie auf** — ein späteres Abmelden öffnet die Anmeldung nicht wieder.
- **Der Raider erfährt es sofort:** `submitSignup` liefert `{ waitlisted, locked, notice }` (und `submitSignups` je Raid) — `PUT /api/signups` und `/bulk` reichen es durch, `SignupDialog` macht daraus den Toast, `BulkSignupDialog` ein Badge „Warteliste“, und in Discord hängt jeder speichernde Pfad (`eventButton.save`, `signupStatus.save`, `eventJoin`, `multiSignup.resultLine`) die Zeile an die Bestätigung. Nichts davon liest der Raider erst im Roster.

## Anmeldung (Bot) (`src/utils/signup/signupDialog.js`, `commands/signup/`, #258)

The same signup as the web, inside Discord: the talk overview's select (`talk-signup`) and the event message's button (`event-signup:<eventId>`) open an **ephemeral** dialog — one embed (date · `Tank 1/2 · Heiler 1/3 · DPS 4/5`, own status, deadline/start hint, wish partners, the last confirmation or error) and at most five component rows: *Charakter · Spec* (the profile's characters with gear level), *Kann auch* (multi-select of the roles other than the spec's), the buttons *Dabei / Vielleicht / Spät / Ersatz / Abmelden* (disabled what `allowedStatuses` forbids), *Kommentar* (only with a signup) and *Im Web öffnen*. Works on both servers — it reads only the stores.

- **Stateless.** Unsaved picks ride in the customIds: `signup-pick:<eventId>:<k|s|a>:<state>` (class / character·spec / kann auch — `signupPick.js`, redraws only), `signup-status:<eventId>:<s|t|l|b|a>:<state>` (`signupStatus.js`, saves) and `signup-comment:<eventId>:<state>` (`signupComment.js`, button + modal like `logevalForce.js`), with `<state>` = `<characterKey>:<specKey>:<roleMask t/h/m/r>`. An id that would pass 100 characters drops the state and the handler falls back to the stored signup. Every step re-reads event, profile and signup (`resolveState` refuses a character that is not the member's) and saves only through `signupService.submitSignup` — deadline, start and spec rules are the service's; its error (German in the service, English through `toEnglish()`) lands in the same message (`interaction.update`), so nothing piles up. A status change keeps the stored comment; the comment modal keeps status and spec, so it works after the deadline.
- **Without a profile character** the dialog offers class → spec from the event's rule set plus "Profil anlegen" (`/profile`). A status click then opens a modal for the character name (prefilled with the Discord display name); its submit adds that character with the spec to the member's profile (`raiderProfileStore.addCharacter`, `source: "manual"`) and signs up. *Abmelden* needs no character; a status the deadline refuses answers with the reason before asking for a name.
- **Only the event's game version (#543).** Every path offers and accepts only the profile characters of `versionOfEvent(event)`: `signableCharacters(profile, versionId)`, `joinPicker.characterOptions(profile, versionId)`, the name modal adds the new character in that version, the manage panel (`eventManageBot`), "Raider eintragen" (`eventManage.raiderCandidates`/`addRaider`) and the setup editor's „Anmeldung bearbeiten" (`setupSignup.signupEditView`) list only them. `signupService.validateSignup` refuses a character of another version with `character_version` — „Devi Res gehört zu WoW Forever – lege einen TBC Anniversary-Charakter im Profil an." (English in the bot through `botEnglish`) — also for the orga with `offProfile`; `submitSignups` (several raids) skips it for that raid with „Charakter aus einer anderen Spielversion". A member whose profile has characters, but none of the event's version, reads `missingVersionLine`: "No WoW Forever character in your profile yet – create a WoW Forever character in your [profile](…) or pick class and spec here." — the class way stays open and the link button says "Add a WoW Forever character". "Zuletzt" (`lastSignupInVersion`) looks only at signups of that version's events (an event that is gone counts as TBC) and at the imported specs of that version. Signups store the character's name, so the comparisons of names and keys go through `profiles.nameKey()`. The web: `GET /api/signups` sends `versionId` per profile character and per own row (always resolved) plus `versions`; `lib/signups/status.ts profileForRows` filters the dialog's characters (mixed rows in the bulk dialog keep all — the server skips), `missingVersionLabel` feeds the dialog's hint „Dieser Raid ist Forever – in deinem Profil steht noch kein Forever-Charakter. Lege einen Forever-Charakter im Profil an", and a raid without a character of its version cannot be ticked for the bulk signup.
- **Raid-Helper events** (from the talk select) get a link button into their event channel (`getStoredEvent().guildId`, else the first server) — the signup stays Raid-Helper's.
- **Access:** `talk-signup` and `event-signup` are `group: "signup"`, `defaultAccess: "everyone"`; the three step handlers declare `accessOf: "event-signup"`. The dialog never acts `byOrga`. **Raider roles:** opening the dialog (button or talk select) answers „Für diesen Raid brauchst du eine Raider-Rolle.“ instead when the event's category wants a role the member lacks and they have no signup yet (`signupService.checkRaiderRole`); the talk overview is one message for everybody, so it cannot leave such raids out. A status click refuses the same way (before the character-name modal, too). Where the roster takes signups only from its members (#658), the same check answers „Für diesen Raid melden sich nur Mitglieder des Rosters an (Stamm, Probe oder Ersatz). Frag die Raidleitung.“ (English: "Only members of the roster (core, trial or bench) sign up for this raid. Ask the raid lead.") to everyone without status core, trial or bench. ## Mehrere Raids auf einmal (Bot) (`src/utils/signup/multiSignup.js`, `commands/signup/talkSignupMulti|signupMulti.js`, #293)

The raid list of a link carries *Mehrere Raids wählen …* above its single-raid select (*Für alle Raids anmelden* was removed in #904 — too easy to sign up for raids one never meant; a click on the old button of an overview posted before only answers ephemerally that it is gone and points to *Mehrere Raids wählen …*, `commands/signup/talkSignupAll.js`). Everything is ephemeral and saves through `signupService.submitSignups`. **One version at a time (#743):** TBC and Forever share the server and a signup never mixes them - `signableRaids({ versionId })` offers the raids of one version only; with raids of two versions (`signableVersions()`) the buttons first ask "Which game version …" with one button per version (`talk-signup-multi[:<from>]:v:<version>`); with one version nothing is asked.

- **Which raids:** `signableRaids({ guildId, here })` — own events of the list's source server that have not begun, are not cancelled/closed, of `config.categoryIds` when set, soonest first, at most 25. Deadline and raider role are **not** filtered out: the result names them per raid.
- **Source server in the button (#904):** the overview posts the button as `talk-signup-multi:<from>` (the list's source server, `buildOverviewMessage`), so a partner's PuG list offers the PuG raids, not the guild's. The source counts only if it is the clicked server itself or a link `from → here` exists (`sourceServer`), and the link's `versions` filter the raids as on the list; anything else — and every button posted before #904 without a source — offers the first server's raids as before. The version question keeps the source.
- **Mehrere Raids wählen …** (`talk-signup-multi`): *Schritt 1* — a multi-select of those raids (nothing preselected, the member picks), a *Status für alle* select and *Weiter: Charaktere*.
- **Schritt 2 is a modal** built from Label components (type 18) with string selects: per raid one select of the member's characters · specs (spec emoji via appEmojis, `max_values` 3, empty = skip that raid), **at most five raids per modal** — Discord's limit of five fields, which is also why the status sits in step 1, not in the modal. With more raids the answer after a submit carries *Weiter: Raids 6–10*; a modal cannot open the next modal by itself.
- **Priority = the order the modal listed the options** (the stored characters or the last-used spec first). Discord returns the picks without their click order, so the listed order is kept in the session when the modal is built and read back on submit (`orderedPicks`).
- **State under a token**, not in the customId (≤ 100): `signup-multi:<token>:r|s` (step-1 selects), `:go:<page>` (opens a modal), `:m:<page>` (the modal) — raids, picked raids, status, option orders and results in memory for 30 minutes, only for the member who started (`getSession`); an expired or foreign token answers „Die Auswahl ist abgelaufen …“ and saves nothing. The last page ends the session.
- **Result:** one line per raid — `✅ **SSC + TK** · Mi 24.09.: Zibbo · Heilig, +Zibbowar · Schutz`, `⏭️ … übersprungen (kein Charakter gewählt)`, `⛔ …: <the service's reason>` with skipped characters and why; a page submitted twice replaces its lines.
- **At one event:** the character select of the event message (`utils/signup/joinPicker.js`) shows *Mehrere Charaktere …* (`signup-multi:e:<eventId>:<code>`) when the member has more than one character · spec — the same modal for that one raid, status from the select, refused first after the deadline or without raider role.
- **Access:** the two handlers declare `accessOf: "talk-signup"`. Tests: `test/commands/signup/signupMulti.test.js`, `test/services/talk/talkOverview.test.js`.

### Hinweis für Nicht-Mitglieder (`src/services/signups/partnerJoinHint.js`, #904)

A raid list of a linked server (`discordServers.links`, "from:to") lets members of the target sign up for raids of the source. Anyone may sign up for an open PuG (no raider role in the category); a raid with raider role refuses as usual. **Role rule:** the raider role is read on the raid's server (`signupRoleIds`); when Discord cannot give the roles and says the member is not on that server (10007/10013), the member has **no** roles — so a category asking for a raider role refuses (otherwise a non-member would slip past it). Any other failure stays lenient (no refusal). The bot does not know beforehand whether the member is on the raid's server, so after a successful save (not after "Abmelden") it asks Discord once:

- **When:** only if the click came from another server than the raid's (`interaction.guildId` ≠ `event.guildId || config.guildId`). The link is `"<raid server>:<this server>"` — customIds are the same on every server, the pair of guild ids identifies the link.
- **How:** **after** the answer went out (`update`/`deferUpdate` first, then `editReply`): member cache, else a single-member fetch (no privileged intent needed), at most 5 s. Only the latest click on a dialog message edits it (an older, slower check never redraws over a newer answer); a failed edit is only logged. Discord's 10007/10013 = not a member; any other error, a timeout or a missing guild = unknown → **no** note (a hiccup never nags).
- **What:** below „Gespeichert“ the line „Tritt dem Server **<Name>** bei, sonst bekommst du keine Pings und Infos.“ (English "Join the server **<name>**, otherwise you will not get pings and info."), plus the link button *<Name> beitreten* when `inviteUrlForLink(linkKey)` returns an https URL (the link's invite from #905, `services/discord/pug/pugInvites.js`, made by a click in *Einstellungen › Discord-Server*; without one, or when it was deleted on Discord, the line comes alone). The name is the server's label in `discordServers.servers`, else the Discord server's name, else „PuG“ (`serverNameOf`, at most 60 characters so the button label fits).
- **Mehrere Raids wählen …:** one check per raid server among the saved raids, one line under the results, one button per distinct invite (the row keeps Discord's five-button limit).
- Tests: `test/services/signups/partnerJoinHint.test.js`, `test/commands/signup/signupStatus*.test.js`, `test/commands/signup/signupMulti.test.js`.

## Anmelder-Nachricht (`src/services/events/eventMessage.js`, `commands/signup/eventPick.js` + `eventButton.js`, #287, #303)

The message in an own event's channel is built like Raid-Helper's, with icons instead of text and plenty of air — our bot, no Raid-Helper branding. `buildEventMessage(event, signups, { emojis, now, icsUrl, raidArt, titleSize })` is **pure and returns plain API JSON** (no builders), so tests and the length checks read it directly.

- **Look per category** (`config.categoryMessageLook`, Einstellungen › Kategorien, `embedLook.messageLookOf`): **Raid-Bild** (default on) puts the leading instance's picture below the message — Blizzard's zone art `render.worldofwarcraft.com/eu/zones/<art>-small.jpg`, 600 × 300, the slug is the instance's `art` in `config/gameVersions`; an event's own banner keeps its place, a cancelled event has none. **Titelgröße** `normal` · `large` (default) · `huge` sets `## ` / `# ` before the line of letter tiles — an emoji grows with the heading it sits in, and a heading is the only larger line an embed description has. Only what differs from the default is stored.

- **Layout (#303):** title and description (with a phase line on top: *Cancelled – reason*, *Signups closed*, *deadline passed*, *raid has started*; the title as letter tiles opens the description, see „Emoji styles“ below). The **head is icon + value only**, three inline columns whose name is a zero-width space, their rows as lines of one field so they sit directly under each other: Leader · Date `<t:…:D>` · voice channel `<#id>` (#305, only when one is set) | `**n** signed up` (the single Discord accounts, no size, no label in front — #520) · Time `<t:…:t>` | Deadline (an empty first line when none is set, so the countdown stays beside date and time) · Countdown `<t:…:R>`. No end time: a duration nobody set would only show the default. The **role totals are columns**: Tanks with Healers directly below · Ranged · Melee (`<icon> Tanks **2**/3`; Tanks/Healers against `composition`, Melee/Ranged as `/min+` or `/min–max` from `compositionMax`) with the role icons of the event's emoji style (the WoW `eh_role_*` are no longer used here), then one empty full-width field. The roster: a **Tanks block first**, then **one inline block per class** in the rule set's fixed order, named `<class icon> __Priest__ (3)`, each line `<spec icon> \`nr\` **Name**` and an empty last line that keeps the rows of blocks apart; then one field with the lines `<status icon> Late (n): \`nr\` Name, …` for Late / Tentative / Bench / Absence, the approved setup (only the approved snapshot, never a draft) and a links line `Event · Comp · Sheet · SR · Calendar` (Sheet/SR only when on record; no „Sign up“/„Setup“ link, they only doubled the buttons and Comp). **Comp (#520)** points at `/e/<id>/comp` on `PUBLIC_BASE_URL`: a message is the same for everybody, so the server decides per reader (`pageRoutes.js` `eventComp`) — logged in with write access in `raids` (`userCan(auth.getUser(req), "raids", "write")`, so an active „Ansicht als“ counts with the viewed role's rights) → 302 to `/raids/detail?event=<id>&tab=setup`, everyone else → 302 to the public page `/e/<id>`, an unknown id → 404; `Cache-Control: no-store`. A markdown link like the others, not a button: the rows below hold the signup components. Only own events get it — Raid-Helper posts its own message, and `/e/<id>` exists only for own events. The comp **sheet** of #357 (`resolveEventSheetLink`) was called „Comp“ before and is „Sheet“ since. Healers and dps stay in their class block. The last row of blocks is filled up to three with empty inline fields — Discord spreads a row of fewer than three over the whole width, and its blocks would stand out of line. Field budget worst case: 3 head + 3 totals + 1 spacer + 10 blocks (Tanks + 9 classes) + status + setup + links = 20; should anything push past 25, `fitFields()` drops the spacers first, never content.
- **Every character of a signup is listed where its own status puts it** (`rosterEntries()`): a raider signed up with a healer and a tank shows up in both blocks, under the **same number**; a first character on „Spät“ sits in the Spät line while the second stays in its class block. An absence is one line per person. **Only the first character counts:** in a class or Tanks block the raiders' first characters come first (bold, by number), their further characters below all of them — **not bold** — and the block's `(n)` counts only the first ones; in the Late/Tentative/Bench lines one raider is one entry (`\`8\` Zibbo / Zibbomage`) and counts once. The Tanks block wears the Protection Warrior's spec icon; Nahkampf is two crossed swords (`eh_r<style>_swords` / `eh_ui_swords`, `scripts/render-role-swords.js` — a new name, because an uploaded emoji is never replaced). **The count is per person:** „n signed up“ (`rosterCounts(...).accounts`, one per Discord account) and the role totals come from `rosterCounts` over the signups' top-level status and role (= the first character's), so a raider takes at most one seat — the setup proposal places one character per person, too.
- **Numbering** by signup time (`at`, then user id) over every signup of the event — stable, since the store keeps `at` when a signup changes.
- **Farbe und Bild** (#307, `src/services/events/embedLook.js`) — der Balken links und das Bild: `event.color` (`#rrggbb`) und `event.image` (`{ mode: "thumbnail" | "banner", url }`), beide vom Event, das sie beim Anlegen von seiner **Raid-Vorlage** geerbt hat (`raidTemplate.color` / `.image`, im Erstellen-Dialog hinter „Mehr“ noch änderbar). Beide fallen **einzeln** auf den Regelsatz zurück (`lookOf()`): Farbe und Boss-Icon (`wowIconUrl(icon, 56)`) der **führenden Instanz** des Abends — der größten, bei Gleichstand der zuerst genannten, dieselbe Regel wie `normalizePlan`s Tank/Heiler-Vorschlag —, sonst `embedAccentColor`. Jede Instanz jedes Regelsatzes hat dafür ein `color` (`gameVersions/*.js`, für den Client in `publicVersions()`), damit SSC, BT und Hyjal **ohne jede Einstellung** auseinanderzuhalten sind. **Nur `https`:** eine Adresse, die Discord nicht laden kann, wird beim Speichern mit einem Satz abgelehnt (`colorProblem`/`imageProblem`, geprüft am Rohtext, damit ein Tippfehler nicht still zu „keine Farbe“ wird) und beim Bauen notfalls weggelassen plus geloggt — ein Bild darf eine Nachricht nie verhindern. Ein **abgesagtes** Event behält den roten Balken und verliert das Bild. Das Bild zählt nicht gegen die 6000 Zeichen, ändert aber den `payloadHash`, also zeichnet der Sweep bestehende Nachrichten einmal neu.
- **Discord's limits are enforced in the builder:** ≤25 fields, ≤1024 per value (a long block ends in "+N weitere"), ≤6000 per embed (blocks are shortened step by step until it fits). Names are markdown-escaped and `@` is broken, so a character name cannot bold, link or ping. Nothing personal goes in beyond the names the raiders signed up with (an absence without a character shows as `<@id>`).
- **Without application emojis the icons are left out** — each head line then leads with its label („Leader: …“, „Date: …“), the totals and status lines keep their words („Tanks **2**/3“, „Late (1): …“), a roster line gets the spec's English name after the raider; no colourful unicode stand-ins. `test/services/events/eventMessage.test.js` holds it (it also refuses emoji code points in the fallback).
- **`event.status`** `"cancelled"` / `"closed"` (the event management, #288) is honoured: red "Cancelled: …" resp. the closed line, and no components (a closed signup keeps *Absagen*).
- **Components** (`buttonRows()` / `messageComponents()`): before the deadline row 1 **Anmelden** (green, `event-btn:<eventId>:quick`, `eh_ui_signed`; one click signs up, see „Anmelden in one click“ below — design canvas „Schnellere Anmeldung“, way A, Oct 2026) · *Spät* · *Vielleicht* · *Ersatz* · *Absagen* (red), each with its flat icon; row 2 the **public select** `event-pick:<eventId>` („Anderer Charakter oder Klasse …“: *Meine Charaktere …* with the `eh_ui_signups` icon, then every class of the event's game version with its class icon; ≤ 25 options); after the deadline *Spät* · *Absagen*; a signup the orga closed (`signupsClosed`) only *Absagen*; after the start or for a cancelled event none. **A category with raider roles** (`config.categoryRoles`, `hasRaiderRoles`) adds the orga's *Fehlende pingen* (`event-missing:<eventId>`, secondary, `tr(lang, "Ping missing")`) — before the deadline in a **row of its own** under the select (Anmelden fills the status row: Discord allows five buttons a row), after it at the end of the status row — the preview and the ping are in docs/discord-servers.md („Fehlende pingen“ under the signup message); without roles the row stays as it is. `buildEventMessage` takes it as `pingMissing` (pure, off by default), `buildPayload` reads it from the config, `messageComponents` (the select reset in `eventPick.js`) asks the config itself when not told. **Why „Meine Charaktere …“ and not the characters themselves:** a message component is one and the same for everybody who sees the message, so a public select cannot list anyone's own characters — picking it opens them ephemerally.
- **Redraws** (`startEventMessageSync()`): a roster change redraws **at once** when the message was not drawn within the quiet window (2 s), changes inside it collapse into one redraw at its end, and redraws of one event run **one after the other** (`redrawEventMessage`, a promise chain per event) — so an older payload can never land after a newer one. The message's **payload hash** is stored with it (`event.message.hash`, `payloadHash()`); `refreshEventMessage` skips an edit whose hash is unchanged, and the **sweep** (30 s after boot, then every 5 min, events of the last two days and later) redraws every message whose current payload differs from its hash — a deadline or start that passed, and a roster change whose redraw was lost to a restart. The first sweep after a deploy that changes the layout therefore restyles every recent message once. `npm run dev` ignores `data/` (`nodemonConfig`), because a signup write used to restart the bot inside the debounce and drop the redraw (#303: the confirmation said „Bank“, the message still „Abgemeldet“).
- **The public select** (`commands/signup/eventPick.js`, `accessOf: "event-btn"`): Discord keeps a picked option shown in the member's client and sends nothing when the same option is picked again, so the handler first **resets the select** with `interaction.update({ components })` (the embed stays untouched) and answers with an ephemeral follow-up (`eventButton.reply()` follows up once the interaction is acknowledged; if the reset fails it replies). *Meine Charaktere …* = the old *Anmelden*, a class = the old *Klasse wählen* with that class already picked.
- **The flows** (`commands/signup/eventButton.js`, `group: "signup"`, `defaultAccess: "everyone"`, every step shares that name; builders and pure rules in `src/utils/signup/signupButtons.js`). Everything answers only the member (a pick or click on the public message answers ephemerally, a step inside that answer updates it) and saves through `signupService.submitSignup`; refusals first (`refusal()`: cancelled, started, closed, deadline — then the raider role via `checkRaiderRole`):
  - **Anmelden in one click** (`quick`, `onQuick`; before it, signing up with one's characters took five moves: open the select, „Meine Charaktere …“, open the second list, tick, close it): signs up at once with `joinPicker.quickPicks()` — **every character of the raider's last own signup in the event's category** (`signupStore.lastOwnSignupOf` with a filter on category and game version), in that order, as far as they are still in the profile and up to the category's limit, else the last one in the game version, else the likeliest single pick (`defaultPick`: an imported Raid-Helper spec, else the first character's best-geared spec). The confirmation carries **one select to swap or add** (`buildChangeRow`: `pick:s`, „Andere oder weitere Charaktere wählen …“, the ones just signed up with on top, nothing preselected). Already *Dabei* with every character → „Du bist schon dabei: …“ with the same select, nothing saved; signed up as Spät/Vielleicht/Ersatz → back to *Dabei* with the same characters; after an absence → signed up anew; **no character in the profile → the class way** (class, spec, name with the Discord name filled in), after which the next click is one click.
  - *Meine Charaktere …*: exactly one fitting character · spec (gear not "none") signs up at once; several → a **multi-select** of the own characters · specs (`event-btn:<id>:pick:<code>`, up to `MAX_CHARACTERS` 3, the current signup's characters listed first, then the likeliest; **nothing preselected**, so picking the same ones again saves — the content says „Bisher: …“) with **the class select below it** (`cls`) for a new character. The priority is the order the select listed them (`orderedValues()` over `interaction.component.options`, Discord does not keep the click order). No profile character → the class select.
  - *a class*: spec select (`spec`, with „Andere Klasse“) → name modal (`name:<code>:<specKey>`, prefilled with the member's character of that class, else the Discord display name). The submit adds the character (or the spec) to the profile (`source: "manual"`, a name the profile has with another class is refused) and **appends it to an existing signup** (same character = replaced in place; a full signup is refused) or starts one.
  - *Spät* / *Vielleicht* / *Ersatz* (status `bench`, until Oct 2026 called „Bank“): signed up → **only the first character** gets the status (`firstCharacterTo()`), the others keep theirs; not signed up (or signed off) → the character select with that status and the classes below, without a profile character straight to the class select. *Vielleicht* first opens the message modal (`note:t`, see „Nachricht bei Vielleicht / Absagen“ below) unless the category asks for none.
  - *Absagen*: a modal (`why`) with a short message (≤ 100, required only where the category says so); the signup becomes an absence with the message as its comment (the characters stay on record). A category with „keine“ signs off at once, without a modal. The modal comes from the public message, so its answer is a reply, never an edit of that message.
  - **The confirmation** (`savedText(event, signup, profile, { emojis })`): with the app emojis `<eh_ui_signed> Gespeichert für **Titel**` and one line per character `\`1\` <spec icon> Devire · Arkan  ·  <status icon> **Ersatz**` (`<eh_ui_absence> Abgemeldet von …` for an absence); without them the plain text of before. Sent as an embed (`savedEmbed(event, signup, profile, { emojis, notice })`, #508): the head line is the **title** („<eh_ui_signed> Saved for Titel“ / „<eh_ui_absence> Signed off from Titel“, no bold marks — a title is bold anyway), the character lines the **description**, under them the raid start as Discord timestamps (`🗓️ <t:…:F> · <t:…:R>`) and the service's notice (`⏳` waiting list); an absence shows „Reason: …“. Colour = the raid's (`embedLook.embedColor`).
- **Every answer is an embed (#508, `src/utils/signup/signupReply.js`).** No part of the signup flow answers with plain `content` any more: `answerEmbed(text, { event, title })` turns a text into an embed — one line → description only, several lines → the first as title (bold marks removed), the rest as description; every line through `toEnglish()` first; colour of the raid (`embedLook.embedColor`, accent colour without an event). `answerPayload()` is the ephemeral reply/follow-up, `answerUpdate()` turns the member's own message into the answer (`content: ""`, no components) — `eventButton.reply/done`, `eventJoin`, `eventSignup`, `signupDialog.plainUpdate`, `signupMulti`, `talkSignup` (Raid-Helper: title „Sign up at Raid-Helper“ plus link button), `talkSignupMulti/All` all go through it; the pickers of `signupButtons.js` carry the raid colour too. Limits and `EmbedBuilder` are `utils/discord/reply.buildEmbed` (docs/bot-commands.md). The „(edited)“ Discord showed under the old text was Discord's own mark of an updated message, not part of our text. Tests assert on `embeds[0]` through `answerOf()` from `test/helpers/signupMocks.js` (`body` = description without the moving timestamp line); `test/utils/signup/signupReply.test.js` holds the embed structure of the main cases.
- **Older messages keep working** until their next redraw: the buttons *Anmelden* / *Klasse wählen* of #302 (`event-btn:<id>:join|class`, same handler), the select `event-join:<eventId>` of #287 (`commands/signup/eventJoin.js` with the character select of `utils/signup/joinPicker.js`, still used for „Mehrere Charaktere …“) and the button `event-signup:<eventId>` of #254 (`eventSignup.js`, the #258 dialog). Tests: `test/services/events/eventMessage.test.js`, `test/commands/signup/eventPick.test.js`, `eventButton.test.js`, `eventJoin.test.js`.

## Nachricht bei Vielleicht / Absagen (`src/services/signups/signupNotes.js`)

Wer „Vielleicht“ oder „Absagen“ wählt, kann der Raidleitung eine kurze Nachricht hinterlassen; der Bot postet sie in einen Kanal.

- **Kanal je Server** (#924): `serverSettings[guildId].signupNoteChannelId` (Einstellungen → Verbindungen → Discord-Server, Tabelle „Kanäle je Server“, je Zeile nur die Kanäle dieses Servers). Es zählt der Server des Raids; es gibt **keinen übergreifenden Standard** — ein Server ohne Eintrag postet nichts und meldet keinen Fehler, die Seite nennt ihn im Hinweis. Er ist der **Standard** für jede Kategorie dieses Servers ohne eigenen Kanal.
- **Eigener Kanal je Kategorie** (#335): `config.categorySignupNoteChannel = { [categoryId]: channelId }`, nur Snowflakes, gespeichert gemergt wie `categoryVoiceChannel` (`""` = Eintrag weg, zurück zum Standard); kein Voll-Admin-Schlüssel. Gewählt auf der Kategorie-Karte direkt unter dem Segment *Pflicht · optional · keine* (Select „Standard (#…) · #…“, Kanäle beider Server aus `GET /api/settings` → `noteChannels: { defaultId, channels }`; bei *keine* oder ohne Kanalliste ausgeblendet). `defaultId` ist der Kanal des aktiven Servers. `noteChannelFor(categoryId, config, { reachable, guildId })` ist die eine Regel: eigener Kanal, wenn der Bot ihn erreicht (`discord.channelVisible`: im Cache, Text, Ansehen + Schreiben), sonst Standard, sonst keiner. Lehnt der eigene Kanal den Post trotzdem ab, versucht `postSignupNote` den Standard — die Nachricht geht nicht still verloren. Die Karte markiert einen Kanal, der nicht in der Liste steht, als **„nicht erreichbar“** (`noteChannelPick`); ohne eigenen Kanal ändert sich nichts gegenüber #331.
- **Je Kategorie** `config.categorySignupNotes = { [categoryId]: "required" | "none" }`, fehlend = `"optional"` (nur Abweichungen werden gespeichert; Einstellungen → Kategorien, Segment *Pflicht · optional · keine*). `noteMode(categoryId)` ist die eine Regel.
- **Discord** (`eventButton.js`): *Vielleicht* und *Absagen* öffnen das Modal `buildNoteModal` (Pflicht = `required` + min. 2 Zeichen, sonst leer erlaubt), *keine* = kein Modal. Beim Vielleicht ohne Anmeldung kommt das Modal **vor** der Charakterwahl; der Text wartet dann 30 min im Speicher (`keepNote`/`takeNote`, je Event + Mitglied, nur für denselben Status) auf den Speicherschritt, weil er nicht in eine customId passt.
- **Web** (`SignupDialog`): bei Vielleicht/Abmelden heißt das Kommentarfeld „Nachricht an die Raidleitung“, `row.noteMode` kommt aus `memberEventRows`; *Pflicht* sperrt den Knopf, und `PUT /api/signups` lehnt eine fehlende Nachricht mit `note_required` (400) ab — die Orga nicht.
- **Gepostet wird in `submitSignup`** (`postSignupNote`, nicht abgewartet, wirft nie): nur bei Status `tentative`/`absence`, nicht leerem Kommentar, und wenn Status oder Kommentar sich geändert haben (`hasNewNote`) — erneutes Speichern postet nicht doppelt; nie `byOrga`, nie bei *keine*. **Der Post ist ein Embed im Look von Raid-Helpers eigener Signup-Notification** (`buildNotePost`, englisch wie alle Raider-Texte): farbiger Balken in `embedAccentColor`, Titel „Notification received!“, Beschreibung `**<@user> (Charakter)** signed up as <icon> **Tentative|Absent** with the following reason:`, Leerzeile, der Kommentar (entschärft), Leerzeile, `<@user> | **[Titel](Link zur Anmelde-Nachricht)** <t:…:f>`. Markdown und `@` im Text werden entschärft; `discord.postNotice` nimmt jetzt Text **oder** `{ content?, embeds? }` und pingt niemanden (`allowedMentions: { parse: [] }`).
- Der Anmelde-Dialog unter der Raid-Liste einer Verknüpfung (`signupStatus.js`) fragt nicht nach einer Nachricht; ein dort gesetzter Kommentar wird aber genauso gepostet. Tests: `test/services/signups/signupNotes.test.js`, `test/commands/signup/eventButton.test.js`, `test/services/signups/signupService.test.js`, `test/web/apiRoutes/events/signups.test.js`, `test/web-client/{settingsLogic,signupsPage,catCard}.test.js`, `test/web/{settingsStore,settingsRoute,discord}.test.js`.

## App-Emojis (`src/services/discord/appEmojis.js`, `scripts/sync-app-emojis.js`, #287)

Spec, class, role and UI icons are **application emojis of the bot's Discord application** (discord.js ≥ 14.16), so they work on every server alike, in embeds, select options and buttons.

- **Names** (≤32, `[a-z0-9_]`): `eh_<class>_<spec>` (`eh_priest_shadow`) and `eh_class_<class>` — WoW icons downloaded from `wow.zamimg.com/images/wow/icons/medium/<icon>.jpg` — plus **`eh_ui_<name>`**, the flat UI icons (`UI_ICONS`: leader, signups, date, time, deadline, start, signed, late, tentative, bench, absence, closed, class, and since #303 the roles tank, healer, melee, ranged, since #305 `voice` and `end`, and the seven coloured raid statuses of the Orga-Zentrale `orgasignup` … `orgacancelled`, docs/events.md, and the four segments of the raid overview's fill bar `barg` green · `baro` orange · `barn` grey · `bare` empty, docs/discord-servers.md). `statusEmojiName(status)` is `eh_ui_<status>`, `roleUiEmojiName(role)` `eh_ui_<role>`. **The WoW role icons `eh_role_*` are gone with #320:** the setup message was their last reader and draws the flat ones like the signup message, so they are out of the catalogue — an application that already has them keeps them, nothing ever deletes an emoji. `emojiCatalog()` lists all 60: `{ name, icon, url }` for the WoW icons, `{ name, icon, file }` for the UI icons.
- **The UI icons are drawn, not downloaded:** single-colour line icons in light grey (`#B9BBBE`, Raid-Helper's look, readable on Discord's dark and light theme) defined as SVG in `scripts/render-ui-emojis.js` and rasterised with `@resvg/resvg-js` into **checked-in 128 px PNGs** under `assets/emojis/eh_ui_<name>.png` (`uiIconFile(name)`). The bot never rasterises these icons at runtime (the drawn message pictures are another matter, see discord-servers.md, „Gezeichnete Bilder“). To change one: edit the SVG, `node scripts/render-ui-emojis.js`, commit the PNG — and delete the old emoji in the developer portal first, because the sync never replaces an existing name. `test/services/discord/appEmojis.test.js` checks every UI icon has a drawing and a 128×128 PNG under Discord's 256 KB.
- **Emoji styles — letter tiles and role icons per event** (`emojiStyle` on the event and the raid template: `arcane` (default) · `gold` · `parchment` · `plain`; picked under „Aussehen“ when creating/editing an event or a template, copied from the template like the colour, logged as „Emoji-Stil“ on an edit). Each drawn style is a full set: **`eh_t<s>_<char>`** letter tiles (`TITLE_TILES`: A–Z, 0–9, `+` `-` `&` → `plus`/`minus`/`amp`) and **`eh_r<s>_<role>`** role icons, `<s>` = `a`/`g`/`p` — 3 × 43 checked-in 128 px PNGs under `assets/emojis/`, listed in `emojiCatalog()` as `{ name, tile, file }` and uploaded by the start sync like the UI icons. `tileEmojiName(char, style)`, `roleEmojiName(role, style)` (`plain` → the flat `eh_ui_<role>`), `emojiStyleOf(x)` (unknown → `arcane`; the client has the same in `lib/raids/raidTemplates.ts`).
  - **The title line:** an embed title cannot show emojis, so the event message puts the title as tiles in the **first line of the description** and drops `embed.title` (Raid-Helper does the same). Upper case; `Ä/Ö/Ü` → `AE/OE/UE`; words set apart by an em space. **Plain title instead** when the style is `plain`, a character has no tile (`(`, `ß`, …), the title is over 32 characters, a tile is not uploaded yet, or the event is cancelled („Abgesagt: …“). The role icons fall back to the flat ones the same way. The setup message draws the style's role icons too.
  - **The images are generated, not drawn:** Gemini 2.5 Flash Image („Nano Banana“, key `GEMINI_API_KEY` in `.env.dev`, prepaid credits needed), one prompt per style with an in-set tile as the style reference, then the white background around the tile flood-filled to transparent, trimmed and scaled to 128 px. A redrawn tile needs the old emoji deleted in the developer portal first (the sync never replaces a name).
- **`eh_status_*` is retired:** the colourful WoW status icons of #287 are no longer in the catalogue or used; an application that has them keeps them (nothing deletes an emoji).
- **Read once per process**: `loadAppEmojis(client)` (after the start sync below and before every message render) fetches `client.application.emojis`, caches only `eh_` names; a failed read is retried after 10 min, never throws. `emojiText(map, name, fallback)` → `<:name:id>`, `emojiOption(map, name, fallback)` → the select option's / button's emoji object.
- **The bot uploads them itself on start** (`src/services/discord/appEmojiSync.js`' `ensureAppEmojis(client)`, called on `clientReady`): it reads the application's emojis, creates **only the missing** ones from the catalogue (never replaces or deletes) — a `file` entry is read from disk (`readIconFile`: png/jpg/gif/webp, ≤ 256 KB), a `url` entry downloaded — and then reads the cache anew — so a fresh application, production included, needs no manual step, and a new spec/class or UI icon arrives with the next restart. It never throws; a refused upload (emoji limit, zamimg down) is logged and the message keeps its fallback. `node scripts/sync-app-emojis.js --dry-run` runs the same sync by hand without starting the bot (lists what is missing; without the flag it creates them; `--dev` reads `.env.dev`).

## Ab- und Anwesenheit (`src/services/signups/availability.js`, `stores/events/availabilityStore.js`, `commands/signup/availability.js`)

Ein Raider sagt einmal „ich bin vom … bis … weg" (**Abwesenheit**, optional mit Grund) oder „ich bin vom … bis … da, mit diesem Charakter · Spec" (**Anwesenheit**), und der Bot meldet ihn für die Raids des Zeitraums ab bzw. als „Dabei" an — sofort und für jeden Raid, der später in diesem Zeitraum angelegt oder dorthin verschoben wird. Jede Änderung kommt per DM.

- **Gespeichert** in `data/settings/availability.json` (`availabilityStore`): `entries` mit `kind` absence/presence, `from`/`to` (`yyyy-MM-dd`, Serverzeit, beide Tage inklusive, höchstens `MAX_DAYS` 180), `scope` (**Geltungsbereich je Server**: `[{ guildId, categoryIds }]`, leere `categoryIds` = alle Raid-Kategorien dieses Servers; ein Eintrag über das Panel einer Kategorie gilt nur für deren Raids), `comment` (Abwesenheit), `characters` (Anwesenheit: `[{ character, spec, versionId }]`, eine Spec je Charakter, mehrere Charaktere je Eintrag), `skip` (beim Eintragen abgewählte Raids: bleiben für immer unberührt), `applied` (je Raid einmal, mit Ergebnis), `createdBy`. Höchstens 20 Einträge je Raider; `createEntry` räumt mit `prune(today, KEEP_DAYS)` Einträge 120 Tage nach ihrem Ende weg (#677: die Anwesenheit liest eine Abwesenheit, die einen vergangenen Raid deckt, als „Urlaub“ statt „Abgemeldet“ — docs/roster-profile.md „Anwesenheit: Status je Abend“). Dazu `panels` (je Kategorie höchstens eins).
  **Alte Einträge** (vor dem Geltungsbereich je Server) werden ohne Migration gelesen (`services/signups/availabilityScope.js`): `scopeOf` macht aus `categoryId` den Bereich `[{ guildId: "", categoryIds: [categoryId] }]` (die Kategorie bestimmt den Server), ohne `categoryId` und ohne `scope` ist das Ergebnis `null` = jeder Raid; `charactersOf` macht aus `character`/`spec`/`versionId` eine Ein-Element-Liste. Geschrieben wird nur noch `scope`/`characters`.
  **Einmalige Umstellung „gilt überall" → ein Server** (`services/signups/availabilityMigration.js`, aus `bot.js` bei `ClientReady`, nicht abgewartet): Einträge ohne `categoryId` und ohne `scope` — auch abgelaufene aus der Historie — bekommen `scope: [{ guildId, categoryIds: [] }]` mit dem **ersten Server der Serverliste** (`discordServers.servers`, in ihrer Reihenfolge), auf dem `guildMembership` den Raider sicher als Mitglied kennt; je Raider und Server eine Abfrage, Raider nacheinander, Abbruch beim ersten Treffer. Ist er nirgends sicher Mitglied (nein oder unbekannt), gilt `firstServerId` — im Log als Fallback gezählt (`N … zugeordnet, davon M … (Fallback)`), aber **nur, wenn alle eingerichteten Server erreichbar waren**. Fehlt einer (Bot nicht im Cache), bleiben die Einträge solcher Raider vorerst ohne Server (gelten weiter überall), die Logzeile nennt sie (`; K offen geblieben`), die Marke wird nicht gesetzt, und der nächste Start fragt nur noch diese Einträge ab. `applied`/`skip` bleiben, Einträge mit Kategorie bleiben unberührt. Erreicht der Bot keinen Server, ist keiner eingerichtet oder wirft eine Abfrage, wird nichts geschrieben und der nächste Start versucht es erneut; fertig setzt sie die Marke `availabilityServers` in `settings/migrations.json` und läuft nie wieder. Bis dahin bleibt der Lesepfad `scopeOf → null` nötig.
- **Welche Einträge eine Seite zeigt** (`entryOnServer`): /signups, „Meine Anwesenheit“, die Zeitleiste, „Pro Raid“ und der Drawer auf /absences zeigen nur Einträge, die den **aktiven Web-Server** betreffen (ein Teil des `scope` auf diesem Server, eine Alt-Kategorie dort, ein Alt-Eintrag ohne Bereich); die Übersicht dazu nur die Raids dieses Servers (`eventServer`). Einträge eines anderen Servers sieht und bearbeitet man nach dem Serverwechsel. Eine Alt-Kategorie, deren Server niemand kennt, bleibt sichtbar.
- **Welche Raids** (`raidsInRange`, `scopeCovers`): eigene Events, deren Tag (Serverzeit) im Zeitraum liegt, nicht begonnen, nicht abgesagt, nicht archiviert, aus `config.categoryIds` (wenn gesetzt), deren Server und Kategorie im `scope` des Eintrags liegt. Eine Anwesenheit deckt nur Raids, für deren Version (`versionOfEvent`) sie einen Charakter hat; angemeldet werden die Charaktere dieser Version in ihrer Reihenfolge, höchstens `maxCharactersFor(event)` (`charactersFor`).
- **Die Regeln** (`applyToRaid`): Eine Abwesenheit **meldet ab, auch wer schon angemeldet ist** (die Abwesenheit sticht; Kommentar = Grund, sonst „Away 24 Oct–31 Oct"); eine schon bestehende Abmeldung bleibt, wie sie ist. Eine Anwesenheit meldet **nie über eine bestehende Anmeldung oder Abmeldung** und nie in einen Raid, den eine Abwesenheit desselben Raiders abdeckt. Jeder Raid wird je Eintrag **genau einmal** angefasst (`applied`) — wer sich nach der automatischen Abmeldung von Hand wieder anmeldet, wird nicht erneut abgemeldet. Gespeichert wird über `signupService.submitSignup`: Anmeldeschluss, geschlossene Anmeldung, Raider-Rolle und Profil gelten; ein Eintrag des Raiders handelt als Raider, einer der Orga (`createdBy` ≠ Raider) als Orga (`byOrga`). Was abgelehnt wird, steht als Fehler im Ergebnis und in der DM.
- **Später angelegte Raids:** `eventCreate.publishOwnEvent` ruft `applyToEvent(eventId)` nach der Anmelde-Nachricht, `updateEvent` bei geändertem Start, ebenso `eventManage.moveEvent` („Verwalten → Verschieben") und `eventManage.reopenEvent` (ein abgesagter Raid wurde übersprungen und holt das nach) (nicht abgewartet — DMs sind langsam und dürfen das Anlegen nie aufhalten). Erst Abwesenheiten, dann Anwesenheiten; je angewandtem Eintrag eine DM „Signed off automatically" / „Signed up automatically" mit Link zur Anmelde-Nachricht. Serien-Events gehen denselben Weg.
- **DMs** (in der Sprache des Raiders, `entrySummary`/`raidDm`; der Standard-Kommentar „Weg 24. Okt.–31. Okt.“ in der Server-Sprache): nach dem Eintragen eine DM mit Zeitraum, Grund bzw. Charakter, je Raid angemeldet/abgemeldet, übersprungen (mit Grund) oder abgelehnt (Fehler über `serviceText`), und dem Satz, dass spätere Raids folgen; von der Orga eingetragen → Fußzeile „Entered for you by the raid lead". Geschlossene DMs: die Antwort im Discord bzw. Web sagt es (`dm: false`).
- **Bearbeiten** (nur Web, `availability.changeEntry`): Zeitraum, Grund, Geltungsbereich und Charaktere lassen sich ändern. `applied` bleibt — Raids, die der Eintrag schon angefasst hat, bleiben, wie sie sind; neu abgedeckte Raids werden sofort angewandt (nicht gewählte aus `eventIds` landen in `skip`), später angelegte über `applyToEvent`. **Wer bearbeitet, bestimmt die Rechte:** `createdBy` wird der Bearbeiter und `via` wird `"web"` — bearbeitet der Raider einen Eintrag, den die Orga für ihn angelegt hat, gelten für neu abgedeckte Raids wieder Raider-Rolle, Anmeldeschluss, Platzgrenze und Mitgliedschaft; Orga-Rechte (`byOrga`) nur, wenn eine Orga einen fremden Eintrag bearbeitet. Danach eine DM „Absence changed" / „Attendance changed".
- **Löschen** stoppt einen Eintrag; die Anmeldungen, die er gemacht hat, bleiben.
- **Discord** (`utils/signup/availabilityDialog.js` baut, `commands/signup/availability.js` verdrahtet, `group: "signup"`, für alle): `/availability` zeigt die eigenen Einträge plus die drei Knöpfe *Abwesend eintragen* · *Dabei eintragen* · *Meine Einträge* (`availability:a|p|l:<categoryId>`; die Modals heißen länger: *Abwesenheit eintragen* / *Anwesenheit eintragen*). Ein Knopf öffnet das Modal (Von, Bis — leer = derselbe Tag —, bei der Abwesenheit der Grund; Datum wie `parseGermanDate`: „24.10.", „24.10.2026", „2026-10-24"), danach eine ephemere Auswahl: bei der Anwesenheit Charakter · Spec (vorgeschlagen der **erste Charakter** der Version — es gibt keinen Main), die Raids des Zeitraums (alle vorausgewählt, höchstens 25) und *Save*/*Cancel*. Die Auswahl liegt 30 Minuten im Speicher unter einem Token (`availability:<token>:c|r|save|x`), nur für den Raider. *My entries* listet die laufenden Einträge mit Ort (Server · Kategorien) und allen Charakteren und einer Auswahl zum Löschen (`availability:del`). **Geltungsbereich aus Discord:** ein Panel-Knopf gilt für seine Kategorie auf deren Server; `/availability` ohne Kategorie gilt auf dem Server, auf dem der Befehl lief. Im DM und auf einem Server, der nicht in der Serverliste steht, **lehnt der Befehl ab** (ephemer: „Please run this on the Discord server the absence or attendance is for – or enter it on the web under Signups.", über `tr()`) — es gibt kein serverübergreifendes „Alle" aus Discord; dasselbe gilt für die Knöpfe ohne Kategorie. Lässt sich der Server einer Panel-Kategorie nicht auflösen, wird der Eintrag in der Altform `[{ guildId: "", categoryIds: [cat] }]` gespeichert (die Kategorie bestimmt den Server). Eine Auswahl von vor dem Deploy ohne `scope` leitet ihn aus `categoryId` bzw. dem Server der Interaktion ab. Das Modal antwortet erst nach `deferReply` (ephemer), weil die Rollenabfrage (`foreignRaids`) dauern kann. Discord bleibt bei einem Charakter je Anwesenheit und ohne Bearbeiten. Fehler kommen englisch (`botEnglish`, Regeln für alle festen Sätze von Store und Service).

- **Warteliste (#775, `services/guildbank/waitlist.js`):** Jedes ausgebbare Item hat eine, **eine je Bank** (`bankKey` + `itemId`), egal aus welcher Kategorie angefragt wird. Einträge sind Anfragen mit `status: "waiting"` und `queueRank` (kleiner = weiter vorn; neue hinten an).
  - **Frei** = `stockView.free` = Verfügbar **minus die offenen (noch nicht bestätigten) Bestandsanfragen** des Items (`reservations.pendingByItem`). Eine offene Anfrage ist nicht vorgemerkt, aber versprochen — so verteilt ein zweiter Scan dieselbe Menge nicht noch einmal. Dieselbe Zahl entscheidet beim Anfragen (`splitAmount`).
  - **Reihenfolge beim Anfragen:** Wartet für das Item schon jemand, kommt eine neue Anfrage **ganz** auf die Warteliste (hinten an), auch wenn gerade etwas frei wäre; danach läuft das Nachrücken (reihum, siehe unten).
  - **Nachrücken reihum in Portionen** (`waitlist.allocate` als reine Kernfunktion, `promoteItem`/`promoteBank`, `guildBankStore.promoteWaiting`): Jedes Item hat eine **Portion pro Runde** (`portion` im Bestand, Standard `PORTION_DEFAULT` = **2**, je Item 1–99 in den Item-Einstellungen). Wer dran ist, bekommt höchstens eine Portion (und nie mehr, als frei ist); will er noch mehr, kommt sein **Rest ans Ende** der Warteliste (neuer höchster `queueRank`), dann ist der Nächste dran — reihum, solange etwas frei ist. Auch ein Teil kleiner als die Portion (nur 1 frei) schickt den Rest ans Ende. Beispiel: frei 4, Portion 2, Liste [A 15, B 2, C 1] → A 2 (Rest 13 ans Ende), B 2 (fertig); danach [C 1, A 13]. Grund: Crimson Spinel kam nur langsam rein, eine 15er-Bestellung hielt die ganze Liste wochenlang auf. Bleibt nach einer vollen Runde noch etwas frei, kommt dieselbe Person im selben Lauf erneut dran; ihre Portionen werden zu **einer** offenen Anfrage zusammengefasst (eine Karte, eine DM je Eintrag und Lauf — mehrere Karten für denselben Raider im selben Moment wären nur Lärm für die Orga). `allocate` liefert die Einträge in der Reihenfolge ihres letzten Zugs, `promoteItem` wendet sie in dieser Reihenfolge an — so stehen die Reste hinten genau so, wie die Runde lief. Die Regel gilt sofort für alle gespeicherten Einträge (keine Migration). Eine neue Anfrage, während niemand wartet, bekommt weiter alles Freie sofort (Portionen gelten nur unter Wartenden). Nachgerückte Anfragen tragen `fromWaitlist: true` und zählen nie gegen `MAX_OPEN`. `guildBank.advanceWaitlist({ bankKey?, itemId? })` rückt **sofort** nach (vor dem ersten `await`, zwei Auslöser verteilen nie dieselbe Menge), postet danach die Orga-Karten (normale offene Karte, Fußnote „… · aus der Warteliste · offen“, mit Rest „… · aus der Warteliste · Rest 13 wartet (Platz 8) · offen“ — `guildBank.restWaiting` liest ihn beim Zeichnen live aus der Warteliste: derselbe Raider bzw. ohne Discord-Konto derselbe Charaktername) und schickt die DM „Du bist dran — Der Gegenstand ist jetzt in der Gildenbank – die Orga bestätigt gleich.“ (+ „13 weitere stehen für dich wieder hinten auf der Warteliste – du bist Nr. 8.“, `movedUpCard` mit `rest` und `position` aus `promoteItem` → `restPosition`). Die Posts laufen über alle Aufrufe nacheinander; eine Karte, die den Kanal nicht erreicht (Bot offline), wird beim nächsten Lauf nachgeholt (offen, `fromWaitlist`, ohne `messageId`). Discord-Fehler werden geloggt, nie geworfen.
  - **Auslöser:** Scan-Upload (`POST /api/ingest/guildbank`), Ablehnen einer Bestandsanfrage, Vormerkung lösen, geänderter Status/Reserve eines Items (`POST /api/guildbank/item`), Bank-Tab ein-/ausgeblendet, jede Änderung der Warteliste im Web (anlegen, umsortieren, entfernen, importieren) und jede neue Warte-Anfrage.
  - **Item von Hand anlegen und Tippfehler im Import:** Ein Item, das die Bank gar nicht hat, bekommt per *Gegenstand hinzufügen* (`POST /api/guildbank/item/add`, Details in [loot-import.md](loot-import.md)) eine Zeile mit Bestand 0 und Status „Ausgebbar“ — so kann sich schon vor dem ersten Scan jemand anstellen. Der Import kennt Namen, die ein bis zwei Buchstaben danebenliegen (`waitlist.findItem`, Levenshtein auf den gefalteten Namen, höchstens 2 und höchstens 20 % der Länge, unter 5 Buchstaben nur exakt): „Crimson Spinal“ findet „Crimson Spinel“, aber nur, wenn genau ein Item am nächsten liegt. Die Vorschau zeigt den echten Namen und darunter „erkannt als …“ (`fuzzy: true`).
  - **Einträge ohne Discord-Nutzer:** Von der Orga importierte oder angelegte Einträge, deren Name keinem Raider-Charakter zugeordnet werden kann, haben nur `characterName` (`userId: ""`, `addedBy` = wer eingetragen hat). Sie rücken wie alle nach (**strenge Reihenfolge, unabhängig von der Verknüpfung** — die Orga verknüpft, bevor sie bestätigt), ihre Karte zeigt „**Name** · ohne Discord-Konto, keine DM“ und den Hinweis „Kein verknüpfter Charakter“, DMs entfallen (die Orga-Antwort sagt „… hat kein Discord-Konto – keine DM.“). Ein Raider ohne Discord-Konto hat kein Raider-Profil — bestätigt wird darum über den Namen selbst (#806): er steht in einem Log/Loot der Version der Bank, oder die Orga prüft ihn im Spiel (*Geprüft & bestätigen* auf der Karte, *Im Spiel geprüft* im Web); alternativ im Web mit einem Profil-Charakter verknüpfen, dann gehen die DMs an diesen Raider.
  - **Grenzen:** `MAX_WAITING` = **10 wartende Einträge je Raider** (Discord; „Höchstens 10 Einträge auf der Warteliste – warte, bis einer drankommt.“), Einträge der Orga ohne Grenze.
  - **Bestätigen** prüft weiter gegen Verfügbar (ohne die offenen abzuziehen — die Anfrage selbst ist ja eine davon); reicht es nicht (z. B. Reserve erhöht), bleibt sie offen.
- **Verknüpfter Charakter** (`services/guildbank/linking.js`): Das Addon schickt die Post an `characterName`-`realm` — ein Name, den es nicht gibt, verliert die Post. Eine Anfrage ist **verknüpft**, wenn sie eine `userId` hat, ihr `characterName` (+ Realm, wenn Anfrage und Charakter beide einen nennen; ohne Leerzeichen, Apostroph, Bindestrich) ein Charakter im Raider-Profil **genau dieses Nutzers** ist — Vergleich ohne Groß-/Kleinschreibung und Akzente (`foldName`, dieselbe Regel wie der Import) — **und dieser Charakter bestätigt ist** (Beleg, siehe unten). Alles **zur Laufzeit** geprüft: ein im Profil gelöschter oder umbenannter Charakter macht die Anfrage wieder unverknüpft, ein später belegter verknüpft sie. `linkedCharacter(request)` liefert den Profil-Charakter (von zwei gleichnamigen den der Version der Bank), `linkState(request)` → `{ linked, linkProblem, character, via }`, `isLinked`/`withLinked` das Flag (`linked` + `linkProblem` in `listForBank`, `pendingForBank` und allen Web-Antworten): `linkProblem` ist `"none"` (kein Profil-Charakter, kein Raider) oder `"unverified"` (Profil-Charakter ohne Beleg), bei verknüpften `""`.
  - **Beleg, dass es den Charakter gibt** (`services/characters/characterEvidence.js`, `characterEvidence(character, { gameVersion })` → `{ verified, via }`): Raider tippen bei der Anmeldung jeden Namen ein (`source: "manual"`, z. B. „Gentle“ statt „Gentleowl“), das allein reicht nicht. Bestätigt ist ein Profil-Charakter, wenn eines zutrifft — in dieser Reihenfolge als `via`:
    - `log`: er steht im Roster einer der 60 neuesten gespeicherten Auswertungen **seiner Spielversion** (`reportStore`, Schlüssel `characterKey(name, versionId)` des Reports), der Klassen-Cache kennt ihn aus einem Report (`characterStore`, Quelle `report`/`wcl`), oder der Raider hat ihn aus den Logs übernommen (`source: "log"`);
    - `loot`: der Loot-Export nennt ihn (`characterStore`, Quelle `export`);
    - `armory`: das Arsenal hat geantwortet (`armory.fetchedAt` **und** ein Level — ein Link allein zählt nicht);
    - `orga`: die Orga hat ihn im Spiel gefunden (`verifiedBy`/`verifiedByName`/`verifiedAt` am Profil-Charakter).
    `manual`-Einträge des Klassen-Caches zählen nie. **Version:** Reports kennen ihre Version; Loot-Export und Klassen-Cache nicht — ihre Namen zählen wie alles vor den Versionen als TBC. Ein Charakter einer anderen Version als der Bank hat keinen Beleg (Forever-Bank = Forever-Beleg). Der Index aus Reports und Cache wird höchstens alle 10 s neu gebaut (`seenIndex`), Listen bauen ihn einmal.
  - **Eigener Beleg des Empfängers (#806, `linking.recipientEvidence`):** Ohne bestätigten Profil-Charakter zählt auch der Name der Anfrage selbst — `orga`, wenn die Orga für ihn gebürgt hat (`recipientCheckedAt` an der Anfrage: bestätigt, *Geprüft & bestätigen*, *Im Spiel geprüft* im Web), sonst `log`/`loot`, wenn der Name (Schlüssel `characterKey(name, Version der Bank)`) im Index der Logs/des Loot-Exports steht, sonst `bank` (#809, `linking.receivedFromBank`), wenn diese Bank dem Namen (+ Realm, wenn beide einen nennen) schon etwas ausgegeben hat — die Post kam an. So lässt sich eine Anfrage **ohne Discord-Konto** (kein Profil) bestätigen. Ein bestätigter Profil-Charakter mit eigenem Beleg geht vor.
  - **Bestätigen ist das Wort der Orga:** `guildBankStore.confirmRequest` speichert, wer bestätigt hat, als Bürgschaft für den Empfänger (eine frühere Prüfung bleibt); *Vormerkung lösen* behält sie (danach geht *Bestätigen* sofort wieder), nur ein neuer Empfänger (`setRecipient`, Umverknüpfen) löscht sie. Eine bestätigte Anfrage fällt so nie mehr still aus der Ausgabeliste, weil eine später eingeführte Regel sie nicht mehr verknüpfen würde (der Fehler von #806: Anfragen, vor #782/#792 bestätigt, fehlten in der Liste und ließen sich nach dem Lösen nicht wieder bestätigen).
  - Nur verknüpfte Anfragen lassen sich **bestätigen** (`guildBank.confirmRequest` → `{ error: NOT_LINKED | NOT_VERIFIED, notLinked: true, linkProblem }`; `guildBank.checkAndConfirm` bürgt vorher für den Namen) und landen in der **Ausgabeliste fürs Addon** (die übrigen zählt `unlinked` je Bank — nur noch vorgemerkte ohne Namen oder mit neuem, ungeprüftem Empfänger).
  - Eine Anfrage eines Raiders aus dem Discord geht an einen Profil-Charakter. Hat er keinen Charakter der Version (`characterName: ""`), ist sie nicht verknüpft: die Orga-Karte warnt, und die Antwort an den Raider bekommt „⚠️ Leg in deinem Profil einen Charakter an, sonst kann die Orga nicht ausgeben.“. Ist sein Charakter unbelegt, bekommt sie „⚠️ Dein Charakter ist noch nicht bestätigt – füg ihn in deinem Profil über die Logs oder das Arsenal hinzu, sonst kann die Orga nicht ausgeben.“ (beides `tr()`, `config/botText/de/guildBank.js`); die Anfrage geht trotzdem raus, die Orga sieht „Charakter nicht bestätigt“.
  - **Bestehende Einträge** werden nicht migriert: Was schon an einem unbelegten Charakter hängt (z. B. „Gentle“), zeigt durch die Laufzeitprüfung von selbst „Charakter nicht bestätigt“, bis die Orga ihn prüft oder neu verknüpft. Ausnahme (#806): eine Anfrage, die **vor #806 vorgemerkt** war und noch keine Bürgschaft gespeichert hat, liest der Store als von dem verbürgt, der sie bestätigt hat (`recipientCheckOf`, `handledBy/ByName/At`) — sie bleibt in der Ausgabeliste und behält das beim Lösen. Eine vorher schon **gelöste** (wieder offene) Anfrage weiß davon nichts mehr: die Orga drückt einmal *Geprüft & bestätigen*.
  - **Verknüpfen im Web** (`guildBank.linkRequest`, `POST /api/guildbank/request/link`): wartende, offene und vorgemerkte Anfragen bekommen den gewählten **bestätigten** Profil-Charakter (ein unbelegter: 400, `linking.pickError` „X ist nicht bestätigt – erst im Arsenal oder im Spiel prüfen, dann verknüpfen.“) als Raider und Empfänger (`guildBankStore.setRecipient`: `userId`, `userName` = Profilname, `characterName`, `realm` = der des Charakters, sonst der Bank); eine gepostete Karte wird neu gezeichnet (`redrawPost`), *Bestätigen* geht dann. Auch eine verknüpfte Anfrage lässt sich umverknüpfen. Die Charaktersuche (`linking.characterChoices`, `GET /api/guildbank/characters`) durchsucht die Raider-Profile der Spielversion der Bank nach Charakter- oder Raidername (auch ein, zwei Tippfehler daneben) und liefert je Wahl `verified` + `evidence` (`log`/`loot`/`armory`/`orga`/`""`). Rangfolge: bestätigte zuerst, dann der Raider, auf den der Name zeigt (Profilname oder ein unbelegter Charakter genau dieses Namens — dessen übrige Charaktere kommen mit), exakter Name, Treffer vor Tippfehlern, Präfix. Im Dialog trägt jede Wahl ihr Beleg-Badge („aus Logs“, „Loot“, „Arsenal“, „von Orga geprüft“); unbelegte stehen ausgegraut als „nicht bestätigt“, sind nicht wählbar und haben zwei Knöpfe: **Im Arsenal prüfen** (`POST /api/guildbank/characters/armory`, Arsenal-Abfrage der Version des Charakters mit seinem Realm, sonst dem der Bank; eine Antwort mit Level wird als `armory` am Profil-Charakter gespeichert → bestätigt; sonst „Arsenal kennt den Charakter nicht oder ist gerade nicht erreichbar – im Spiel per /who prüfen.“) und **Im Spiel geprüft** (`POST /api/guildbank/characters/verify`, Rückfrage in der Zeile „Nur bestätigen, wenn du den Charakter im Spiel gefunden hast, z. B. per /who.“, setzt `verifiedBy/At`). Beides Schreibrecht `raids`, nur Banken des aktiven Servers.
  - **Import:** Ein Name wird **nur einem bestätigten Charakter** automatisch zugeordnet (`waitlist.matchCharacter`). Ein exakter Treffer auf einen unbelegten Charakter („Gentle“) wird nicht verknüpft (`unverified: true`); als Kandidaten kommen dann die bestätigten Charaktere, die der Name meinen kann (`linking.suggestedCharacters`): zuerst die übrigen des Raiders, dem der unbelegte Treffer gehört bzw. dessen Profilname passt, dann bestätigte, deren Name mit dem Sheet-Namen anfängt („Gentle“ → „Gentleowl“, „Gentletwowl“) — höchstens 6, nie unbelegte. Nicht zugeordnete, mehrdeutige und solche Zeilen lassen sich in der Vorschau direkt verknüpfen (`links`: Zeile → `{ userId, characterKey }`; die Kandidaten `candidates` als Chips — „„Gentle“ ist nicht bestätigt – meinst du:“ —, sonst die Suche). Ohne Auswahl wird weiter „nur Charakter“ importiert, aber als „nicht verknüpft“ markiert (`unlinked` in der Antwort). *Eintrag anlegen* nimmt statt des Namens auch `userId` + `characterKey`; ein unbelegter oder versionsfremder Charakter wird dort wie im Import abgelehnt (`linking.pickError`).
- **Status:** `waiting → open` (Nachrücken), `open → confirmed → handedOut`, `confirmed → open` (lösen), `open → rejected`; Freitext `open → done | rejected` (`guildBankStore.confirmRequest/releaseRequest/handOutRequest/resolveRequest`; eine Anfrage aus dem Bestand wird nie „done“). Vorgemerkte Mengen zählen bei „Verfügbar“ (`reservations.reservedByItem`), ausgegebene bis zum nächsten Scan auch (`reservations.handedOutSince`, nach `scannedAt`) — Verfügbar springt bei der Ausgabe nicht wieder hoch. Eine zweite Ausgabe-Meldung wird mit der Anfrage abgewiesen (für #634 idempotent).
- **Wer darf:** nur, wer **Schreibrecht auf `raids`** hat — dasselbe Rechte-Modell wie im Web, aufgelöst über die Rollen auf den Servern der Liste (`services/discord/members/userAccess.js`, `userMayAny`). Das Bot-Gate lässt den Klick durch (`group: "signup"`, `defaultAccess: "everyone"`), geprüft wird im Handler; ohne Recht: „Das darf nur die Orga mit Raid-Rechten.“ Eine schon erledigte Anfrage: „Diese Anfrage ist schon erledigt.“ (bzw. „… schon vorgemerkt/ausgegeben.“), und der Post wird neu gezeichnet (alte Knöpfe weg).
- **DM** an den Raider in **seiner** Sprache (`langOf`, `decisionCard`): „Anfrage bestätigt — Für dich vorgemerkt – du bekommst es bald im Spiel. An: …“, „Anfrage ausgegeben — An X ausgegeben.“ / „Per Post an X geschickt.“, „Anfrage erledigt“, „Anfrage abgelehnt — Grund: …“. Vormerkung lösen schickt keine DM. Discord-Fehler (Post nicht editierbar, DMs zu) werden geloggt und der Orga gesagt, nie geworfen.
- **Item-Emojis** (`services/guildbank/itemEmojis.js`): Wird ein Item auf „Ausgebbar“ gesetzt, legt der Bot sein Icon als **App-Emoji** `gb_<itemId>` an (Application Emojis, max. 2000, unabhängig von den Server-Plätzen; das zamimg-Icon „large“, 56 px jpg, so wie es ist); bietet keine Bank es mehr an, wird es gelöscht. **Ein Emoji je Item-ID**, geteilt über Banken und Versionen (die „Referenz“ ist `guildBankStockStore.offeredIcons()`, berechnet, nie gezählt); die ID steht im Bestand (`emojis[itemId]`, Item-Ansicht `emojiId`). Ein geändertes Icon oder ein von Hand gelöschtes Emoji wird neu angelegt, ein streunendes `gb_<id>` übernommen bzw. gelöscht; die `eh_`-Emojis fasst es nie an. `queueItemEmojiSync()` wartet 2 s (mehrere Klicks = ein Lauf), läuft einzeln, macht 1 s Pause zwischen zwei Aufrufen, blockiert nie die Web-Antwort und versucht Fehler (oder den Bot offline) nach 15 Minuten erneut; ausgelöst von `POST /api/guildbank/item` (geänderter Status), `POST /api/settings/guild-banks/delete`, dem Scan-Upload (wenn die Bank Ausgebbares hat) und 30 s nach dem Bot-Start. Volle Anwendung: Log-Zeile, das Select zeigt das Item ohne Emoji.
- **Web:** Tab *Anfragen* auf der Seite „Gildenbank“ (`RequestsTab.tsx`, `GET /api/guildbank/requests?key=`, ein Abruf je Seite): die offenen und vorgemerkten Anfragen der Bank, zuerst *Vorgemerkt* („wartet auf Ausgabe im Spiel“), dann *Offen* („wartet auf die Orga“); je Zeile Icon, Menge × Name, der Empfänger groß, Raider, seit wann, bei Vorgemerkt „vorgemerkt von X · vor N Std.“, Wofür und „aus der Warteliste“ — nur lesend, entschieden wird auf der Karte im Discord. Dieselben Daten machen in der Item-Liste die Zahl bei *Vorgemerkt* anklickbar: ein kleines Fenster nennt, für wen die Menge zurückgelegt ist. Nicht verknüpfte Anfragen tragen im Tab (und in der Warteliste) das Badge „nicht verknüpft“ bzw. „Charakter nicht bestätigt“ (`linkProblem`) und den Knopf *Verknüpfen* (Schreibrecht; die Suche öffnet sich in einem kleinen Dialog), verknüpfte ein kleines Ketten-Symbol zum Umverknüpfen (`CharacterPicker.tsx`). Über der Suche steht bei einer nicht verknüpften Anfrage mit Namen „Kein passendes Profil (z. B. ohne Discord-Konto)? Den Namen selbst prüfen:“ mit **Im Spiel geprüft** für den bisherigen Empfänger (#806, Rückfrage in der Zeile, `POST /api/guildbank/request/verify` → `guildBank.checkRequestRecipient`, Karte neu gezeichnet). Unter den Treffern stehen **Andere Namen (ohne Raider-Profil)** (#809, `services/guildbank/knownNames.js`, `names` von `GET /api/guildbank/characters`): Namen, denen diese Bank schon etwas ausgegeben hat („schon Gildenbank-Post bekommen“), dann Namen aus Logs und Loot der Version — ohne Profil-Charaktere, höchstens 8, auch mit Tippfehler — ein Klick nimmt sie als Empfänger (`POST /api/guildbank/request/recipient`, `guildBank.reassignRequest`); jeder andere getippte Name geht nach **Im Spiel geprüft** (Rückfrage in der Zeile, dann mit Bürgschaft). Hat die Anfrage einen Raider, kann der Name gleich **ins Profil** übernommen werden (Klasse aus dem Klassen-Cache, sonst nicht übernommen mit Hinweis; von der Orga geprüft; er rückt an die erste Stelle der Version nur, wenn dort bisher ein unbelegter getippter Name stand, `raiderProfileStore.moveCharacterFirst`) — künftige Anfragen gehen dann an ihn. Daneben der Tab *Warteliste* gleich neben *Ausgebbar* (`WaitlistTab.tsx`, #775; Zähler = wartende Einträge, der Badge „N warten“ im Kopf springt dorthin): je Item die Schlange (Platz, Raider oder Charakter, Menge, seit wann; im Item-Kopf neben „Verfügbar N“ das Label „reihum je 2“ = die Portion; die Filterzeile sucht nach Item oder Spieler), mit Schreibrecht umsortieren, entfernen, anlegen (`WaitlistAddDialog.tsx`) und importieren (`WaitlistImportDialog.tsx`) — beides Knöpfe rechts in der Filterzeile des Tabs, je ein kleiner Dialog — Routen in [loot-import.md](loot-import.md#die-seite-gildenbank-632). Der Tab *Ausgegeben* direkt danach (`HandedOutTab.tsx`) zeigt, was an wen rausging, sobald es abgehakt ist (die ausgegebenen Anfragen der letzten 90 Tage).
