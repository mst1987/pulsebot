# Anmeldung

Endnutzer-Sicht: siehe [guide-discord.md#anmeldung](guide-discord.md#anmeldung), [guide-web-admin.md#anmeldungen](guide-web-admin.md#anmeldungen).

> **Sprache im Discord:** Alles, was ein Raider im Discord rund um Events und Anmeldung liest (Anmelder-Nachricht samt Titel-Kacheln und Fallback-Texten ohne App-Emojis, Dialoge, Modals inkl. Vielleicht-/Absage-Nachricht und Forever-Namen, Antworten, Ankündigung, Erinnerungen, DMs, Setup-Nachricht mit dem Knopf *Call invites*, Discord-Event, Raid-Übersicht auf dem Talk-Server, Nachricht im Notizkanal, `/profil`, die Absage des Berechtigungs-Gates in `botAccess.denyMessage`), ist **Englisch** — Klassen/Specs über `labelEn` (`config/gameVersions/classes.js`, `labelEnOf()`, `ROLE_LABELS_EN`), das Web behält `label` (Deutsch; die Web-Oberfläche bekommt ihre Sprache über die i18n-Schicht im Client). Deutsche Meldungen der gemeinsamen Services (`signupService`, `raiderProfileStore`, `utils/characterNames.js`, Bank-Gründe aus `utils/setup/reasons.js`) übersetzt der Bot mit `utils/botEnglish.js` `toEnglish()` — wer dort einen Satz ändert oder neu anlegt, trägt ihn in `RULES` nach (der Test prüft alle festen `fail(...)`-Sätze und jede Absage der Namensregel). Datum/Uhrzeit im Discord sind immer **Discord-Timestamps** (`<t:…:F>` usw., `utils/discordTime.js`); wo keiner rendert (Select-Optionen, Modal-Labels, öffentliche Seite) steht englischer Text in Serverzeit (Europe/Berlin). Gespeicherte Werte (Status-Keys, Spec-Keys) bleiben unverändert. **Deutsch bleiben vorerst** die Orga-Texte im Bot (`/event`, Event verwalten, die private Vorschau hinter *Call invites*, Auktionen, GDKP, Logcheck, Lookup-Befehle) und die Beschreibungen der Slash-Befehle (`data` im jeweiligen Befehlsmodul, erst mit einem neuen `npm run register` sichtbar). Es gibt keinen Sprachschalter im Bot.

## Anmeldung (Web) (`/signups`, `signup` area, #256)

The member's coming raids and their own signup. Menu entry *Anmeldungen* next to *Mein Profil*.

- **The rules live in `src/web/signupService.js`**, UI-agnostic so the Discord signup (#258) uses it 1:1: `await submitSignup(eventId, userId, input, { byOrga, now, roleIds?, config? })` → `{ signup, event, waitlisted, locked, notice }` (#306) or `{ error, code }` (`httpStatusFor(code)`; **async** since it reads the member's roles). **Raider roles are checked on save, not only on the page:** a category with `categoryRoles` takes a *new* signup only from a holder of one (`checkRaiderRole`, `discord.memberRoleIds` on the event's server, `raider_role` → 403 „Für diesen Raid brauchst du eine Raider-Rolle.“); roles that cannot be read let it through, an existing own signup may still be changed or withdrawn, `byOrga` is exempt. `categoryVisible` (the page's rule) lives in the service too and uses the same `categoryRoleAllowed`. Only an own event (`raidhelper` otherwise), not after its start (`started`); the character must be in the raider's profile and the spec one of that character's profile specs (`character`/`spec`, then the rule set via `signupStore.normalizeSignup`). **After `signupDeadline` a member may only pick `absence` or `late`**, or keep the status and spec they already had (to edit the comment); `byOrga` (whoever has `raids` write) is bound by neither. `canAlso` omitted = prefilled from the profile (`defaultCanAlso`: effective off-tank/heal switches plus the roles of the character's other specs, never the own role). `rosterCounts`/`roleCounts` are the one counting rule (signed + late take a seat) — `eventMessage.js` imports it. Saving goes through `signupStore.saveSignup`, so the event message and the talk overview update through `onSignupsChanged` with nothing extra.
- **Several characters (#293):** `submitSignup` takes `characters[]` and checks **each** against the profile (character and spec) — the first failing one names itself ("Brokk steht nicht in deinem Profil."); the same character twice counts once, more than three are refused (`characters`). A request with only `character`/`spec` (the Discord status buttons, the comment modal) **keeps the stored alternates**, so no front end that knows one character drops them. After the deadline "unchanged" means same status and same character list. `submitSignups(userId, [{ eventId, characters, status }])` runs the full `submitSignup` per raid (role check, deadline, start — one refused raid never stops the others; the member's roles are read once per server) and first drops per raid what cannot go there (`fitCharactersToEvent`: a spec the event's game version does not have → "Klasse passt nicht zu diesem Raid", gear "none" → "laut Profil ohne brauchbares Gear"); a raid left without characters is `no_character`. Comment and "kann auch" of an existing signup are kept.
- **API** (`apiRoutes/signups.js`): `GET /api/signups` (area `signup`: upcoming events of both sources + own status + the profile's characters), `PUT /api/signups` (area `signup`, body `{ eventId, characters: [{ character, spec }], status, canAlso, comment }` — a single `character`/`spec` still works — **always the session's `user.id`**, a `userId` in the body is ignored), `POST /api/signups/bulk` (area `signup`, #293: `{ eventIds[], characters[], status }` → `results` per raid with `ok`, `error`/`code`, `skipped` and the fresh `counts`; again only the session's account), `GET /api/signups/event?id=` (area `raids`: every signup with Discord name, "kann auch" and comment). The raid detail payload carries the same list as `ownSignups` for an own event.
- **Which events a member sees** (`signupView.categoryVisible`): only `config.categoryIds` (when set); a category with raider roles (`categoryRoles`) only for holders of one (`discord.memberRoleIds`, one member fetch, no privileged intent). Roles that cannot be read show the category; an event the member already signed up for always shows; the orga (`raids` read) sees all. Raid-Helper rows carry only `discordUrl` and the own reaction — **they have no signup button**, the page links "In Discord".
- **Wish partners** (`wishPartnersSignedUp`): only the member's *own* wishes that already signed up, as one badge in the dialog — nobody else's wishes, never whether it is mutual.
- **Client:** `pages/SignupsPage.tsx` (one row per raid: icon, title large, date/deadline small, fill `Bar` with the role counts in its tooltip, own status badge or the one action), `components/SignupDialog.tsx` (the characters as numbered lines — `components/SignupCharacterPicks.tsx`: 1 = the choice, the others "kann auch mit", arrows to reorder, "+ Kann auch mit …" up to three, rules in the strippable `lib/signupPicks.ts` run for real in the test —, spec with gear level, status segment with the `--sig-*` dots — disabled what the deadline no longer allows —, "Ich kann auch" chips, comment, wish badge) opened by `?event=<id>`, vocabulary in `lib/signups.ts`, CSS `styles/anmeldung.css` (`an-`).
- **The status belongs to the character, in the web as in Discord (#320).** Discord's buttons have moved only the *first* character since #302 while the web set them all — the same act with two outcomes. Each line of `SignupCharacterPicks` now carries its own status (a `--sig-*` dot plus a compact select, `an-pick-status`, only where one single signup is edited and there is more than one character — `statuses` + `allowedStatuses`, deliberately **not** a second block of switches), and the dialog's segment below is "Status für alle": it sets every character at once, shows nothing as chosen while they differ and says so in one line. `lib/signupPicks.ts` holds the rules (`setPickStatus`, `setAllStatuses`, `commonStatus`, `signupStatusOf`, and `picksToInput` sending `status` per character); the signup's own status keeps mirroring the first character's, so a person still takes at most one seat. The server side was already there — `signupService.withStatuses` — the client simply sent too little. `CHARACTER_STATUS_ORDER` in `lib/signups.ts` is the server's `CHARACTER_STATUSES`: no absence, because signing off is for the person. The bulk dialog keeps its one *Status für alle* for every raid and sends no per-character status at all. **Several raids at once (#293):** every own row that still takes a signup has a checkbox; once one is picked, a compact bar at the bottom (`an-bulk`, like the channels page) offers *Alle wählen* and *Für alle gewählten anmelden*, which opens `components/BulkSignupDialog.tsx` — the chosen raids as badges, the same character lines, *Status für alle* — and afterwards lists every raid's result: saved with its characters, or the reason, plus skipped characters. The own status badge shows `+N` for alternates, the characters in its tooltip. The raid detail's roster tab shows an own event's signups in role columns (`OwnSignupGroups`), "kann auch" and comment only as marks plus tooltip. Guarded by `test/web/signupService.test.js`, `test/web/signupsRoute.test.js`, `test/web-client/signupsPage.test.js`.

## Warteliste und Ankündigung (`src/web/signupService.js`, `src/web/eventAnnounce.js`, #306)

Zwei Dinge, die Raid-Helper konnte und wir nicht: ein voller Raid nimmt keine Anmeldung mehr an, und ein neues Event sagt den Raidern Bescheid.

- **Am Event** (`eventStore`, wie `fairness`/`wishes`, nicht im Plan validiert): `overflow` `"bench"` (Voreinstellung) | `"off"` und `lockAtLimit` (aus). Beides steht auch in der **Raid-Vorlage** (`raidTemplates.normalizeTemplate`) und wird beim Anlegen kopiert (`eventCreate.templateDefaults`, `PLAN_KEYS`) — das Event behält seine eigene Kopie.
- **Der Überlauf greift bei jeder *neuen* Anmeldung, die einen Platz belegt** (`applyOverflow`, aufgerufen zwischen `validateSignup` und `saveSignup`): ist `rosterCounts(...).attending` ohne die eigene Anmeldung ≥ `size`, wird aus der Anmeldung **Bank** (jeder Charakter auf `bench`) samt `notice` „Der Raid ist voll (25/25) – du stehst auf der Warteliste (Bank). …“, bei `overflow: "off"` wird sie mit `code: "full"` (409) abgelehnt. **Wer schon einen Platz hält** (`signed`/`late`, `holdsSeat`) behält ihn — auch beim Spec-Wechsel und beim Wechsel von „Dabei“ auf „Spät“ —, die Orga (`byOrga`) ist nicht gebunden, ein Event ohne `size` hat keine Grenze. ⚠️ **„Dabei“ und „Spät“ zählen beide** (`ATTENDING`): `rosterCounts` zählt sie gleich, also käme man an einer vollen Warteliste sonst einfach mit „Spät“ vorbei und die Nachricht stünde auf 3/2. „Vielleicht“, „Bank“ und eine Abmeldung belegen keinen Platz und werden nie angefasst.
- **Kein automatisches Nachrücken.** Meldet sich jemand ab, rückt niemand nach — das entscheidet die Orga im Setup. Der Roster-Tab der Raid-Detailseite sagt darum „3 auf der Warteliste“ (Badge neben „n abgemeldet“, Namen im Tooltip).
- **`lockAtLimit`** (`lockIfFull`, nach dem Speichern, zählt ebenfalls `attending` — eine „Spät“-Anmeldung, die den Raid voll macht, schließt ihn also auch): der volle Raid setzt `signupsClosed` wie „Anmeldung schließen“ (#288) und protokolliert es (`appendEventLog`, Aktion `lock`). **Nur zu, nie auf** — ein späteres Abmelden öffnet die Anmeldung nicht wieder.
- **Der Raider erfährt es sofort:** `submitSignup` liefert `{ waitlisted, locked, notice }` (und `submitSignups` je Raid) — `PUT /api/signups` und `/bulk` reichen es durch, `SignupDialog` macht daraus den Toast, `BulkSignupDialog` ein Badge „Warteliste“, und in Discord hängt jeder speichernde Pfad (`eventButton.save`, `signupStatus.save`, `eventJoin`, `multiSignup.resultLine`) die Zeile an die Bestätigung. Nichts davon liest der Raider erst im Roster.
- **Ankündigung beim Anlegen:** `config.categoryAnnounce = { [categoryId]: { enabled, target } }` (`target` wie `pingDelivery`: event | talk | both; aus ist Voreinstellung, nur eingeschaltete Kategorien werden gespeichert), Einstellungen → Kategorien als ein Segment *aus · Event-Kanal · Talk · beide*. `eventAnnounce.announceEvent(eventId, { want })` postet über **`pingDelivery.deliverAnnouncement`** (keine zweite Logik) eine Zeile „Neuer Raid: *Titel*“ mit `<t:…:F>` und Link auf die Anmelde-Nachricht und pingt die `categoryRoles` der Kategorie. `want` ist der Schalter des Erstellen-Dialogs bzw. `/event anlegen` und sticht die Kategorie.
- **Genau einmal:** `event.announcedAt` (`eventStore.setEventAnnounced`, überschreibt einen früheren Zeitpunkt nie) — Bearbeiten, ein erneutes Posten der Nachricht oder ein zweiter Aufruf kündigen nicht noch einmal an. Ein Fehlschlag wird **nicht** vermerkt (er kommt als `announceError` zurück und lässt sich über Raid-Detail → Anmelde-Aufruf nachholen) und lässt das Event stehen. **Serien-Events (#289) gehen denselben Weg**, weil `eventSeries` über `eventCreate.createEvent` anlegt und kein `announce` mitschickt — ein Schalter, kein Sonderweg. Nur eigene Events; ein Raid-Helper-Event kündigt nichts an.
- **Wo es steht:** Erstellen-Dialog — die zwei Schalter hinter „Mehr“ des Raid-Schritts, „Beim Anlegen ankündigen“ im Schritt *Kanal & Anmeldung*, beides als Zeile im Schritt *Prüfen* (`overflowLine` in `lib/eventPlan.ts`); `/event anlegen` — Knopf „Ankündigung: an/aus“ in Schritt 1, der Zustand reist als sechster Teil (`ann`) im customId mit. Tests: `test/web/signupService.test.js`, `test/web/eventAnnounce.test.js`, `test/web/eventCreate.test.js`, `test/web/eventDraft.test.js`, `test/commands/signup/eventButton.test.js`, `test/web-client/{eventCreateDialog,signupsPage,settingsLogic,raidEvents}.test.js`.

## Anmeldung (Bot) (`src/utils/signupDialog.js`, `commands/signup/`, #258)

The same signup as the web, inside Discord: the talk overview's select (`talk-signup`) and the event message's button (`event-signup:<eventId>`) open an **ephemeral** dialog — one embed (date · `Tank 1/2 · Heiler 1/3 · DPS 4/5`, own status, deadline/start hint, wish partners, the last confirmation or error) and at most five component rows: *Charakter · Spec* (the profile's characters with gear level), *Kann auch* (multi-select of the roles other than the spec's), the buttons *Dabei / Vielleicht / Spät / Bank / Abmelden* (disabled what `allowedStatuses` forbids), *Kommentar* (only with a signup) and *Im Web öffnen*. Works on both servers — it reads only the stores.

- **Stateless.** Unsaved picks ride in the customIds: `signup-pick:<eventId>:<k|s|a>:<state>` (class / character·spec / kann auch — `signupPick.js`, redraws only), `signup-status:<eventId>:<s|t|l|b|a>:<state>` (`signupStatus.js`, saves) and `signup-comment:<eventId>:<state>` (`signupComment.js`, button + modal like `logevalForce.js`), with `<state>` = `<characterKey>:<specKey>:<roleMask t/h/m/r>`. An id that would pass 100 characters drops the state and the handler falls back to the stored signup. Every step re-reads event, profile and signup (`resolveState` refuses a character that is not the member's) and saves only through `signupService.submitSignup` — deadline, start and spec rules are the service's; its error (German in the service, English through `toEnglish()`) lands in the same message (`interaction.update`), so nothing piles up. A status change keeps the stored comment; the comment modal keeps status and spec, so it works after the deadline.
- **Without a profile character** the dialog offers class → spec from the event's rule set plus "Profil anlegen" (`/profile`). A status click then opens a modal for the character name (prefilled with the Discord display name); its submit adds that character with the spec to the member's profile (`raiderProfileStore.addCharacter`, `source: "manual"`) and signs up. *Abmelden* needs no character; a status the deadline refuses answers with the reason before asking for a name.
- **Raid-Helper events** (from the talk select) get a link button into their event channel (`getStoredEvent().guildId`, else the event server) — the signup stays Raid-Helper's.
- **Access:** `talk-signup` and `event-signup` are `group: "signup"`, `defaultAccess: "everyone"`; the three step handlers declare `accessOf: "event-signup"`. The dialog never acts `byOrga`. **Raider roles:** opening the dialog (button or talk select) answers „Für diesen Raid brauchst du eine Raider-Rolle.“ instead when the event's category wants a role the member lacks and they have no signup yet (`signupService.checkRaiderRole`); the talk overview is one message for everybody, so it cannot leave such raids out. A status click refuses the same way (before the character-name modal, too). Tests: `test/utils/signupDialog.test.js`, `test/commands/signup/*` (in-memory stores in `test/helpers/signupMocks.js`).

## Mehrere Raids auf einmal (Bot) (`src/utils/multiSignup.js`, `commands/signup/talkSignupAll|talkSignupMulti|signupMulti.js`, #293)

The raid overview on the talk server carries *Für alle Raids anmelden* and *Mehrere Raids wählen …* above its single-raid select. Everything is ephemeral and saves through `signupService.submitSignups`.

- **Which raids:** `signableRaids()` — own events of the event server that have not begun, are not cancelled/closed, of `config.categoryIds` when set, soonest first, at most 25. Deadline and raider role are **not** filtered out: the result names them per raid.
- **Mehrere Raids wählen …** (`talk-signup-multi`): *Schritt 1* — a multi-select of those raids (all preselected), a *Status für alle* select and *Weiter: Charaktere*. **Für alle Raids anmelden** (`talk-signup-all`) skips it and opens the modal at once (a modal can only answer a click).
- **Schritt 2 is a modal** built from Label components (type 18) with string selects: per raid one select of the member's characters · specs (spec emoji via appEmojis, `max_values` 3, empty = skip that raid), **at most five raids per modal** — Discord's limit of five fields, which is also why the status sits in step 1, not in the modal. With more raids the answer after a submit carries *Weiter: Raids 6–10*; a modal cannot open the next modal by itself. *Für alle* is one modal: one character select for every raid plus *Status für alle*.
- **Priority = the order the modal listed the options** (the stored characters or the last-used spec first). Discord returns the picks without their click order, so the listed order is kept in the session when the modal is built and read back on submit (`orderedPicks`).
- **State under a token**, not in the customId (≤ 100): `signup-multi:<token>:r|s` (step-1 selects), `:go:<page>` (opens a modal), `:m:<page>` (the modal) — raids, picked raids, status, option orders and results in memory for 30 minutes, only for the member who started (`getSession`); an expired or foreign token answers „Die Auswahl ist abgelaufen …“ and saves nothing. The last page ends the session.
- **Result:** one line per raid — `✅ **SSC + TK** · Mi 24.09.: Zibbo · Heilig, +Zibbowar · Schutz`, `⏭️ … übersprungen (kein Charakter gewählt)`, `⛔ …: <the service's reason>` with skipped characters and why; a page submitted twice replaces its lines.
- **At one event:** the character select of the event message (`utils/joinPicker.js`) shows *Mehrere Charaktere …* (`signup-multi:e:<eventId>:<code>`) when the member has more than one character · spec — the same modal for that one raid, status from the select, refused first after the deadline or without raider role.
- **Access:** the three handlers declare `accessOf: "talk-signup"`. Tests: `test/commands/signup/signupMulti.test.js`, `test/web/talkOverview.test.js`.

## Anmelder-Nachricht (`src/web/eventMessage.js`, `commands/signup/eventPick.js` + `eventButton.js`, #287, #303)

The message in an own event's channel is built like Raid-Helper's, with icons instead of text and plenty of air — our bot, no Raid-Helper branding. `buildEventMessage(event, signups, { emojis, now, icsUrl, raidArt, titleSize })` is **pure and returns plain API JSON** (no builders), so tests and the length checks read it directly.

- **Look per category** (`config.categoryMessageLook`, Einstellungen › Kategorien, `embedLook.messageLookOf`): **Raid-Bild** (default on) puts the leading instance's picture below the message — Blizzard's zone art `render.worldofwarcraft.com/eu/zones/<art>-small.jpg`, 600 × 300, the slug is the instance's `art` in `config/gameVersions`; an event's own banner keeps its place, a cancelled event has none. **Titelgröße** `normal` · `large` (default) · `huge` sets `## ` / `# ` before the line of letter tiles — an emoji grows with the heading it sits in, and a heading is the only larger line an embed description has. Only what differs from the default is stored.

- **Layout (#303):** title and description (with a phase line on top: *Cancelled – reason*, *Signups closed*, *deadline passed*, *raid has started*; the title as letter tiles opens the description, see „Emoji styles“ below). The **head is icon + value only**, three inline columns whose name is a zero-width space, their rows as lines of one field so they sit directly under each other: Leader · Date `<t:…:D>` · voice channel `<#id>` (#305, only when one is set) | Signed up `**n** / size` · Time `<t:…:t>` | Deadline (an empty first line when none is set, so the countdown stays beside date and time) · Countdown `<t:…:R>`. No end time: a duration nobody set would only show the default. The **role totals are columns**: Tanks with Healers directly below · Ranged · Melee (`<icon> Tanks **2**/3`; Tanks/Healers against `composition`, Melee/Ranged as `/min+` or `/min–max` from `compositionMax`) with the role icons of the event's emoji style (the WoW `eh_role_*` are no longer used here), then one empty full-width field. The roster: a **Tanks block first**, then **one inline block per class** in the rule set's fixed order, named `<class icon> __Priest__ (3)`, each line `<spec icon> \`nr\` **Name**` and an empty last line that keeps the rows of blocks apart; then one field with the lines `<status icon> Late (n): \`nr\` Name, …` for Late / Tentative / Bench / Absence, the approved setup (only the approved snapshot, never a draft) and a links line `Event · Sign up · Setup (only when approved) · Calendar`. Healers and dps stay in their class block. The last row of blocks is filled up to three with empty inline fields — Discord spreads a row of fewer than three over the whole width, and its blocks would stand out of line. Field budget worst case: 3 head + 3 totals + 1 spacer + 10 blocks (Tanks + 9 classes) + status + setup + links = 20; should anything push past 25, `fitFields()` drops the spacers first, never content.
- **Every character of a signup is listed where its own status puts it** (`rosterEntries()`): a raider signed up with a healer and a tank shows up in both blocks, under the **same number**; a first character on „Spät“ sits in the Spät line while the second stays in its class block. An absence is one line per person. **Only the first character counts:** in a class or Tanks block the raiders' first characters come first (bold, by number), their further characters below all of them — **not bold** — and the block's `(n)` counts only the first ones; in the Late/Tentative/Bench lines one raider is one entry (`\`8\` Zibbo / Zibbomage`) and counts once. The Tanks block wears the Protection Warrior's spec icon; Nahkampf is two crossed swords (`eh_r<style>_swords` / `eh_ui_swords`, `scripts/render-role-swords.js` — a new name, because an uploaded emoji is never replaced). **The count is per person:** „Angemeldet n / size“ and the role totals come from `rosterCounts` over the signups' top-level status and role (= the first character's), so a raider takes at most one seat — the setup proposal places one character per person, too.
- **Numbering** by signup time (`at`, then user id) over every signup of the event — stable, since the store keeps `at` when a signup changes.
- **Farbe und Bild** (#307, `src/web/embedLook.js`) — der Balken links und das Bild: `event.color` (`#rrggbb`) und `event.image` (`{ mode: "thumbnail" | "banner", url }`), beide vom Event, das sie beim Anlegen von seiner **Raid-Vorlage** geerbt hat (`raidTemplate.color` / `.image`, im Erstellen-Dialog hinter „Mehr“ noch änderbar). Beide fallen **einzeln** auf den Regelsatz zurück (`lookOf()`): Farbe und Boss-Icon (`wowIconUrl(icon, 56)`) der **führenden Instanz** des Abends — der größten, bei Gleichstand der zuerst genannten, dieselbe Regel wie `normalizePlan`s Tank/Heiler-Vorschlag —, sonst `embedAccentColor`. Jede Instanz jedes Regelsatzes hat dafür ein `color` (`gameVersions/*.js`, für den Client in `publicVersions()`), damit SSC, BT und Hyjal **ohne jede Einstellung** auseinanderzuhalten sind. **Nur `https`:** eine Adresse, die Discord nicht laden kann, wird beim Speichern mit einem Satz abgelehnt (`colorProblem`/`imageProblem`, geprüft am Rohtext, damit ein Tippfehler nicht still zu „keine Farbe“ wird) und beim Bauen notfalls weggelassen plus geloggt — ein Bild darf eine Nachricht nie verhindern. Ein **abgesagtes** Event behält den roten Balken und verliert das Bild. Das Bild zählt nicht gegen die 6000 Zeichen, ändert aber den `payloadHash`, also zeichnet der Sweep bestehende Nachrichten einmal neu.
- **Discord's limits are enforced in the builder:** ≤25 fields, ≤1024 per value (a long block ends in "+N weitere"), ≤6000 per embed (blocks are shortened step by step until it fits). Names are markdown-escaped and `@` is broken, so a character name cannot bold, link or ping. Nothing personal goes in beyond the names the raiders signed up with (an absence without a character shows as `<@id>`).
- **Without application emojis the icons are left out** — each head line then leads with its label („Leader: …“, „Date: …“), the totals and status lines keep their words („Tanks **2**/3“, „Late (1): …“), a roster line gets the spec's English name after the raider; no colourful unicode stand-ins. `test/web/eventMessage.test.js` holds it (it also refuses emoji code points in the fallback).
- **`event.status`** `"cancelled"` / `"closed"` (the event management, #288) is honoured: red "Cancelled: …" resp. the closed line, and no components (a closed signup keeps *Absagen*).
- **Components** (`buttonRows()` / `messageComponents()`): before the deadline row 1 the **public select** `event-pick:<eventId>` („Anmelden – Charakter oder Klasse wählen …“: *Meine Charaktere …* with the `eh_ui_signups` icon, then every class of the event's game version with its class icon; ≤ 25 options), row 2 *Spät* · *Vielleicht* · *Bank* · *Absagen* (red), each with its flat icon; after the deadline *Spät* · *Absagen*; a signup the orga closed (`signupsClosed`) only *Absagen*; after the start or for a cancelled event none. **Why „Meine Charaktere …“ and not the characters themselves:** a message component is one and the same for everybody who sees the message, so a public select cannot list anyone's own characters — picking it opens them ephemerally.
- **Redraws** (`startEventMessageSync()`): a roster change redraws **at once** when the message was not drawn within the quiet window (2 s), changes inside it collapse into one redraw at its end, and redraws of one event run **one after the other** (`redrawEventMessage`, a promise chain per event) — so an older payload can never land after a newer one. The message's **payload hash** is stored with it (`event.message.hash`, `payloadHash()`); `refreshEventMessage` skips an edit whose hash is unchanged, and the **sweep** (30 s after boot, then every 5 min, events of the last two days and later) redraws every message whose current payload differs from its hash — a deadline or start that passed, and a roster change whose redraw was lost to a restart. The first sweep after a deploy that changes the layout therefore restyles every recent message once. `npm run dev` ignores `data/` (`nodemonConfig`), because a signup write used to restart the bot inside the debounce and drop the redraw (#303: the confirmation said „Bank“, the message still „Abgemeldet“).
- **The public select** (`commands/signup/eventPick.js`, `accessOf: "event-btn"`): Discord keeps a picked option shown in the member's client and sends nothing when the same option is picked again, so the handler first **resets the select** with `interaction.update({ components })` (the embed stays untouched) and answers with an ephemeral follow-up (`eventButton.reply()` follows up once the interaction is acknowledged; if the reset fails it replies). *Meine Charaktere …* = the old *Anmelden*, a class = the old *Klasse wählen* with that class already picked.
- **The flows** (`commands/signup/eventButton.js`, `group: "signup"`, `defaultAccess: "everyone"`, every step shares that name; builders and pure rules in `src/utils/signupButtons.js`). Everything answers only the member (a pick or click on the public message answers ephemerally, a step inside that answer updates it) and saves through `signupService.submitSignup`; refusals first (`refusal()`: cancelled, started, closed, deadline — then the raider role via `checkRaiderRole`):
  - *Meine Charaktere …*: exactly one fitting character · spec (gear not "none") signs up at once; several → a **multi-select** of the own characters · specs (`event-btn:<id>:pick:<code>`, up to `MAX_CHARACTERS` 3, the current signup's characters listed first, then the likeliest; **nothing preselected**, so picking the same ones again saves — the content says „Bisher: …“) with **the class select below it** (`cls`) for a new character. The priority is the order the select listed them (`orderedValues()` over `interaction.component.options`, Discord does not keep the click order). No profile character → the class select.
  - *a class*: spec select (`spec`, with „Andere Klasse“) → name modal (`name:<code>:<specKey>`, prefilled with the member's character of that class, else the Discord display name). The submit adds the character (or the spec) to the profile (`source: "manual"`, a name the profile has with another class is refused) and **appends it to an existing signup** (same character = replaced in place; a full signup is refused) or starts one.
  - *Spät* / *Vielleicht* / *Bank*: signed up → **only the first character** gets the status (`firstCharacterTo()`), the others keep theirs; not signed up (or signed off) → the character select with that status and the classes below, without a profile character straight to the class select. *Vielleicht* first opens the message modal (`note:t`, see „Nachricht bei Vielleicht / Absagen“ below) unless the category asks for none.
  - *Absagen*: a modal (`why`) with a short message (≤ 100, required only where the category says so); the signup becomes an absence with the message as its comment (the characters stay on record). A category with „keine“ signs off at once, without a modal. The modal comes from the public message, so its answer is a reply, never an edit of that message.
  - **The confirmation** (`savedText(event, signup, profile, { emojis })`): with the app emojis `<eh_ui_signed> Gespeichert für **Titel**` and one line per character `\`1\` <spec icon> Devire · Arkan  ·  <status icon> **Bank**` (`<eh_ui_absence> Abgemeldet von …` for an absence); without them the plain text of before.
- **Older messages keep working** until their next redraw: the buttons *Anmelden* / *Klasse wählen* of #302 (`event-btn:<id>:join|class`, same handler), the select `event-join:<eventId>` of #287 (`commands/signup/eventJoin.js` with the character select of `utils/joinPicker.js`, still used for „Mehrere Charaktere …“) and the button `event-signup:<eventId>` of #254 (`eventSignup.js`, the #258 dialog). Tests: `test/web/eventMessage.test.js`, `test/commands/signup/eventPick.test.js`, `eventButton.test.js`, `eventJoin.test.js`.

## Nachricht bei Vielleicht / Absagen (`src/web/signupNotes.js`)

Wer „Vielleicht“ oder „Absagen“ wählt, kann der Raidleitung eine kurze Nachricht hinterlassen; der Bot postet sie in einen Kanal.

- **Kanal:** `discordServers.signupNoteChannelId` (Einstellungen → Verbindungen → Discord-Server, Feld „Vielleicht- & Absage-Nachrichten“, Kanäle beider Server; die Event-Karte zeigt ihn). Leer = es wird nichts gepostet. Anders als die Talk-Kanäle bleibt er auch ohne zweiten Server stehen (`discordServersPatch`). Er ist der **Standard** für jede Kategorie ohne eigenen Kanal.
- **Eigener Kanal je Kategorie** (#335): `config.categorySignupNoteChannel = { [categoryId]: channelId }`, nur Snowflakes, gespeichert gemergt wie `categoryVoiceChannel` (`""` = Eintrag weg, zurück zum Standard); kein Voll-Admin-Schlüssel. Gewählt auf der Kategorie-Karte direkt unter dem Segment *Pflicht · optional · keine* (Select „Standard (#…) · #…“, Kanäle beider Server aus `GET /api/settings` → `noteChannels: { defaultId, channels }`; bei *keine* oder ohne Kanalliste ausgeblendet). `noteChannelFor(categoryId, config, { reachable })` ist die eine Regel: eigener Kanal, wenn der Bot ihn erreicht (`discord.channelVisible`: im Cache, Text, Ansehen + Schreiben), sonst Standard, sonst keiner. Lehnt der eigene Kanal den Post trotzdem ab, versucht `postSignupNote` den Standard — die Nachricht geht nicht still verloren. Die Karte markiert einen Kanal, der nicht in der Liste steht, als **„nicht erreichbar“** (`noteChannelPick`); ohne eigenen Kanal ändert sich nichts gegenüber #331.
- **Je Kategorie** `config.categorySignupNotes = { [categoryId]: "required" | "none" }`, fehlend = `"optional"` (nur Abweichungen werden gespeichert; Einstellungen → Kategorien, Segment *Pflicht · optional · keine*). `noteMode(categoryId)` ist die eine Regel.
- **Discord** (`eventButton.js`): *Vielleicht* und *Absagen* öffnen das Modal `buildNoteModal` (Pflicht = `required` + min. 2 Zeichen, sonst leer erlaubt), *keine* = kein Modal. Beim Vielleicht ohne Anmeldung kommt das Modal **vor** der Charakterwahl; der Text wartet dann 30 min im Speicher (`keepNote`/`takeNote`, je Event + Mitglied, nur für denselben Status) auf den Speicherschritt, weil er nicht in eine customId passt.
- **Web** (`SignupDialog`): bei Vielleicht/Abmelden heißt das Kommentarfeld „Nachricht an die Raidleitung“, `row.noteMode` kommt aus `memberEventRows`; *Pflicht* sperrt den Knopf, und `PUT /api/signups` lehnt eine fehlende Nachricht mit `note_required` (400) ab — die Orga nicht.
- **Gepostet wird in `submitSignup`** (`postSignupNote`, nicht abgewartet, wirft nie): nur bei Status `tentative`/`absence`, nicht leerem Kommentar, und wenn Status oder Kommentar sich geändert haben (`hasNewNote`) — erneutes Speichern postet nicht doppelt; nie `byOrga`, nie bei *keine*. **Der Post ist ein Embed im Look von Raid-Helpers eigener Signup-Notification** (`buildNotePost`, englisch wie alle Raider-Texte): farbiger Balken in `embedAccentColor`, Titel „Notification received!“, Beschreibung `**<@user> (Charakter)** signed up as <icon> **Tentative|Absent** with the following reason:`, Leerzeile, der Kommentar (entschärft), Leerzeile, `<@user> | **[Titel](Link zur Anmelde-Nachricht)** <t:…:f>`. Markdown und `@` im Text werden entschärft; `discord.postNotice` nimmt jetzt Text **oder** `{ content?, embeds? }` und pingt niemanden (`allowedMentions: { parse: [] }`).
- Der Anmelde-Dialog des Talk-Servers (`signupStatus.js`) fragt nicht nach einer Nachricht; ein dort gesetzter Kommentar wird aber genauso gepostet. Tests: `test/web/signupNotes.test.js`, `test/commands/signup/eventButton.test.js`, `test/web/signupService.test.js`, `test/web/signupsRoute.test.js`, `test/web-client/{settingsLogic,signupsPage,catCard}.test.js`, `test/web/{settingsStore,settingsRoute,discord}.test.js`.

## App-Emojis (`src/web/appEmojis.js`, `scripts/sync-app-emojis.js`, #287)

Spec, class, role and UI icons are **application emojis of the bot's Discord application** (discord.js ≥ 14.16), so they work on the event and the talk server, in embeds, select options and buttons.

- **Names** (≤32, `[a-z0-9_]`): `eh_<class>_<spec>` (`eh_priest_shadow`) and `eh_class_<class>` — WoW icons downloaded from `wow.zamimg.com/images/wow/icons/medium/<icon>.jpg` — plus **`eh_ui_<name>`**, the flat UI icons (`UI_ICONS`: leader, signups, date, time, deadline, start, signed, late, tentative, bench, absence, closed, class, and since #303 the roles tank, healer, melee, ranged, since #305 `voice` and `end`). `statusEmojiName(status)` is `eh_ui_<status>`, `roleUiEmojiName(role)` `eh_ui_<role>`. **The WoW role icons `eh_role_*` are gone with #320:** the setup message was their last reader and draws the flat ones like the signup message, so they are out of the catalogue — an application that already has them keeps them, nothing ever deletes an emoji. `emojiCatalog()` lists all 56: `{ name, icon, url }` for the WoW icons, `{ name, icon, file }` for the UI icons.
- **The UI icons are drawn, not downloaded:** single-colour line icons in light grey (`#B9BBBE`, Raid-Helper's look, readable on Discord's dark and light theme) defined as SVG in `scripts/render-ui-emojis.js` and rasterised with the devDependency `@resvg/resvg-js` into **checked-in 128 px PNGs** under `assets/emojis/eh_ui_<name>.png` (`uiIconFile(name)`). The bot never rasterises at runtime. To change one: edit the SVG, `node scripts/render-ui-emojis.js`, commit the PNG — and delete the old emoji in the developer portal first, because the sync never replaces an existing name. `test/web/appEmojis.test.js` checks every UI icon has a drawing and a 128×128 PNG under Discord's 256 KB.
- **Emoji styles — letter tiles and role icons per event** (`emojiStyle` on the event and the raid template: `arcane` (default) · `gold` · `parchment` · `plain`; picked under „Aussehen“ when creating/editing an event or a template, copied from the template like the colour, logged as „Emoji-Stil“ on an edit). Each drawn style is a full set: **`eh_t<s>_<char>`** letter tiles (`TITLE_TILES`: A–Z, 0–9, `+` `-` `&` → `plus`/`minus`/`amp`) and **`eh_r<s>_<role>`** role icons, `<s>` = `a`/`g`/`p` — 3 × 43 checked-in 128 px PNGs under `assets/emojis/`, listed in `emojiCatalog()` as `{ name, tile, file }` and uploaded by the start sync like the UI icons. `tileEmojiName(char, style)`, `roleEmojiName(role, style)` (`plain` → the flat `eh_ui_<role>`), `emojiStyleOf(x)` (unknown → `arcane`; the client has the same in `lib/raidTemplates.ts`).
  - **The title line:** an embed title cannot show emojis, so the event message puts the title as tiles in the **first line of the description** and drops `embed.title` (Raid-Helper does the same). Upper case; `Ä/Ö/Ü` → `AE/OE/UE`; words set apart by an em space. **Plain title instead** when the style is `plain`, a character has no tile (`(`, `ß`, …), the title is over 32 characters, a tile is not uploaded yet, or the event is cancelled („Abgesagt: …“). The role icons fall back to the flat ones the same way. The setup message draws the style's role icons too.
  - **The images are generated, not drawn:** Gemini 2.5 Flash Image („Nano Banana“, key `GEMINI_API_KEY` in `.env.dev`, prepaid credits needed), one prompt per style with an in-set tile as the style reference, then the white background around the tile flood-filled to transparent, trimmed and scaled to 128 px. A redrawn tile needs the old emoji deleted in the developer portal first (the sync never replaces a name).
- **`eh_status_*` is retired:** the colourful WoW status icons of #287 are no longer in the catalogue or used; an application that has them keeps them (nothing deletes an emoji).
- **Read once per process**: `loadAppEmojis(client)` (after the start sync below and before every message render) fetches `client.application.emojis`, caches only `eh_` names; a failed read is retried after 10 min, never throws. `emojiText(map, name, fallback)` → `<:name:id>`, `emojiOption(map, name, fallback)` → the select option's / button's emoji object.
- **The bot uploads them itself on start** (`src/web/appEmojiSync.js`' `ensureAppEmojis(client)`, called on `clientReady`): it reads the application's emojis, creates **only the missing** ones from the catalogue (never replaces or deletes) — a `file` entry is read from disk (`readIconFile`: png/jpg/gif/webp, ≤ 256 KB), a `url` entry downloaded — and then reads the cache anew — so a fresh application, production included, needs no manual step, and a new spec/class or UI icon arrives with the next restart. It never throws; a refused upload (emoji limit, zamimg down) is logged and the message keeps its fallback. `node scripts/sync-app-emojis.js --dry-run` runs the same sync by hand without starting the bot (lists what is missing; without the flag it creates them; `--dev` reads `.env.dev`).
