# Roster und Raider-Profil

Endnutzer-Sicht: siehe [guide-web-admin.md#mein-profil](guide-web-admin.md#mein-profil), [guide-web-admin.md#roster](guide-web-admin.md#roster).

## Roster-Seiten (`roster` area, #654)

`/roster` is the overview of the raid rosters (the store below, "Roster je Kategorie"), `/roster/r/<id>` one roster, `/roster/chars` the old list of every character ("Alle Charaktere", next section). The menu entry "Roster" stays active on all three; the roster page names itself in the breadcrumb through `hooks/usePageCrumb.ts` (a `PageCrumbContext` the shell provides around its outlet — the outlet context keeps carrying the user only). Read only for now: adding and editing members comes with #655, the Abgleich tab and the "Rolle geben" action with the client part of #656 (its backend is below), creating rosters, settings, managers and Komposition with #657.

- **API** (`src/web/apiRoutes/rosters.js`, area `roster` read; the views are `src/web/roster/rosterView.js`): `GET /api/rosters` answers `rosters` (one head per roster of the active server), `categoriesWithoutRoster` (`config.categoryIds` without a roster; a category another server's Discord names stays off) and `canCreate` (full admin). `GET /api/rosters/roster?id=` answers `roster` (the head), `members`, `window` (the category's attendance window), `membersKnown` and `canManage` (`canManageRosterLive`); 400 without id, 404 for an unknown roster or one of another server.
- **A head** (card and roster page): name, category name, version (`versionLabel`), the category's raids (`contents`, `raids`, `icon` from `categoryInfo` over the nights of the roster's version), `mainRole` and `discordRoles` (`discord.listRoles`; a role Discord does not list keeps its id and an empty name), `slots`, `counts` per status, `places` (**core + trial take a place**; bench and pause are counted per status only), `roleCounts` (tank/healer/dps/unknown of the places, by each member's first character), `attendance` (mean of the members' shares, paused members left out; null without a counted night) and `todo` (`withoutRole` — null when the Discord member list is unavailable —, `withoutChar`, `trial`). The card adds "n Plätze frei" from `slots.total - places`; the damage target is `total - tank - healer`.
- **A member**: `displayName` and `avatarUrl` from the cached Discord member list (`listHumanMembers`), else the profile's name, else the first character, else the id; `onServer` (null when the list is unavailable); `status`, `since`, `trialUntil`; `chars` resolved server-side — the raider profile of the roster's version (spec key, `specId`, `specLabel`, WoW `specIcon`, class colour), else the character cache (`iconUrl` from class and spec), else the name the roster stored (`charNames`), else the key's name part; `role` = what the first character last played in a log, else its spec's role; `hasRole` = holds one of the roster's `roleIds` (null when the list is unavailable or the roster has no role); `attendance` **per person** (`attendanceForAccounts` with `nights`, the roster's characters plus every profile character of the version, the window from `categoryAttendanceFor`; null without category or without characters), in the shape the shared `AttendanceBar` reads (`present` beside `missed`).
- **Client** (`pages/roster/`: `RostersPage.tsx`, `RosterDetailPage.tsx`, `RosterParts.tsx` for the version line and the role chip; rules in `lib/roster/rosters.ts`; styles `styles/rosters.css`, prefix `rn-`, the status colours are the tokens `--rn-core/-trial/-bench/-pause` set through `[data-st]`). The overview: one card per roster (a link), the dashed card per category without roster (no button until #657), "Alle Charaktere" as the head's ghost button — no primary button. The roster page: back button "Alle Roster", the head, the tab bar (`TABS` in the page; a later phase adds its line and uses the route's `:tab` segment), then the members tab: square status fields (toggles with counts; pause off at first), the role `Segment`, a search over names and characters, the table grouped by status and sorted per group by its `SortTh` heads (`useTableSort("roster-members-sort")`, the filter in `usePersistedState("roster-members-view")`). Below 700 px the table turns into one block per person. Statuses read DE Stamm/Probe/Ersatz/Pause, EN Core/Trial/Bench/Paused (`roster.status.*`).
- **Tests:** `test/web/apiRoutes/rosters.test.js` (router, gate, parameters), `test/web/roster/rosterView.test.js` (figures, characters, roles, attendance, without Discord), Vitest `pages/roster/RostersPage.test.tsx`, `RosterDetailPage.test.tsx`, `lib/roster/rosters.test.ts`, the crumb in `components/shell/Shell.test.tsx`.

## Alle Charaktere (`/roster/chars`, `roster` area)

Every known character of the guild, grouped by raid category (design #218) — the page that was `/roster` before #654 (`pages/roster/RosterCharsPage.tsx`, with a back button to the overview). Three things about the list itself:

- **The column heads are the sort control** (`SortLabel`, the same one the loot council's grid uses), and the sort is applied **per group**, because the attendance column measures against *that* category — a roster sorted by attendance across groups would compare Monday's raid with the pug night. The sort lives in its own store (`useTableSort("roster-sort", …)`), the rest of the view (search, role, class, spec, open groups, which list) in `usePersistedState("roster-view", …)`.
- **Class chips, then spec pills.** The spec row appears only once a class is picked and lists the specs that class actually has in the roster — thirty specs at once is not a filter. A stored spec the current class does not have filters nothing instead of emptying the page.
- **Per game version (#543).** `GET /api/roster[?version=<id>|all]` answers one version — the main version unless the page asks for another or `all` (`roster.js versionFilter`) — with `version`, `mainVersion` and `versions` (every version with characters plus the main one, with counts); the page shows the segment only with more than one. A row's `versionIds` come from `services/characters/characterVersions.js`: a profile character of that name first, then its loot (an own event's version, anything else TBC — stored records never move), only then the versions its categories play, else TBC. Attendance counts only the raid nights of the version shown (`buildAttendanceContext(guildId, { versionId })`: an own event's version, a Raid-Helper night is TBC). Links follow the settings of that version (#542, `versionSettings.versionLinks`): the filtered version, else the row's own (the main version first) — a version without templates gets no link. The loot history's "Charaktere" tab filters the same way on the client (`/api/history` sends `versionIds` per character, `versions`, `mainVersion`), `/api/history/char?version=` picks the links.
- **Characters can be taken off the roster** (`src/stores/rosterHiddenStore.js`, `POST /api/roster/hide`, `data/settings/roster-hidden.json`). A roster built from loot and logs keeps everyone who ever raided, and "40 % Anwesenheit" over a guild half of whom left says nothing about the half that is still here. Hiding **deletes nothing** — loot history, evaluations and the character page stay whole; `GET /api/roster` simply answers with `chars` (the roster) and `hiddenChars` (with the note who hid them and when) apart, and `stats` counts only the former. The page's "Ausgeblendet" tab lists them and puts them back. Like the council's exclude list this is an explicit decision, never a rule such as "nobody who has not raided in 60 days" — the difference between *gone* and *was ill* is one only a person knows.
- **The attendance tooltip** (`AttendanceBar`, `components/roster/RosterCommon.tsx`) is a `RichTip` (`components/ui`): the count and share on top, then "Dabei" and one group per reason for a missed night ("Nicht im Log", "Keine Anmeldung", "Abgemeldet", "Vorläufig", "Ersatzbank", in that order; `lib/roster/rosterView.ts attendanceGroups`), each night a small date field, newest first. The server's German reasons are translated in the client (`roster.badge.reason.*`). `GET /api/roster` sends the attended nights as a slim `present` list beside `missed` (not the full night list, which only the character page gets as `raids`). Design canvas "Anwesenheits-Tooltip", variant C.

## Roster je Kategorie (Store)

Epic "Roster je Kategorie", part 1 (#653): the data and the rights, no page yet. Who belongs to a raid lives in `src/stores/rosterStore.js` (`data/settings/rosters.json`, shape in its head comment): one roster per raid category at most (`categoryId`, or `null` for a roster without category), its game version, the Discord roles that mean "in the roster" (`roleIds`, the first is the main role; `trialRoleId` optional), the managers (`managers.roleIds` / `userIds`, 20 each), slot targets, `allowMultipleChars` (off: a member keeps one character), `source` (`manual` / `kader` / `migration`) and the members (`core` / `trial` / `bench` / `pause`, `since`/`by` of the last status change, characters as profile keys `characterKeyOf(name, versionId)`, note, `trialUntil`). Every change writes a history line (`at`, `by`, `userId`, `what`, `detail`; the newest 500 stay). Beyond the issue's shape a member carries `charNames` (key → the name as it was assigned, e.g. `"Keslight-Thunderstrike"`), because a key is the lower-case name without realm and the facade below must hand out the name unchanged.

- **API:** `listRosters(guildId)` (`""` = all), `getRoster`, `rosterForCategory`, `createRoster(data, { actor })`, `updateRoster(id, patch, { actor })` (members, history, id and creator are not patchable), `deleteRoster`, `upsertMember(rosterId, userId, patch, { actor })`, `removeMember`, `appendHistory`. Conflicts throw a `RosterError` with `code` (`category_taken`, `invalid_name`, `member_limit`). Strict normalisation on read and write: unknown fields drop out, limits (name 40, note 500, members 500, managers 20) are cut.
- **Migration** (`settingsMigration.js` → `services/roster/rosterMigration.js` → `rosterStore.migrateCategories`): every category with `config.categoryRoles` or entries in `raider-characters.json` gets a roster (`source.kind: "migration"`, roles = `categoryRoles`, assigned raiders as `core` with their character first). The server of a category comes from the category name snapshot (`category-names.json`), else a stored event of that category, else the first configured event server (`discordServers.eventGuilds[0]`, else `guildId`) — nothing stored names it directly. The name: snapshot, else the newest event's `categoryName`, else the id. Handled categories are listed in `migratedCategories`, so the migration runs once per category: an existing roster is never touched, a deleted one never comes back, a category that gets roles later gets its roster on the next start.
- **Facade:** `raiderCharactersStore.js` keeps its API and answers. A category with a roster is read from it (each member with a character → his first one, by `charNames`, else the profile character's name, else the character cache, else the key's name part); `setCategoryAssignments` writes into the roster: a raider in the map gets the character first (a new one joins as `core`), a member left out loses his characters but **stays in the roster with his status** — the assignment says which character, membership is the roster's own business. Reading back gives exactly the saved map. Categories without roster still use `raider-characters.json`; the file is not changed by the migration. `test/stores/raiderCharactersStore.roster.test.js` is the golden master (same answers before and after the migration).
- **Expected roles:** `services/roster/categoryRoles.js expectedRoleIds(categoryId, config)` = the roster's `roleIds` when the category has a roster, else `config.categoryRoles`. Readers that mean "which roles" ask it (announcement ping, sign-up gate, raider-characters route, the event panel's role list). Since #658 "who is expected in this raid" (missing lists, missing ping, reminders) asks the roster itself — its core and trial members (`services/roster/expectedRaiders.js`, "Roster und der Rest des Tools" below) — and falls back to these roles only without a roster. The settings page still edits `categoryRoles`; `syncRosterRoleIds` carries a save over to the rosters, and `mirrorCategoryRoles` carries a roster's roles set in the roster API (#657) back into `categoryRoles`, so both always stay equal.
- **Rights:** `services/roster/rosterAccess.js canManageRoster(user, roster, memberRoleIds)` — full admin, or the account in `managers.userIds`, or a role in `managers.roleIds` (`canManageRosterLive` fetches the roles via `discord.memberRoleIds` on the roster's server, unknown = none). Managing = members, status, characters and Discord roles of that roster; reading needs the area `roster` (read); creating rosters and setting managers is for full admins.

## Roster und Discord-Rollen (#656)

Roster and Discord role are one thing, in both directions. The backend is in place; the "Abgleich" tab of the roster page comes with the client later.

- **Tool → Discord** (`services/roster/rosterRoleSync.js` `applyMemberAdded` / `applyStatusChange` / `applyMemberRemoved`, called by `services/roster/rosterMembers.js` `addMember` / `setStatus` / `removeMember` — the base for the member routes of #655): taken into the roster → the main role `roleIds[0]`, status `trial` also `trialRoleId`; away from `trial` → `trialRoleId` taken; removed → **every** role of the roster taken (`roleIds` + `trialRoleId`). `pause` and `bench` touch no role (a paused member keeps his role and stays a member). Each write leaves a history line `role-given` / `role-taken`, or `role-give-failed` / `role-take-failed` with the reason code in `detail` (`@Raider: no_permission`); "nothing to do", and "not on the server" on a take, leave none. These functions never throw and answer `{ ok, skipped?, results: [{ roleId, roleName, give, ok, code, changed }] }`.
- **The one remover** is `services/discord/memberRoles.js` (`giveRole` / `takeRole`): it touches only a role that some roster **of that server** lists (`not_roster_role` otherwise — defence in depth against any caller), needs "Rollen verwalten" (`roleSync.canManageRoles`, unknowable = missing) and a role below the bot's highest that is not managed, and answers a code instead of throwing: `done`, `unchanged`, `bad_request`, `not_roster_role`, `offline`, `no_permission`, `unknown_role`, `role_too_high`, `not_member`, `failed`. The web translates the codes (DE/EN). `roleSync.js` keeps its own "never remove" guard — its test scans only `roleSync.js`, so the guard needed no change.
- **Discord → Tool** (`onGuildMemberUpdate` / `onGuildMemberAdd` in `bot.js`, beside the role sync): gaining any role of `roleIds` makes the person a roster member (`core`, the first profile character of the roster's version via `raiderProfileStore.firstCharacter`, history detail `via Discord · core, <key>`); losing the last one removes him (history `member-removed`, detail `via Discord`). `trialRoleId` alone makes nobody a member. With the old roles unknown (partial member) a holder is added, nobody removed.
- **No loop:** the tool writes the store first and the role second, so the gateway event of its own role write finds the member already in or already out. Status changes only move `trialRoleId`, which the Discord side ignores. A role write through the web (`POST /api/rosters/roles`) changes membership *through* Discord: taking someone's last roster role drops them, giving one to a non-member takes them in.
- **Reconcile** (`reconcile(guildId)`, job `rosterRoleSync` in `web/http/jobs.js`: a minute after start, then every 10 minutes, only servers with a roster that has roles) catches what the events missed, carefully: a failed or empty member fetch changes nothing; every holder who is no member is added — except someone the tool removed and could not take the role from (latest history line of that user `role-take-failed`; a person decides in the Abgleich list, and giving a roster role anew in Discord counts as that decision); a member is removed only if the **previous** run saw him holding a role and this one does not (kept in memory, so the first run after a start only adds, and a changed `roleIds` list skips removals once). Members who never held the role — e.g. from the #653 migration — therefore stay and show up as "im Roster ohne Rolle". A role deleted on the server is ignored (all deleted = roster left alone), and a run that would remove more than half of a roster's members (at least 5) removes none and logs it. The member list is cached for a minute, so the tool's own writes of the last three minutes (`memberRoles.recentWrite`) win over the cached roles. **On the first deploy the reconcile fills each roster with the current holders of its roles** — the decision of #659 ("Rolle im Discord bekommen = im Roster").
- **Routes** (`web/apiRoutes/rosterRoles.js`): `POST /api/rosters/roles` `{ rosterId, userId, give, roleId? }` (area `roster` write + CSRF, then `canManageRosterLive`, else 403 `not_manager`; `roleId` must be one of the roster's `roleIds` or its `trialRoleId`, default the main role; refusals as codes `not_found`, `bad_request`, `no_role`, `not_roster_role`, `no_guild` and the memberRoles codes — `offline` 503, `not_member`/`unknown_role` 404, the rest 409). `GET /api/rosters/sync?id=` (area `roster` read, `services/roster/rosterSyncView.js`): `inRosterWithoutRole` `[{ userId, displayName, status }]`, `roleWithoutRoster` `[{ userId, displayName, takeFailed }]`, `withoutChar` `[{ userId, displayName, suggestion: { key, name, className } | null }]`, `logCharsWithoutPerson` `[{ key, character, className, nights, lastSeen, claimedBy }]` (characters of the category's last raid nights — the attendance window of `rosterAttendance.js`, the roster's version — that no member plays and that are not hidden in `rosterHiddenStore`; `claimedBy` = profiles that have that character), plus `roles` (names, main/trial, `exists`), `canManageRoles`, `membersError` (`offline` / `members_unavailable` — then the two role lists stay empty, never "everyone lacks the role"), `mirrored` (roster roles in `config.roleSync`, `incoming` / `outgoing` seen from the roster's side) and `canManage` for the caller.
- **Role sync interplay** (docs/discord-servers.md): a roster role mirrored to the other server (`outgoing`) is not taken there — the role sync only adds. A roster role the sync *gives* from the other server (`incoming`) comes back after the tool takes it, as long as the person holds the other role, and the person returns to the roster; the Abgleich tab is to warn about both.

## Mitglieder bearbeiten (#655, backend)

Members are changed through `services/roster/rosterMembers.js` (`addMember` / `updateMember` / `removeMember` / `setStatus`: store first, roles second, never throws for a refusal) and the routes of `web/apiRoutes/rosterMembers.js`. Area `roster` **write** + CSRF, then `canManageRosterLive` (full admin or a manager of that roster), else 403 `not_manager`. Every change writes a history line with the caller as `by`.

- **Characters** are profile keys of the roster's version, in order, the first counts. A name that is no profile character of that person is kept as typed (key of the name, the name in `charNames`, "Charakter von Hand zuweisen"); a profile character keeps the profile's spelling. Without `allowMultipleChars` exactly one — a second answers `single_char_only` (the store alone would cut it silently). A new member without `chars` gets the first profile character of the roster's version. `note` ≤ 500 (`note_too_long`), `trialUntil` a date or `null` (`invalid_date`).
- **Roles:** taking in gives the main role (trial also `trialRoleId`), a status change to/from trial moves `trialRoleId`, taking out takes every roster role (`rosterRoleSync`, "Roster und Discord-Rollen" above). The answer's `roles` carries the role results, so the page can say which role failed and why.
- `POST /api/rosters/members` `{ rosterId, userId, mode?: "add"|"update", status?, chars?, charNames?, note?, trialUntil? }` → `{ userId, created, member, roles }`. Without `mode`: add when the user is no member, else update; `mode: "add"` on a member is 409 `already_member`, `"update"` on a stranger 404 `not_member`. Other codes: `not_found` 404, `member_limit` 409, `bad_request`, `invalid_status`, `invalid_chars`, `single_char_only`, `note_too_long`, `invalid_date` 400.
- `POST /api/rosters/members/remove` `{ rosterId, userId }` → `{ userId, removed: true, roles }` (`not_member` 404).
- `GET /api/rosters/member-search?id=&q=[&version=]` (area `roster` read, `services/roster/rosterMemberSearch.js`) → `{ results: [{ userId, displayName, inRoster, chars: [{ key, name, className, spec }] }] }`: the cached member list of the roster's server (bots left out, matched on display name, account name and profile character names of the version, non-members first, 25 at most); without `id` the active server and `version` (manager picker of the create dialog). 503 `offline` / `members_unavailable` when the list cannot be read — never an empty "nobody found".

## Roster anlegen und einstellen (#657, backend)

`web/apiRoutes/rosterAdmin.js`, services `rosterCreate.js`, `rosterSettings.js`, `rosterOptions.js`, `rosterComposition.js` (all `services/roster/`). Area `roster` is the gate (write for the POSTs, read for the GETs).

- **Who may what:** creating and deleting a roster and setting its managers is for **full admins** (403 `admin_only`). A full admin edits every field; a **manager** of that roster edits `name`, `slots`, `allowMultipleChars` and `signupOnly` — not managers, roles (`roleIds`, `trialRoleId`), category or version. An admin-only field sent by a manager with a *changed* value answers 403 `admin_only` (the unchanged value of a whole form passes); anyone else 403 `not_manager`. Everything stays editable later, the name too.
- `POST /api/rosters/create` (full admin) on the **active server**: `{ name? (≤ 40, default the category's name, else the Kader's), categoryId?, versionId? (default the category's version / the main version; from a Kader without category the Kaderplaner's version, Forever when that rule set exists, #658), roleIds?, trialRoleId?, managers?: { roleIds, userIds }, slots?: { total, tank, healer, bench }, allowMultipleChars?, signupOnly?, source?: "role"|"kader"|"raids"|"none", kaderId? }` → `{ roster, initial: { source, added, skipped, roleFailures: [{ userId, roleId, code }], error } }`. Codes: `category_taken` 409 (one roster per category), `kader_not_found` 404, `invalid_name`, `name_too_long`, `invalid_version`, `invalid_roles`, `unknown_role` (a role the server does not have, checked while the bot sees the server), `invalid_managers`, `invalid_slots` (0–200 each; tank + healer ≤ total), `invalid_source`, `no_role` (source role without roles), `no_category` (source raids without category) 400.
- **First members** (`rosterCreate.js`): `role` = everyone holding one of `roleIds` now, as core with the profile's first character — **no role is given**, they hold it already (`initial.error` `offline` / `members_unavailable` when the list cannot be read; the roster is created anyway and the reconcile fills it later). `kader` = `createRosterFromKader(kaderId, opts)` (the entry #658 builds its button on): roster → core, bench → bench, tentative → trial; the character is the planner's active one mapped to the profile key of the roster's version when the profile has it, else that name kept as typed; without one a profile character of the decided class, else the profile's first. `raids` = every account present at least once in the category's last 4 counted raid nights of the roster's version (one of their profile characters in the night's log, or — for a night without log — signed up `signed`/`late`). `none` = nobody. Members from `kader` and `raids` are being taken in: `rosterMembers.addMember` gives them the main role (trial also the trial role). Mind that the reconcile of #656 adds every holder of the roster's roles within ten minutes in any case.
- `POST /api/rosters/update` `{ rosterId, …fields }` (only what is sent changes; `slots` and `managers` merge per key) → `{ roster, trimmedChars }` (`trimmedChars`: members cut to their first character by switching `allowMultipleChars` off). **Changing `roleIds` touches no member's Discord roles** — the old role stays with them, the new one is not handed out; the reconcile then adds the new role's holders (and skips its removals once). Changing the version leaves the members' character keys as they are.
- `POST /api/rosters/delete` `{ rosterId }` (full admin) → `{ rosterId, deleted: true }`. Nothing happens in Discord: the roles stay, nobody's roles are touched.
- **Roles ↔ settings:** a roster's `roleIds` are mirrored into `config.categoryRoles` of its category (`categoryRoles.mirrorCategoryRoles`, on create and on every change of roles or category), so a later save of Einstellungen › Kategorien (`syncRosterRoleIds`) hands the roster the same roles back instead of old ones, and after a delete the category keeps the roster's last roles. A category that got a roster in the tool counts as migrated (`rosterStore` `migratedCategories`), so the start-up migration never brings a deleted roster back.
- `GET /api/rosters/options` → `{ guildId, categories: [{ id, name, versionId, rosterId, rosterName }], versions: [{ id, label, short }], defaultVersion, roles: [{ id, name, color, position, manageable }], canManageRoles, online, kaders: [{ id, name, inRoster, candidates }], templateSlots: { [categoryId]: { total, tank, healer, bench, templateId, templateName } }, isAdmin }` — categories as the Kaderplaner lists them (marked for events or with a stored raid) plus every category with a roster; `manageable` = not managed and below the bot's highest role; `kaders` only for a reader of the area `kader` (counts only); `templateSlots` from the category's default raid template (`categoryRaidTemplate`, size + tanks/healers) to prefill the slots.
- `GET /api/rosters/composition?id=` (`rosterComposition.js`) → `{ rosterId, versionId, slots, counts: { core, trial, bench, pause }, roles: [{ role: "tank"|"healer"|"dps", target, actual }], dps: { melee, ranged }, unknown, bench: { target, actual }, open, classes: [{ className, label, labelEn, color, icon, count }], buffs: [{ key, label, labelEn, icon, scope, providers: [userId], covered }], buffsAvailable, canManage }`. Counted are core + trial; class, spec and role come from each member's first character as the profile knows it (first spec = main); a character typed by hand counts as `unknown`. Buffs are the rule set's `raidBuffs` + `partyBuffs` (config/gameVersions), covered when a member's main spec is a provider.

## Roster und der Rest des Tools (#658)

What a roster changes elsewhere. Statuses throughout: core = Stamm, trial = Probe, bench = Ersatz, pause = Pause.

- **Kaderplaner → Roster:** docs/kaderplaner.md "Roster aus einem Kader" — "Roster anlegen" (full admins, `POST /api/rosters/create` with `source: "kader"`) and "Ins Roster übernehmen" (`POST /api/kader/roster/sync`, `services/roster/rosterCreate.js syncRosterFromKader`): players in roster / bench / tentative who are no member yet join as core / bench / trial with the main role; members already in the roster stay exactly as they are. Only status and the decided character cross.
- **"Anmeldung nur für das Roster"** (`signupOnly`, a manager may switch it): the category's roster replaces the raider-role rule — only members with status core, trial or bench take a *new* signup, on the web and in Discord (`signupService.rosterOnlyAccess` inside `checkRaiderRole`; code `roster_only`, 403). **Paused members are not allowed** (a pause means "not now"; the orga can still enter them). Exempt as before: the orga (`byOrga`) and an existing own signup (change or withdraw). The web's signup row carries `rosterOnly: true` for a member who may not sign up, so the dialog says it up front and keeps its button off. Docs: docs/signups.md.
- **Setup proposal:** `setupInput.rosterStatusFor` hands the proposal `rosterStatus` (`{ userId: status }` of the events' categories' rosters); the weight `roster` (200) values core 1, trial 0.6, bench 0.3, everyone else 0 — core before trial before bench, non-members after. Without a roster nobody has a status and the weight is off (`weights.roster` 0). Docs: docs/setup.md.
- **Who is expected** (`services/roster/expectedRaiders.js`): a category with a roster expects its members with status **core or trial** — not bench, not pause — instead of the role holders: the "fehlt" list of the raid detail (`attendanceSource: "roster"`) and of the dashboard's next raid, "Fehlende pingen" (web, Event verwalten, the button under the signup message, which now also shows for a roster without roles) and the "missing" reminders. Names come from the cached Discord member list (who left the server is dropped); when the list cannot be read the roster's members still count, named by profile or id. Without a roster: the raider roles as before (`expectedRoleIds`). The announcement ping on creating an event still pings the roles.
- **End of the trial** (`services/roster/rosterTrials.js`): `GET /api/rosters` gives every card `trialEnding: [{ userId, displayName, trialUntil, overdue }]` — trial members whose `trialUntil` lies within the next 7 days or has passed, earliest first. The dashboard turns them into calm rows in "Offene Aufgaben" (`dashboardData.loadTrialEndings`, `dashboardOverview.trialTasks`; only rosters the caller manages, area `roster` write): "Probezeit endet: <Name>" (accent) or "Probezeit abgelaufen" (yellow), linking to the roster, with **Übernehmen** (status core, `trialUntil` cleared) and **Verlängern** (`extendTo` = 14 days after the old end, or after today when it has passed) through `POST /api/rosters/members`. Nothing changes by itself: a trial that ran out stays a trial until somebody decides.
- **Tests:** `test/services/roster/rosterCreate.test.js` (sync, privacy markers), `expectedRaiders.test.js`, `rosterTrials.test.js`, `test/web/apiRoutes/kader.test.js` (roster routes, gates, privacy), `test/services/signups/signupService.test.js` + `test/web/apiRoutes/signups.test.js` + `test/commands/signup/eventSignup.test.js` (signup lock, web and Discord), `test/utils/setup/proposal.roster.test.js`, the missing/reminder suites (`missingPing`, `reminders`, `raidDetailView`, `dashboardData`), Vitest `pages/kader/RosterLink.test.tsx`, `SignupDialog.test.tsx`, `DashboardPage.test.tsx`, `RosterTab.test.tsx`.

## Abwesenheiten (`/absences`, areas `signup` or `roster`, October 2026)

Who is away when over the next weeks, what it does to the coming raids, who keeps signing off without saying for how long — and every raider's own attendance. Its own line in the menu under **Start**, right after Anmeldungen (`menu.json`, `areas: ["signup", "roster"]`, either opens it; area colour `--area-absences`), so raiders reach it quickly. The first address `/roster/absences` (PR #646) redirects to `/absences` with its query. Client: `pages/absences/` (page, timeline, raid cards, drawer, head figures, hint cards, `MyAttendance.tsx`), the layout rules in `lib/roster/absences.ts` (day → column, bar place and cut edges, ISO weeks, missing per raid day, filters, the verdict words of "Meine Anwesenheit"), styles `styles/absences.css` (`ab-`, away is the token `--ab-away`).

- **Views:** with `roster` the switch „Zeitleiste | Pro Raid | Meine Anwesenheit" (the choice is `usePersistedState("absences-view")`); without `roster` only „Meine Anwesenheit", and the overview is never requested. `?userId=<id>` shows „Meine Anwesenheit" of that raider (opened by the orga from the drawer, „Anwesenheit ansehen"), with a back button to the overview.
- **Meine Anwesenheit** (`GET /api/availability/attendance[?userId=]`, area `signup`: own data, or — for the orga, `raids` write — anyone's; built by `src/web/availability/raiderAttendance.js` with the setup editor's attendance rules): on top the own absence entries that are not over (`GET /api/availability` → `entries`; delete, „Abwesenheit eintragen" through the dialog); then one card per raid category: the quota as one big number („82 %") with „9 von 11 Raids", an „auto" badge when the characters were matched automatically, the counted raids as dots (newest last; in = filled accent, missed = orange ring; tooltip date, title, verdict), the same raids as a short list (newest first, the verdict in words — the server's German reasons are translated by `reasonText()`), and „Nächste Raids" with the own status as a pill linking to the event. A category without counted raids says so instead of „0 %"; no category at all gets its own sentence. With more than one category a chip row above the cards („Alle Kategorien" + one per category) shows one of them (`usePersistedState("absences-mine-category")`, a pick no longer offered falls back to all).
- **Per category** (`config.categoryAttendance`, Einstellungen › Kategorien › tab Anmeldung; `configSchema.attendanceSettings` / `categoryAttendanceFor`, stored as a diff from the defaults, a category's object replaced whole): **„Anwesenheit anzeigen"** (`show`, default on) — off leaves the category out of „Meine Anwesenheit"; **„Quote über"** 4/8/11/16 raids (`window`, default 11 = `RAID_WINDOW`) — passed as `window` to `attendanceForAccounts`, so the card („über die letzten n Raids") and the setup editor's tooltip (`setupAttendance.js`) count the same nights; **„In Abwesenheiten zeigen"** (`absences`, default on) — off drops the category's raids, the entries bound to it, its hints and its raids in the drawer's history out of the overview (`absenceOverview.inOverview`). Entries for every category stay.

- **API** (`src/web/apiRoutes/availability.js`, built by `src/services/signups/absenceOverview.js`): `GET /api/availability/overview?weeks=<1–13>&category=<id>` answers the weeks from this Monday on — `raiders` (sorted: away today, longest, first day, name; each with `periods` as bars, `singles` = raids signed off one by one without a period, `hint`), `raids` (with `absent[]` and the tank/healer gap against the raid's composition), `hints`, the four `tiles` and `canEdit`/`withReasons` (raid lead only: reasons and entering/deleting). `GET /api/availability/overview/raider?userId=` gives one raider's entries (`state` planned/running/past, `done`) and their last ten raids (`in`/`off`/`none`/`other`). Identity fields (`character`, `spec`, `classColor`, `specIcon`, `role`) come from the server, never recomputed in the client.
- **Category chips** (Zeitleiste and Pro Raid, from two categories on): „Alle" plus one toggle chip per raid category in its timeline colour (`categoryTone`), any number picked at once; every category or none picked is „Alle". Stored comma-separated in `absences-view.category` and sent as `category=a,b`; the server filters raids, category-bound entries and hints to the picked ones but always answers every category of the weeks in `categories` (so the chips and the colours stay put) and the pick in `picked`.
- **Zeitleiste** (default view): four figures, a filter line (category chips, 4/8/13 weeks — both new requests —, the switch „Anwesenheiten zeigen" and a name/character search, both on the client), the hint cards, then the timeline: one row per raider (left column sticky, the box scrolls sideways), week heads, raid days tinted with a dot per category, „fehlen" per raid day (strong from 4), absence bars (≥ 14 days filled), rings for single sign-offs, a line for today. A cut-off start is dashed, a period running past the end ends in an arrow.
- **Pro Raid**: one calm card per coming raid — date block, title (link to the event), category pill, time, a bar of who is in against the places („20 dabei · 25 Plätze") and „Zum Setup". No absence info on the cards (the user's choice, October 2026); who is away is the timeline's business.
- **Raider drawer** (like the setup editor's): what they play, the running or next absence large, every entry (delete while not over), the effect („Schon von n Raids abgemeldet"), the last ten raids as dots, and for the orga „Anwesenheit ansehen" (that raider's attendance view). Esc or X closes it.
- **Hinweis**: 3 of the last 4 raids of a category signed off one by one, none covered by a period. A quiet card titled „Hinweis" (deliberately not „Auffällig") with one button „Zeitraum eintragen" — no DM button.
- **Entering** goes through the signup page's `components/signup/AvailabilityDialog.tsx`, which takes a `target` (the raider picked on this page, still changeable) and brings `styles/signups.css` along itself.

## Raider-Profil ("Mein Profil", `signup` area, #255)

The member's own page (`/profile`, `pages/profile/ProfilePage.tsx`, `styles/profile.css`) and `/profil` in the bot (`commands/profile/profil.js`: short ephemeral summary, "kann Offtank/heilen" buttons `profil:tank|heal` — they switch the raider's **first character** of the main version, the other characters are switched on the web — link to the page).

- **Stored** in `src/stores/raiderProfileStore.js` (`data/settings/raider-profiles.json`, key = Discord user id): characters (up to `MAX_CHARACTERS` 12 **per game version** — TBC characters take no place from Forever ones, `countInVersion`; `source` log/armory/manual, each with its game version `versionId`, #543) **in the raider's own order — there is no main** (a main/twink split was felt as toxic): `PUT /api/profile { order: [keys] }` reorders (`inOrder`, unknown keys ignored, so a save never adds or drops), a new character goes to the end, and wherever the system must pick one it takes the raider's **first character of the version** (`firstCharacter(profile, versionId, { preferVersion })`: the signup's preselection in web and Discord, the setup's slot without a name, `/profil`'s switches, the Kaderplaner's starting character, Raid-Helper's class match, the wish list's name of another raider — `raiderRef` → `character`) — never labelled "Main". The profile page moves a character **forward / back within its version** (card head, `lib/roster/characterVersions.ts moveInVersion`; the moved one stays selected). A profile stored while mains existed: `legacyMainFirst()` puts each version's former main in front on read, `migrateCharacterOrder()` (settingsMigration at start) writes it once without the flag — nobody's suggestion changes, per character specs from the rule set (`classes.js` keys, only the character's class) with `gear` none/usable/ready, availability (weekdays), preferred raids (rule-set instance ids of any version), wishes (user ids of raiders with a profile), the "nicht zusammen" list (below), note.
- **"Kann Offtank / heilen" is per character** (`canOfftank`/`canHeal` on the character, `null` = not set). `characterRoles(profile, character)` resolves it: the character's own word, else the **old profile-wide field** (profiles saved before the switches moved — read as fallback, never written by the page or accepted by `PUT /api/profile` any more), else what *this character's* specs allow — and **never "yes" for a class without such a spec** (`classCan(className)`, `possible` in the view: a mage neither tanks nor heals, a rogue neither; the page greys the switch out with the reason in the tooltip, a save never stores the "yes", `/profil` leaves the button out). `explicit` is the stated word alone: the setup proposal (`model.js characterFlags`) adds an off-role only on a stated word, the signup's "kann auch" prefill (`signupService.defaultCanAlso`, `lib/signups/status.ts`) uses the effective value of the character signed up with — a priest twink's healing no longer rubs off on the mage main. The profile-level `canOfftank`/`canHeal` in the API view is only a summary ("any character").
- **"Nicht zusammen raiden mit"** (`avoidEnabled` + `avoid`, max 10 user ids of raiders with a profile): **off at first**; switching it on on the page asks first ("in der Community sollte jeder eine Chance bekommen"), switching it off **forgets the names** (`normalizeProfile` keeps `avoid` empty while off). Nobody is on both lists — a wish wins. The owner sees whom they named; **nobody else ever sees it, the orga's profile view included** (there is no reverse list). Only the setup proposal reads it, and only when the orga says yes (docs/setup.md, „Nicht zusammen").
- **Weekdays have colours** (`[data-day]` in `profile.css`, `--day` / `--day-dark` for light mode) — in the buttons and in the folded summary. `raiderCharactersStore` stays the orga's per-category assignment; the profile only uses it to rank suggestions. Tests point the store at their own file with `useFile()`.
- **Own profile only.** Every handler in `apiRoutes/profile.js` works on the session's `user.id`; no body field or query names another account. `GET/PUT /api/profile`, `GET /api/profile/log-characters`, `POST /api/profile/characters` (add or `{ remove }`), `GET /api/profile/raiders?q=` (names + main only) are area `signup`; another raider's profile `GET /api/profile/user?id=` and `GET /api/roster/character-claims` are area `roster`. Members get the page once an admin grants `signup` (read + write) in the **Basiszugang** — it is not on by default.
- **Wishes never reach a member** (`web/characters/profileView.js`): the owner sees whom they wished for, never `mutual` or `wishedBy` — those exist only with `forOrga`. `test/web/apiRoutes/profile.test.js` holds that line.
- **Three ways to add a character, no orga confirmation.** *Aus Logs* takes class and spec from `profileLogs.logIndex()` (the newest evaluations' rosters + `characterStore`), never from the request; suggestions rank the category assignment, then a name matching the Discord name. *Armory* always stores the `charLinks` link and takes class/level/guild from `Blizzard.getCharacterSummary()` when configured — any failure means link only, and without a class the API answers `422 class_required` so the dialog asks for it. Link and realm are **per game version** (#542, docs/raid-templates.md "Einstellungen je Spielversion"): `charLinks.armoryUrlFor(name, versionId)` / `profileView.lookupArmory(name, realm, versionId)` take the character's version (#543), a version without armory settings gives no link and asks no API. *Von Hand* is name, class, specs. A character another account already has is added anyway and carries `claimedBy`; the roster page shows the conflicts as one "n doppelt vergeben" badge.
- **Characters per game version (#543).** Every character carries `versionId` — a raider plays TBC and WoW Forever side by side. **Key rule:** a TBC character's key is its lower-case name as ever (`"devi"`), a character of any other version carries the version (`utils/loot/lootImport.js characterKeyOf(name, versionId)` → `"forever~devi res"`), so "Devi Res", "Devi Rew" and a TBC "Devi" are three characters and a Forever "Devi" without last name is not the TBC one. Loot, logs, attendance, council and hidden-list keys are the bare names and do not move (golden master in `test/stores/raiderProfileStore.versions.test.js`); `nameKeyOf()` strips a version prefix where a signup's name is compared with a profile key. `charactersOfVersion(profile, versionId)` and `findCharacter(profile, ref, versionId)` (key or name; with a version only that version's) are what every signup path uses. **Migration:** `migrateCharacterVersions()` (run by `settingsMigration.js` at start, logged as `[settings] Migration: raider-profiles.json: n Charakter(e) … "tbc"`) writes `versionId: "tbc"` onto every stored character without one; idempotent, keys unchanged; a character read before the migration already counts as TBC. `addCharacter` takes the version from `data.versionId`, else the `versionId` option (the Discord name modal hands the event's), else TBC; `POST /api/profile/characters` sends the dialog's choice, missing = the main version. **The page** groups the chips by version (the main version first, a heading only with more than one group; `lib/roster/characterVersions.ts groupByVersion`), the card's line names the version then; the add dialog asks for the version first (`versions` from `GET /api/profile`, the main version preselected), picks classes from `classesByVersion[version]`, and a version with `characterNames.lastName` (Forever) gets a first- and a last-name field (12 letters each). The Raid-Helper suggestion ("Von Hand") is taken per version (`specHistory` entries carry `versionId`).
- **Typed names follow the game's rule** (`src/utils/signup/characterNames.js`, checked in `raiderProfileStore.addCharacter` for every *new* character not from the logs — web *Von Hand* / *Armory* and the Discord name modals): letters only (umlauts and accents count), 2–12 per name, written "Aldric" whatever was typed. **WoW Forever has first and last name** ("Aldric Sturmwind", 12 letters each, key `aldric sturmwind`); the rule set switches it on with `characterNames: { lastName: true }` (`gameVersions/forever.js`). The Discord modal knows the event's version and refuses a last name elsewhere (its `max_length` is 12, in Forever 25 with the placeholder "Vorname Nachname"); the web profile checks each character by its own version (#543) — a TBC character never has a last name. **Profanity filter** (`src/config/profanity.js`): three lists — `CONTAINS` (roots never part of a harmless name), `PREFIX`, `EXACT` — checked per name part and on first + last name joined ("Hit Ler"), after folding accents and doubled letters. The split exists for the Scunthorpe problem: "Hancock", "Barsch", "Torpedo", "Assassin" must pass, `test/utils/signup/characterNames.test.js` holds them. Names from the logs and existing characters are never re-checked.
- **"Laut Logs"** per spec (`specEvidence`): `seen` (the logs resolved this spec), `other` (character in the logs with another spec — a hint for the orga, never a lock), `unknown`. The evaluations know class, not spec, so the spec comes from `characterStore`.
- **Kalender-Abo** (#312): the last folded line of the side column mints and revokes the raider's **own** subscription link (`GET /r/cal/user/<token>.ics` — every raid they are signed up for). The secret is shown **once** and kept only as a sha256 hash, revoking is immediate, and `GET/POST /api/profile/calendar` (area `signup`, `{ revoke: id }` on the POST) works on the session's account like every other handler here. The rules of the feed itself — what may be in it, the 30/90-day window, the five-minute cache, the plain 404 for an unknown or revoked token — are in docs/events.md, „Kalender-Abo je Raider".
- **Calm layout**: character chips on top, the selected character's card on the left — specs (name large, gear segment, logs badge) and at its foot that character's two switches — availability / raids / wishes / nicht zusammen / note / Kalender-Abo as folded parts on the right (one open at a time), the add dialog with the three ways as a segment. `src/web-client/src/pages/profile/ProfilePage.test.tsx` scans for it.
