# Roster und Raider-Profil

Endnutzer-Sicht: siehe [guide-web-admin.md#mein-profil](guide-web-admin.md#mein-profil), [guide-web-admin.md#roster](guide-web-admin.md#roster).

## Roster (`roster` area)

Every known character of the guild, grouped by raid category (design #218). Three things about the list itself:

- **The column heads are the sort control** (`SortLabel`, the same one the loot council's grid uses), and the sort is applied **per group**, because the attendance column measures against *that* category — a roster sorted by attendance across groups would compare Monday's raid with the pug night. The sort lives in its own store (`useTableSort("roster-sort", …)`), the rest of the view (search, role, class, spec, open groups, which list) in `usePersistedState("roster-view", …)`.
- **Class chips, then spec pills.** The spec row appears only once a class is picked and lists the specs that class actually has in the roster — thirty specs at once is not a filter. A stored spec the current class does not have filters nothing instead of emptying the page.
- **Characters can be taken off the roster** (`src/stores/rosterHiddenStore.js`, `POST /api/roster/hide`, `data/settings/roster-hidden.json`). A roster built from loot and logs keeps everyone who ever raided, and "40 % Anwesenheit" over a guild half of whom left says nothing about the half that is still here. Hiding **deletes nothing** — loot history, evaluations and the character page stay whole; `GET /api/roster` simply answers with `chars` (the roster) and `hiddenChars` (with the note who hid them and when) apart, and `stats` counts only the former. The page's "Ausgeblendet" tab lists them and puts them back. Like the council's exclude list this is an explicit decision, never a rule such as "nobody who has not raided in 60 days" — the difference between *gone* and *was ill* is one only a person knows.

## Raider-Profil ("Mein Profil", `signup` area, #255)

The member's own page (`/profile`, `pages/profile/ProfilePage.tsx`, `styles/profil.css`) and `/profil` in the bot (`commands/profile/profil.js`: short ephemeral summary, "kann Offtank/heilen" buttons `profil:tank|heal` — they switch the **main**, the other characters are switched on the web — link to the page).

- **Stored** in `src/stores/raiderProfileStore.js` (`data/settings/raider-profiles.json`, key = Discord user id): characters (several, exactly one main, `source` log/armory/manual), per character specs from the rule set (`classes.js` keys, only the character's class) with `gear` none/usable/ready, availability (weekdays), preferred raids (rule-set instance ids of any version), wishes (user ids of raiders with a profile), the "nicht zusammen" list (below), note.
- **"Kann Offtank / heilen" is per character** (`canOfftank`/`canHeal` on the character, `null` = not set). `characterRoles(profile, character)` resolves it: the character's own word, else the **old profile-wide field** (profiles saved before the switches moved — read as fallback, never written by the page or accepted by `PUT /api/profile` any more), else what *this character's* specs allow — and **never "yes" for a class without such a spec** (`classCan(className)`, `possible` in the view: a mage neither tanks nor heals, a rogue neither; the page greys the switch out with the reason in the tooltip, a save never stores the "yes", `/profil` leaves the button out). `explicit` is the stated word alone: the setup proposal (`model.js characterFlags`) adds an off-role only on a stated word, the signup's "kann auch" prefill (`signupService.defaultCanAlso`, `lib/signups.ts`) uses the effective value of the character signed up with — a priest twink's healing no longer rubs off on the mage main. The profile-level `canOfftank`/`canHeal` in the API view is only a summary ("any character").
- **"Nicht zusammen raiden mit"** (`avoidEnabled` + `avoid`, max 10 user ids of raiders with a profile): **off at first**; switching it on on the page asks first ("in der Community sollte jeder eine Chance bekommen"), switching it off **forgets the names** (`normalizeProfile` keeps `avoid` empty while off). Nobody is on both lists — a wish wins. The owner sees whom they named; **nobody else ever sees it, the orga's profile view included** (there is no reverse list). Only the setup proposal reads it, and only when the orga says yes (docs/setup.md, „Nicht zusammen").
- **Weekdays have colours** (`[data-day]` in `profil.css`, `--day` / `--day-dark` for light mode) — in the buttons and in the folded summary. `raiderCharactersStore` stays the orga's per-category assignment; the profile only uses it to rank suggestions. Tests point the store at their own file with `useFile()`.
- **Own profile only.** Every handler in `apiRoutes/profile.js` works on the session's `user.id`; no body field or query names another account. `GET/PUT /api/profile`, `GET /api/profile/log-characters`, `POST /api/profile/characters` (add or `{ remove }`), `GET /api/profile/raiders?q=` (names + main only) are area `signup`; another raider's profile `GET /api/profile/user?id=` and `GET /api/roster/character-claims` are area `roster`. Members get the page once an admin grants `signup` (read + write) in the **Basiszugang** — it is not on by default.
- **Wishes never reach a member** (`web/characters/profileView.js`): the owner sees whom they wished for, never `mutual` or `wishedBy` — those exist only with `forOrga`. `test/web/apiRoutes/profile.test.js` holds that line.
- **Three ways to add a character, no orga confirmation.** *Aus Logs* takes class and spec from `profileLogs.logIndex()` (the newest evaluations' rosters + `characterStore`), never from the request; suggestions rank the category assignment, then a name matching the Discord name. *Armory* always stores the `charLinks` link and takes class/level/guild from `Blizzard.getCharacterSummary()` when configured — any failure means link only, and without a class the API answers `422 class_required` so the dialog asks for it. *Von Hand* is name, class, specs. A character another account already has is added anyway and carries `claimedBy`; the roster page shows the conflicts as one "n doppelt vergeben" badge.
- **Typed names follow the game's rule** (`src/utils/signup/characterNames.js`, checked in `raiderProfileStore.addCharacter` for every *new* character not from the logs — web *Von Hand* / *Armory* and the Discord name modals): letters only (umlauts and accents count), 2–12 per name, written "Aldric" whatever was typed. **WoW Forever has first and last name** ("Aldric Sturmwind", 12 letters each, key `aldric sturmwind`); the rule set switches it on with `characterNames: { lastName: true }` (`gameVersions/forever.js`). The Discord modal knows the event's version and refuses a last name elsewhere (its `max_length` is 12, in Forever 25 with the placeholder "Vorname Nachname"); the web profile is not tied to a version, so it allows one. **Profanity filter** (`src/config/profanity.js`): three lists — `CONTAINS` (roots never part of a harmless name), `PREFIX`, `EXACT` — checked per name part and on first + last name joined ("Hit Ler"), after folding accents and doubled letters. The split exists for the Scunthorpe problem: "Hancock", "Barsch", "Torpedo", "Assassin" must pass, `test/utils/signup/characterNames.test.js` holds them. Names from the logs and existing characters are never re-checked.
- **"Laut Logs"** per spec (`specEvidence`): `seen` (the logs resolved this spec), `other` (character in the logs with another spec — a hint for the orga, never a lock), `unknown`. The evaluations know class, not spec, so the spec comes from `characterStore`.
- **Kalender-Abo** (#312): the last folded line of the side column mints and revokes the raider's **own** subscription link (`GET /r/cal/user/<token>.ics` — every raid they are signed up for). The secret is shown **once** and kept only as a sha256 hash, revoking is immediate, and `GET/POST /api/profile/calendar` (area `signup`, `{ revoke: id }` on the POST) works on the session's account like every other handler here. The rules of the feed itself — what may be in it, the 30/90-day window, the five-minute cache, the plain 404 for an unknown or revoked token — are in docs/events.md, „Kalender-Abo je Raider".
- **Calm layout**: character chips on top, the selected character's card on the left — specs (name large, gear segment, logs badge) and at its foot that character's two switches — availability / raids / wishes / nicht zusammen / note / Kalender-Abo as folded parts on the right (one open at a time), the add dialog with the three ways as a segment. `src/web-client/src/pages/profile/ProfilePage.test.tsx` scans for it.
