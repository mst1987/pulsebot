# Setup

## Setup-Vorschlag (`src/utils/setup/`, #262)

`buildSetupProposal(input, options)` (`proposal.js`) builds raid groups and a bench from signups, profiles, attendance, earlier setups and the orga's fixed places. **It is always only a proposal — a human approves it** (the editor, the routes and the approval: "Setup-Editor" below). Pure and deterministic: no store, no clock, no randomness; ties go by signup `at`, then user id, and the input order of the signups does not matter.

- **Input** (`src/web/setupInput.js`' `collectSetupInput(eventIds)` reads it from the stores; `proposeSetup(eventIds, options)` = collect + build): `events` (`{ id, title, size, composition, requiredBuffs, fairness, wishes }` — several ids = raids that run **in parallel** and share the raiders), `signups` (signupStore shape + `eventId`), `profiles` (raiderProfileStore), `attendance` (`{ userId: pct }` from `rosterAttendance` in the event's category), `history` (`[{ eventId, startTime, placed[], bench[] }]`) and `fixed` (`{ userId, eventId, group (1-based), spec }` or `{ userId, bench: true }` — the `locked` slots of the event's current draft). Required buffs are the event's own (`event.requiredBuffs`, set in the create dialog, #261) once it was planned from a template or has any, else the category's raid template's (`config.categoryRaidTemplate`); melee/ranged go in as `{ min, max }` where the event stores a `compositionMax`. **The bench history is derived from approved setups** (`setupInput.approvedLineup()`: the `approved` snapshot, never a draft changed after it; same categories, earlier start, last 10) and never stored on its own; while none exists the stored signups stand in (signed/late = placed, "Ersatzbank" = bench), `historySource` says which.
- **Composition:** `tank`/`healer` are exact targets (min = max), a melee/ranged **number is a minimum** (0 = none, the dps fill the rest), `{ min, max }` a range. Groups hold 5, `ceil(size/5)` of them.
- **Hard rules** (`model.js` + `score.js`, a broken one scores `-Infinity`, so the search can never accept it): size, 5 per group, each raider at most once across all events, role maximums, never a spec the profile marks `gear: "none"`, never an absence, fixed places stay (a fixed raider beyond a role maximum widens it and turns the check red; a fixed place of somebody who signed off is ignored with a `warnings` entry). Role minimums and "bench signup only as a fallback" are constants far above every weight (`ROLE_MIN` 30000 per missing raider > `FILL` 10000 per placed raider > `BENCH_STATUS` 6000 > 10 × `MAX_WEIGHT` 500), so no weight setting can trade a missing healer for a nicer group — but too few healers never throws: the check goes red.
- **Options per raider:** every named character (#293, `signup.characters`, else the single one) with its signed spec (main; each option carries its `priority`, 0 = the choice) — **one place per person** stays a hard rule, so exactly one of them is placed — plus, for the first choice only, off-spec roles from the signup's `canAlso` and a stated `canOfftank/canHeal === true` of **that character** (`model.characterFlags`: the character's own switch, else the old profile-wide one), played as the class's spec for that role the profile has geared best (a feral who can tank → `Druid-Guardian`).
- **Each option carries its own character's status (#320)**, not the signup's (`model.characterStatus`): "Spät" on the first character leaves the second "Dabei", so the second is the better option and only the option that is actually placed says "Kommt später". A character without a status of its own takes the signup's. **The absence stays a matter for the whole person** — a signed-off raider has no options at all — and a person still takes at most one seat.
- **Soft goals** (`DEFAULT_WEIGHTS`, overridable via `options.weights`, 0 = off, clamped to 0…500): `partyBuffs` 60, `raidBuffs` 40, `requiredBuffs` 300, `mainSpec` 120, `preferredCharacter` 100 (a **cost** for placing a "kann auch mit" character, so raiders with one character score as before — **waived** where that character's own status makes it the more available one, `score.moreAvailableThanFirst`: the order of the characters is a preference, a status is a statement about the evening, and 100 would otherwise always outweigh the 40 that separate "Dabei" from "Spät"), `gear` 30 (ready > unknown > usable), `status` 80 (signed 1, late ½, tentative 0.3 — **per character** since #320), `fairness` 150, `attendance` 40, `wishes` 60. `fairness`/`wishes` only count where the event's flag is on (`options.fairness`/`options.wishes` override); the output's `weights` are the effective ones (0 when off). **Fairness** per raider over their last 10 nights: 0.6 if benched the last time they were in a setup + 0.4 × min(1, benches/3). **Wishes** are unordered pairs, mutual 1, one-sided ½; same group = full, same raid ⅕ (with parallel raids ½ — there the raid is what counts).
- **Nicht zusammen** (`avoid` 100, a **penalty**): pairs from the profiles' "nicht zusammen raiden mit" lists (only while a raider has it switched on, docs/roster-profile.md), one pair even when both named each other. Costs the full weight when the pair stands in the **same group** (one raid) or the **same raid** (parallel raids) — it separates, it never benches anybody on its own. **No event flag — the orga is asked:** `options.avoid === true` alone turns it on; the setup remembers the answer in `options.avoid` (`null` = never asked). The editor gets `avoidPairs` (a count, `setupEditor.avoidPairCount`) and asks once before the first proposal when it is > 0; afterwards a switch in the side column changes it (a save re-values the lineup, "Neu vorschlagen" separates). `checks.avoid` = `{ on, together, total }` — **counts only, never who named whom**, in no output and no reason.
- **Party buffs** come from the rule set (`gameVersions/buffs.js`, which gained `slot` and the setup-only `vampiricTouch`): per group each buff counts the members who want it, once per key; a buff with a `slot` (a totem element, a warrior's shout) once per provider per slot, most valuable first — a shaman drops one air totem, so Windfury + Wrath of Air in one group take two shamans. A buff everybody wants (`universal`: Blood Pact, Healing Stream) counts half and is never named as a reason.
- **Search:** fixed places → greedy (scarce roles first: fewest spare candidates, then the least flexible raider, bench signups last; then every free place with whoever adds most) → local search with strict improvements only (add, replace, switch role/event, switch role + fill the freed role, move/swap between groups, swap between parallel raids), at most `MAX_PASSES` 40. A 25-man and a 40-man from 60 signups take well under a second (tested).
- **Output** (JSON, stable for #263): `{ version, versionId, groups: [{ index, slots: [{ userId, character, classId, spec, role, main, status, locked, reasons[] }] }], bench: [{ …, eventIds, locked, reasons[] }], checks: { ok, size, roles: { tank: { count, min, max, ok }, … }, buffs: { ok, required[], raid[], party: [{ key, label, icon, groups[] }] }, wishes: { met, total, pairs[] } }, events: [{ eventId, title, groups, bench, checks }], weights, score: { total, parts }, warnings[] }`. `groups`/`checks` are the first (usually only) event's; with parallel raids every event has its own entry, `bench` lists who is in none, `checks.wishes` counts across all.
- **Reasons** (`reasons.js`, German, at most four): "Von der Orga fixiert", for a raider with several characters first which one and why — "1. Wahl: Zibbo" or "Mit Zibbowar als Tank statt Zibbo (Heiler voll (3/3))" / "(Tanks fehlten)" / "(kommt später)" — #320, and it comes before the other two, because the raider said it themselves — / "(passte besser in die Aufstellung)", "Zweitspec als Heiler", "Kommt später", "Gr. 2 wegen Totem des Windzorns (5 profitieren)", "Bringt als Einziger Segen der Könige" / "(Pflicht-Buff)", "War zuletzt auf der Bank – hat Vorrang", "Wunsch erfüllt: mit X (gegenseitig)", "Anwesenheit 91 %", "Eingeteilt in PuG 2"; on the bench "Heiler voll (6/6)", "Raid voll (25/25)", "Nur „Vielleicht“ angemeldet", "War zuletzt dabei", "Keine Spec mit brauchbarem Gear", "Von der Orga auf die Bank gesetzt".
- **Tests:** `test/utils/setup/` — fixtures (10/25/40 Classic), determinism, a seeded property loop over random inputs checking every hard rule, bench rotation over seven evenings, wishes (mutual beats one-sided), fixed places, too few healers, Windfury/shadow priest placement, runtime; `test/web/setupInput.test.js` for the collection. Not covered yet: raid **debuffs** (the rule set has none for the setup), availability/preferred raids from the profile.

## Setup-Editor (Raid-Detail › Setup, `src/web/setupEditor.js`, #263)

The proposal becomes an evening here: the orga proposes, moves, locks and **approves**. ⚠️ **The setup is only ever a proposal until someone with `raids` write approves it, and raiders never see a draft** — not through any endpoint, message or bot command.

- **Stored on the event** (`eventStore.setEventSetup`, one object): the proposal output v1 for the event (`groups`, `bench`, `checks`, `weights`, `score`, `warnings`, `historySource`; the per-event `events[]` is dropped), `status` draft/approved, `version` (bumps on every change of **who stands where** — `lineupSignature()`; a lock, a weight or the fairness switch alone keeps version and approval), `origin` proposal/manual/auto, `options { weights, fairness, wishes }` (the orga's overrides, reused by the next proposal), `updatedAt/By`, `approvedAt/By/Version`, **`approved`** (the frozen raider-facing snapshot: names, specs, roles, groups, bench — no reasons, no locks, no wishes), `changedSinceApproval`, `explanation { text, model, version, at }`.
- **Change after approval:** a new lineup turns the setup back into a draft with `changedSinceApproval`; the `approved` snapshot stays, so raiders keep seeing the last approved lineup until the next approval. `eventStore.saveSetupDraft()` (the automatic proposal at the signup deadline, `reminders.runAutoSuggest`) writes the same shape with `origin: "auto"` — the editor badges it "automatischer Vorschlag" — and never replaces an approved setup or a draft changed after one.
- **Manual lineups** are validated by `utils/setup/manual.js`' `validatePlacement()` (group index within the raid, ≤ 5 per group, ≤ size, nobody twice, only non-absent signups, a spec of the class of one of the named characters — the slot keeps `character`, which one plays (fixed places and `lineupSignature` include it), a role the spec can play) and valued by `proposal.js`' `evaluateSetup(input, placement, options)` — every raider fixed where the orga put them, no search, same output shape (checks, reasons, score), so a hand-made and a proposed setup read alike. Whatever only makes the setup worse (too few healers, a missing buff) is not refused — the checks go red and approving asks once more.
- **What everyone else sees** goes only through `approvedSetupOf()` / `approvedPlacementFor()` / `raidHelperSlots()`: the signup page's `placement` per own row, the setup message in the event channel (`setupMessage.js`, below — the event message only links to it, no inline preview), `show-mysetups`/`show-allsetups` (`utils/raidhelper.ownApprovedSetup`; `eventSources.ownSignedUpEvents` adds own events to `show-allsetups`), the sheet fill. The raid detail payload carries only `ownSetup` (counts and state, `setupSummary()`), and its setup step is done only once approved.
- **API** (`apiRoutes/setup.js`, area `raids`, listed in `apiAccess.js`): `GET /api/raids/setup?event=` (a caller without write gets only `approved`, the payload has no `setup` key at all), `POST /api/raids/setup/propose` `{ event, weights?, fairness?, wishes? }` (locked places kept via `setupInput.fixedFromSetup`), `PUT /api/raids/setup` `{ event, version, groups, bench, fairness? }` (409 `conflict` on an outdated version), `POST /api/raids/setup/approve` `{ event, version }` (only the version the editor showed), `POST /api/raids/setup/explain` (background job via `evalJobs`, 400 `no_api_key` without `config.anthropic.apiKey`) and `GET …/explain?event=` (job + stored text). Discord names are resolved on the GET only — a member fetch per raider is slow where Discord does not know them, and a move must answer at once.
- **KI-Begründung** (`utils/setup/explainText.js`, same client and call shape as `recommendationText.js`): groups, bench, reasons, checks and the signup comments ("kommt 20:30") in, a few German paragraphs out. It only explains — it never moves anybody and never approves; the modal marks a text written for an older version as outdated.
- **Client:** tab "Setup" of the raid detail, only for an own event (`?tab=setup`; for a Raid-Helper event that old link still lands on the roster). `pages/raid-detail/SetupEditor.tsx`: a bar (status badges, "n/size Plätze", "n fixiert", actions KI-Begründung · Neu vorschlagen · Freigeben), group cards (party-buff icons in the head, one line per raider: spec tile, name in class colour, spec · role small, an off-spec role tinted, status dot, lock button), the bench as a column, and a summary column with only Tanks/Heiler/DD as large numbers against the plan, a buffs badge, the fairness switch, wishes met/total and "Gewichte…" (a `Modal` with the sliders, "Neu vorschlagen"). **Reasons live in the line's tooltip only.** Moving: HTML5 drag & drop (no library) onto a group, the bench or a raider (swap), or click/Enter a raider and then the target ("Hierher"/"Auf die Bank", Esc cancels). Moves are pure in `lib/setupEditor.ts` (strippable, run for real in `test/web-client/setupEditor.test.js`), drawn at once and saved one after the other with the last confirmed version, so quick moves never trip the conflict check; approving waits for them. CSS `styles/setup-editor.css` (`se-`). Changing the dragged element inside `dragstart` cancels the drag in Chrome — the dimmed look is set a tick later.
- **Tests:** `test/utils/setup/manual.test.js`, `test/utils/setup/explainText.test.js`, `test/web/setupEditor.test.js` (locks survive a proposal, validation, conflict, approval, change after approval, nothing of a draft reaches members or the event message), `test/web/setupRoute.test.js` (reader never gets the draft, write needed, explain with a mocked client), plus the member-facing checks in `signupsRoute`, `utils/raidhelper`, `showAllSetups`, `apiRouter` (sheet fill) and `raidDetailSteps`. **Not yet:** editing several parallel events in one editor (the API takes one event; `proposeSetup` could do more), adding a raider who did not sign up.

## Setup im Kanal (`src/web/setupMessage.js`, #290)

An approved setup of an own event is posted into the event channel as **its own message** (beside the signup message, which only links to it — no inline preview, #setup-confirm: that duplicated the roster and wrapped badly on a full one) and, optionally, sent to each raider per DM. ⚠️ Only `approvedSetupOf()` is ever read — a draft is never posted or DM'd, and a draft changed after an approval leaves the message on the approved lineup. The message also carries a **Confirm/Cancel** row (`setupConfirmBot.js`): each placed raider confirms or declines their own slot with one click, marked next to their name (green check / red cross, an emoji-sized transparent placeholder while unanswered so nothing shifts); declining only marks it — the orga rebenches by hand, nothing here moves anybody automatically.

- **Message** (`buildSetupMessage(event, approved, { emojis })`, pure, plain API JSON, `null` without an approval): title `Setup · <Titel>`, description `<t:start:F>` plus one line of role totals in the **flat role icons** `eh_ui_tank|healer|melee|ranged` (since #320 the same ones the signup message draws; the colourful WoW `eh_role_*` are gone), one **inline field per non-empty group** (`<spec emoji> **Name**`), the bench as **one** field `🪑 Bank (n)` (`Name · Name …`, clipped with "+N weitere"), a link `Im Web ansehen` (`/signups?event=`), footer `Freigegebenes Setup · Stand <version>`, timestamp = approval. Der Balken trägt **dieselbe Farbe wie die Anmelde-Nachricht** (#307, `embedLook.embedColor`) — die beiden Posts stehen in einem Kanal und gehören zusammen; das Bild bleibt bei der Anmelde-Nachricht. Without app emojis the text fallbacks of `appEmojis.js` (`**Name** · Heilig`, 🛡️ 💚 ⚔️ 🏹, 🪑). Limits like the event message (≤25 fields, ≤1024 per value, ≤6000 — if too long the bench and then the groups drop their icons). A cancelled event draws only "Abgesagt: Setup · …" with the reason.
- **Post vs. edit:** `postOrEditSetupMessage(eventId)` posts the first time and **edits** afterwards; where it sits is `event.setupPost` (`eventStore.setEventSetupPost`, merged: `channelId, messageId, version, postedAt/By, editedAt/By, error/errorAt, dms, told`). A message deleted in Discord is posted anew; a cancelled event only gets an existing message marked (`cancelled` otherwise). Never throws — a Discord error is stored and returned as `{ code, error }`, so an offline bot never fails the approval.
- **Hooks:** `POST /api/raids/setup/approve` awaits `publishSetup()` (message first, its failure appended to the answer's message) — not for an "already approved" repeat; `POST /api/raids/setup/post` (area `raids`, write) is the editor's "Setup posten": post/edit again and send outstanding DMs. `eventManage`'s `refreshMessage` (cancel, reopen, move) also calls `refreshSetupMessage()`, which only edits an existing message, never posts.
- **DMs** are a switch per category: `config.categorySetupDms = { [categoryId]: true }` (off by default, only switched-on categories stored; the PATCH sends `false` so the merge can drop one), Einstellungen › Kategorien › *Setup-DMs*, not full-admin-only. `sendSetupDms()` runs in the background after the post, **one after the other** with `DM_DELAY_MS` (1.2 s) between, one run per event at a time. Texts (`buildSetupDm`): "Du bist in **Gruppe 2** als **Heiler** (Zibbo · Heilig)." / "Diesmal **Bank** (Zibbo · Heilig) – nächstes Mal hast du Vorrang." (the Vorrang part only with fairness on) plus `Grund: …` from the proposal's bench reasons — only while the stored setup is the approved version, at most two, never a wish reason (it names other raiders) — and a link to the posted message. **Once per placement:** `setupPost.told[userId]` keeps the signature (`g2/Priest-Holy/healer` or `bench/<spec>`) of what a raider was told; a new approval writes only to those whose place changed, a failed DM is not marked and goes out again on the next run. The run's outcome is `setupPost.dms { status running|done, total, sent, failed[{ userId, character, error }], unchanged }`. Never for a draft or a cancelled event.
- **Editor** (`pages/raid-detail/SetupEditor.tsx`, `PublishLine` under the bar; text pure in `lib/setupEditor.ts`' `publishHint()`): the GET gives the orga `publish` (`setupMessage.publishView`: channel name, `dmsEnabled`, recipients, pending DMs, posted/outdated, error, dms). Before approving: "Beim Freigeben: postet Setup in #kanal · DMs an 12 Raider (aus)" (with "DMs einschalten" → settings); after: "gepostet 17:40 in #kanal · 22 DMs · 3 fehlgeschlagen" — failures, an outdated message ("zeigt noch Stand 1") and the rules in the tooltip, one ghost button "Setup posten". While the DMs run the page polls only `publish` every 3 s (never the lineup, so a move is not overwritten).
- **Invite callen** (`src/web/inviteCall.js`, one service for web and Discord): the orga pings **groups 1–5** of the approved snapshot (never a draft; groups 6–8 and the bench wait, the caller is never pinged) in the event channel with `/w <Charakter> inv` — `discord.postMissingPing(channelId, ids, text)`, so long rosters split under 2000 characters. `<Charakter>` is the caller's own: their place in the approved setup (group or bench), else their signup's character; none = refused (`no_character`). Also refused: cancelled, no approved setup, nobody in 1–5 but the caller, another server's event. Logged on the event (`action: "invite"`, "Invite gecallt"). **Discord:** the setup message carries one button `Invite callen` (`inviteCallBot.inviteButtonRow`, customId `invite-call:p:<eventId>`; a cancelled message none) — the click answers privately with the preview (count + the line) and `Jetzt pingen` (`invite-call:c:<eventId>`) posts; the command `commands/event/inviteCallButton.js` has `accessOf: "event"`, so only the orga may. A message posted before this button existed gets it with its next edit (approval, "Setup posten", cancel/move). **Web:** "Invite callen" in the raid detail's Verwalten menu (`lib/eventManage.ts`, `state.invite` = `ownSetup.approvedAt`; also after the start, never when cancelled) → `pages/raid-detail/manage/InviteModal.tsx`, preview via `POST /api/raids/invite-call { event, dryRun: true }` → `{ count, text, groups }`, then the same call without `dryRun` (area `raids`, write; the caller is the logged-in user's Discord id). Tests: `test/web/inviteCall.test.js`, `test/web/raidDetailInviteCall.test.js`, the menu in `test/web-client/eventManage.test.js`, the button in `test/web/setupMessage.test.js`.
- **Tests:** `test/web/setupMessage.test.js` (layout, emoji fallback, escaping, 40-man limits, post/edit/repost, never a draft, cancelled, DMs only with switch, once per placement, failures retried), `test/web/setupRoute.test.js` (approve posts, repeat does not, `/post`, `publish` only for the orga), `test/web/eventManage.test.js` (cancel/reopen refresh), `test/web/settingsRoute.test.js` + `settingsStore.test.js` (switch), `test/web-client/setupEditor.test.js` (`publishHint`), `test/web-client/settingsLogic.test.js`.
