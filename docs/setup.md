# Setup

## Setup-Vorschlag (`src/utils/setup/`, #262)

`buildSetupProposal(input, options)` (`proposal.js`) builds raid groups and a bench from signups, profiles, attendance, earlier setups and the orga's fixed places. **It is always only a proposal — a human approves it** (the editor, the routes and the approval: "Setup-Editor" below). Pure and deterministic: no store, no clock, no randomness; ties go by signup `at`, then user id, and the input order of the signups does not matter.

- **Input** (`src/services/setup/setupInput.js`' `collectSetupInput(eventIds)` reads it from the stores; `proposeSetup(eventIds, options)` = collect + build): `events` (`{ id, title, size, composition, requiredBuffs, fairness, wishes }` — several ids = raids that run **in parallel** and share the raiders), `signups` (signupStore shape + `eventId`), `profiles` (raiderProfileStore), `attendance` (`{ userId: pct }` from `rosterAttendance` in the event's category), `history` (`[{ eventId, startTime, placed[], bench[] }]`), `rosterStatus` (`{ userId: "core" | "trial" | "bench" | "pause" }` of the events' categories' rosters, #658; empty without one) and `fixed` (`{ userId, eventId, group (1-based), spec }` or `{ userId, bench: true }` — the `locked` slots of the event's current draft). Required buffs are the event's own (`event.requiredBuffs`, set in the create dialog, #261) once it was planned from a template or has any, else the category's raid template's (`config.categoryRaidTemplate`); melee/ranged go in as `{ min, max }` where the event stores a `compositionMax`. **The bench history is derived from approved setups** (`setupInput.approvedLineup()`: the `approved` snapshot, never a draft changed after it; same categories, earlier start, last 10) and never stored on its own; while none exists the stored signups stand in (signed/late = placed, "Ersatzbank" = bench), `historySource` says which.
- **Composition:** `tank`/`healer` are exact targets (min = max), a melee/ranged **number is a minimum** (0 = none, the dps fill the rest), `{ min, max }` a range. Groups hold 5, `ceil(size/5)` of them.
- **Hard rules** (`model.js` + `score.js`, a broken one scores `-Infinity`, so the search can never accept it): size, 5 per group, each raider at most once across all events, role maximums, never a spec the profile marks `gear: "none"`, never an absence, fixed places stay (a fixed raider beyond a role maximum widens it and turns the check red; a fixed place of somebody who signed off is ignored with a `warnings` entry). Role minimums and "bench signup only as a fallback" are constants far above every weight (`ROLE_MIN` 30000 per missing raider > `FILL` 10000 per placed raider > `BENCH_STATUS` 7000 > 12 weights × `MAX_WEIGHT` 500; it was 6000 until the `roster` weight made twelve), so no weight setting can trade a missing healer for a nicer group — but too few healers never throws: the check goes red.
- **Options per raider:** every named character (#293, `signup.characters`, else the single one) with its signed spec (main; each option carries its `priority`, 0 = the choice) — **one place per person** stays a hard rule, so exactly one of them is placed — plus, for the first choice only, off-spec roles from the signup's `canAlso` and a stated `canOfftank/canHeal === true` of **that character** (`model.characterFlags`: the character's own switch, else the old profile-wide one), played as the class's spec for that role the profile has geared best (a feral who can tank → `Druid-Guardian`).
- **Each option carries its own character's status (#320)**, not the signup's (`model.characterStatus`): "Spät" on the first character leaves the second "Dabei", so the second is the better option and only the option that is actually placed says "Kommt später". A character without a status of its own takes the signup's. **The absence stays a matter for the whole person** — a signed-off raider has no options at all — and a person still takes at most one seat.
- **Soft goals** (`DEFAULT_WEIGHTS`, overridable via `options.weights`, 0 = off, clamped to 0…500): `partyBuffs` 60, `raidBuffs` 40, `requiredBuffs` 300, `mainSpec` 120, `preferredCharacter` 100 (a **cost** for placing a "kann auch mit" character, so raiders with one character score as before — **waived** where that character's own status makes it the more available one, `score.moreAvailableThanFirst`: the order of the characters is a preference, a status is a statement about the evening, and 100 would otherwise always outweigh the 40 that separate "Dabei" from "Spät"), `gear` 30 (ready > unknown > usable), `status` 80 (signed 1, late ½, tentative 0.3 — **per character** since #320), `fairness` 150, `attendance` 40, `wishes` 60, `roster` 200 (#658: in a category with a roster core 1, trial 0.6, bench 0.3, a paused member or a non-member 0 — the roster comes first, core before trial before bench, everyone else after; the input's `rosterStatus` is `{ userId: status }` from `setupInput.rosterStatusFor`, the first event's roster first with parallel raids; **without a roster nobody has a status and the effective weight is 0**, so categories without roster propose exactly as before; slider "Roster-Status"). `fairness`/`wishes` only count where the event's flag is on (`options.fairness`/`options.wishes` override); the output's `weights` are the effective ones (0 when off). **Fairness** per raider over their last 10 nights: 0.6 if benched the last time they were in a setup + 0.4 × min(1, benches/3). **Wishes** are unordered pairs, mutual 1, one-sided ½; same group = full, same raid ⅕ (with parallel raids ½ — there the raid is what counts).
- **Nicht zusammen** (`avoid` 100, a **penalty**): pairs from the profiles' "nicht zusammen raiden mit" lists (only while a raider has it switched on, docs/roster-profile.md), one pair even when both named each other. Costs the full weight when the pair stands in the **same group** (one raid) or the **same raid** (parallel raids) — it separates, it never benches anybody on its own. **No event flag — the orga is asked:** `options.avoid === true` alone turns it on; the setup remembers the answer in `options.avoid` (`null` = never asked). The editor gets `avoidPairs` (a count, `setupEditor.avoidPairCount`) and asks once before the first proposal when it is > 0; afterwards a switch in the side column changes it (a save re-values the lineup, "Neu vorschlagen" separates). `checks.avoid` = `{ on, together, total }` — **counts only, never who named whom**, in no output and no reason.
- **Party buffs** come from the rule set (`gameVersions/buffs.js`, which gained `slot` and the setup-only `vampiricTouch`): per group each buff counts the members who want it, once per key; a buff with a `slot` (a totem element, a warrior's shout) once per provider per slot, most valuable first — a shaman drops one air totem, so Windfury + Wrath of Air in one group take two shamans. A buff everybody wants (`universal`: Blood Pact, Healing Stream) counts half and is never named as a reason.
- **Search:** fixed places → greedy (scarce roles first: fewest spare candidates, then the least flexible raider, bench signups last; then every free place with whoever adds most) → local search with strict improvements only (add, replace, switch role/event, switch role + fill the freed role, move/swap between groups, swap between parallel raids), at most `MAX_PASSES` 40. A 25-man and a 40-man from 60 signups take well under a second (tested).
- **Bench and pool (#517):** a proposal **never benches anybody by itself**. Who is in no group is split: `bench` holds only who the orga put there (`fixed: { userId, bench: true, locked? }` — every entry of the draft's bench, locked or not, `setupInput.fixedFromSetup`; `locked` only decides whether the editor shows the lock), `pool` everybody else signed up and not placed (the editor's **„Angemeldet“**, with the same reasons, e.g. "Heiler voll (6/6)"). A "Bank" signup (status `bench`) that is left over waits in the pool, marked, like everybody else — the raider's status says "I'd sit out", the bench is the orga's decision and is posted, so it only ever comes from the orga. The **fairness history** (`setupInput.setupMembers` → the approved snapshot's `bench`) therefore counts only the explicit bench.
- **Shadowban (#981, docs/vermerke.md):** whoever has an active Vermerk of level `shadowban` on the raid's server (own or shared from another server, not hidden there, not expired — `vermerkeShort.shadowbannedAmong`) is **never placed by the proposal** and waits in the pool (`model.buildCandidates` marks the candidate, `proposal.placeFixed` bans all its options unless the orga fixed it). Warnings and hints change nothing. Placing the person by hand stays allowed, without asking; a fixed place stays. The lookup is **injected**: `collectSetupInput(ids, { shadowbannedOf })` / `proposeEventSetup(…, { shadowbannedOf })` — only the orga's callers pass it (`POST …/setup/propose`, the auto proposal in `web/events/reminders.js`), so `setupInput`/`setupEditor` never load the Vermerke store and the pages a raider reads stay free of it (`vermerkeNeverToPerson.test.js`, whole require closure). Raid-Helper signups go by their userId; parallel raids (#811) ban the person in every raid. No reason, no output field of the proposal names the shadowban — the hint is the editor's: its answers (GET and every write, only when `maySeeShort` in `services/vermerke/vermerkeAccess.js` says yes) carry `shadowbanInPool` `[{ userId, name }]`, **everyone with a shadowban in the pool of the stored setup** (not only whom the last proposal held back), shown as "N Person(en) mit Shadowban im Pool · Name"; `name` is the cached Discord name, else the character (docs/vermerke.md "In the answers of the orga").
- **Output** (JSON, stable for #263): `{ version, versionId, groups: [{ index, slots: [{ userId, character, classId, spec, role, main, status, locked, reasons[] }] }], bench: [{ …, eventIds, locked, reasons[] }], pool: [{ …same shape }], checks: { ok, size, roles: { tank: { count, min, max, ok }, … }, buffs: { ok, required[], raid[], party: [{ key, label, icon, groups[] }] }, wishes: { met, total, pairs[] } }, events: [{ eventId, title, groups, bench, checks }], weights, score: { total, parts }, warnings[] }`. `groups`/`checks` are the first (usually only) event's; with parallel raids every event has its own entry, `bench` lists who is in none, `checks.wishes` counts across all.
- **Reasons** (`reasons.js`, German, at most four): "Von der Orga fixiert", for a raider with several characters first which one and why — "1. Wahl: Zibbo" or "Mit Zibbowar als Tank statt Zibbo (Heiler voll (3/3))" / "(Tanks fehlten)" / "(kommt später)" — #320, and it comes before the other two, because the raider said it themselves — / "(passte besser in die Aufstellung)", "Zweitspec als Heiler", "Kommt später", "Gr. 2 wegen Totem des Windzorns (5 profitieren)", "Bringt als Einziger Segen der Könige" / "(Pflicht-Buff)", "War zuletzt auf der Bank – hat Vorrang", "Wunsch erfüllt: mit X (gegenseitig)", "Anwesenheit 91 %", "Eingeteilt in PuG 2"; on the bench "Heiler voll (6/6)", "Raid voll (25/25)", "Nur „Vielleicht“ angemeldet", "War zuletzt dabei", "Keine Spec mit brauchbarem Gear", "Von der Orga auf die Bank gesetzt".
- **Tests:** `test/utils/setup/` — fixtures (10/25/40 Classic), determinism, a seeded property loop over random inputs checking every hard rule, bench rotation over seven evenings, wishes (mutual beats one-sided), fixed places, too few healers, Windfury/shadow priest placement, runtime; `test/services/setup/setupInput.test.js` for the collection. Not covered yet: raid **debuffs** (the rule set has none for the setup), availability/preferred raids from the profile.

## Setup-Editor (Raid-Detail › Setup, `src/services/setup/setupEditor.js`, #263)

The proposal becomes an evening here: the orga proposes, moves, locks and **approves**. ⚠️ **The setup is only ever a proposal until the orga approves it, and raiders never see a draft** — not through any endpoint, message or bot command.

- **Who is the orga of a setup (#725, docs/permissions.md "Kategorie-Orga"):** the global orga (`userIsOrga`) with `raids` write for every raid, and a **manager of the roster of the raid's category** (in the raid's version, `categoryOrga.canOrgaEvent`) for that category's raids — without `raids` write, and only while that roster is the one the category plays **now** (a roster prepared for a coming version gives no right yet). Every write route of `web/apiRoutes/events/setup.js` (propose, save, approve, post, ping text, ping, confirm, extra role, the signup dialog, search message, explanation, presence, the raid group routes) is `orgaScoped` on the event in the body (the GETs: in the query); a raid of another category answers 403 `not_category_orga`, a raider role with `raids` write but no orga rank 403 `orga_only`. `move-raid` names **both** raids, the source and the `target`. The GET's `canWrite` — and with it the draft, the names, the attendance and the publish panel — is the same rule per event (`web/setup/setupAccess.js` `canWriteSetup(user, event, req)`, sharing the gate's Discord role lookup); the „Comp“ link (`/e/<id>/comp`, `pageRoutes.js`) sends by it too. The answer's **`canEditEvent`** gates „Mehr → Raidgröße“: the size goes through the event's own `PATCH /api/raids`, `orgaScoped` by the event since #728 — so it is `canWrite` (the same rule). The setup buttons in Discord („Alle pingen“, „Invite callen“) are not part of this: they follow `/event`'s command access (`botAccess.js`).

- **No proposal needed (October 2026):** before anything is stored, `editorView(event, { blank: true })` (the GET passes it) answers an **empty start** — `setupEditor.blankSetup()`: empty groups valued by `evaluateSetup` (so the counts read "0 von 3"), every signup in the pool, `version: 0`, `blank: true`, nothing written. The first move is an ordinary `PUT …/setup` with version 0 (no stored setup = no conflict check) and stores version 1. The client draws it like any draft: "Angemeldet" is the **`PoolPanel`** (`setup/PoolPanel.tsx`): a side column beside the groups (sections tank/healer/melee/ranged, a search over character, Discord name and spec — every signed character included, `setupText.matchesQuery` —, one card per person with all their characters („Mehrere Charaktere im Editor" below), role and status filter chips, each block sorted signed → late → tentative → bench („Signup-Stand auf einen Blick" below), "n abgemeldet") — or, where the editor is narrower than 1080 px (a **container query** on `.se-stage`, which wraps only the layout: containment on `.se-editor` would trap the fixed drawer), a **dock at the bottom of the window** (`position: sticky; bottom: 0`, one row to scroll sideways, folded by its arrow — `se-pp-collapsed` — and folded by itself while one of its raiders is picked, `se-pp-picking`, so the free places to tap stay in view). „Setup posten“ is disabled while nobody stands in a group.
- **„Automatisch füllen“ / „Freie Plätze füllen“** (bar, while somebody is in the pool and places are free): with nobody placed it proposes at once (`POST …/setup/propose`); otherwise `FillModal` (`SetupModals.tsx`) asks — **only the free places** (default, `keep: "placed"`: `setupInput.fixedFromSetup(event, { keepPlaced: true })` fixes everybody in a group for the run; `setupEditor.keptAsPlaced()` then gives back only the orga's own locks — the others `locked: false` without the reason "Von der Orga fixiert" — and their places 1–5, `inPlacedOrder`) or **everything anew** (the old „Neu vorschlagen“, which also stays under „Mehr“). Answer message „Freie Plätze gefüllt.“.
- **The automatic proposal at the deadline never replaces hand work:** `reminders.autoSuggestDue` skips an event whose setup has anybody in a group or on the bench, or an approval (`hasLineup`); a draft dragged empty again still gets it. The raid detail's step for an event without a setup reads „Setup bauen“.
- **„Alle bestätigen“ asks first** (`useConfirm`: how many get the check, a cancel stays) before `POST …/setup/confirm-all`.
- **Who else is in the editor** (`src/services/setup/setupPresence.js`, in memory only, nothing stored): every open editor sends a heartbeat `POST /api/raids/setup/presence { event, action?, since?, leave? }` (area `raids`, write, CSRF) every 3 s while the tab is visible (`setup/usePresence.ts`) and at once when what it holds changes — `action` = `{ kind: "drag", userId }` (dragged or picked) or `{ kind: "edit", userId }` („Anmeldung bearbeiten“ open). The answer: the other editors with their action and Discord picture (`avatarUrl`, "" = initials; gone `PRESENCE_TTL_MS` = 15 s after their last heartbeat, at once with `leave: true` when the editor closes), the stored `version`, the Confirm/Cancel marks (`confirmations`, as `confirmationsFor` shows them) and the activity after `since` — **only what the others did**. The routes write the activity: `putSetup` → `recordMoves(before, after)` (one entry per raider who went to another group, the bench or back to the pool; more than four in one change = one "n Raider verschoben"), `postPropose` → `recordNote("fill"|"propose", { count })`, a post → `"post"`; at most 20 entries, ten minutes. **In the editor:** the bar shows the others as coloured avatars (`LiveParts.PresenceChip`, „Exitus ist auch hier“ / „3 im Setup“, what each holds in the tooltip; colour per user, `presenceColor`); a raider another one holds is ringed in their colour with a name tag (`se-held`, „Exitus zieht“ / „… bearbeitet“) and can be neither picked, dragged nor dropped on — a soft lock, the server enforces nothing; what another one just moved glows 4 s with their name (`se-flash`, only for news after the page opened); „Gerade eben“ (`ActivityFeed`) lists the others' last five changes under the summary line. **Somebody else saved:** a heartbeat with a newer `version` than the page's makes the editor fetch `GET …/setup?event=&light=1` (no Discord names, no attendance — the page keeps its own) and redraw, unless a move of its own is on its way. **A raider answered in Discord:** Confirm/Cancel under the setup message changes no `version`, so the editor takes the heartbeat's `confirmations` over directly — not while „Alle bestätigen“ is on its way, not from a heartbeat sent before its own last mark was answered, and an own mark still on its way stays on top (`withPending`). **Two moves at once:** a save that meets a newer lineup (409 `conflict`) no longer ends in "bitte neu laden": the editor fetches the newer lineup, applies the same move to it (`moveRaider` once more — a taken place falls back to the next free one, a swap where the other is gone fails) and saves again, saying „Jemand hat zwischendurch geändert – dein Zug wurde auf den neuen Stand gesetzt.“ Raid detail: `ownSetupEditors` (names) makes the setup step say „Exitus arbeitet dran“ (`raidDetailSteps.withEditors`). Raiders never see any of it.

- **Stored on the event** (`eventStore.setEventSetup`, one object): the proposal output v1 for the event (`groups`, `bench`, `pool` (#517), `checks`, `weights`, `score`, `warnings`, `historySource`; the per-event `events[]` is dropped), `status` draft/approved, `version` (bumps on every change of **who stands where** — `lineupSignature()`; a lock, a weight or the fairness switch alone keeps version and approval), `origin` proposal/manual/auto, `options { weights, fairness, wishes }` (the orga's overrides, reused by the next proposal), `updatedAt/By`, `approvedAt/By/Version`, **`approved`** (the frozen raider-facing snapshot: names, specs, roles, groups, bench — no reasons, no locks, no wishes), `changedSinceApproval`, `explanation { text, model, version, at }`.
- **Bench, pool and old setups (#517):** `setupCore.benchAndPool(setup)` is the one reader: a setup stored before #517 has no `pool`, its bench was everybody left over — there only the **locked** bench entries count as the explicit bench and the rest is the pool (`withSetupDefaults`, `fixedFromSetup`, `snapshotOf`, `lineupSignature`, `setupSummary` all go through it). Late signups (`addUnplacedSignups`) land in the pool. `lineupSignature()` includes the bench's user ids: moving somebody onto the bench or off it is a change of the lineup (new version, a draft again) — the bench is posted. The approved snapshot carries only the explicit bench, never the pool; `approvedPlacementFor` gives a pool raider `null`.
- **Change after approval:** a new lineup turns the setup back into a draft with `changedSinceApproval`; the `approved` snapshot stays, so raiders keep seeing the last approved lineup until the next approval. **Once the setup message is posted it goes live instead** (`setupEditor.postedLive`: `setupPost.messageId`, an approved snapshot, not cancelled): `storeSetup()` approves every changed lineup at once in the name of whoever changed it — a move, „Neu vorschlagen“, „Anmeldung bearbeiten“, and a draft left from before the post with the next save — and answers `live: true`; the route (`followLive` in `apiRoutes/events/setup.js`) then awaits `setupMessage.refreshLiveSetup()` (the message edited to the new lineup, one edit after the other per event, **no ping, no DMs** — the editor's line says „n DMs offen“ and „Setup posten“ sends them) and refreshes the event message like an approval. Confirm/Cancel stay untouched (see "Confirm/Cancel" below), the last ping's list follows (see "The ping follows the setup"). An empty lineup never goes live. A failed edit never fails the change: the answer's `message` says „Setup-Nachricht nicht aktualisiert: …“. `eventStore.saveSetupDraft()` (the automatic proposal at the signup deadline, `reminders.runAutoSuggest`) writes the same shape with `origin: "auto"` — the editor badges it "automatischer Vorschlag" — and never replaces an approved setup or a draft changed after one.
- **Manual lineups** are validated by `utils/setup/manual.js`' `validatePlacement()` (group index within the raid, ≤ 5 per group, ≤ size, nobody twice, only non-absent signups, a spec of the class of one of the named characters — the slot keeps `character`, which one plays (fixed places and `lineupSignature` include it), a role the spec can play) and valued by `proposal.js`' `evaluateSetup(input, placement, options)` — every raider fixed where the orga put them, no search, same output shape (checks, reasons, score), so a hand-made and a proposed setup read alike. Whatever only makes the setup worse (too few healers, a missing buff) is not refused — the checks go red and approving asks once more.
- **What everyone else sees** goes only through `approvedSetupOf()` (`setupCore.js`) / `approvedPlacementFor()` / `raidHelperSlots()`: the signup page's `placement` per own row, the setup message in the event channel (`setupMessage.js`, below — the event message only links to it, no inline preview), `show-mysetups`/`show-allsetups` (`utils/raidhelper.ownApprovedSetup`; `eventSources.ownSignedUpEvents` adds own events to `show-allsetups`), the sheet fill. The raid detail payload carries only `ownSetup` (counts and state, `setupSummary()`), and its setup step is done only once approved.
- **Layers (#424):** `src/services/setup/setupCore.js` is the pure bottom layer — `approvedSetupOf`, the ping text (`PING_TEXT`, `pingTextOf`), `confirmationsFor` and the button row under the setup message (`confirmButtonRow`/`inviteButtonRow`/`pingButtonRow` with their custom-id prefixes). It requires no setup module back. `setupEditor`, `setupPing`, `inviteCall` and `setupMessage` build on it; the `*Bot.js` button handlers only require downwards (`setupConfirmBot` → `setupConfirm` → `setupMessage`), never the other way round. `test/web/noCycles.test.js` keeps all of `src/` (without `web-client/`) free of require cycles (lazy requires count too).
- **API** (`apiRoutes/events/setup.js`, area `raids`, listed in `apiAccess.js`): `GET /api/raids/setup?event=` (a caller without write gets only `approved`, the payload has no `setup` key at all), `POST /api/raids/setup/propose` `{ event, weights?, fairness?, wishes? }` (locked places kept via `setupInput.fixedFromSetup`), `PUT /api/raids/setup` `{ event, version, groups, bench, fairness? }` (409 `conflict` on an outdated version), `POST /api/raids/setup/approve` `{ event, version }` (only the version the editor showed), `POST /api/raids/setup/explain` (background job via `evalJobs`, 400 `no_api_key` without `config.anthropic.apiKey`) and `GET …/explain?event=` (job + stored text). Discord names are resolved on the GET only — a member fetch per raider is slow where Discord does not know them, and a move must answer at once.
- **KI-Begründung** (`utils/setup/explainText.js`, same client and call shape as `recommendationText.js`): groups, bench, reasons, checks and the signup comments ("kommt 20:30") in, a few German paragraphs out. It only explains — it never moves anybody and never approves; the modal marks a text written for an older version as outdated.
- **Client:** tab "Setup" of the raid detail, only for an own event (`?tab=setup`; for a Raid-Helper event that old link still lands on the roster). `pages/raid-detail/setup/SetupEditor.tsx`: one toolbar line (see "Layout" below), group cards (party-buff icons in the head, one line per raider: spec tile, name in class colour, the spec small — plus „Tank“/„Heiler“, **never melee/ranged** (the spec says it); an off-spec tints the role where shown, else the spec —, the signup state as a labelled square field (see "Signup-Stand auf einen Blick" below), a small lock mark in the slot's corner while fixed, so it takes no width from the name), the bench as one row under the groups, and a summary line whose "Details" holds Tanks/Heiler/DD as large numbers against the plan, a buffs badge, the fairness switch, wishes met/total ("Gewichte…" — a `Modal` with the sliders, "Neu vorschlagen" — is under „Mehr“). **Reasons live in the raider drawer only** (see "Raider tooltip" below). Under the bench the row **„Angemeldet“** (`PoolCard` in `setup/Board.tsx`, drawn like the bench, no lock, a "Bank" signup marked with the field „Bank“). Moving: HTML5 drag & drop (no library) onto a group, the bench, „Angemeldet“ (`{ pool: true }` — out of the setup again) or a raider (swap; a swap with somebody in the pool puts the pool raider on the exact place and the other into the pool), or click/Enter a raider and then the target ("Hierher"/"Auf die Bank", Esc cancels). The save request has no pool — who is in neither `groups` nor `bench` is in it (`lib/signups/setupEditor.applyLocal` redraws it at once); resizing the raid drops the bumped raiders into the pool, not onto the bench. Moves are pure in `lib/signups/setupEditor.ts` (strippable, run for real in `test/web-client/conventions/events/setupEditor.test.js`), drawn at once and saved one after the other with the last confirmed version, so quick moves never trip the conflict check; approving waits for them. CSS `styles/setup-editor.css` (`se-`). Changing the dragged element inside `dragstart` cancels the drag in Chrome — the dimmed look is set a tick later.
- **Places inside a group (`pos`):** every group slot carries the place 1–5 the orga put it on, so a group of two may stand on places 1 and 5 (a free place is a drop target of its own: `FreePlace`, "Hierher 5" for the keyboard path). `validatePlacement()` keeps a valid, unused `pos`, gives every other slot the lowest free place in order and sorts by it (`manual.placeSlots()`); `saveEventSetup` → `inPlacedOrder()` stores it, `snapshotOf()` copies it into the approved lineup, and `decorateLineup()` gives a proposal or an old draft the places 1, 2, 3 … The client mirrors the rule in `lib/signups/setupEditor.ts` (`withPlaces`, `placeGrid`; `moveRaider` takes `{ group, pos }`; a swap exchanges the places too; a drop on the group card itself still means "the lowest free place", inside the own group "to the end, places closing up"). The array order stays the place order, so every consumer that reads `slots` in order is unchanged. `lineupSignature()` ignores `pos`: a change of place alone keeps the version and an approval — who stands in which group, and in which order, is what counts.

## Raid-Gruppe: weitere Raids aus einer Anmeldung (`src/services/events/raidGroup.js`, #811)

Melden sich deutlich mehr an als Plätze da sind (20+ für einen 10er), macht die Orga mit einem Klick einen **weiteren Raid** daraus. **Entscheidung:** die Raider melden sich **einmal** an, am ersten Raid; die Orga verteilt sie.

- **Datenmodell** (`utils/raidGroup.js`, rein; Felder in `eventStore.complete`): `raidGroupId` = die Id des **ersten** Raids auf jedem Raid der Gruppe (`""` = keine Gruppe), `raidGroupIndex` = Platz (1 = der erste, 2, 3 … die weiteren). Der erste Raid („primary“) ist also das Event, dessen Id die Gruppen-Id ist; `signupEventIdOf(event)` ist für jeden Raid der Gruppe die Id des ersten — **seine Anmeldungen gelten für alle Raids**. `isRaidSibling`/`isRaidPrimary`/`inRaidGroup`/`raidIndexOf` lesen das.
- **Weiteren Raid hinzufügen** (`raidGroup.addRaid`, `POST /api/raids/setup/raid-add { event, title? }`, Bereich `raids` schreiben): legt ein Geschwister-Event an — gleicher Start, Dauer, Kategorie, Version, Vorlage, Größe, Komposition (samt Maxima), Pflicht-Buffs, Kanal, Anmeldeschluss, Fairness/Wünsche —, Titel `<Titel> <n>` oder der im Dialog geänderte; **keine** Anmelde-Nachricht, kein Discord-Event, `autoSuggest`/`lockAtLimit` aus. Der erste Raid bekommt dabei `raidGroupId` = seine eigene Id. Bis 8 Raids; abgesagt oder schon begonnen wird abgelehnt (`cancelled`/`started`), Raid-Helper-Events auch. Protokoll `raidAdd` an beiden.
- **Mehrere Raids auf einmal** (#1035): `raidGroup.addRaids(eventId, { count, titles? })` legt `count` weitere Raids in einem Zug an (Titel `<Titel> n` fortlaufend), **ein** Protokolleintrag „n Raids angelegt“; über 8 Raids insgesamt → 400 `too_many`. `POST /api/raids/setup/raid-add { event, count? }` (Standard 1, ungültig → 400 `invalid`), zeichnet die Anmelde-Nachricht **einmal** neu und antwortet `{ event, events, title, raidGroup, message }`. **Vorschlag** `suggestedRaidTotal({ active, size })` = ⌈aktive Anmeldungen / Größe⌉, höchstens 8; Vorläufig und Bank zählen, Abwesend nicht. `editorView` liefert dazu `signupCount` und `suggestedTotal` (die **Gesamtzahl** der Raids: 50 Anmeldungen für einen 10er → 5). Der Server zählt bei `count` die **neuen** Raids, die Umrechnung (Gesamtzahl − bestehende Raids) macht der Client.
- **Auflösen** (`raidGroup.dissolveRaid`, `POST /api/raids/setup/raid-remove { event }`): nur ein weiterer Raid **ohne** freigegebenes Setup (sonst 409 `approved`, der Weg ist dann Verwalten › Löschen); der erste nie (`primary`). Er wird gelöscht, seine Eingeteilten stehen wieder unter „Angemeldet“ (der Pool wird ja aus den Anmeldungen berechnet), die übrigen rücken in der Nummer auf (`closeUp`), mit dem letzten endet die Gruppe. `eventManage.deleteEvent` lehnt den ersten Raid ab, solange weitere bestehen (`raid_group`), und rückt nach dem Löschen eines weiteren auf; `moveEvent` nimmt die weiteren mit (`followPrimary`: Start und Anmeldeschluss).
- **Unsichtbar für jeden Leser, der Anmeldungen oder Abende zählt:** `eventStore.listEvents` lässt die weiteren Raids weg, außer mit `{ siblings: true }` — das fragen nur Setup (`setupInput.benchHistory`, `raidGroup`), Raid-Liste (`eventSources.ownEventGroupRows`, `listStoredEvents(…, { siblings: true })` für die vergangenen Raids), Log-Zuordnung (`ownMatchableEvents`) und Anwesenheit. So bekommen Erinnerungen, Raider-Zentrale, Mehrfach-Anmeldung, Talk-Übersicht, Orga-Zentrale, Kalender-Abo und `ownEventInChannel` (gleicher Kanal!) nur den ersten Raid. `toEventGroupShape` gibt einem weiteren Raid die Anmeldungen des ersten (Detailseite, „fehlt“-Liste); Talk-Übersicht und Raid-Übersicht im Discord filtern ihn heraus, die Anmeldeseite (`signupView.memberEventRows`) auch.
- **Ein Editor für die ganze Gruppe:** `collectSetupInput` gibt jedem Raid der Gruppe die Anmeldungen des ersten (je Raid mit dessen `eventId`), also kann jeder überall stehen und die harte Regel „each raider at most once across all events“ hält es bei einem Platz. `editorView` liefert `raidGroup` (`groupSummary`: `{ id, primaryId, count, places, raids: [{ id, title, index, size, placed, status, approved, posted, cancelled }] }`) und `placedElsewhere` (Zahl); **„Angemeldet“ ist ein gemeinsamer Pool**: die Anmeldungen minus alle, die in irgendeinem Raid der Gruppe in einer Gruppe oder auf der Bank stehen (`placedElsewhere(event)` → `withoutElsewhere`).
- **Ein Platz je Person (Server):** `saveEventSetup` lehnt eine Aufstellung ab, die jemanden enthält, der in einem anderen Raid der Gruppe steht (Gruppe oder Bank) — `taken`, 409, „Zibbo steht schon in Zul'Aman – jede Person hat in der Raid-Gruppe nur einen Platz.“
- **Zwischen den Raids verschieben:** `setupEditor.moveToRaid`, `POST /api/raids/setup/move-raid { event, target, userId, character? }`: aus einem Gruppenplatz (wie er steht), von der Bank oder aus dem Pool (als genannter Charakter, sonst der erste, #293) auf den **ersten freien Platz** des Ziel-Raids (`full` 409, wenn keiner frei ist). Erst wird der Quell-Raid ohne ihn gespeichert, dann der Ziel-Raid; scheitert das zweite, kommt der Raider zurück. Beide folgen live, wenn gepostet.
- **Vorschlag und „Freie Plätze füllen“ rechnen über alle Raids:** `proposeEventSetup` eines Raids einer Gruppe ruft `proposeGroupSetup` → `proposeSetup([alle Ids])`; jeder Raid speichert seinen Teil aus `events[]` (Gruppen, Checks), die explizite Bank bleibt bei dem Raid, dessen Setup sie hatte, der Pool ist gemeinsam; mit `keep: "placed"` bleibt in jedem Raid, wer steht. Antwort: der gefragte Raid plus `others` (die Route zieht jeden geposteten nach).
- **Freigabe, Posten, Ping, DMs, Invite je Raid** — unverändert pro Event. Die Setup-Nachricht trägt als erste Zeile **„Raid 2 von 2“** (`buildSetupMessage(…, { raidOf })`, `tr("Raid {index} of {count}")`), die DM im Kicker auch. Die Anmelde-Nachricht gibt es nur am ersten Raid; sie zeigt **„2 Raids · 20 Plätze“** (`buildEventMessage(…, { raidGroup })`); `refreshEventMessage`/`postEventMessage` eines weiteren Raids zeichnen die des ersten. Anlegen und Auflösen zeichnen sie neu.
- **Mehrere Charaktere** (#293) bleiben: `characters` am Pool/Slot, „Charakter wechseln“, `validatePlacement` gegen die Anmeldung des ersten Raids; „Anmeldung bearbeiten“ aus dem Editor eines weiteren Raids ändert die Anmeldung am ersten (`setupSignup`), das Setup des gezeigten Raids folgt.

## Leader je Raid (#1036, Epic #1033)

Jeder Raid soll **genau einen Leader** haben. Wer leiten darf, steht in den Leader-Flags (#1034, `services/roster/leaderFlags.js` › `canLead`: Version × Instanz, sofort gültig).

- **Wann die Regel gilt** (`setupInput.serverHasLeaders`): nur, wenn auf dem Server des Events (`guildId`; leer = keine Regel) jemand ein Leader-Flag hat, das die Version (`versionOfEvent`) **und** die Instanzen dieses Raids deckt (`canLead` mit den `instanceIds`; ein Gruul-Flag macht in Kara keine Regel). Ein Konto mit passendem Flag zählt für den Server, wenn es unter den Anmeldern der Raids (bzw. der Raid-Gruppe) steht, im Roster der Kategorie steht oder sich zu einem **kommenden** Event desselben `guildId` angemeldet hat (vergangene Events zählen nicht). Bauweise: erst die passenden Flag-Träger bestimmen, dann je Träger `signupsOfUser` und `getEvent` nur für dessen Treffer — kein `listEvents`, kein Vollscan. Kein Discord-Member-Fetch (hängt ohne GuildMembers-Intent); billiger Ausstieg, wenn niemand ein passendes Flag hat; Ergebnis je Version + Instanzen und Lauf gecacht; läuft nur bei Orga-Aktionen. **Ohne Flag** kommt `leaders` nicht in die Eingabe — kein `checks.leader`, kein „Leader x/1“, keine Rückfrage bei der Freigabe, alles wie vor #1036.
- **Eingabe** (`setupInput.leaderFacts`): mit Regel je Event `leaders` = die angemeldeten Konten, deren Flag die Version **und** die Instanzen des Raids deckt (ein Flag für Gruul zählt in Kara nicht); immer `instanceShort` für den Grund, `leaderUserId` = die Wahl der Orga und `raidLeadId` = die im Event eingetragene Raidleitung (`event.leaderId`). Die Regel gilt nur, wenn `leaders` ein Array ist (`model.leaderRule`) — alte Eingaben, Skripte und Golden-Fixtures ohne das Feld bleiben unverändert.
- **Vorrang** (`reasons.leaderOf`, unter den Platzierten eines Raids): Wahl der Orga (`setup.leaderUserId`) > eingetragene Raidleitung (`event.leaderId`) > erster Flag-Träger nach Anmeldereihenfolge — alles nur **mit Regel**. Mit Regel tragen Raidleitung und Wahl der Orga die Krone auch ohne eigenes Flag. **Ohne Regel gibt es gar keine Krone**: kein `leader: true`, auch nicht für die Raidleitung oder eine gespeicherte Orga-Wahl; `event.leaderId` bleibt unberührt.
- **Mindestregel** (`score.js`, nur mit Regel): ein Raid ohne Leader kostet `LEADER_MIN` = `ROLE_MIN` (30000), also wie eine fehlende Rolle, plus `LEADER_ORDER` (1000) je späterem Raid, den er vor sich hat (höchstens 9): **frühe Raids bekommen zuerst einen Leader**, fehlt einer, dann in den letzten Raids (5 Raids, 4 Leader → Raid 5 rot). Nichts wirft: `checks.leader = { count, ok, candidates }` sagt es. Ein zweiter Leader bringt nichts extra. Der Leader ist ein normaler Raider auf seinem Rollenplatz.
- **Suche** (`proposal.js`): `greedyLeaders` setzt vor den knappen Rollen in Raid-Reihenfolge (`raidGroupIndex`, Ausgangs-Raid zuerst) je Raid ohne Leader einen Kandidaten — den, der die wenigsten anderen Raids leiten könnte. Deterministisch; die lokale Suche kennt den Malus und tauscht keinen Leader weg.
- **Ausgabe** (`reasons.js`, nur mit Regel): höchstens ein Slot je Raid trägt `leader: true` mit dem Grund „Leitet diesen Raid (Kara)“. Der Property-Test (`fixtures.randomInput` mit zufälligen `leaders`/`raidLeadId`/`leaderUserId`) prüft: höchstens einer je Raid, und einer, sobald jemand platziert ist, der leiten darf.
- **„Als Leader setzen“** im Raider-Panel (`SlotTip`): nur für Raider in einer Gruppe und nur mit Leader-Regel. Ohne Flag erst eine Rückfrage (`useConfirm`). Gespeichert als `setup.leaderUserId` (`PUT /api/raids/setup` mit `leaderUserId`; `""` löscht, ohne das Feld bleibt die alte Wahl). „Neu vorschlagen“ und „Freie Plätze füllen“ behalten den gewählten Leader an seinem Platz, **ohne Schloss**: der Lauf hält ihn intern fest, `setupEditor.leaderUnlocked` nimmt danach `locked` und „Von der Orga fixiert“ wieder weg (außer die Orga hatte ihn selbst fixiert). Steht er nicht mehr in einer Gruppe, verfällt die Wahl. „Verschieben in einen anderen Raid“ gibt die Wahl beim Rollback mit.
- **„Leader-Wahl aufheben“** im Raider-Panel: nur mit Leader-Regel und nur am Leader, den die Orga gewählt hat; speichert `leaderUserId: ""`, danach bestimmt der Vorschlag den Leader wieder selbst.
- **Signatur:** `lineupSignature` hängt `|leader:<uid>` nur an, wenn ein Slot `leader: true` trägt — ein Setup ohne Leader (und jedes Setup ohne Regel) behält seine alte Signatur byte-gleich, eine Freigabe bleibt `approved`. Ein neuer Leader ist eine Änderung (Freigabe wird wieder Entwurf). `placementSignature` hängt `/lead` nur an den Platz des Leaders.
- **DM beim Leaderwechsel:** nur der alte und der neue Leader bekommen eine neue DM (ihr Platz ändert sich über `/lead`), alle anderen nicht.
- **Raidleitung im Event** (`setupEditor.leaderIdFor`, beim Speichern und bei der Freigabe): `event.leaderId` ändert sich nur, wenn die Orga im Setup ausdrücklich einen Leader gewählt hat, oder das Event keine Raidleitung hat bzw. die eingetragene nicht im Raid steht. Hat das Setup keinen Leader, bleibt `leaderId` unverändert — eine im Event-Edit gesetzte Raidleitung wird nie still durch einen Flag-Träger ersetzt. Der approved-Schnappschuss trägt `leader: true`.
- **Editor:** Krone (`CrownIcon`, `.se-lead-mark`, 16 px, Akzentfarbe, ohne Hintergrund) am Leader-Slot; im Raider-Panel steht die Krone neben dem Namen **nur**, wenn er diesen Raid leitet (`.se-tip-lead`), die Flags stehen darunter als „Kann leiten“ bzw. als Chips. „Leader 1/1“ in der Leiste und der Seitenleiste (`summaryFigures.leaderFigure`, nur mit Regel); Chip „Leader“ in „Angemeldet“ filtert auf die Kandidaten. Texte `setup.leader.*` (DE/EN, Platzhalter `{name}`).
- **Bot:** Krone im Setup-Bild (`setupImage.leaderCrown`), 👑 vor dem Namen in der Textform, DM-Zeile „Raidleitung: <Name>“ (`tr()`, de-Katalog `config/botText/de/setup.js`).
- **Tests:** `test/utils/setup/proposal.leader.test.js` (5 Raids/5 Leader/50 Anmeldungen, 5 Raids/4 bzw. 3 Leader, Vorrang, keine Krone ohne Regel, falsche Instanz, Determinismus, Laufzeit), `proposal.test.js` (Property-Invarianten), `test/services/setup/setupEditor.leader.test.js` (Wahl ohne Schloss, `leaderIdFor`, Regel nur mit Flag auf dem Server, keine Regel bei Flag nur auf anderem Server / nur in vergangenem Event / für andere Instanz, Freigabe ohne Regel bleibt `approved` mit gleichen Signaturen, Signatur), `test/services/events/raidGroup.test.js` (Rollback), `setupInput`/`setupImage`/`setupMessage`; Vitest `setup/__tests__/SetupEditor.leader.test.tsx` (aufheben, Krone im Panel, Rückfrage-Text).

## Setup im Kanal (`src/services/setup/setupMessage.js`, #290)

- **Message** (`buildSetupMessage(event, approved, { emojis })`, pure, plain API JSON, `null` without an approval): title `Setup · <Titel>`, description `<t:start:F>` plus one line of role totals in the **flat role icons** `eh_ui_tank|healer|melee|ranged` (since #320 the same ones the signup message draws; the colourful WoW `eh_role_*` are gone), one **inline field per non-empty group** (`<spec emoji> **Name**`), filled up with empty inline fields to a multiple of three (`GRID_COLUMNS`) — Discord spreads a short last row over the whole width, so without them Group 5 would sit in the middle instead of under Group 2; the signup message does the same for its two-column class blocks (`eventMessage`, `spacer(true)`), the talk overview has no inline grid —, the bench as **one** field `🪑 Bank (n)` (`Name · Name …`, clipped with "+N weitere") — **only with "Bench mitposten"** (`bench: true`, #517; the pool is never posted), a link `View the comp` (`/e/<id>/comp`: the orga lands in the setup editor, everyone else on the public event page at `#setup`, pageRoutes.eventComp), footer `Freigegebenes Setup · Stand <version>`, timestamp = approval. Der Balken trägt **dieselbe Farbe wie die Anmelde-Nachricht** (#307, `embedLook.embedColor`) — die beiden Posts stehen in einem Kanal und gehören zusammen; das Bild bleibt bei der Anmelde-Nachricht. Without app emojis the text fallbacks of `appEmojis.js` (`**Name** · Heilig`, 🛡️ 💚 ⚔️ 🏹, 🪑). Limits like the event message (≤25 fields, ≤1024 per value, ≤6000 — if too long the bench and then the groups drop their icons). A cancelled event draws only "Abgesagt: Setup · …" with the reason.
- **Setup als Grafik (Entwurf „F“, Test, Okt 2026; Schalter `setupImage` des Event-Servers, sonst `config.discordVisuals.setupImage` (#961), Standard an):** statt der Gruppen-Felder (und des Bank-Felds) trägt das Embed ein gezeichnetes Bild (`src/services/setup/setupImage.js`, rein, SVG; `buildSetupMessage(…, { image: true })`): je Gruppe ein Panel „GRUPPE 1“…, drei nebeneinander (zwei bei zwei oder vier Panels, vier ab sieben), je Raider eine Zeile mit seinem **Spec-Icon** und dem Namen in Klassenfarbe (zu lang → „…“) — **kein Spec-Text**, das Icon sagt es (Design-Canvas „Setup-Post mit Spec-Icons“, Variante C, Okt 2026). Die Antwort ist ein **großer Kreis rechts in der Zeile** (Canvas-Runde 2, Variante C, Okt 2026 — ein Abzeichen am Icon war im auf ~400 px verkleinerten 25er-Bild zu klein): grüner Haken und die Zeile leicht grün hinterlegt, rotes Kreuz mit ausgegrautem Icon und Namen, ein leerer grauer Ring solange offen (so sieht man auch, wer noch nicht geantwortet hat) — dieselben Antworten, die die Textform als Emojis zeigt. Die Icons sind eingecheckt (`assets/specs/<icon>.jpg`, dieselben zamimg-Icons wie die Spec-Emojis, geholt mit `npm run data:spec-icons` = `scripts/fetch-spec-icons.js`) und gehen als data-URI ins SVG (`utils/image/specIcons.js`; resvg lädt nichts aus dem Netz); ohne Spec das Klassen-Icon, ohne beides ein Quadrat in Klassenfarbe. Die Bank (nur mit „Bank mitposten“) ist das letzte Panel und **abgesetzt** (Runde 2, Variante A): gestrichelter Rahmen ohne Füllung, ohne Trennlinien, Namen etwas blasser, keine Antwort-Kreise; ab 9 Namen „+n weitere“. Buffs fehlen: der freigegebene Schnappschuss trägt keine. Kopf (Datum, Rollen-Summen), „Comp ansehen“, Fuß, Zeitstempel und **die Knöpfe bleiben genau wie vorher**; DMs sind unverändert, der Ping steht in der Nachricht (siehe „The ping is part of the setup message“). **Entscheidungen:** (1) keine Text-Kopie der Namen unter dem Bild — das Bild soll beurteilt werden, der Schalter holt die Felder zurück; (2) das Bild ist das **Embed-Bild** (`image.url = attachment://setup.png`), keine Components-V2-Media-Gallery: eine einmal als V2 gepostete Nachricht kann nie wieder ein Embed werden, und ausschalten muss die heutige Nachricht zurückgeben. Gepostet/bearbeitet wird mit `discordImage.withImages` (`files` + `attachments: []`, die alte Datei wird ersetzt), das PNG je Event zwischengespeichert (`setup:<eventId>`) und nur bei geändertem SVG neu gerendert; scheitert das Rendern, kommen die Felder. Abgesagt: ohne Bild (die alte Datei verschwindet).
- **"Bench mitposten" (#517):** `setupPost.bench` (off by default) — the orga's last choice, sent as `bench: true|false` with `POST /api/raids/setup/approve` and `/post` (anything else keeps the stored choice) and stored before the message is built (`postOrEditSetupMessage(eventId, { bench })`); `setupCore.benchPosted(event)` reads it for the message, the DMs (`placementsOf(approved, { bench })`), `publishView` (`bench`, `benchCount`, recipients) and the public event page. In the editor the switch **„Bank mitposten“** sits in the primary split button's menu „Beim Posten“ (`Controls.PostSplit`, no detour through „Mehr“), its state written beside the button („mit Bank“ / „ohne Bank“); it applies to the approval and to "Setup posten". A switch flipped after the post brings "Setup posten" back as the primary button (`optionsChanged`), so the change reaches the message.
- **Post vs. edit:** `postOrEditSetupMessage(eventId)` posts the first time and **edits** afterwards; where it sits is `event.setupPost` (`eventStore.setEventSetupPost`, merged: `channelId, messageId, version, postedAt/By, editedAt/By, error/errorAt, dms, told`). A message deleted in Discord is posted anew; a cancelled event only gets an existing message marked (`cancelled` otherwise). Never throws — a Discord error is stored and returned as `{ code, error }`, so an offline bot never fails the approval.
- **Posting is approving — there is no separate approval step for the orga.** The editor's bar has one button **„Setup posten“** for a draft (it calls `POST /api/raids/setup/approve`, which approves the version shown and posts); once posted the state badge reads „Gepostet · Stand n“, the bar's one button becomes „Alle pingen“ and every change goes live (see "Change after approval"). The raid detail's step says „Setup posten“ too (`raidDetailSteps.js`).
- **Hooks:** `POST /api/raids/setup/approve` awaits `publishSetup()` (message first, its failure appended to the answer's message) — not for an "already approved" repeat; `POST /api/raids/setup/post` (area `raids`, write) is the line's "Setup posten": post/edit again and send outstanding DMs — **a draft is approved first** (`approveEventSetup` with the optional `version` the editor showed, 409 `conflict` otherwise).
- **Confirm/Cancel** (`src/services/setup/setupConfirm.js`, one service for the raider's click — `setupConfirmBot.js` — and the orga): stored as `setupPost.confirmations { userId: { status: "confirmed"|"declined", at, by } }`, `by` = the raider or the orga member. **An answer is for the evening, not for one version:** it stays through every later change of the lineup; `setupCore.confirmationsFor(event, approved)` shows it for everybody standing in a group of the approved lineup (a move to another group keeps it, who left the groups has none shown and gets it back on return). The setup message draws the marks; after every change the posted message is edited (never a first post). **How fast:** a raider's click awaits the edit in the event's edit queue (`setupMessage.editSetupMessageQueued` — one edit after the other, so concurrent clicks never land out of order; the ping is left alone). The orga's marks do not wait: `POST /api/raids/setup/confirm { event, userId, status: "confirmed"|"declined"|"" }` (area `raids`, write; 409 `not_placed` outside the groups) stores and answers at once with only `{ confirmations }`, and `setupMessage.scheduleSetupEdit()` edits the message **once, `MARK_EDIT_DELAY_MS` (1.2 s) after the last of a run of clicks** (a failure lands in `setupPost.error` and the editor's line). **„Alle bestätigen“** — `POST /api/raids/setup/confirm-all { event }` → `setupConfirm.confirmAll()`: everybody in a group without an answer gets the check (`by` = the orga member); a „Cancel“ stays, the bench is no part of it; answers `{ confirmations, count }`. **In the editor** the GET gives the orga `confirmations` (`{ userId: status }`); a group slot with an answer is tinted green (`se-confirmed`, the check a small round badge on the spec icon's bottom right corner — `se-slot-tile`, like an online status, ringed in the line's colour, so the line's right stays free) or red (`se-declined`, a cross in the badge), the bench never. **Nothing on a raider's line is clickable but the line itself** (pick, drag, right click = „Anmeldung bearbeiten“): a fixed place shows a small lock (`se-lock-mark`), and the actions — **Bestätigen**, **Fixieren**, **Anmeldung** — are buttons in the raider panel (`SlotTip`'s `ActionRow`; the check only for a group place of a posted = approved setup). The panel **holds on to the raider clicked last** (`pinned` in `SetupEditor.tsx`): the pointer passing other lines on its way to the panel changes nothing; a panel action drops the pick (so the next raider clicked is picked, not swapped) but the panel stays; Esc lets go. The picked line (`se-picked`) wins over the green/red tint, the held one is framed (`se-pinned`). The check toggles confirmed ↔ none, a cancel turns into a check; marks are drawn at once and sent one after the other — a mark still on its way overrides what the answer to an earlier one says (`pendingMarks`), so quick clicks never jump back; a failed save puts the line back. „Alle bestätigen“ sits in the bar while somebody in the groups has no answer (the count is the bar's „x von y bestätigt“). **The bar** shows only „Mehr ▾“, „Alle bestätigen“ and the one primary button; everything else is under **„Mehr ▾“** (`MoreMenu` in `setup/Controls.tsx`, a portalled `Popover`; see "Layout").
- **The ping is part of the setup message** (Design-Canvas „Setup-Post mit Spec-Icons“, „Ping 3“, Okt 2026 — it saves the extra card under the message): the ping text and the mentions stand **in the embed, between the role totals and „View the comp“** (`buildSetupMessage(…, { ping })`, `pingLines`). A mention in an embed notifies nobody, so the ping is always a **new** message whose `content` carries the mentions and the text (`pingInContent`, `allowedMentions: { users }` for exactly the named ones, at most 100 and under 2000 characters) — which is what notifies — and is **edited straight away** into the embed, the content emptied (it then shows „(edited)“). The first post does that (`publishSetup` passes `setupPingPlan` to `postOrEditSetupMessage(…, { ping })`); **„Ping everyone“ / „Alle pingen“** is `setupMessage.callSetupPing`: in the event's edit queue it posts the setup anew (`repost: true`) and deletes the old message plus a ping card of the time before. Known limits (told the orga): the push notification arrives, but Discord may drop the red @ badge once the mention left the content; a member Discord does not know yet shows as an id in the embed. `setupPost.ping { inMessage: true, userIds, text, by }` is remembered; every later edit of the message (live change, Confirm/Cancel) names everybody placed now (`shownPing` → `setupPingPlan`, the pinger left out) — newcomers are named, not notified (an edit notifies nobody), who left disappears. **A ping card of the time before** (`setupPost.ping { channelId, messageIds, … }`, posted before this change as a card of its own) still follows: after a live change `refreshLiveSetup` calls `setupPing.refreshSetupPing()`, which **edits** it (`discord.editPingMessages`, `allowedMentions: { parse: [] }`); a chunk more is posted quietly, one left over deleted; a ping deleted by hand stays deleted; the same list is no edit. The next „Ping everyone“ deletes it. `eventManage`'s `refreshMessage` (cancel, reopen, move) also calls `refreshSetupMessage()`, which only edits an existing message, never posts.
- **„Ping unconfirmed“ / „Unbestätigte pingen“** (Oct 2026) is the fifth button of the row, after „Ping everyone“, and shown only while somebody in a group has neither confirmed nor cancelled (`setupCore.unansweredOf` over the marks the message shows; the bench never counts). Custom id `setup-ping:<eventId>:open`, same module and access as „Ping everyone“ (`setupPingBot.js`, the orga). Its modal is titled with how many it reaches („Unbestätigte pingen (3)“) and pre-filled with a reminder (`PING_OPEN_TEXT`, „⏳ Bitte bestätige oder sag deinen Platz im Setup ab.“) — its text is **never saved** as `setupPingText`. It runs `callSetupPing({ …, open: true })` → `setupPingPlan(…, { open: true })`: the setup is posted anew like „Ping everyone“, mentioning only who has not answered (the pinger left out, `nobody_open` when nobody is left). `setupPost.ping` carries `open: true`, so every later edit (`shownPing`) names only who **still** has not answered — the list shrinks with each Confirm/Cancel and the ping lines disappear once everybody answered. Each DM is one `card()` in the event's colour (`buildSetupDm`): kicker "Setup für <Raid>", title "Gruppe 2 als Heiler" with "Zibbo · Heilig" and the start as a fact / title "Auf der Bank" with "Diesmal **Bank** (Zibbo · Heilig) – nächstes Mal hast du Vorrang." (the bench only while it is posted, #517; the pool never gets a DM) (the Vorrang part only with fairness on) plus `Grund: …` from the proposal's bench reasons — only while the stored setup is the approved version, at most two, never a wish reason (it names other raiders) — and the link to the posted message as a button ("Zum Setup"). **Once per placement:** `setupPost.told[userId]` keeps the signature (`g2/Priest-Holy/healer` or `bench/<spec>`) of what a raider was told; a new approval writes only to those whose place changed, a failed DM is not marked and goes out again on the next run.
