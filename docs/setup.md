# Setup

Endnutzer-Sicht: siehe [guide-web-admin.md#setup-editor](guide-web-admin.md#setup-editor), [guide-discord.md#setup-gruppeneinteilung](guide-discord.md#setup-gruppeneinteilung).

## Setup-Vorschlag (`src/utils/setup/`, #262)

`buildSetupProposal(input, options)` (`proposal.js`) builds raid groups and a bench from signups, profiles, attendance, earlier setups and the orga's fixed places. **It is always only a proposal — a human approves it** (the editor, the routes and the approval: "Setup-Editor" below). Pure and deterministic: no store, no clock, no randomness; ties go by signup `at`, then user id, and the input order of the signups does not matter.

- **Input** (`src/services/setup/setupInput.js`' `collectSetupInput(eventIds)` reads it from the stores; `proposeSetup(eventIds, options)` = collect + build): `events` (`{ id, title, size, composition, requiredBuffs, fairness, wishes }` — several ids = raids that run **in parallel** and share the raiders), `signups` (signupStore shape + `eventId`), `profiles` (raiderProfileStore), `attendance` (`{ userId: pct }` from `rosterAttendance` in the event's category), `history` (`[{ eventId, startTime, placed[], bench[] }]`) and `fixed` (`{ userId, eventId, group (1-based), spec }` or `{ userId, bench: true }` — the `locked` slots of the event's current draft). Required buffs are the event's own (`event.requiredBuffs`, set in the create dialog, #261) once it was planned from a template or has any, else the category's raid template's (`config.categoryRaidTemplate`); melee/ranged go in as `{ min, max }` where the event stores a `compositionMax`. **The bench history is derived from approved setups** (`setupInput.approvedLineup()`: the `approved` snapshot, never a draft changed after it; same categories, earlier start, last 10) and never stored on its own; while none exists the stored signups stand in (signed/late = placed, "Ersatzbank" = bench), `historySource` says which.
- **Composition:** `tank`/`healer` are exact targets (min = max), a melee/ranged **number is a minimum** (0 = none, the dps fill the rest), `{ min, max }` a range. Groups hold 5, `ceil(size/5)` of them.
- **Hard rules** (`model.js` + `score.js`, a broken one scores `-Infinity`, so the search can never accept it): size, 5 per group, each raider at most once across all events, role maximums, never a spec the profile marks `gear: "none"`, never an absence, fixed places stay (a fixed raider beyond a role maximum widens it and turns the check red; a fixed place of somebody who signed off is ignored with a `warnings` entry). Role minimums and "bench signup only as a fallback" are constants far above every weight (`ROLE_MIN` 30000 per missing raider > `FILL` 10000 per placed raider > `BENCH_STATUS` 6000 > 10 × `MAX_WEIGHT` 500), so no weight setting can trade a missing healer for a nicer group — but too few healers never throws: the check goes red.
- **Options per raider:** every named character (#293, `signup.characters`, else the single one) with its signed spec (main; each option carries its `priority`, 0 = the choice) — **one place per person** stays a hard rule, so exactly one of them is placed — plus, for the first choice only, off-spec roles from the signup's `canAlso` and a stated `canOfftank/canHeal === true` of **that character** (`model.characterFlags`: the character's own switch, else the old profile-wide one), played as the class's spec for that role the profile has geared best (a feral who can tank → `Druid-Guardian`).
- **Each option carries its own character's status (#320)**, not the signup's (`model.characterStatus`): "Spät" on the first character leaves the second "Dabei", so the second is the better option and only the option that is actually placed says "Kommt später". A character without a status of its own takes the signup's. **The absence stays a matter for the whole person** — a signed-off raider has no options at all — and a person still takes at most one seat.
- **Soft goals** (`DEFAULT_WEIGHTS`, overridable via `options.weights`, 0 = off, clamped to 0…500): `partyBuffs` 60, `raidBuffs` 40, `requiredBuffs` 300, `mainSpec` 120, `preferredCharacter` 100 (a **cost** for placing a "kann auch mit" character, so raiders with one character score as before — **waived** where that character's own status makes it the more available one, `score.moreAvailableThanFirst`: the order of the characters is a preference, a status is a statement about the evening, and 100 would otherwise always outweigh the 40 that separate "Dabei" from "Spät"), `gear` 30 (ready > unknown > usable), `status` 80 (signed 1, late ½, tentative 0.3 — **per character** since #320), `fairness` 150, `attendance` 40, `wishes` 60. `fairness`/`wishes` only count where the event's flag is on (`options.fairness`/`options.wishes` override); the output's `weights` are the effective ones (0 when off). **Fairness** per raider over their last 10 nights: 0.6 if benched the last time they were in a setup + 0.4 × min(1, benches/3). **Wishes** are unordered pairs, mutual 1, one-sided ½; same group = full, same raid ⅕ (with parallel raids ½ — there the raid is what counts).
- **Nicht zusammen** (`avoid` 100, a **penalty**): pairs from the profiles' "nicht zusammen raiden mit" lists (only while a raider has it switched on, docs/roster-profile.md), one pair even when both named each other. Costs the full weight when the pair stands in the **same group** (one raid) or the **same raid** (parallel raids) — it separates, it never benches anybody on its own. **No event flag — the orga is asked:** `options.avoid === true` alone turns it on; the setup remembers the answer in `options.avoid` (`null` = never asked). The editor gets `avoidPairs` (a count, `setupEditor.avoidPairCount`) and asks once before the first proposal when it is > 0; afterwards a switch in the side column changes it (a save re-values the lineup, "Neu vorschlagen" separates). `checks.avoid` = `{ on, together, total }` — **counts only, never who named whom**, in no output and no reason.
- **Party buffs** come from the rule set (`gameVersions/buffs.js`, which gained `slot` and the setup-only `vampiricTouch`): per group each buff counts the members who want it, once per key; a buff with a `slot` (a totem element, a warrior's shout) once per provider per slot, most valuable first — a shaman drops one air totem, so Windfury + Wrath of Air in one group take two shamans. A buff everybody wants (`universal`: Blood Pact, Healing Stream) counts half and is never named as a reason.
- **Search:** fixed places → greedy (scarce roles first: fewest spare candidates, then the least flexible raider, bench signups last; then every free place with whoever adds most) → local search with strict improvements only (add, replace, switch role/event, switch role + fill the freed role, move/swap between groups, swap between parallel raids), at most `MAX_PASSES` 40. A 25-man and a 40-man from 60 signups take well under a second (tested).
- **Bench and pool (#517):** a proposal **never benches anybody by itself**. Who is in no group is split: `bench` holds only who the orga put there (`fixed: { userId, bench: true, locked? }` — every entry of the draft's bench, locked or not, `setupInput.fixedFromSetup`; `locked` only decides whether the editor shows the lock), `pool` everybody else signed up and not placed (the editor's **„Angemeldet“**, with the same reasons, e.g. "Heiler voll (6/6)"). A "Bank" signup (status `bench`) that is left over waits in the pool, marked, like everybody else — the raider's status says "I'd sit out", the bench is the orga's decision and is posted, so it only ever comes from the orga. The **fairness history** (`setupInput.setupMembers` → the approved snapshot's `bench`) therefore counts only the explicit bench.
- **Output** (JSON, stable for #263): `{ version, versionId, groups: [{ index, slots: [{ userId, character, classId, spec, role, main, status, locked, reasons[] }] }], bench: [{ …, eventIds, locked, reasons[] }], pool: [{ …same shape }], checks: { ok, size, roles: { tank: { count, min, max, ok }, … }, buffs: { ok, required[], raid[], party: [{ key, label, icon, groups[] }] }, wishes: { met, total, pairs[] } }, events: [{ eventId, title, groups, bench, checks }], weights, score: { total, parts }, warnings[] }`. `groups`/`checks` are the first (usually only) event's; with parallel raids every event has its own entry, `bench` lists who is in none, `checks.wishes` counts across all.
- **Reasons** (`reasons.js`, German, at most four): "Von der Orga fixiert", for a raider with several characters first which one and why — "1. Wahl: Zibbo" or "Mit Zibbowar als Tank statt Zibbo (Heiler voll (3/3))" / "(Tanks fehlten)" / "(kommt später)" — #320, and it comes before the other two, because the raider said it themselves — / "(passte besser in die Aufstellung)", "Zweitspec als Heiler", "Kommt später", "Gr. 2 wegen Totem des Windzorns (5 profitieren)", "Bringt als Einziger Segen der Könige" / "(Pflicht-Buff)", "War zuletzt auf der Bank – hat Vorrang", "Wunsch erfüllt: mit X (gegenseitig)", "Anwesenheit 91 %", "Eingeteilt in PuG 2"; on the bench "Heiler voll (6/6)", "Raid voll (25/25)", "Nur „Vielleicht“ angemeldet", "War zuletzt dabei", "Keine Spec mit brauchbarem Gear", "Von der Orga auf die Bank gesetzt".
- **Tests:** `test/utils/setup/` — fixtures (10/25/40 Classic), determinism, a seeded property loop over random inputs checking every hard rule, bench rotation over seven evenings, wishes (mutual beats one-sided), fixed places, too few healers, Windfury/shadow priest placement, runtime; `test/services/setup/setupInput.test.js` for the collection. Not covered yet: raid **debuffs** (the rule set has none for the setup), availability/preferred raids from the profile.

## Setup-Editor (Raid-Detail › Setup, `src/services/setup/setupEditor.js`, #263)

The proposal becomes an evening here: the orga proposes, moves, locks and **approves**. ⚠️ **The setup is only ever a proposal until someone with `raids` write approves it, and raiders never see a draft** — not through any endpoint, message or bot command.

- **Stored on the event** (`eventStore.setEventSetup`, one object): the proposal output v1 for the event (`groups`, `bench`, `pool` (#517), `checks`, `weights`, `score`, `warnings`, `historySource`; the per-event `events[]` is dropped), `status` draft/approved, `version` (bumps on every change of **who stands where** — `lineupSignature()`; a lock, a weight or the fairness switch alone keeps version and approval), `origin` proposal/manual/auto, `options { weights, fairness, wishes }` (the orga's overrides, reused by the next proposal), `updatedAt/By`, `approvedAt/By/Version`, **`approved`** (the frozen raider-facing snapshot: names, specs, roles, groups, bench — no reasons, no locks, no wishes), `changedSinceApproval`, `explanation { text, model, version, at }`.
- **Bench, pool and old setups (#517):** `setupCore.benchAndPool(setup)` is the one reader: a setup stored before #517 has no `pool`, its bench was everybody left over — there only the **locked** bench entries count as the explicit bench and the rest is the pool (`withSetupDefaults`, `fixedFromSetup`, `snapshotOf`, `lineupSignature`, `setupSummary` all go through it). Late signups (`addUnplacedSignups`) land in the pool. `lineupSignature()` includes the bench's user ids: moving somebody onto the bench or off it is a change of the lineup (new version, a draft again) — the bench is posted. The approved snapshot carries only the explicit bench, never the pool; `approvedPlacementFor` gives a pool raider `null`.
- **Change after approval:** a new lineup turns the setup back into a draft with `changedSinceApproval`; the `approved` snapshot stays, so raiders keep seeing the last approved lineup until the next approval. **Once the setup message is posted it goes live instead** (`setupEditor.postedLive`: `setupPost.messageId`, an approved snapshot, not cancelled): `storeSetup()` approves every changed lineup at once in the name of whoever changed it — a move, „Neu vorschlagen“, „Anmeldung bearbeiten“, and a draft left from before the post with the next save — and answers `live: true`; the route (`followLive` in `apiRoutes/setup.js`) then awaits `setupMessage.refreshLiveSetup()` (the message edited to the new lineup, one edit after the other per event, **no ping, no DMs** — the editor's line says „n DMs offen“ and „Setup posten“ sends them) and refreshes the event message like an approval. Confirm/Cancel stay untouched (see "Confirm/Cancel" below), the last ping's list follows (see "The ping follows the setup"). An empty lineup never goes live. A failed edit never fails the change: the answer's `message` says „Setup-Nachricht nicht aktualisiert: …“. `eventStore.saveSetupDraft()` (the automatic proposal at the signup deadline, `reminders.runAutoSuggest`) writes the same shape with `origin: "auto"` — the editor badges it "automatischer Vorschlag" — and never replaces an approved setup or a draft changed after one.
- **Manual lineups** are validated by `utils/setup/manual.js`' `validatePlacement()` (group index within the raid, ≤ 5 per group, ≤ size, nobody twice, only non-absent signups, a spec of the class of one of the named characters — the slot keeps `character`, which one plays (fixed places and `lineupSignature` include it), a role the spec can play) and valued by `proposal.js`' `evaluateSetup(input, placement, options)` — every raider fixed where the orga put them, no search, same output shape (checks, reasons, score), so a hand-made and a proposed setup read alike. Whatever only makes the setup worse (too few healers, a missing buff) is not refused — the checks go red and approving asks once more.
- **What everyone else sees** goes only through `approvedSetupOf()` (`setupCore.js`) / `approvedPlacementFor()` / `raidHelperSlots()`: the signup page's `placement` per own row, the setup message in the event channel (`setupMessage.js`, below — the event message only links to it, no inline preview), `show-mysetups`/`show-allsetups` (`utils/raidhelper.ownApprovedSetup`; `eventSources.ownSignedUpEvents` adds own events to `show-allsetups`), the sheet fill. The raid detail payload carries only `ownSetup` (counts and state, `setupSummary()`), and its setup step is done only once approved.
- **Layers (#424):** `src/services/setup/setupCore.js` is the pure bottom layer — `approvedSetupOf`, the ping text (`PING_TEXT`, `pingTextOf`), `confirmationsFor` and the button row under the setup message (`confirmButtonRow`/`inviteButtonRow`/`pingButtonRow` with their custom-id prefixes). It requires no setup module back. `setupEditor`, `setupPing`, `inviteCall` and `setupMessage` build on it; the `*Bot.js` button handlers only require downwards (`setupConfirmBot` → `setupConfirm` → `setupMessage`), never the other way round. `test/web/noCycles.test.js` keeps all of `src/` (without `web-client/`) free of require cycles (lazy requires count too).
- **API** (`apiRoutes/setup.js`, area `raids`, listed in `apiAccess.js`): `GET /api/raids/setup?event=` (a caller without write gets only `approved`, the payload has no `setup` key at all), `POST /api/raids/setup/propose` `{ event, weights?, fairness?, wishes? }` (locked places kept via `setupInput.fixedFromSetup`), `PUT /api/raids/setup` `{ event, version, groups, bench, fairness? }` (409 `conflict` on an outdated version), `POST /api/raids/setup/approve` `{ event, version }` (only the version the editor showed), `POST /api/raids/setup/explain` (background job via `evalJobs`, 400 `no_api_key` without `config.anthropic.apiKey`) and `GET …/explain?event=` (job + stored text). Discord names are resolved on the GET only — a member fetch per raider is slow where Discord does not know them, and a move must answer at once.
- **KI-Begründung** (`utils/setup/explainText.js`, same client and call shape as `recommendationText.js`): groups, bench, reasons, checks and the signup comments ("kommt 20:30") in, a few German paragraphs out. It only explains — it never moves anybody and never approves; the modal marks a text written for an older version as outdated.
- **Client:** tab "Setup" of the raid detail, only for an own event (`?tab=setup`; for a Raid-Helper event that old link still lands on the roster). `pages/raid-detail/setup/SetupEditor.tsx`: one toolbar line (see "Layout" below), group cards (party-buff icons in the head, one line per raider: spec tile, name in class colour, the spec small — plus „Tank“/„Heiler“, **never melee/ranged** (the spec says it); an off-spec tints the role where shown, else the spec —, status dot, a small lock mark in the slot's corner while fixed, so it takes no width from the name), the bench as one row under the groups, and a summary line whose "Details" holds Tanks/Heiler/DD as large numbers against the plan, a buffs badge, the fairness switch, wishes met/total ("Gewichte…" — a `Modal` with the sliders, "Neu vorschlagen" — is under „Mehr“). **Reasons live in the raider drawer only** (see "Raider tooltip" below). Under the bench the row **„Angemeldet“** (`PoolCard` in `setup/Board.tsx`, drawn like the bench, no lock, a "Bank" signup marked „Ersatz“). Moving: HTML5 drag & drop (no library) onto a group, the bench, „Angemeldet“ (`{ pool: true }` — out of the setup again) or a raider (swap; a swap with somebody in the pool puts the pool raider on the exact place and the other into the pool), or click/Enter a raider and then the target ("Hierher"/"Auf die Bank", Esc cancels). The save request has no pool — who is in neither `groups` nor `bench` is in it (`lib/setupEditor.applyLocal` redraws it at once); resizing the raid drops the bumped raiders into the pool, not onto the bench. Moves are pure in `lib/setupEditor.ts` (strippable, run for real in `test/web-client/conventions/setupEditor.test.js`), drawn at once and saved one after the other with the last confirmed version, so quick moves never trip the conflict check; approving waits for them. CSS `styles/setup-editor.css` (`se-`). Changing the dragged element inside `dragstart` cancels the drag in Chrome — the dimmed look is set a tick later.
- **Places inside a group (`pos`):** every group slot carries the place 1–5 the orga put it on, so a group of two may stand on places 1 and 5 (a free place is a drop target of its own: `FreePlace`, "Hierher 5" for the keyboard path). `validatePlacement()` keeps a valid, unused `pos`, gives every other slot the lowest free place in order and sorts by it (`manual.placeSlots()`); `saveEventSetup` → `inPlacedOrder()` stores it, `snapshotOf()` copies it into the approved lineup, and `decorateLineup()` gives a proposal or an old draft the places 1, 2, 3 … The client mirrors the rule in `lib/setupEditor.ts` (`withPlaces`, `placeGrid`; `moveRaider` takes `{ group, pos }`; a swap exchanges the places too; a drop on the group card itself still means "the lowest free place", inside the own group "to the end, places closing up"). The array order stays the place order, so every consumer that reads `slots` in order is unchanged. `lineupSignature()` ignores `pos`: a change of place alone keeps the version and an approval — who stands in which group, and in which order, is what counts.
- **Layout (redesign, October 2026): one toolbar line, the groups right under it.** `.se-bar` is ONE line (from 1200 px of viewport it does not wrap; the counts give way with an ellipsis, the buttons never): **one state badge** (`lib/setupEditor.ts`' `setupState()` — „Entwurf", „Entwurf · geändert seit dem Posten", „Freigegeben · nicht gepostet", „Posten fehlgeschlagen", „Gepostet · Stand 2 · veraltet", „Gepostet · Stand 2", plus „· DMs laufen" while they run; it can never say „Gepostet" beside „noch nicht gepostet"; what posting will do or did — the old line under the bar, `publishHint()` — and the auto-proposal note are its tooltip), the counts with words („Tanks 3 von 3 · Heiler 7 von 7 · DD 15 von 15 · 23 von 25 bestätigt", the confirmed count only once approved; places only when they are off; `setup/summaryFigures.ts`), „n fixiert" when anything is fixed, then **„Mehr ▾"**, „Alle bestätigen" (while somebody in the groups has no answer) and **one primary button** following the state: not approved → „Setup posten" (approve = post); approved but not out / failed / outdated → „Setup posten" (`POST …/setup/post`); posted and current → **„Alle pingen"** (`POST /api/raids/setup/ping { event, dryRun? }` — the web twin of „Ping everyone" under the message, `setupPing.callSetupPing`; the dry run fills the question „n Raider … werden gepingt: „<Text>"", then it posts). While a raider is picked, the counts make room for „Ziel wählen …". **„Mehr ▾"** (`MoreMenu`, entries and „sep" lines) holds everything else: Neu vorschlagen, Gruppenzahl… (the size control in a small dialog, still entered as a **number of groups** 1–8, committing `groups × 5` on blur/Enter through the same `resize`), Ping-Nachricht… (the ping text field in a small dialog, commit on blur/Enter), the switches Fairness, Wünsche, „Nicht zusammen" (only with such pairs) and „Bench mitposten" (only with a bench), „Setup posten" again when posted (pending DMs, a redraw), „DMs einschalten" (→ settings, while DMs are off), Kompakt, Suche, KI-Begründung, Gewichte…. The five groups follow at once (`minmax(188px, 1fr)`, two-line raiders, five in a row from about 1000 px of content), then **the bench and „Angemeldet" as rows** (`SlotRow`: name and count, the raiders side by side, one sentence when empty, a „Hierher" place while somebody is picked; the whole row is the drop zone), then **one summary line** (`SummaryLine`: „Buffs vollständig ✓ · Fairness an · 2 von 3 Wünschen erfüllt", „Nicht zusammen" and hints when they apply) whose **„Details"** opens the old tiles and switches (`Summary` in an `EditorDialog`). A raider (`.se-slot`) and a free place (`.se-ph`) share one row height, `--se-row` (46 px, 32 px compact), so the cards are equally tall whether a place is taken or not. `se-compact` (a switch "Kompakt" under „Mehr", **off by default**, `localStorage` `eh-setup-compact`, a per-viewer convenience) draws one-line raiders on cards of `minmax(158px, 1fr)` for small screens. Group size itself stays 5 — the proposal, validation and messages all rest on it. Checked in a real browser (dark, 1440 × 900 and 390 × 844): nothing overlaps, nothing is cut off but the counts' ellipsis on a narrow bar.
- **"Im Setup als" — a raider who plays several specs:** the raider panel's last column offers the specs of the raider's class as icon buttons (`classSpecs`, sent with every decorated person; name and role in the tooltip, the spec played now ringed). A click puts the raider into the setup as that spec — the third tank, an extra healer: `lib/setupEditor.respecRaider()` changes the slot's `spec` and `role`, keeps its place and **locks** it (so a new proposal does not undo it), saved through the usual `PUT …/setup`; the server already accepts it (`validatePlacement`: a spec of the class of one of the named characters, a role the spec can play) and counts it for the role checks — "Zweitspec als Tank" appears as the reason. Not for somebody on the bench (no slot yet: "erst in eine Gruppe ziehen"). Checked in a real browser: a retribution paladin turned into protection took the tanks from 3/4 to 4/4.
- **Suche (`src/services/setup/raidSearch.js`):** which classes and specs the raid still needs, and a message that looks for them. `suggestSearch(event)` reads the stored setup's checks: a **role** whose minimum is not met (tank / healer / melee / ranged: `missing` and the specs of that role), a **required buff** or a **raid buff** nobody brings (the specs that provide it, from `gameVersions/buffs.js`), and the **open places** (size minus the placed raiders); `specInfo` carries icon, name and class colour for the page. It comes with the editor payload (`search`, orga only, `null` without a setup) and builds the draft of the message: **English** (raiders read it), the English class and spec names (`labelEn`), a whole class that brings a buff as "Shaman (any spec)", the start as a Discord timestamp, the link to the signup message; empty text when nothing is missing. The bar's **Suche** button opens `SearchModal`: the gaps as rows (a role with its spec chips — icon, name, class; buffs grouped by the same set of specs, `lib/setupEditor.groupSearchBuffs()`), the message in an editable textarea (max. 2000 characters) and **"Im Kanal posten"** → `POST /api/raids/setup/search { event, text }` (area `raids`, write, CSRF) → `raidSearch.postSearch()`: own events only, not cancelled, needs a channel, text ≤ 2000 (Discord's limit), `discord.postNotice` (no mentions), logged on the event (`action: "search"`). Refused with a reason otherwise (`raidhelper` 409, `not_found`, `cancelled`, `no_channel`, `nothing_needed`, `too_long`, `post_failed` 502). Tests: `test/services/setup/raidSearch.test.js`, the dialog in `test/web-client/conventions/setupEditor.test.js`.
- **Editing the Suche:** the dialog works on a copy of the suggestion. Per role a `-`/`+` count (1–40, at 0 the role drops out), the role's specs as toggle chips (`suggestSearch` returns `roleSpecs` and `specInfo` for every spec), "+ role" adds one nobody was missing, and a buff row can be dropped. Every change asks `POST /api/raids/setup/search/text` (`textForNeeds`, area `raids`, writes nothing) for the English message; the server cleans what the page sends (known roles, specs of that role, known buffs). Once the orga types in the message it is no longer rewritten — "Write the text again" does that. Posting is unchanged (`POST /api/raids/setup/search` with the text).
- **Icons in the Suche message:** `buildText` puts the app emoji in front of every spec (`eh_<class>_<spec>`), of a whole class (`eh_class_<class>`, for "any spec") and of the role (`eh_ui_<role>`), as the signup message does. An emoji that is not uploaded yet is left out, the text reads the same. The dialog's text field shows the raw `<:name:id>` codes; Discord draws them.
- **Extra tank / extra healer:** "Also as" in the raider panel marks a raider in the setup who plays another role on some bosses — a third tank, a healer who is DPS on most. It offers the roles (tank, healer) the raider's class has a spec for and the setup does not use them for. The mark is `event.extraRoles` (`{ userId: ["tank", "healer"] }`, `eventStore.setEventExtraRole`), **not part of the setup**: a new proposal, a move or an approval leaves it alone. `POST /api/raids/setup/extra-role` (`{ event, userId, role, on }`, area `raids`) sets it, `GET /api/raids/setup` returns `extraRoles`; the tile shows a small "+Tank" / "+Healer" pill. It counts nowhere in the role checks — the raid plan is meant to read it. "In the setup as" stays what it was: it puts the raider in the setup as that spec.
- **Anmeldung bearbeiten (#521, `src/services/setup/setupSignup.js`):** the orga changes one raider's signup inside the editor — status, character, spec. A pencil on every raider line (an overlay left of the lock, on hover/focus; groups, bench and „Angemeldet“ alike) and a right click open `setup/SignupEditModal.tsx` (status as a `Segment`, the characters as chips only when there is a choice, the specs of the class as chips — a spec the profile lacks is dashed and, once picked, named in one hint line; rules pure in `lib/setupSignupEdit.ts`). `GET /api/raids/setup/signup?event=&user=` (`signupEditView`: the signup, the statuses, per character — the profile's, then the signup's own ones the profile lacks — every spec of its class in the event's rule set with `inProfile`) and `PUT /api/raids/setup/signup` `{ event, userId, status, character?, spec?, from? }` (area `raids`, write, CSRF; `from` = the character the setup shows, the one replaced — the signup's other characters stay). The PUT goes through `signupService.submitSignup(…, { byOrga: true, offProfile: true })`, so the signup message, the talk overview and every `onSignupsChanged` listener follow; one event log entry `signupEdit` („Anmeldung geändert (Orga)“, `Brokk · Bank → Dabei · Verstärkung → Elementar`). **The stored setup follows** (`setupEditor.saveEventSetup` with the lineup as it stands): a placed raider keeps group and place and shows the new character/spec (role from the spec — a role that no longer fits is the checks' business); a status change alone keeps an „Im Setup als“ spec; an absence takes the raider out of groups and bench (an absence is in no part of the setup, „Angemeldet“ included); raiders who signed off elsewhere are dropped the same way, since the save would refuse them. A changed lineup turns an approval back into a draft as usual; a status alone does not. The answer is the editor payload plus `message`. Tests: `test/services/setup/setupSignup.test.js`, `test/web/apiRoutes/setup.signup.test.js`, `setup/SetupEditor.signupEdit.test.tsx`, `lib/setupSignupEdit.test.ts`.
- **Attendance details in the panel** are icons, not sentences: signed icon + `attended/total` with the Auto badge or the check mark (the character link; the sentence is its tooltip), bench icon + the date of the last night on the bench ("–" for never in the nights looked at).
- **Raider drawer and drag glow:** the raider panel is `SlotTip` in `setup/SlotTip.tsx`, shown in a **side drawer that a click (or Enter) on a raider opens** (`.se-drawer`, fixed at the right edge, 440 px, scrolling inside itself; on a phone a sheet from the bottom) — nothing stands open before, hovering opens nothing; its X or Esc closes it. One column: a header (`.se-tip-top`: spec tile, the name, spec · role · Discord name · status, the actions, then the **attendance as the big number**: `AttendanceHead` with the check/"Auto" badge and the bar), then brings · why here · plays as / extra · `AttendanceDetails` (raids counted, how sure the link is, last on the bench). It shows the raider clicked last (`pinned`) and is looked up fresh each render, so a move redraws it. The read-only lineup has no panel. Content: the spec tile (no separate role icon — "Shadow · Ranged" is text), the name **always in full and on one line** (no wrap, no ellipsis — the header gives it the width), Discord name, signup status, **attendance for everybody**, the buffs the raider brings as icons, and the proposal's reasons (its own "Anwesenheit …" reason is dropped — `tipReasons()`). A reader of the approved lineup gets no attendance row.
  - **Attendance per Discord account** (`setupAttendance.js` → `rosterAttendance.attendanceForAccounts`, only on the page load — `view()` passes it on the GET, the client keeps it across the answers of moves; the proposal's own `attendance` input for the weights is unchanged). The window is the last 11 nights **of the same kind of raid** in the event's category (`comparableTo()`): a category such as "PUG Raids" runs a 10-man Karazhan night and a 25-man SSC/TK/Gruul night side by side, and somebody who only joins one must not be marked absent for the other. The kind is the raid size (10 vs. the bigger ones) — the event's own against the night's, read from its title and its logs' zones; a night whose size cannot be told counts, an event without a size counts every night of the category. A night counts when *any* character of the account stands in the log. The account's characters: the orga's assignment for the event's category and the characters of the raider's own profile (**manual**) plus the characters of the signup (**auto**). Where none is in a log, a **class guess** may still count the night: an unclaimed log player of the class the account plays, at least as many of them as accounts of that class that are missing — never over a signed-off night. `link` is `"manual"` only when a manual character stands behind it and no night was guessed; the tooltip draws a check for `manual` and an `auto` badge otherwise. No countable raid = "noch keine Raids gezählt". **Last on the bench:** the same result carries `lastBench` (start, unix seconds, of the newest earlier night the raider signed up but stood on the bench) and `benchNights` (how many nights were looked at) — from the fairness history (`setupInput.benchHistory`: approved setups, else the stored signups; the last 10 nights of the category). The attendance block ends with "Zuletzt auf der Bank: 12.09.2026", or "Nicht auf der Bank in den letzten 10 Raids"; nothing without any earlier night.
  - **Buffs and the glow** (`setupEditor.withBuffInfo`, on the draft only): every raider carries `brings` (`[{ key, label, icon, scope: "party"|"raid", count }]` — party buffs for the group they stand in with how many profit, universal buffs left out, a slotted buff once per provider; raid buffs for the whole raid) and `fit` (`{ [group]: n }` — for every other group how many would profit if they stood there). While a raider is dragged or picked, `lib/setupEditor.ts`' `suggestGroup()` glows (`.se-suggest`, a soft pulse, off with `prefers-reduced-motion`) the group **with a free place** where `fit` is highest; nothing glows where no buff helps. `fit` comes from the last server answer, so it lags one move behind the local redraw.

## Setup im Kanal (`src/services/setup/setupMessage.js`, #290)

- **Message** (`buildSetupMessage(event, approved, { emojis })`, pure, plain API JSON, `null` without an approval): title `Setup · <Titel>`, description `<t:start:F>` plus one line of role totals in the **flat role icons** `eh_ui_tank|healer|melee|ranged` (since #320 the same ones the signup message draws; the colourful WoW `eh_role_*` are gone), one **inline field per non-empty group** (`<spec emoji> **Name**`), filled up with empty inline fields to a multiple of three (`GRID_COLUMNS`) — Discord spreads a short last row over the whole width, so without them Group 5 would sit in the middle instead of under Group 2; the signup message does the same for its two-column class blocks (`eventMessage`, `spacer(true)`), the talk overview has no inline grid —, the bench as **one** field `🪑 Bank (n)` (`Name · Name …`, clipped with "+N weitere") — **only with "Bench mitposten"** (`bench: true`, #517; the pool is never posted), a link `View the comp` (`/e/<id>/comp`: the orga lands in the setup editor, everyone else on the public event page at `#setup`, pageRoutes.eventComp), footer `Freigegebenes Setup · Stand <version>`, timestamp = approval. Der Balken trägt **dieselbe Farbe wie die Anmelde-Nachricht** (#307, `embedLook.embedColor`) — die beiden Posts stehen in einem Kanal und gehören zusammen; das Bild bleibt bei der Anmelde-Nachricht. Without app emojis the text fallbacks of `appEmojis.js` (`**Name** · Heilig`, 🛡️ 💚 ⚔️ 🏹, 🪑). Limits like the event message (≤25 fields, ≤1024 per value, ≤6000 — if too long the bench and then the groups drop their icons). A cancelled event draws only "Abgesagt: Setup · …" with the reason.
- **"Bench mitposten" (#517):** `setupPost.bench` (off by default) — the orga's last choice, sent as `bench: true|false` with `POST /api/raids/setup/approve` and `/post` (anything else keeps the stored choice) and stored before the message is built (`postOrEditSetupMessage(eventId, { bench })`); `setupCore.benchPosted(event)` reads it for the message, the DMs (`placementsOf(approved, { bench })`), `publishView` (`bench`, `benchCount`, recipients) and the public event page. In the editor a switch under „Mehr ▾“, shown only while the bench has somebody; it applies to the approval and to "Setup posten".
- **Post vs. edit:** `postOrEditSetupMessage(eventId)` posts the first time and **edits** afterwards; where it sits is `event.setupPost` (`eventStore.setEventSetupPost`, merged: `channelId, messageId, version, postedAt/By, editedAt/By, error/errorAt, dms, told`). A message deleted in Discord is posted anew; a cancelled event only gets an existing message marked (`cancelled` otherwise). Never throws — a Discord error is stored and returned as `{ code, error }`, so an offline bot never fails the approval.
- **Posting is approving — there is no separate approval step for the orga.** The editor's bar has one button **„Setup posten“** for a draft (it calls `POST /api/raids/setup/approve`, which approves the version shown and posts); once posted the state badge reads „Gepostet · Stand n“, the bar's one button becomes „Alle pingen“ and every change goes live (see "Change after approval"). The raid detail's step says „Setup posten“ too (`raidDetailSteps.js`).
- **Hooks:** `POST /api/raids/setup/approve` awaits `publishSetup()` (message first, its failure appended to the answer's message) — not for an "already approved" repeat; `POST /api/raids/setup/post` (area `raids`, write) is the line's "Setup posten": post/edit again and send outstanding DMs — **a draft is approved first** (`approveEventSetup` with the optional `version` the editor showed, 409 `conflict` otherwise).
- **Confirm/Cancel** (`src/services/setup/setupConfirm.js`, one service for the raider's click — `setupConfirmBot.js` — and the orga): stored as `setupPost.confirmations { userId: { status: "confirmed"|"declined", at, by } }`, `by` = the raider or the orga member. **An answer is for the evening, not for one version:** it stays through every later change of the lineup; `setupCore.confirmationsFor(event, approved)` shows it for everybody standing in a group of the approved lineup (a move to another group keeps it, who left the groups has none shown and gets it back on return). The setup message draws the marks; after every change the posted message is edited (never a first post). **How fast:** a raider's click awaits the edit in the event's edit queue (`setupMessage.editSetupMessageQueued` — one edit after the other, so concurrent clicks never land out of order; the ping is left alone). The orga's marks do not wait: `POST /api/raids/setup/confirm { event, userId, status: "confirmed"|"declined"|"" }` (area `raids`, write; 409 `not_placed` outside the groups) stores and answers at once with only `{ confirmations }`, and `setupMessage.scheduleSetupEdit()` edits the message **once, `MARK_EDIT_DELAY_MS` (1.2 s) after the last of a run of clicks** (a failure lands in `setupPost.error` and the editor's line). **„Alle bestätigen“** — `POST /api/raids/setup/confirm-all { event }` → `setupConfirm.confirmAll()`: everybody in a group without an answer gets the check (`by` = the orga member); a „Cancel“ stays, the bench is no part of it; answers `{ confirmations, count }`. **In the editor** the GET gives the orga `confirmations` (`{ userId: status }`); a group slot with an answer is tinted green (`se-confirmed`, the check a small round badge on the spec icon's bottom right corner — `se-slot-tile`, like an online status, ringed in the line's colour, so the line's right stays free) or red (`se-declined`, a cross in the badge), the bench never. **Nothing on a raider's line is clickable but the line itself** (pick, drag, right click = „Anmeldung bearbeiten“): a fixed place shows a small lock (`se-lock-mark`), and the actions — **Bestätigen**, **Fixieren**, **Anmeldung** — are buttons in the raider panel (`SlotTip`'s `ActionRow`; the check only for a group place of a posted = approved setup). The panel **holds on to the raider clicked last** (`pinned` in `SetupEditor.tsx`): the pointer passing other lines on its way to the panel changes nothing; a panel action drops the pick (so the next raider clicked is picked, not swapped) but the panel stays; Esc lets go. The picked line (`se-picked`) wins over the green/red tint, the held one is framed (`se-pinned`). The check toggles confirmed ↔ none, a cancel turns into a check; marks are drawn at once and sent one after the other — a mark still on its way overrides what the answer to an earlier one says (`pendingMarks`), so quick clicks never jump back; a failed save puts the line back. „Alle bestätigen“ sits in the bar while somebody in the groups has no answer (the count is the bar's „x von y bestätigt“). **The bar** shows only „Mehr ▾“, „Alle bestätigen“ and the one primary button; everything else is under **„Mehr ▾“** (`MoreMenu` in `setup/Controls.tsx`, a portalled `Popover`; see "Layout").
- **The ping follows the setup:** `callSetupPing` (the first post's ping and „Ping everyone“) remembers the last ping as `setupPost.ping { channelId, messageIds, userIds, by, text }` (`discord.postMissingPing` now answers every message id of a split ping). After a live change `refreshLiveSetup` calls `setupPing.refreshSetupPing()`: the ping's messages are **edited** (`discord.editPingMessages`, `allowedMentions: { parse: [] }`) to everybody placed now, the pinger left out as before — newcomers are named, not notified (an edit notifies nobody), who left disappears. A chunk more is posted quietly, one left over deleted; a ping deleted by hand stays deleted; the same list is no edit. `eventManage`'s `refreshMessage` (cancel, reopen, move) also calls `refreshSetupMessage()`, which only edits an existing message, never posts.
- **DMs** are a switch per category: `config.categorySetupDms = { [categoryId]: true }` (off by default, only switched-on categories stored; the PATCH sends `false` so the merge can drop one), Einstellungen › Kategorien › *Setup-DMs*, not full-admin-only. `sendSetupDms()` runs in the background after the post, **one after the other** with `DM_DELAY_MS` (1.2 s) between, one run per event at a time. Each DM is one `card()` in the event's colour (`buildSetupDm`): kicker "Setup für <Raid>", title "Gruppe 2 als Heiler" with "Zibbo · Heilig" and the start as a fact / title "Auf der Bank" with "Diesmal **Bank** (Zibbo · Heilig) – nächstes Mal hast du Vorrang." (the bench only while it is posted, #517; the pool never gets a DM) (the Vorrang part only with fairness on) plus `Grund: …` from the proposal's bench reasons — only while the stored setup is the approved version, at most two, never a wish reason (it names other raiders) — and the link to the posted message as a button ("Zum Setup"). **Once per placement:** `setupPost.told[userId]` keeps the signature (`g2/Priest-Holy/healer` or `bench/<spec>`) of what a raider was told; a new approval writes only to those whose place changed, a failed DM is not marked and goes out again on the next run. The run's outcome is `setupPost.dms { status running|done, total, sent, failed[{ userId, character, error }], unchanged }`. Never for a draft or a cancelled event.
- **Editor** (`pages/raid-detail/setup/SetupEditor.tsx`; the state badge `StatusBadge` in `setup/Controls.tsx`, text pure in `lib/setupEditor.ts`' `setupState()` and `publishHint()`): the GET gives the orga `publish` (`setupMessage.publishView`: channel name, `dmsEnabled`, recipients, pending DMs, posted/outdated, error, dms). The badge's tooltip says before posting "Beim Posten: postet Setup in #kanal · DMs an 12 Raider (aus)" ("DMs einschalten" → settings is under „Mehr“); after: "gepostet 17:40 in #kanal · 22 DMs · 3 fehlgeschlagen" — failures, an outdated message ("zeigt noch Stand 1") and the rules. Not out yet, failed or outdated: the bar's primary button is "Setup posten"; posted and current, "Setup posten" again (pending DMs) is under „Mehr“. While the DMs run the page polls only `publish` every 3 s (never the lineup, so a move is not overwritten).
- **Invite callen** (`src/services/setup/inviteCall.js`, one service for web and Discord): the orga pings **groups 1–5** of the approved snapshot (never a draft; groups 6–8 and the bench wait, the caller is never pinged) in the event channel with `/w <Charakter> inv` — `discord.postMissingPing(channelId, ids, text)`, so long rosters split under 2000 characters. `<Charakter>` is the caller's own: their place in the approved setup (group or bench), else their signup's character; none = refused (`no_character`). Also refused: cancelled, no approved setup, nobody in 1–5 but the caller, another server's event. Logged on the event (`action: "invite"`, "Invite gecallt"). **Discord:** the setup message carries one button `Invite callen` (`inviteCallBot.inviteButtonRow`, customId `invite-call:p:<eventId>`; a cancelled message none) — the click answers privately with the preview (count + the line) and `Jetzt pingen` (`invite-call:c:<eventId>`) posts; the command `commands/event/inviteCallButton.js` has `accessOf: "event"`, so only the orga may. A message posted before this button existed gets it with its next edit (approval, "Setup posten", cancel/move). **Web:** "Invite callen" in the raid detail's Verwalten menu (`lib/eventManage.ts`, `state.invite` = `ownSetup.approvedAt`; also after the start, never when cancelled) → `pages/raid-detail/manage/InviteModal.tsx`, preview via `POST /api/raids/invite-call { event, dryRun: true }` → `{ count, text, groups }`, then the same call without `dryRun` (area `raids`, write; the caller is the logged-in user's Discord id).
