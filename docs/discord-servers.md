# Mehrere Event-Server plus ein Talk-Server (event servers and talk server)

Endnutzer-Sicht: siehe [guide-discord.md#was-der-bot-sonst-noch-automatisch-macht](guide-discord.md#was-der-bot-sonst-noch-automatisch-macht).

The bot can work with several **Event-Discords** at once (#251, #361 — each with its own event channels, Raid-Helper, raids), plus one **Kommunikations-Discord** (sign-up per bot, pings). Each event server can independently post its own raid overview to a channel on **any** server the bot is on — the talk server, another event server, or itself. Nothing configured = the old one-server behaviour.

- **Stored** as `config.discordServers = { eventGuilds, talkGuildId, talkPingChannelId, signupNoteChannelId }`. `eventGuilds` is a list, `[{ guildId, label, overviewGuildId, overviewChannelId }]` (settingsStore's `normalizeEventGuildEntry`/`normalizeEventGuilds`): `guildId` a snowflake or the entry is dropped, dedupe by `guildId` (first wins, capped at 10 entries), `label` a free-text name shown next to the server ("PvE", "PvP", …), `overviewGuildId`/`overviewChannelId` both set or both cleared — a half-set target posts nowhere. `talkGuildId` is cleared when it equals any configured event server (no longer a second server then). An old-shape config (`eventGuildId`/`talkOverviewChannelId`, no `eventGuilds` array yet) migrates into one entry automatically on the next read (`migrateLegacyEventGuilds`), persisted for good on the next save — no explicit migration step. `config.guildId` stays the **fallback**: `getConfig().guildId` reports the *first* configured event server, and saving one writes it into `guildId` too — so `auth.js`, `activeGuild.js` and everything else reading `guildId` follow without change.
- **Read** through `src/web/guildRoles.js`: `eventGuildIds()` (every configured event server, falling back to `[config.guildId]` when none is set), `eventGuildId()` (the first of those — kept only for the handful of call sites deliberately still scoped to "the primary event server", see below), `talkGuildId()`, `configuredGuildIds()`, `guildRole(id)` (`"event" | "talk" | ""` — tags *any* configured event server as `"event"`), `eventGuild()`/`eventGuildCards()`/`talkGuild()` (status cards: connected, member count, `permissions` from `discord.botPermissionsIn()` — null = not knowable, never "all missing"; `eventGuildCards()` additionally carries each entry's `label`, `overviewGuildId`/`overviewChannelId` and a best-effort `overviewGuildName`) and `memberOverlap()` (human members of the *first* event server also on the talk server, via `fetchGuildMembersCached`; failures come back as `error`, never thrown — not generalised to every event server, a real "N-way overlap" feature nobody has asked for yet).
- **Edited** in Einstellungen → Verbindungen → *Discord-Server* (`components/SettingsDiscordServers.tsx`, section `discordserver`, adminOnly + standalone): one card per configured event server (name, own label, connection state, its own raid-overview row once a target is set) plus the talk-server card, rights as "4 von 5" with the list in the tooltip, a "+ Event-Server hinzufügen" affordance, a dialog that PATCHes only this block — one row per event server (guild picker excluding every other picked server, a label field, its own target-server-and-channel picker), plus the unchanged talk-server fields. `GET /api/settings/discord-servers` serves the cards (`events: EventServerCard[]`, `talk`), overlap and every bot server with its text channels. `discordServers` is **full-admin-only** (`GUILD_KEYS` in `apiRoutes/settings.js`): the event servers decide whose roles count (see the admin-role check below).
- **The web server switcher stays** — it still offers every server the bot is on (the Kanäle page edits any of them through it) and only shows the role as an *Event*/*Talk* badge (`/api/session` tags `guilds[].role`).
- The Discord & Raid-Helper card no longer edits `guildId`; that moved into the dialog above, and names the *first* configured event server.
- **The admin-role check runs against every configured event server, not just one**: `auth.js`'s `computeAccess()` tries each of `guildRoles.eventGuildIds()` in turn — a member of any one of them with a qualifying role gets access (role permissions union across every server they belong to), not being a member of one is not fatal, only a `guild.fetch` failure on *every* configured server throws ("bot offline everywhere"). This is a pure broadening versus the old single-guild check: nobody who had access before loses it, but an admin who only holds a role on a *secondary* event server now gets in too, which used to be impossible.
- **Deliberately still scoped to the first/primary event server**, not generalised (#361 kept its blast radius narrow — extend these only if a real second use case shows up): role sync (`roleSync.js`), Raid-Helper retirement (`raidhelperRetirement.js`), an event series' default guild id fallback (`eventSeries.js`, only hit when no explicit guild id is already in context), the talk overview's own Raid-Helper sign-up fallback (`commands/signup/talkSignup.js`, `utils/multiSignup.js`), and `memberOverlap()` above.

**Pings, reminders and role sync across the servers (#264).** Two Discord rules shape all three: a mention only notifies someone who is on the server it is posted on, and a role mention only works on the role's own server.

- **Ping targets** (`src/web/pingDelivery.js`): "Fehlende pingen" and the Anmelde-Aufruf take `target` = `event` (default, the old single post — the route still calls `discord.postMissingPing`/`postAnnouncement` directly) | `talk` (the talk server's `talkPingChannelId`) | `both`. On the talk server raiders are mentioned one by one and only if they are there (`fetchGuildMembersCached`); an event role becomes its talk counterpart from `roleSync`, a role without one becomes user mentions. **Whoever is not on the talk server gets a DM (`sendDirectMessage`) — only for `talk`**: with `both` they were reached in the event channel already. The talk members are read *before* anything is posted, so a failure never leaves a half-delivered ping. `postMissingPing` splits mentions over several messages under Discord's 2000-character limit. The raid-detail payload carries `pingTargets` (`pingTargetInfo()`), and `pages/raid-detail/modals/TargetField.tsx` renders the "Wohin" segment only when a talk ping channel exists; the modal head says where it goes (`targetHint`).
- **Reminders** (`src/web/reminders.js`, `startReminders()` every 5 min in `server.js`): `config.categoryReminders = { [categoryId]: { missingHours, signedHours, target } }` — hours 1–168, 0 = off, a category with both off is dropped (`normalizeCategoryReminders`). Every sweep loops **every configured event server** (`guildRoles.eventGuildIds()`), so a raid category on a secondary event server gets reminders exactly like one on the first; one server's events failing to load (Raid-Helper down there) never blocks the sweep on the others, and the sweep only reports an error when *every* server failed. *missing* goes `missingHours` before `event.signupDeadline` (EventHelper's own events, #254; `raidEventGroups` passes it through when an event has one) or, without one, before the start, to the category's role holders who have not reacted; *signed* goes `signedHours` before the start to signed/late signups. **Never after the start**, a *missing* one never after the deadline. Exactly once: `reminderStore.js` (`data/settings/reminders-sent.json`) marks *before* sending, a failed send takes its mark back so the next sweep retries, a member list that cannot be read skips without marking; marks are pruned after 30 days (event ids are globally unique, so one store works across every server). Not guarded (`categoryReminders` is a plain settings key).
- **Setup proposal at the deadline** (same sweep, independent of `categoryReminders`): `runAutoSuggest()` in `reminders.js` — an own event with `autoSuggest` whose `signupDeadline` has passed, that has not started and has no `setup` yet gets `setupInput.proposeSetup([eventId])`, stored **only as a draft** through `eventStore.saveSetupDraft(eventId, proposal)` → `event.setup = { ...proposal, status: "draft", createdBy: "auto", createdAt }`. Already server-agnostic (`eventStore.listEvents("")` over every guild), unaffected by #361. Never approved here; an approved setup is never overwritten (`code: "approved"`). Marked once as kind `autoSuggest` in `reminderStore`, a failed proposal takes the mark back. ⚠️ The setup editor (#263) must store its drafts in the same shape (reuse `saveSetupDraft` or align both).
- **Role sync** (`src/web/roleSync.js`): `config.roleSync = [{ eventRoleId, talkRoleId, direction: "toTalk" | "toEvent" | "both" }]`, **full-admin-only** (`ROLE_SYNC_KEYS`), scoped to the *first* configured event server and the talk server (not generalised, see above). Runs for the one member on `guildMemberUpdate` (only when the roles changed) / `guildMemberAdd` (`bot.js`), and over everyone every 10 min (`startRoleSync()`, first run a minute after boot). ⚠️ **It only ever calls `member.roles.add` — never a remove** (decided in #250/#264; `test/web/roleSync.test.js` scans the source for it). Without "Rollen verwalten" on a target server (`botPermissionsIn`; unknowable counts as missing) it adds nothing there and reports `missingPermission`; a role above the bot's own is skipped. `roleSyncDrift()` lists who holds the synced role but no longer the source role (one-way entries only — with `both` the sync gives it straight back), **computed on read, nothing stored**.
- **UI**: under the server cards, `SettingsRoleSync.tsx` (only with a talk server: one line per pair, add/edit in a modal, drift as a badge plus a fold-out with Discord profile links, a "Recht fehlt" line) and `SettingsReminders.tsx` (one line per event category across every configured event server with "24 h vor Schluss · 1 h vor Raid", details in a modal). `GET /api/settings/role-sync` (full admin) and `GET /api/settings/reminders` serve them (the latter names a category by its name on whichever configured event server actually has it); both save through `PATCH /api/settings`. Drift is also a dashboard task (`roleDriftTask`, full admins only, links to `?section=discordserver`).

**Each event server's raid overview (#257, #361).** One bot message per configured event server that has an overview target set, listing *that server's own* upcoming raids — both sources, via `loadEventGroups(entry.guildId)` — posted wherever its `overviewGuildId`/`overviewChannelId` point (the talk server, another event server, or itself), so whoever reads that channel knows what is planned without opening the event server itself.

- **Built** by `src/web/talkOverview.js`'s `buildOverviewMessage(groups, opts)` (pure, plain API JSON, called once per configured entry with that entry's own `groups`/guild): one embed field per category (only `config.categoryIds` when set; categories ordered by their soonest raid — `loadEventGroups()` already scopes every category to its own guild, so a category id belonging to a *different* event server can never leak into another server's overview, no extra guild check needed), one line per raid — `**Titel** · Do 17.09. 19:30 · 👥 15/25 · [#kanal](https://discord.com/channels/<eventGuild>/<channel>) · Raid-Helper` (the marker only on Raid-Helper events; `15/25` = signed + late against `size`, without a size just the count). The link is a plain URL on purpose: `<#id>` does not resolve across servers. Below: the buttons *Für alle Raids anmelden* / *Mehrere Raids wählen …* (`talk-signup-all` / `talk-signup-multi`, only while an EventHelper event is listed — see "Mehrere Raids auf einmal (Bot)" in docs/signups.md), the select `talk-signup` ("Einzelnen Raid wählen …", the next 25 raids) and three link buttons (Web-Übersicht `/raids`, Meine Anmeldungen `/signups`, Mein Profil `/profile`). Discord's limits are enforced in the builder: ≤25 fields, ≤1024 per field ("+N weitere"), ≤6000 per embed (footer "+N weitere Raids in der Web-Übersicht"), ≤25 options. Nothing time-dependent goes into the payload, so its sha1 (`payloadHash`) says whether anything changed.
- **Synced** by `runSync({ repost, guildId })` (serialised — two triggers never post two messages on top of each other): with a `guildId`, only that one entry syncs, returning its single result; without one, every configured entry syncs in turn (`{ results: [...] }`) — one entry's failure never blocks another's. Per entry: unconfigured → nothing; unchanged hash → no edit; changed → `message.edit`; message deleted in Discord (10008) → posted anew; `repost` or a changed channel → the old message is deleted, a new one posted. When that server's event list could not be loaded completely (Raid-Helper down) its existing message is **left alone** rather than edited into a list without Raid-Helper events. Where each one sits lives in `src/web/talkOverviewStore.js` (`data/settings/talk-overview.json`: `{ [guildId]: { channelId, messageId, hash, postedAt/editedAt/checkedAt, error } }`, one record per event server — an old flat-shape file migrates into the first guild that reads it, once) — deliberately not in the settings config, which a PATCH would race.
- **Triggers**: `startTalkOverview()` in `server.js` — `onSignupsChanged` (debounced 3 s), a sweep every 5 min (Raid-Helper signups, raids that started; first run 30 s after boot), and `eventCreate.js` calls `scheduleOverviewSync()` after creating an event (35 s for a Raid-Helper event, which outlasts `raidEventGroups`' 30-s cache) — none of these pass a `guildId`, so every configured entry resyncs on every trigger; each entry's own hash check keeps the no-op case cheap, and the guild count is small.
- **The select** (`commands/signup/talkSignup.js`, `group: "signup"`, `defaultAccess: "everyone"`) opens the Discord signup dialog for an own event and links a Raid-Helper event into its event channel — see "Anmeldung (Bot)" in docs/signups.md. Still scoped to the first configured event server (see the "deliberately still scoped" bullet above).
- **Web**: each event-server card in Einstellungen → Discord-Server shows its own "Übersicht" row (`SettingsTalkOverview.tsx`, now a controlled component fed from one shared fetch in `SettingsDiscordServers.tsx` rather than fetching itself) once its own overview target is set — a badge "bearbeitet vor 3 Min." linking to the message, the times, any error and the target server/channel in its tooltip (`talkOverviewBadge` in `settingsLogic.ts`), and "Neu posten" (now takes that entry's `guildId`). `GET /api/settings/talk-overview` without a `guildId` returns every configured entry's status (`{ statuses }`, what the cards render); with `?guildId=` it returns one entry's status plus `preview` (the payload a sync would post now, a dry run; `?preview=0` skips it — currently unused by the frontend). `POST` requires `{ guildId, repost? }` and syncs just that one entry; both full-admin-only.
