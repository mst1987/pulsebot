# Server-Verbund (server network)

Endnutzer-Sicht: siehe [guide-discord.md#was-der-bot-sonst-noch-automatisch-macht](guide-discord.md#was-der-bot-sonst-noch-automatisch-macht).

The bot can work with several **servers** at once (#251, #361, server network #893 — each with its own event channels, Raid-Helper, raids; since #897 every server of the list is an ordinary one). Each server can independently post its own raid overview to a channel on **any** server the bot is on — another server of the list, a pure overview target, or itself. Nothing configured = the old one-server behaviour.

- **Stored (server network, #890 of epic #893)** as `config.discordServers = { servers, links }` (the Vielleicht/Absage and guild bank channels moved into `serverSettings` with #924, see "Data per server" below; an old `talkPingChannelId` is dropped, #894; `talkGuildId` is gone, #897), normalised on every read by `configSchema.normalizeDiscordServers`:
  - `servers = [{ guildId, label }]` — every server of the network, equal in rank: `guildId` a snowflake or the entry is dropped, dedupe by `guildId` (first wins), at most 10 (`MAX_SERVERS`), `label` a free-text name ("PvE", "PvP", …).
  - `links = [{ from, to, channelId, lang, versions }]` — "server `from` shows its raids on server `to` in channel `channelId`". A link counts only when `from` is in `servers`, `to` is a valid guild id and `channelId` is set — `to` need **not** be in `servers` (a pure overview target is no server: it never held raids and must not gain a raid server's rights in userAccess, reminders, category lifecycle or the guild bank); `from = to` is allowed (the overview on its own server); a repeated `from:to` is dropped (first wins). Links are made by hand in the web only; there are no external entries.
    - `lang` — `"de"`, `"en"` or `""` (default): the language of the raid list on the target; `""` falls back to the server language (`serverLang`). Anything else is stored as `""`. The link dialog (#891) suggests the target server's Discord language (`preferredLocale`, served as `guilds[].lang`).
    - `versions` — game version ids from `config/gameVersions` (`VERSIONS`: `tbc`, `classic`, `forever`) the list shows; empty = every version. Unknown ids and duplicates are dropped.
    - The raid list of the link reads both (#892, see "Each link's raid list" below). Migrated links get `lang: ""`, `versions: []`: server language, every version.
  - An old `talkGuildId` is only read as migration input: `normalizeDiscordServers` **adds it to `servers` when missing** (while fewer than 10 are listed) and never hands it out again. The start migration (`settingsMigration.migrateDiscordFederation`, #897) writes the federation shape once and drops `talkGuildId` from the file; with ten servers already listed the talk server does not fit and the migration logs a WARNUNG line.
  - **Migration on read, idempotent:** a block without a `servers` array is the old shape (`legacyServersAndLinks`): every `eventGuilds` entry becomes a server (label kept), its `overviewGuildId`/`overviewChannelId` the link `{ from: guildId, to: overviewGuildId, channelId }` (a target that is neither an event server nor the talk server stays outside `servers`), the talk server joins when missing; a config with no event server at all seeds `config.guildId` as the one server. A block that already has `servers` is only normalised — a second run changes nothing. The start migration (`settingsMigration`, `eventGuildId` → `eventGuilds`) skips blocks with `servers`. The output carries no `eventGuilds`.
  - `config.guildId` stays the **fallback**: `getConfig().guildId` reports the *first* server, and saving writes it into `guildId` too — so `auth.js`, `activeGuild.js` and everything else reading `guildId` follow without change.
  - An empty stored list still works on that fallback server, and the page lists it as a server. Adding a server to the empty list therefore keeps it in front (`configStore.mergeDiscordServers`). Before this fix (Oct 2026), adding Pulse Forever on prod saved only the new server; Pulse Fresh lost its web rights and dropped out of every server loop.
- **Read** through `src/services/discord/guildRoles.js`: `serverIds()` (every server, falling back to `[config.guildId]`), `serverLabel(id)`, `links()` (the valid links), `linkedSources(id)` (links whose `to` is this server — whose raids show here) and `linkedTargets(id)` (links whose `from` is this server — where its raids show). `eventGuildIds()` = `configuredGuildIds()` = `serverIds()`, `resolveServer({ guildId })` (a listed id, else null; without one the first server), `guildRole(id)` (`"event"` for any server, else `""`), `eventGuildCards()` (status cards: connected, member count, `permissions` from `discord.botPermissionsIn()` — null = not knowable, never "all missing"; `eventGuildCards()` additionally carries each entry's `label`, `overviewGuildId`/`overviewChannelId` from its first link and a best-effort `overviewGuildName`) and `guildOverlap(a, b)` (human members of server `a` also on server `b`, via `fetchGuildMembersCached`; failures come back as `error`, never thrown). The first server is `serverIds()[0]` — there is no `eventGuildId()`/`talkGuildId()` any more (#897).
- **The old dialog is gone (#891):** `GET /api/settings/discord-servers` no longer serves the `eventGuilds` shape, and `PATCH /api/settings` refuses a `discordServers.eventGuilds` with 400 `invalid_discord_servers` ("Veraltetes Format – bitte die Seite neu laden.") so a tab still open on the old dialog cannot overwrite links it knows nothing about. The re-derivation in `configStore.saveConfig` (`keepLinkExtras`) and `guildRoles.legacyEventGuilds` are gone (#897).
- **Edited** in Einstellungen → Verbindungen → *Discord-Server* (`pages/settings/SettingsDiscordServers.tsx`, section `discordserver`, adminOnly + standalone; design SB of epic #893): two sortable tables. **Links** come first, the main element: source → target, channel, overview status in words (badge with times and error in the tooltip, `linkStatusBadge`), language and versions in short form (`linkSummary`: "Englisch · nur TBC", "Serversprache · alle Versionen"), actions *Neu posten* and *Entfernen* (confirm). **Servers** below: the Discord name as main text with the optional label as extra title, connection status in words (`serverCardState`, the rights list in the tooltip), raid categories in words ("keine" is a normal state — such a server only shows lists), members; add (bot server picker + label) and remove (also drops the links it is the source of). The link modal: Quelle (a configured server), Ziel (any bot server), Kanal on the target, Sprache (suggested from the target's `preferredLocale`, empty = server language), Versionen as chips (empty = all) and a hint when the source has no raid category yet (the list would stay empty). The Vielleicht/Absage and Gildenbank channels sit in a table **per server** below (#924), each row with its own modal whose pickers list only that server's channels; a server without a channel there is named in a hint ("Dort postet der Bot diese Nachrichten nicht."). Every change PATCHes only its own fields (`{ links }`, `{ servers, links }`, `{ channels: { [guildId]: { signupNoteChannelId?, guildBankChannelId? } } }`); there is no `talkGuildId` any more (#897; `talkPingChannelId` is gone, #894). The PATCH checks servers and links and names what is wrong (unknown source, missing channel, duplicate `from:to`, a label over 60 characters is cut). Every server can be removed (#897 dropped the lock on the old ping server); a PATCH with only `{ servers }` that drops the source of a stored link → 400, so the normalisation cannot silently undo a save. `GET /api/settings/discord-servers` serves `{ discordServers, channels: { [guildId]: { signupNoteChannelId, guildBankChannelId } }, servers: ServerRow[], guilds (with lang and text channels), versions }`. `discordServers` is **full-admin-only** (`GUILD_KEYS` in `apiRoutes/settings.js`): the server list decides whose roles count — the roles of **every** server in `servers` count as soon as their id is entered in `adminRoleIds`, `orgaRoleIds` or `rolePermissions` (see the admin-role check below; docs/permissions.md).
- **The web server switcher stays** — it still offers every server the bot is on (the Kanäle page edits any of them through it) and only marks the configured servers (`/api/session` tags `guilds[].role`: `"event"` or `""`).
- The Discord & Raid-Helper card no longer edits `guildId`; that moved into the dialog above, and names the *first* configured server.
- **The admin-role check runs against every configured server, not just one**: `auth.js`'s `computeAccess()` tries each of `guildRoles.eventGuildIds()` in turn — a member of any one of them with a qualifying role gets access (role permissions union across every server they belong to), not being a member of one is not fatal, only a `guild.fetch` failure on *every* configured server throws ("bot offline everywhere"). This is a pure broadening versus the old single-guild check: nobody who had access before loses it, but an admin who only holds a role on a *secondary* server now gets in too, which used to be impossible.
- **Deliberately still scoped to the first server** (`serverIds()[0]`), not generalised (#361 kept its blast radius narrow — extend these only if a real second use case shows up): Raid-Helper retirement (`raidhelperRetirement.js`), an event series' default guild id fallback (`eventSeries.js`, only hit when the series carries no guild id), the raid list's Raid-Helper sign-up fallback (`commands/signup/talkSignup.js` uses the event's own guild first, `utils/signup/multiSignup.js`) and the bot command rights (`botAccess.js`).

**Pings, reminders and role sync across the servers (#264).** Two Discord rules shape all three: a mention only notifies someone who is on the server it is posted on, and a role mention only works on the role's own server.

- **Pings stay on the raid's server (#894, epic #893)** (`src/services/discord/pingDelivery.js`): there is no ping target any more — no `target` in the requests, no talk ping channel, no "Wohin" choice in the dialogs. `deliverUserPing` ("Fehlende pingen", reminders, Event verwalten, the button under the signup message) reads the raid server's member list first (`fetchGuildMembersCached`, at most `MEMBER_FETCH_MS` = 10 s), mentions whoever is there in the raid channel (`discord.postMissingPing`) and sends **everyone else a DM** (`sendDirectMessage`, `dmCard`) — the result is `{ event, mentioned, dm, membersUnreadable }`, `dmSummary(delivery)` turns it into " · 3 per DM". **Fallback without a member list:** when the fetch throws or times out (missing GuildMembers intent, a hanging first fetch), everyone is mentioned in the raid channel as before #894 and nobody gets a DM; the log gets a warning, `membersUnreadable` is set, and the web answer and the bot's „Fehlende pingen“ say „Mitgliederliste nicht lesbar, alle im Kanal erwähnt“. A reminder sent that way counts as done. The bot not on the raid's server → „Der Bot ist nicht auf dem Server des Raids.“ The Anmelde-Aufruf (`POST …/notify`) posts its role mentions straight into the raid channel (`discord.postAnnouncement`): whoever holds a raid-server role is on that server, so there is nobody to DM. The raid-detail payload has no `pingTargets`; the dialogs say where the ping goes („in #kanal“) and that whoever is not on the server gets a DM. Old `target` values (`talk`/`both`) in `categoryReminders` and `categoryAnnounce` are dropped on read, which reads as "the raid's server".
- **Pings and their DMs are cards (Oct 2026, `utils/discord/card.js`, see docs/bot-commands.md).** `discord.postMissingPing` posts kind `warn` with the mentions as the card's **first line** (`mentions` — they notify from inside the container, tried on the dev server) and the text under them, `allowedMentions: { users }` for exactly the pinged users; many mentions are split over several cards under Discord's **4000** characters of text per card, every mention whole, the text on the last card. `editPingMessages` (a setup ping card of the time before) edits into the same cards with `allowedMentions: { parse: [] }` — an old plain-text ping turns into a card on its next edit. The same path carries „Invite callen“; **the setup ping is no card any more** but part of the setup message (docs/setup.md, „The ping is part of the setup message“). A DM (`pingDelivery.dmCard`) is kind `warn` without mentions: the raid as heading, the text, the start short (`<t:…:d> <t:…:t> · <t:…:R>`, never `:F`) and **only** a link button „Im Web öffnen“ / "Open on the web" (the raid's web page) in the reader's language — no link to the channel or the signup message: a DM goes only to whoever is not on the raid server, and a link into that server leads them nowhere. Reminder texts use the short start too.
- **„Fehlende pingen“ under the signup message** (`src/services/events/missingPingBot.js`, `commands/event/missingPingButton.js`, customIds `event-missing:<eventId>[:go|:no]`): the orga's button under the own event's signup message (before the deadline in a row of its own under the select — „Anmelden“ fills the status row —, after it at the end of the status row), drawn **only when the category has raider roles or a roster** (`config.categoryRoles`, `eventMessage.hasRaiderRoles` → `expectedRaiders.hasExpected`, #658) and only while signing up still makes sense (open or past the deadline, not started, not cancelled or closed). Everyone sees it — a component cannot be hidden per viewer —, the click is `/event`'s (`accessOf: "event"`, checked by `botAccess.guardInteraction` before the handler; a raider gets the router's refusal). An orga click answers **ephemerally** with a preview card: who is missing (`missingPing.findMissingRaiders` — the same derivation as the raid detail and Event verwalten: the expected raiders without a reaction — with a roster its core and trial members, else the role holders, `services/roster/expectedRaiders.js`), the count, the first 25 names and „+N weitere“, buttons *Jetzt pingen* / *Abbrechen*; nobody missing → an ok card „Alle haben reagiert“; no roles, started raid, unreadable member list → an error card with the reason. *Jetzt pingen* first replaces the preview by a card without buttons, then posts through `pingMissingRaiders` (raid server plus DMs; re-derived, so whoever signed up meanwhile is spared), logs `action: "ping"` on the event and says „N Raider gepingt“. **Against a double ping:** one ping per event at a time (in process), and a ping logged on the event (this button or Event verwalten) in the last 2 minutes refuses another one („Schon gepingt … von …“).
- **Reminders** (`src/web/events/reminders.js`, `startReminders()` every 5 min, started by `jobs.js`): `config.categoryReminders = { [categoryId]: { missingHours, signedHours } }` (sent through `deliverUserPing`: the raid's server, a DM for whoever is not there) — hours 1–168, 0 = off, a category with both off is dropped (`normalizeCategoryReminders`). Every sweep loops **every configured server** (`guildRoles.eventGuildIds()`), so a raid category on a secondary server gets reminders exactly like one on the first; one server's events failing to load (Raid-Helper down there) never blocks the sweep on the others, and the sweep only reports an error when *every* server failed. *missing* goes `missingHours` before `event.signupDeadline` (EventHelper's own events, #254; `raidEventGroups` passes it through when an event has one) or, without one, before the start, to the expected raiders who have not reacted (a category with a roster: its core and trial members, #658; else the category's role holders); *signed* goes `signedHours` before the start to signed/late signups. **Never after the start**, a *missing* one never after the deadline. Exactly once: `reminderStore.js` (`data/settings/reminders-sent.json`) marks *before* sending, a failed send takes its mark back so the next sweep retries, a member list that cannot be read skips without marking; marks are pruned after 30 days (event ids are globally unique, so one store works across every server). Not guarded (`categoryReminders` is a plain settings key).
- **Setup proposal at the deadline** (same sweep, independent of `categoryReminders`): `runAutoSuggest()` in `reminders.js` — an own event with `autoSuggest` whose `signupDeadline` has passed, that has not started and has no `setup` yet gets `setupInput.proposeSetup([eventId])`, stored **only as a draft** through `eventStore.saveSetupDraft(eventId, proposal)` → `event.setup = { ...proposal, status: "draft", createdBy: "auto", createdAt }`. Already server-agnostic (`eventStore.listEvents("")` over every guild), unaffected by #361. Never approved here; an approved setup is never overwritten (`code: "approved"`). Marked once as kind `autoSuggest` in `reminderStore`, a failed proposal takes the mark back. ⚠️ The setup editor (#263) must store its drafts in the same shape (reuse `saveSetupDraft` or align both).
- **Role sync per server pair** (`src/services/discord/roleSync.js`, #896): `config.roleSync = [{ fromGuildId, fromRoleId, toGuildId, toRoleId, direction: "toTarget" | "toSource" | "both" }]`, **full-admin-only** (`ROLE_SYNC_KEYS`). `toTarget` gives the role on `toGuildId` to whoever holds the role on `fromGuildId`, `toSource` the other way, `both` both. Any two servers of `servers` can be paired — they must differ, **no link between them is needed**; a pair naming a server outside `servers`, the same server twice or a missing role is dropped on read and on save (`configSchema.normalizeRoleSync` with `roleSyncContext`), so removing a server from the list drops its pairs.
  - **Migration on read:** an old entry `{ eventRoleId, talkRoleId, direction }` becomes `fromRoleId`/`toRoleId` with `fromGuildId` = the first server of `servers` and `toGuildId` = the old `talkGuildId`; `toTalk` → `toTarget`, `toEvent` → `toSource`. Without a talk server, or with the talk server being the first server, the old entry is dropped (it never ran then either). The start migration (`migrateDiscordFederation`, #897) persists the pairs before `talkGuildId` leaves the file; `roleSyncContext` still reads a stored talk id as migration input.
  - Per pair: the bot's "Rollen verwalten" is checked on the server the pair writes to, the drift (`roleSyncDrift()`, groups carry `guildId`/`sourceGuildId`/`guildName`/`sourceGuildName`) and the member overlap (`guildRoles.guildOverlap(a, b)`, the pair sorted, served as `overlaps`) are computed per pair. `lastRun.missingPermission` is a list of guild ids. `pingDelivery.mapRoles(roleIds, config, fromGuildId, toGuildId)` maps an event role through the pairs of exactly that server pair.
  - Runs for the one member on `guildMemberUpdate` (only when the roles changed) / `guildMemberAdd` (`bot.js`), and over everyone every 10 min (`startRoleSync()`, first run a minute after boot). ⚠️ **It only ever calls `member.roles.add` — never a remove** (decided in #250/#264; `test/services/discord/roleSync.test.js` scans the source for it). Without "Rollen verwalten" on a target server (`botPermissionsIn`; unknowable counts as missing) it adds nothing there and reports `missingPermission`; a role above the bot's own is skipped. `roleSyncDrift()` lists who holds the synced role but no longer the source role (one-way entries only — with `both` the sync gives it straight back), **computed on read, nothing stored**.
- **Roster roles and the role sync (#656):** the rosters give and take their Discord roles (`services/discord/memberRoles.js`, the only module that removes a role, and only roster roles — docs/roster-profile.md "Roster und Discord-Rollen"). The role sync stays add-only, so **a roster role mirrored to the other server of a pair is not removed there** when the tool takes it on the roster's server (it turns up in the drift list). The other way round, a roster role the sync *gives* from the other server comes back after the tool takes it, as long as the person holds the source role — and with it the person returns to the roster. `GET /api/rosters/sync` reports both cases per role as `mirrored` (`outgoing` / `incoming`, each with `side` `"from"`/`"to"` of the pair since #896) for the Abgleich tab's hint.
- **UI**: under the server cards, `SettingsRoleSync.tsx` (always mounted, #896: one line per pair "Server @Rolle → Server @Rolle" with the member overlap, add/edit in a modal with a server select and a role picker per side — changing a server clears its role, the same server twice blocks saving —, drift per pair as a badge plus a fold-out with Discord profile links, a "Recht fehlt" line naming the servers; with fewer than two servers it says so and offers no add button) and `SettingsReminders.tsx` (one line per event category across every configured server with "24 h vor Schluss · 1 h vor Raid", details in a modal). `GET /api/settings/role-sync` and `GET /api/settings/reminders` (both full admin, #957: the reminders list every server's categories) serve them (the latter names a category by its name on whichever configured server actually has it); both save through `PATCH /api/settings`. Drift is also a dashboard task (`roleDriftTask`, full admins only, links to `/settings/all?section=discordserver`). The section lives on the full-admin page *Alle Server › Einstellungen* (`/settings/all`, #957); `categoryReminders` is a full-admin key (`REMINDER_KEYS` in `FULL_ADMIN_KEYS`).

**Wie aktuell die Mitgliederliste ist (Okt 2026).** Every page that needs "who is on the server / who holds role X" (raid detail attendance and „Fehlende pingen“, roster and its Discord sync view, member search, dashboard drift, settings overlap, bot command access) reads the full member list through `discord.fetchGuildMembersCached(guildId, guild)` — one `guild.members.fetch()` per guild, capped at 25 s. It is served **stale-while-revalidate**:

- under **60 s** old (`MEMBERS_CACHE_TTL_MS`): as it is;
- **60 s – 30 min** (`MEMBERS_STALE_MAX_MS`): at once, and one refresh starts in the background — the page never waits for Discord; a failed refresh is logged and the old list stays;
- older, or nothing yet: the caller waits. Parallel callers (the cold first fetch included) share one fetch per guild, so a burst of pages or the raid detail's parallel reads cost one.
- **`{ fresh: true }`** waits for a list fetched now (or joins the running fetch): only the two jobs that *write* roles from the list use it — the role-sync sweep (`roleSync.runRoleSync`) and the roster reconcile (`rosterRoleSync.reconcile`), both every 10 minutes, which keeps the shared list warm for the pages too. „Fehlende pingen“ deliberately does not: it must ping exactly the raiders the page just showed, and a second full fetch is what once pushed it past the proxy's 60 s.
- **What can be old:** role changes reach the cached members in place through the GuildMembers intent (`GUILD_MEMBER_UPDATE` patches the same `GuildMember` objects), so a role given or taken shows up within the gateway's lag. Joins and leaves show up with the next refresh: normally at the second page view after a minute, at worst 30 minutes later (no page view and no job). `guild.members.cache` itself is not served — after a reconnect or without the intent it silently holds a partial list.
- At **bot start** (`ClientReady` in `bot.js`) `discord.warmGuildMembers(configuredGuildIds())` fetches the configured servers in the background.

**Links in overviews (#537).** "Links dürfen nicht kaputt sein." Every link an overview writes goes through `src/services/discord/linkCheck.js`: `channelLink`/`messageLink`/`eventLink` (Discord), `webLink`/`webTarget(kind, id)` (web: `event`, `comp`, `calendar` only for an own event that exists, `raidplan` only for a published plan, `signup`, `setup`) and `externalLink` (sheet, softres: stored and `https?://`). Channel state: the bot's cache is authoritative while it is online (every guild channel is cached), else `checkChannel()` asks Discord (10003/10008/50001/404 = missing) and keeps the answer 5 min; **bot offline = the last state known in this process, nothing known = no link** (a missing link costs a click, a dead one trust). `src/services/discord/linkWatch.js` hooks `channelDelete` and the raw `MESSAGE_DELETE(_BULK)` packets (no `Partials.Message`, #430): a deleted channel is missing at once, its own events get the log entry "Kanal in Discord gelöscht", the overviews redraw (1.5 s); a deleted signup message is posted anew, a deleted setup post is forgotten, a deleted overview message is reposted by its sync. The web lists get `channelState` per row (`linkCheck.withChannelState`, raids, past raids, dashboard, history, raid detail) and `lib/discord/discordLinks.ts` links the post only on `"ok"`. The raid plan post follows its share (`syncRaidplanPost` after `POST /api/raidplan/publish`: new token in, withdrawn share out). `test/services/discord/linkCheck.guard.test.js` keeps `discord.com/channels/` out of every other file in `src/` (client: only `lib/discord/discordLinks.ts`). A missing channel of an own upcoming raid is a dashboard task with "Kanal neu anlegen" — see docs/channels.md.

**Each link's raid list (#257, #361, #890, #892).** One bot message **per link** (`from` → `to`), listing the source server's own upcoming raids — both sources, via `loadEventGroups(from)` — in the link's channel on its `to` server (another server, or itself), so whoever reads that channel knows what is planned without opening the source server. Two links of the same source (say PvE → PuG and PvE → PvE) get two messages, each in its own language and with its own version filter. `talkOverview.overviewEntries()` turns every link into a sync entry `{ key: "from:to", legacyKey, from, to, guildId: from, label, overviewGuildId: to, overviewChannelId, lang, versions }`; `linkWatch` (a deleted list message) and `botMessages` (the Discord overview's list of the bot's messages) read the same entries.

- **Built** by `src/services/talk/talkOverview.js`'s `buildOverviewMessage(groups, opts)` (pure, plain API JSON, called once per link with its source's `groups`) as an **agenda by day** (design D3, Oct 2026, no emojis):
  - **Title** „Kommende Raids“, on another server than the source „Raids von PvE“ (the source's label, else its Discord name); the description says the list updates itself and, cross-server, that channel links lead to the source server.
  - **One field per day**, the heading in server time (Berlin, „Donnerstag, 17. September“ / „Thursday 17 September“); a day over 1024 characters continues in a field without a heading. Raids in start order across every category (only `config.categoryIds` when set — `loadEventGroups()` already scopes every category to its own guild, so no category of another server can leak in).
  - **Each raid two lines:** `<t:…:t> · **[Titel](/e/<id>)** · SSC + TK 25`, below small (`-#`): version (only when more than one is listed), category, `Leitung <name>`, `2 Tanks, 5 Heiler, 18 DD`, `25 Anmeldungen`, the channel, `Raid-Helper` on Raid-Helper events. The time is a Discord timestamp (every reader sees their own zone), the title links the public event page only for an own event and only with a real `PUBLIC_BASE_URL`. Instance = the short names from the instance list plus the size, left out when the event names none. **The lead is a name from the source server's member cache** (`cachedLeaderName`, never a fetch — 1 vCPU, no 120-s wait without the GuildMembers intent); not cached = left out, never a mention. Counts = the single Discord accounts on signed + late (`capacity.accountCount` with `attendance.signupStatus`, each account once by its first attending entry; role from the stored role, else the spec's, else Raid-Helper's `roleName`; a signup with none of these — „Late“, an unknown spec — counts in the signups but in no role, never as DD). A further raid of a raid group (#811) is not listed, the evening shows by its first raid.
  - **Cancelled** raids (#288) stay until their day: `<t:…:t> · ~~Titel~~ · abgesagt`, below version, category, channel; never offered for signup.
  - **Channel** as a plain URL on purpose (`<#id>` does not resolve across servers), on another server with the server named: `[#do-ssc](…) auf PvE`. **Only a channel that exists is linked (#537):** the line asks `linkCheck.channelInfo()` (see "Links in overviews" above) — a deleted channel reads „Kanal fehlt“ without a link, a channel nothing is known about yet its bare `#name`; `currentPayload()` confirms every listed channel with `linkCheck.checkChannels()` before it builds.
  - **Space:** ≤25 fields, ≤1024 per field, ≤6000 per embed (80 reserved for the footer); when the raids do not fit, the **latest** fall away and the footer says „+N weitere Raids in der Web-Übersicht“.
  - **Languages:** the frame (title, description, day headings, buttons, footer) speaks `link.lang`, else `serverLang`; each raid's two lines speak its category's language (`eventLang`, PuG categories English). Catalogue `config/botText/de/talk.js`. The hash (`payloadHash`) covers the payload and the frame language.
  - **Versions:** `link.versions` filters the raids by their stored version (empty = every version), on top of `hideOtherVersions`.
- **Below the list:** the button *Mehrere Raids wählen …* (`talk-signup-multi:<source server>`, only while an EventHelper event is listed — see "Mehrere Raids auf einmal (Bot)" in docs/signups.md; *Für alle Raids anmelden* is gone since #904; its old button only says so), the select `talk-signup` ("Einzelnen Raid wählen …", the next 25 raids) and three link buttons (Web-Übersicht `/raids`, Meine Anmeldungen `/signups`, Mein Profil `/profile`). Discord's limits are enforced in the builder: ≤25 fields, ≤1024 per field ("+N weitere"), ≤6000 per embed (footer "+N weitere Raids in der Web-Übersicht"), ≤25 options. Nothing time-dependent goes into the payload, so its sha1 (`payloadHash`) says whether anything changed.
- **Signing up from a partner's list (#904):** the list on the target server signs up straight away — members of the target who are not on the raid's server may, as long as the category asks for no raider role (an open PuG); a raid with raider role refuses as on its own server (`checkRaiderRole` reads the raid's server; not on it = no roles = refused). After „Gespeichert“ the bot checks once whether the member is on the raid's server; if not, the answer adds „Tritt dem Server **<Name>** bei, sonst bekommst du keine Pings und Infos.“ plus the link button *<Name> beitreten* when the link has an invite (#905), otherwise the line alone. See "Hinweis für Nicht-Mitglieder" in docs/signups.md.
- **Grouped per game version (#743):** TBC and Forever run on the same Discord server, so the version never comes from the server. `upcomingGroups()` reads the stored version of each raid (`versionOfEvent`) and, as soon as more than one version is listed, the raid's small line names it first (`Forever · Montag · …`, short name from `events/versionTag.js`). Raids of a hidden version (`hideOtherVersions`) are left out; one list per version is a link with `versions` set (#892) — two links of the same source into two channels. The same rule holds for reminders (`web/events/reminders.js`), "Fehlende pingen" (`events/missingPing.js`) and the subscription calendar (`web/pages/calendarFeed.js`, optional `?version=` on `/r/cal/user/<token>.ics`): hidden versions are skipped. Raid posts carry their version as a small label (event embed footer, `kicker` of the missing-ping and setup cards).
- **Synced** by `syncOverview({ repost, key | guildId })` (serialised — two triggers never post two messages on top of each other): with a `key` (`"from:to"`) only that link syncs, returning its single result (`unconfigured` when there is no such link — a `key` never falls back to another link of its source, neither here nor in `currentPayload` or `GET /api/settings/talk-overview`, which answers an unknown key with 400); `guildId`, the older form, means the first link of that source; without either, every link syncs in turn (`{ results: [...] }`) — one link's failure never blocks another's. Per link: unconfigured → nothing; unchanged hash → no edit; changed → `message.edit`; message deleted in Discord (10008) → posted anew; `repost` or a changed channel → the old message is deleted, a new one posted. When that server's event list could not be loaded completely (Raid-Helper down) its existing message is **left alone** rather than edited into a list without Raid-Helper events. Where each one sits lives in `src/stores/talkOverviewStore.js` (`data/settings/talk-overview.json`: `{ ["from:to"]: { channelId, messageId, hash, postedAt/editedAt/checkedAt, error } }`, one record per link) — deliberately not in the settings config, which a PATCH would race. **Migration (#892):** before #892 the record sat under the source's guild id. `overviewKeys(links)` names each link's `legacyKey` — the source id, but only for the **first** link of that source — and `getOverviewState(key, { legacyKey })` moves such a record to `from:to` on its first read (the old key is deleted; an existing `from:to` record wins). So the message posted before the update is **edited on, not posted anew**; a second link of the same source posts its own. An even older flat-shape file migrates into the first key that reads it, once. **Orphaned lists (#892):** a link that is removed or gets another source or target (a new key) leaves a record without a link; the full sync (no `key`/`guildId`) then deletes that message and drops the record (`pruneOrphans`, `listOverviewKeys`/`removeOverviewState`; a message or channel already gone counts as deleted, any other failure keeps the record for the next sweep and warns; the result carries `pruned: [keys]`). Guarded: only with the bot online, after a clean read of `config.json` (`configStore.readStored()` has a `discordServers` block — a missing or broken file reads as defaults and must never look like "every link removed") and with at least one link. So removing the **last** link leaves its message standing. Records that may still migrate (keyed by the source alone, or the flat shape) are never listed.
- **Triggers**: `startTalkOverview()` (started by `jobs.js`) — `onSignupsChanged` (debounced 3 s), a sweep every 5 min (Raid-Helper signups, raids that started; first run 30 s after boot), and `eventCreate.js` calls `scheduleOverviewSync()` after creating an event (35 s for a Raid-Helper event, which outlasts `raidEventGroups`' 30-s cache) — none of these pass a `guildId`, so every configured entry resyncs on every trigger; each entry's own hash check keeps the no-op case cheap, and the guild count is small.
- **The select** (`commands/signup/talkSignup.js`, `group: "signup"`, `defaultAccess: "everyone"`) opens the Discord signup dialog for an own event and links a Raid-Helper event into its event channel — see "Anmeldung (Bot)" in docs/signups.md. A Raid-Helper event without its own guild id falls back to the first configured server (see the "deliberately still scoped" bullet above).
- **Web**: the links table in Einstellungen → Discord-Server shows each link's raid-list status from one shared fetch (`linkStatusOf` matches by the link's `key` = `from:to`, so two links of the same source each show their own status; no fallback to the source) as a badge in words linking to the message, the times and any error in its tooltip, and "Neu posten" per row (`repostTalkOverview(linkKey(link))`, sends `{ key, repost: true }`). The former per-card row `SettingsTalkOverview.tsx` is folded into that table (#891). `GET /api/settings/talk-overview` without a parameter returns every link's status (`{ statuses }`, each with `key`, `from`, `to`, `lang`, `versions`, message and times); with `?key=from:to` (or the older `?guildId=`, the source's first link) one status plus `preview` (the payload a sync would post now, a dry run; `?preview=0` skips it). `POST` takes `{ key | guildId, repost? }` and syncs just that link — 400 „Keine Verknüpfung angegeben.“ without either, „Für diese Verknüpfung ist keine Raid-Liste eingestellt.“ for an unknown one; both full-admin-only.

## Data per server: settings and assignment (#917, epic #926)

The groundwork for keeping loot, logs and settings strictly per Discord server.

- **`config.serverSettings = { [guildId]: { key: value } }`**: settings per server. `configSchema.normalizeServerSettings` keeps only the blocks of servers in `discordServers.servers`, of pure link targets (`links[].to`) and of the home server (`config.guildId`, for installs without a server list). Only the keys in `SERVER_SETTING_DEFAULTS` are allowed; parts 4–8 of the epic add theirs (#921: `logChannels`, docs/logcheck.md; #924: see below). An empty block stays empty; every other config field is left alone.
- **Saving**: `configStore.saveConfig` merges `serverSettings` per server and per key (`configSchema.mergeServerSettings`, like `versionSettings`): a save that sends the block of one server leaves the blocks of the other servers untouched, a save without `serverSettings` keeps them all.
- **Reading** only through `services/discord/serverSettings.serverSetting(guildId, key, { config, fallback })`. Order: the server's value, else `fallback`, else the part's default. There is no global fallback: one server's value never answers for another.
- **First server** = `discordServers.servers[0]`, else `config.guildId` (`serverOf.firstServerId`).
- **Server of a raid** (`serverOf.guildOfEvent`): `event.guildId`; for Raid-Helper events without a `guildId` the server of their category (from `category-names.json`). `logcheck/matchableEvents.loadMatchableEvents` stamps the server it loads for on every row. Loot belongs to a server through its raid; only a raidless bucket stores the server it was imported on (#919, rule in docs/loot-import.md „Loot je Discord-Server“).
- **Server of a log** (`serverOf.logGuild`): rule *linked raid → origin server → first server*.
  - Stored in `log.guildId`.
  - `guildFrom` names the rule that applied: `event`, `channel` (the origin server) or `first`.
  - `postGuildId` holds the **origin server**: the server the log was posted in or added on, with or without a channel. Before #917 `guildId` was exactly that server for every log; `saveLog` keeps writing it for new logs.
  - The first server applies only to a log that knows no server at all; a log without a channel whose raid is gone keeps its origin server.
  - A log still linked to a raid that can no longer be found keeps the raid's server.
- **Linking at once**: `logStore.linkEvent(id, { …, guildId })` moves the log to its raid's server right away (`guildId`, `guildFrom: "event"`, the origin server stays in `postGuildId`); without a known raid server the log's server stays as it is. `unlinkEvent` falls back to the origin server at once, else to the first server. Every caller (`/api/cla` log-link and automatch, `logAutoLink`, `manualLog`) passes the raid's server through `matchableEvents.eventLinkFields`.
- **Start run** `settingsMigration.migrateLogGuilds`: recomputes every log by the rule on each start and writes only on a change, followed by the line „logs.json: N Log(s) ihrem Discord-Server fest zugeordnet (#917)“. The server list is only read.
- **Active server of a web request**: still only `web/http/activeGuild.activeGuildFor(req)`.
- **Raid categories per server** (`services/events/categoryGuild.js`, prod incident 2026-10-27): `config.categoryIds` stays one global list; the settings page shows and saves only the active server's part. A category counts as deleted only when its server is **proven and configured** and the bot sees that server — a server missing from `servers` makes its categories "Server unklar", never deleted and never closable. Details: docs/events.md "Which server a category belongs to".
- **Armory/log links and realm per server (#923)**: `serverSettings[<guildId>].versionOverrides`, field by field over `versionSettings` (Einstellungen → Server → Links & Realm) — see docs/game-versions.md.
- **Raid-Helper per server (#927)**: `serverSettings[guildId].raidhelper = { enabled, serverId, apiKey }`, off by default; own key, own synced list and own daily budget per server, a 429 pauses only that server. A server without Raid-Helper sends no request and offers only EventHelper. Details and migration: [raidhelper-retirement.md](raidhelper-retirement.md).

### Applications, defaults and channels per server (#924)

- **Channels and roles — strictly per server:** `applicationChannelId`, `officerRoleId`, `raidDefaults` (`{ channelId }`), `signupNoteChannelId`, `guildBankChannelId`. Read through `services/discord/serverDefaults.js` (one server each, a snowflake or `""`). There is **no global value and no cross-server fallback**: a server without a channel posts nothing there and raises no error.
- **Bot language — global default plus an own value:** `config.botLanguage` (top level) is the default for every server, new ones included; `serverSettings[id].botLanguage` is a server's optional own value. `botLanguage.serverLang(config, guildId)` reads own value → default (`defaultLang`) → `de`; **without a `guildId` it is the default** (never the first server's own value) — so is `langOf` without a server and `categoryLang` for a category whose server is unknown.
- **Who uses which server:** `/apply` posts to the application channel and pings the officer role of the server it was typed on (no channel there → the answer says so); the raid defaults and the language follow the raid's or the interaction's server (`eventLang`, `langOfInteraction`: own choice > Discord language > that server); a Vielleicht/Absage note goes to the channel of the raid's server (a category's own channel first, docs/signups.md); the guild bank's orga channel and the organizer's guild bank part follow the server of the organizer or the bank. `botCheck` checks the rights per server.
- **Web:** Einstellungen › Server (group "server", subtitle = the active server) edits Raid-Standardwerte, Recruitment and the bot language of the **active** server; `PATCH /api/settings` gets them only when changed (the client's `serverDefaultsChanges`) and writes them into `serverSettings[active]` (no active server → 400 `no_active_server`; the client toasts "Bitte erst oben einen Server wählen"). The bot language card is the switch "Eigener Wert auf <Server>" (`ui/OwnValue`) with "Standard verwenden": `botLanguage: null` drops the own value. Without an active server the card edits the global default — a body with `botLanguage` then writes the top-level default, also when it carries other keys of the form such as `categoryIds` or `raidhelper` (saved as usual, `raidhelper` keeps its first-server fallback); writing the default is **full admins only** (403 otherwise). Without a server, `botLanguage: null` and channels, roles or raid defaults still get 400 `no_active_server`. GET sends `botLanguage` (effective), `botLanguageDefault` and `botLanguageOwn`. They are `SERVER_SCOPED_KEYS`: the client sends `serverSettingsGuildId`, a tab left on another server gets 409 `server_switched` (docs/logcheck.md). The two channels are edited per server on the Discord-Server page (above).
- **Start migration** (`settingsMigration`, synchronous, idempotent): the old global `applicationChannelId`/`officerRoleId` go to the server that owns the channel/role, else to the first server; `discordServers.signupNoteChannelId`/`guildBankChannelId` to the channel's own server, else **to the first server only** (the other servers stay empty and show "no channel"; a channel of one server never lands on another). The old global `raidDefaults` channel goes to the server that owns it, else to the first server (a non-snowflake is dropped). The old global `botLanguage` stays as the **default**; servers get no own value from it and existing own values stay. Afterwards the global channel/role fields are removed; without any known server they stay untouched.

## Raid-Übersicht je Kategorie (`/createoverview`)

Eine Karte je Kategorie, die die kommenden Raids der Kategorie zeigt und sich selbst aktuell hält — die Kategorie-Variante der Raid-Liste einer Verknüpfung oben. Entwurf „C“ (Okt 2026), ohne Knöpfe.

- **Aufbau** (`src/services/events/raidOverviewPanel.js`, rein, ein Components-V2-Container in der Akzentfarbe): Überschrift = Kategoriename; darunter die Raids **gruppiert nach Raid-ID** (Sperrwoche Mittwoch bis Dienstag, `src/utils/time/raidId.js`): „Diese ID“ (laufende), „Nächste ID“, sonst „ID“, dazu die Spanne „Mi 14.10. – Di 20.10.“. Je Raid drei Zeilen: `Sa 18.10. · **Titel** · <t:…:t> · <t:…:R>`, dann `<#Kanal> · geleitet von <@Leiter>`, dann klein die Füllung: „17 / 25 angemeldet“, „10 / 10 voll · Warteliste offen“ (nur bei `overflow: waitlist`) oder „Anmeldung geschlossen“ (Anmeldung vom Orga geschlossen oder Frist vorbei); ohne Größe (Raid-Helper) nur „17 angemeldet“. Gezählt wird wie überall `talkOverview.attendingCount`. Abgesagte und schon begonnene Raids fehlen, Raids einer ausgeblendeten Spielversion auch. Grenzen: höchstens 3 IDs und 15 Raids (`MAX_IDS`, `MAX_RAIDS`), der Text bleibt unter 3700 Zeichen, der Rest steht als „+n weitere Raids“. Fuß: „Aktualisiert sich selbst · letzte Änderung <t:…:t>“.
- **Grafik (Entwurf „C2“):** jeder Raid ist eine *Section* mit dem Zonenbild als Thumbnail — das eigene Bild des Events (`lookOf(event).url`), sonst das Zonenbild der Instanzen wie in der Anmelde-Nachricht (`ruleSetLook(...).art`; Raid-Helper-Zeilen ohne `instanceIds` lesen sie aus dem Titel über `raidContentIds`). Ohne Bild (oder ohne https-Adresse) ein schlichter Text. Vor der Füllzeile ein Balken aus fünf App-Emojis (`eh_ui_barg`/`baro`/`barn`/`bare`): so viele Segmente gefüllt wie die Anmeldungen die Plätze füllen (mindestens eins, sobald jemand dabei ist), grau unter einem Drittel, grün dazwischen, orange wenn voll, der Rest leer; ohne Emojis 🟩🟧⬜▫️. Raid-Helper-Zeilen ohne Größe: kein Balken. Kleine Icons `eh_ui_time` vor der Uhrzeit, `eh_ui_leader` vor dem Leiter, `eh_ui_date` vor der ID-Überschrift. Die Emojis stehen im Hash — kommen sie später hinzu, zeichnet sich die Nachricht neu. **Komponenten:** eine Section mit Bild zählt 3 (Section, Text, Thumbnail), ein Raid ohne Bild 1; `raidOverviewPanel` zählt gegen Discords 40 mit und kürzt mit „+n weitere Raids“ (praktisch etwa 10 Raids mit Bild).
- **Wochenleiste als Bild (Entwurf „D“, Test, Okt 2026; Schalter `config.discordVisuals.overviewWeekStrip`, Standard an):** jede ID beginnt mit einem gezeichneten Bild statt ihrer Überschriftszeile (`src/services/events/raidWeekStrip.js`, rein, SVG): „NÄCHSTE ID“/„DIESE ID“/„ID“ mit Spanne, darunter sieben Tageskacheln Mi…Di (Wochentag kurz, Tageszahl groß, Sprache der Kategorie). Ein Tag mit Raid bekommt einen Rahmen in der Füllfarbe (grün, orange voll, grau unter einem Drittel — dieselbe Regel wie der Emoji-Balken), die Startzeit des ersten Raids, je Raid ein Kürzel aus den Instanz-Kurznamen („HYJAL + BT“, „KARA“; ohne Instanz der Titel in Großbuchstaben; ein langes Kürzel wird erst kleiner, dann mit „…“ gekürzt) und einen dünnen Füllbalken; zwei Raids am Tag stehen untereinander, ab dem dritten „+n“. In der laufenden ID sind vergangene Tage abgeblendet, heute ist violett markiert. Das Bild ist ein Components-V2-**Media-Gallery**-Eintrag `attachment://raid-id-<n>.png` mit Alt-Text (die Raids als Text, ≤ 1024 Zeichen); **ein Bild je ID** (höchstens 3), es kostet so viele Komponenten wie die ersetzte Überschriftszeile (2 mit Trenner), die 40er-Grenze ändert sich also nicht. Die klickbaren Raid-Zeilen darunter bleiben unverändert. Der **Hash** umfasst die SVGs (das Bild kann sich ändern, wenn der Text gleich bleibt — z. B. wandert die Heute-Markierung einmal am Tag); die Fußzeit steht nie im Bild. Gerendert wird nur bei geändertem Hash, das PNG je Nachricht im Speicher gehalten (`services/discord/discordImage.js`, siehe „Gezeichnete Bilder“ unten). Aus = die Textform von vorher beim nächsten Sweep.
- **Raid-ID-Zwilling:** `utils/time/raidId.js` ist das Backend-Gegenstück zu `src/web-client/src/lib/raids/raidId.ts` (Berlin, Reset-Stunde 5: ein Raid am Dienstag 23:30 oder Mittwoch 03:00 gehört noch zur Vor-ID). `test/utils/time/raidId.test.js` hält Konstanten und Logik gleich (es führt die TS-Funktionen aus und vergleicht zwei Jahre, Zeitumstellung inklusive).
- **Sprache:** die der Kategorie (`botLanguage.categoryLang`) — PuG-Kategorien englisch, sonst die Serversprache (Standard Deutsch). Katalog: `config/botText/de/raidOverview.js`.
- **Daten:** `loadEventGroups(guildId)` (beide Quellen, Raid-Helper nur über den zentralen Sync und seinen Cache, nie eine eigene Anfrage). Lässt sich die Liste nicht vollständig laden, bleibt die Nachricht unverändert.
- **Gemerkt** in `stores/raidOverviewStore.js` (`data/settings/raid-overviews.json`): `{ guildId, channelId, messageId, categoryId, hash, lastChange }`, mehrere je Kategorie (je Kanal eine). `/createoverview` (`commands/setup/createOverview.js`) postet die Karte und merkt sie; liegt im selben Kanal schon eine Übersicht dieser Kategorie, wird diese neu gezeichnet statt einer zweiten.

Der nächste Lauf zeichnet sie neu. Ein Kanal, der sich nicht lesen lässt, wird übersprungen; ein Server gilt erst als durchsucht, wenn alle Kanäle gelesen wurden (sonst nächster Sweep wieder).

- **Übersicht des ganzen Servers** (`/createoverview scope:server`, Okt 2026): eine Karte mit den Raids **aller Raid-Kategorien dieses Servers** — gedacht für einen öffentlichen Kanal wie `📋》raid-overview` auf dem PuG-Server, der in irgendeiner oder keiner Kategorie liegen darf. Ohne `scope` (oder `scope:category`) bleibt alles wie oben.
  - **Inhalt** (`raidOverview.currentServerContent`): alle Gruppen aus `loadEventGroups(guildId)` mit einer Kategorie (lose Raids ohne Kategorie fehlen), ohne Raid-Gruppen-Zwillinge (`raidGroupId`), ohne Raids, deren Kategorie zu einem anderen Server gehört (`serverOf.guildOfEvent`; unbekannter Besitzer bleibt drin), mit denselben Filtern (ausgeblendete Spielversion, abgesagt, begonnen) und Grenzen (3 IDs, 15 Raids, 40 Komponenten). Die Wochenleiste zeigt alle Raids.
  - **Aufbau:** Überschrift `## Raids` (`tr`), die zweite Zeile je Raid beginnt mit dem Kategorienamen ohne Emoji (`plainCategoryName`): `40er · <#Kanal> · led by <@Leiter>`. Die Kategorie-Variante ist byteweise unverändert (gleicher Hash, Test).

Sie steht neben einer Kategorie-Übersicht im selben Kanal, ohne sie zu ersetzen. `adoptExisting()` übernimmt sie nie als Übersicht der Kategorie ihres Kanals (sie ist schon gemerkt). Sweep, Anstoß, Hash und „gelöscht = vergessen“ wie oben.

Web: Einstellungen → Raid-Standardwerte → „Bilder in Bot-Nachrichten“ (`pages/settings/DiscordVisualsCard.tsx`, im Entwurf der Seite): mit aktivem Server die Schalter unter „Eigener Wert auf <Server>“ (aus = der Standard gilt, Zeile nennt die eingeschalteten Bilder), ohne Server der Standard selbst (nur Voll-Admins). `PATCH /api/settings { discordVisuals }` nimmt nur bekannte Schlüssel als Boolean; mit Server für diesen Server, `null` entfernt die eigenen Schalter; ohne Server der Standard (Rechte: [permissions.md](permissions.md)). `GET` liefert `discordVisuals` (was der aktive Server zeichnet), `discordVisualsDefault` und `discordVisualsOwn`. Lesen: `serverSettings.serverVisuals(guildId)` bzw. `discordImage.visualOn(config, key, guildId)` mit dem Server der Nachricht (Raid-Übersicht: Server der Kategorie, Setup und Titelbild: `event.guildId`). Aus = die Textform ab der nächsten Neuzeichnung der Nachricht.
- **Zeichnen:** die Bauer liefern ein SVG als Text (rein, testbar), `src/utils/image/svg.js` (Escaping, Text, Rechtecke, dunkle Palette wie Discord: Grund `#1a1b26`, Flächen `#232533`, Text `#f2f3f5`/`#9aa0b4`, grün `#3ad07a`, orange `#f0b232`, violett `#8e7cf0`), Textbreiten aus der Schrift selbst (`src/utils/image/fontMetrics.js` liest `cmap`/`hmtx` der TTF), damit Namen vor dem Rand mit „…“ enden.
- **Rendern:** `src/services/discord/discordImage.js` mit `@resvg/resvg-js` (seit diesem Test eine Laufzeit-Abhängigkeit) und **nur der mitgelieferten Schrift** `assets/fonts/NotoSans-Regular.ttf` / `-Bold.ttf` (Noto Sans, SIL Open Font License, `assets/fonts/OFL.txt`; auf Latin + Latin-Erweiterungen gekürzt, Umlaute und Akzente drin), `loadSystemFonts: false` — der kleine Linux-Server zeichnet genau wie ein Entwicklerrechner. Ein Zeichen ohne Glyphe (Emoji im Namen) fällt weg. Je Schlüssel (Nachricht + Bildname) bleibt das letzte PNG mit dem Hash seines SVGs im Speicher (höchstens 60), die Renderzeit steht im Debug-Log (`[discordImage] … rendered in … ms`). Gemessen: Wochenleiste ~20 ms, Setup 25er ~40 ms, 40er ~60 ms.
- **Anhängen:** ein Bauer gibt `images: [{ name, svg }]` mit; `withImages(payload, { key })` macht daraus discord.js-`files` und `attachments: []` — beim Bearbeiten ersetzt das die alte Datei, statt eine zweite anzuhängen; ohne Bild entfernt es eine alte. Klappt das Rendern nicht (z. B. fehlt das resvg-Binary), wird die Nachricht in Textform gezeichnet und einmal gewarnt.

## Discord-Übersicht (Daten und API, Okt 2026)

Eine lesende Übersicht je Server der Serverliste (`guildId`) für den Discord-Bereich im Web: wer neu ist oder gegangen ist, ob der Bot hat, was seine Funktionen brauchen, ob seine festen Nachrichten noch stehen, und wie aufgeräumt die Rollen sind. Hier stehen Daten und API; die Oberfläche ist der Reiter *Übersicht* unter *System › Discord* (docs/channels.md, `DiscordOverviewPage.tsx`).

- **API:** `GET /api/discord/overview?guildId=<id>[&fresh=1]` (`src/web/apiRoutes/discordOverview.js`), Bereich `channels`, nur lesen. Erlaubt ist nur ein Server aus `discordServers.servers` (`guildRoles.resolveServer`, über `src/web/http/serverQuery.js`); ohne Angabe gilt der erste, ein unbekannter → 400 `unknown_guild`. Ein alter Link mit `?side=talk` landet auf dem ersten Server (#897, der Parameter wird nicht mehr ausgewertet). Antwort `{ guildId, online, members, botCheck, messages, hygiene }`, die Form steht im Kopf der Datei. Der Bot-Check prüft je Server nur, was dort eingerichtet ist; ob ein Server Raids hat, ergibt sich nur lesend aus echten Quellen (erster Server der Liste, Events mit Kategorie in `eventStore`, eine konfigurierte Raid-Kategorie, die auf diesem Server liegt), nie aus der Liste aller bekannten Kategorien. Die wählbaren Server liefert `GET /api/discord/servers` (Bereich `channels`, lesen: `{ guildId, name, label, online, iconUrl }`); dieselbe `guildId`-Regel gilt für `/api/discord/roles`, `/members`, `/tab-counts` und `/api/role-messages/options`.
- **Neu und gegangen** (`members`): `guildMemberAdd` / `guildMemberRemove` in `bot.js` → `services/discord/memberActivity.js` → `stores/memberActivityStore.js` (`data/settings/member-activity.json`). Nur konfigurierte Server, keine Bots, der Listener wirft nie. Gemerkt: Server, Nutzer, Anzeigename, Zeit, `join`/`leave`, beim Gehen die Rollen (ohne @everyone). 14 Tage, höchstens 2000 Einträge (`KEEP_DAYS`, `MAX_ENTRIES`), aufgeräumt bei jedem Schreiben. Die API liefert die letzten 7 Tage, neueste zuerst, je Eintrag `relation`: offene Roster mit Status (`rosterStore`) und die Zahl der Charaktere (aus `memberRelation.js`: Profil, offene Roster und Zuordnungen aller Kategorien, je Spielversion und Name einmal — ein gleichnamiger TBC- und Forever-Charakter zählt zweimal, ein Name ohne Version nur, wenn er sonst fehlt; seit der Mitglieder-Seite zählen auch Roster-Charaktere, die nur im Roster stehen); wer `channels` lesen darf, sieht das (docs/permissions.md). Braucht den GuildMembers-Intent; ohne ihn kommen die Ereignisse nicht an. **Lücke beim Gehen:** der Bot hat kein `Partials.GuildMember` (und bekommt hier keins dazu) — wer geht, ohne im Mitglieder-Cache zu stehen (etwa kurz nach einem Neustart, bevor die Liste geladen ist), löst kein `guildMemberRemove` aus und fehlt in der Liste.
- **Bot-Check** (`services/discord/botCheck.js`): eine Tabelle `BOT_FUNCTIONS` „Funktion → Rechte“ (Kanäle, Posts, Reaktionen, Rollen, Mitglieder-Intent, Server-Events, Bewerbungs-Threads, Message-Content-Intent; die drei letzten nur auf der Event-Seite, sonst `not_needed`). Je Funktion `ok` / `missing` / `unknown` (Bot offline; Intents sind trotzdem bekannt) mit den einzelnen Rechten. Dazu die eingestellten Kanäle der Seite (Bewerbungen, Log-Kanäle, Gildenbank, Addon-Zentrale …) mit `ok` / `missing` (Rechte im Kanal fehlen, mit Namen) / `channel_missing` / `not_set` / `unknown`; ein Kanal zählt zu dem Server, auf dem er liegt — liegt er auf einem dritten Server (etwa einem weiteren Server der Liste), fehlt er in beiden Seiten, statt als „Kanal fehlt“ zu erscheinen. Getrennt davon `rolesAboveBot`: Rollen, die der Bot vergibt (offene Roster, Probe-Rolle, Rollen-Abgleich, Rollen-Nachrichten der Seite, Ping-Rolle der Addon-Zentrale) und die auf oder über seiner höchsten Rolle stehen (`memberRoles.roleBelowBot`, also `comparePositionTo`) oder von einer Integration verwaltet werden. Ebenso getrennt `pugRolesGranting`: Onboarding-Rollen aus `config.pugRoles`, die noch ein altes Recht haben (#930, unten). Die Rechte selbst bleiben in `REQUIRED_BOT_PERMISSIONS` (`discord.js`), die Tabelle liest nur.
- **Feste Bot-Nachrichten** (`services/discord/botMessages.js`): Orga-Zentrale, Raid-Zentrale, Raid-Übersicht, Raid-Übersicht im Talk (liegt auf dem Ziel-Server `to` des ersten Links der Quelle), Rollen-Nachrichten der Seite, Addon-Zentrale, Rekrutierung — je Eintrag Art, Titel/Kategorie, Kanal, Link und Status `ok` („steht“), `deleted`, `channel_missing`, `no_access` (dem Bot fehlt im Kanal „Kanal ansehen“ oder „Nachrichtenverlauf lesen“, vorab über `permissionsFor` geprüft, oder Discord antwortet 50001/50013/403), `unknown` (Bot offline, Zeitlimit, Discord antwortet nicht oder mit 5xx). Geprüft im Kanal des Bot-Caches (erst der Nachrichten-Cache, sonst `messages.fetch`, höchstens 4 gleichzeitig); der Link nur für eine stehende Nachricht über `linkCheck.messageLink`, eine gefundene Nachricht wird dort wieder verlinkbar (`linkCheck.messageFound`). Jede Antwort wird 10 Minuten **je Nachricht** gemerkt, `unknown` nie; eine neue Nachricht in der Liste wird sofort geprüft. Eine Prüfung endet nach 5 s (`CHECK_MS`), was bis dahin nicht geantwortet hat, ist `unknown`. `fresh=1` fragt Discord für jede Nachricht der Seite neu — der Knopf dafür ist also nicht kostenlos.
- **Rollen-Hygiene** (`services/discord/roleHygiene.js`), nur Zahlen: Rollen gesamt (ohne @everyone und Integrationsrollen), leer, über dem Bot, mit heiklen Rechten (Administrator, Server/Rollen/Kanäle verwalten, Bannen, Kicken, @everyone erwähnen, Webhooks, Timeout, Nachrichten/Spitznamen/Events/Threads verwalten, Audit-Log ansehen — die eine Liste `SENSITIVE`, die auch die Rollen-Seite nutzt; „Ausdrücke verwalten“ zählt bewusst nicht); „über dem Bot“ über `comparePositionTo` mit seiner höchsten Rolle. Es wird **nie** ein Member-Fetch gemacht (1 vCPU, siehe GuildMembers-Intent); „leer“ ist `null`, solange der Mitglieder-Cache nicht vollständig ist. Offline → `known: false`, alle Zahlen `null`.
- **Tests:** `test/stores/memberActivityStore.test.js`, `test/services/discord/memberActivity.test.js`, `botCheck.test.js`, `botMessages.test.js`, `roleHygiene.test.js`, `test/web/apiRoutes/discordOverview.test.js`, die Listener in `test/bot.test.js`.

## Einladungen je Verknüpfung und Herkunft (PuG-Server, #905)

Jede Verknüpfung `from → to` kann eine eigene, dauerhafte Einladung auf ihrem Quell-Server `from` haben (`maxAge 0`, `maxUses 0`, `unique`); der Partner-Server `to` gibt sie weiter. Wer über sie beitritt, kam von diesem Partner. Dazu kann jeder Server eine **allgemeine Einladung** ohne Verknüpfung haben (für Nicht-Mitglieder im Web, #907). Code in `src/services/discord/pugInvites.js`.

- **Schnittstelle:** `inviteUrlForLink("from:to")` und `generalInviteUrl(guildId)` lesen nur den Store, synchron, und geben `https://discord.gg/<code>` oder `""`. Erzeugen (`ensureLinkInvite`, `ensureGeneralInvite`) und Neu-Erzeugen (`regenerateLinkInvite`, `regenerateGeneralInvite`) sind async.
- **Nur auf Knopfdruck:** Einladungen entstehen nur über „Erzeugen“ in der Verknüpfungs-Tabelle bzw. im Server-Dialog — nie beim Start und nie beim Speichern einer Verknüpfung. **Neu erzeugen** speichert erst die neue und löscht dann die alte — eine schon geteilte alte Einladung führt danach ins Leere (das Web fragt vorher nach).
- **Abgleich** (`reconcileInvites`, beim `ready`, beim Öffnen der Einstellungsseite und alle 10 Minuten): Eine Einladung, die jemand auf Discord gelöscht hat, wird als `deleted` markiert und **nicht** von selbst neu erzeugt; die Seite zeigt „Einladung gelöscht – neu erzeugen?“ mit dem Knopf „Erzeugen“. Findet der Abgleich den Code dagegen auf Discord, leert er einen alten Fehler am Eintrag (etwa von einem gescheiterten Klick). Lesefehler (fehlendes Recht, Discord nicht erreichbar) loggt er je Server und Fehlerart einmal als Warnung, danach nur noch als Debug. `inviteCreate` / `inviteDelete` beschleunigen das nur, Discord schickt sie nur mit „Kanäle verwalten“, um das der Bot nicht bittet.
- **Lebenszyklus:** Wird eine Verknüpfung oder ein Server entfernt, löscht der nächste Abgleich die zugehörige Einladung auf Discord und den Eintrag im Store (der Entfernen-Dialog sagt das vorher). Schlägt das Löschen auf Discord fehl, wird der Eintrag trotzdem entfernt (nur Log-Warnung); ist der Bot gar nicht mehr auf dem Server, steht das als Info im Log. Derselbe Abgleich leert den Einladungs-Kanal entfernter Server (auch ohne Einladung) und löscht die Herkünfte entfernter Verknüpfungen. Entfernt die Orga die letzte Verknüpfung, wird deren Einladung genauso gelöscht. **Schutz:** Hat `config.json` selbst keine brauchbare Serverliste (Datei fehlt oder ist unlesbar, kein Block `discordServers`, `servers` kein Array), löscht der Abgleich gar nichts — keine Link-Einladung, keine allgemeine Einladung, keinen Einladungs-Kanal, keine Herkunft —, denn `getConfig()` liefert dann still die Standardwerte (Serverliste nur `GUILD_ID`, keine Verknüpfungen), und das sähe aus wie „alles entfernt“. Er warnt einmal im Log, bis die Datei wieder sauber gelesen wird. Eine gespeicherte **leere** Liste zählt dagegen als brauchbar: Die Orga hat den letzten Server entfernt (oder eine Installation ohne Liste hat gespeichert, `saveConfig` schreibt dann `servers: []` – derselbe Zustand). Der Abgleich löscht dann die Link-Einladungen und Herkünfte; die allgemeine Einladung und der Einladungs-Kanal des Rückfall-Servers (`guildId`, nach dem Entfernen der zuletzt erste Server) bleiben, denn auf ihm arbeitet der Bot weiter.
- **Kanal der Einladung:** je Server einstellbar (Server-Dialog, „Kanal für Einladungen“, `POST /api/settings/pug-invites/channel`); leer = Systemkanal des Servers, sonst der oberste Textkanal. Gilt für neu erzeugte Einladungen.
- **Rechte auf dem Quell-Server:** „Einladung erstellen“ (`CreateInstantInvite`) zum Erzeugen und **„Server verwalten“** (`ManageGuild`) — nur damit liefert Discord die Einladungen mit ihren Nutzungszählern, und damit löscht der Bot eine alte. Fehlt eines, steht das als Fehler an der Verknüpfung („Dem Bot fehlt das Recht …“); erzeugt wird dann nichts. Der Bot-Check (`botCheck.js`, Funktion „Einladungen“) prüft beide Rechte auf jedem Quell-Server einer Verknüpfung und auf jedem Server mit einer gespeicherten Einladung — schon bevor die erste erzeugt ist.
- **Intent:** `GuildInvites` (nicht privilegiert, kein Portal-Schritt) liefert `inviteCreate` / `inviteDelete` (siehe Abgleich); der Beitritt selbst kommt über `guildMemberAdd` und braucht wie oben den GuildMembers-Intent.
- **Herkunft:** gezählt wird nur auf Servern mit mindestens einer gespeicherten Einladung des Bots. Der Bot hält die Nutzungszähler ihrer Einladungen im Speicher (beim Abgleich gelesen). Beitritte eines Servers werden gesammelt und gemeinsam ausgewertet: ist **genau ein** Zähler gestiegen, und zwar um so viele, wie Beitritte warten, kamen alle über diese Einladung; ist sie die Einladung einer Verknüpfung, wird sie mit `linkKey` als Herkunft gespeichert. Ein Beitritt über die **allgemeine** Einladung wird nicht gespeichert — sie wird nirgends ausgewertet (Datensparsamkeit). Beitritte, die eintreffen, während die Zähler gelesen werden, kommen mit in denselben Vergleich (Discord zählt sie dort womöglich schon); steigen die Zähler dann um weniger, als Beitritte warten, bleiben alle unbekannt und der nächste Vergleich beginnt neu, damit ein erst später gezählter Beitritt nicht dem nächsten Mitglied zugeschrieben wird. Alles andere (kein, mehrere oder anders gestiegene Zähler, fremde Einladung, nicht lesbar, Verknüpfung inzwischen entfernt) → Herkunft unbekannt, und **unbekannt wird nicht gespeichert**. **Bekannte Grenze des Zählverfahrens:** Kommt das Gateway-Event eines Beitritts erst *nach* der REST-Antwort an, in der Discord ihn schon mitgezählt hat, gehört sein Anstieg zum falschen Vergleich. Kam der wartende Beitritt z. B. über eine Vanity-URL (kein Zähler) und der verspätete über eine Link-Einladung, wird der wartende fälschlich der Verknüpfung zugeschrieben, der verspätete bleibt unbekannt. Das Fenster ist klein und wird bewusst nicht abgefangen. Keine Bots. Gespeichert in `memberOriginStore` (`data/settings/member-origins.json`); je Server und Mitglied zählt die **erste** bekannte Herkunft, sie bleibt auch nach dem Verlassen stehen.
- **Web:** `GET /api/settings/pug-invites` (Bereich `settings`, stößt vorher den Abgleich an) liefert je Verknüpfung Einladung, Fehler, `deleted`, **Beigetreten** (Herkünfte mit diesem `linkKey`) und **davon angemeldet** (davon mit einer Anmeldung zu einem Event des Quell-Servers, Abwesenheit zählt nicht), dazu je Server die allgemeine Einladung und den Kanal. `POST /api/settings/pug-invites` mit `{ key }` oder `{ guildId }`, optional `regenerate: true`. Oberfläche: Verknüpfungs-Tabelle und Server-Dialog in *Einstellungen › Discord-Server* (`SettingsDiscordServers.tsx`).
- **Tests:** `test/stores/discordInviteStore.test.js`, `test/stores/memberOriginStore.test.js`, `test/services/discord/pugInvites.test.js`, `test/web/apiRoutes/pugInvites.test.js`, die Listener in `test/bot.test.js`.

## Rollen & Onboarding (PuG-Server, #906)

Auf einem PuG-Server richten sich neue Mitglieder über das **Discord-eigene Onboarding** selbst ein: „Which versions do you play?“ vergibt eine Versionsrolle, die die PuG-Kategorien dieser Version sichtbar macht; „Which classes do you play?“ eine Klassenrolle in Klassenfarbe. Der Bot legt das nicht von selbst an: das Web zeigt Soll und Ist, eine Vorschau „Das ändert sich in Discord“, und erst der Knopf „In Discord übernehmen“ schreibt. Nur Voll-Admins (Bereich `settings`, `full: true`).

- **Nur auf PuG-Servern:** je Server der Schalter „PuG-Server“ im Dialog „Server bearbeiten“ (`config.discordServers.servers[].pug`, gespeichert nur als `pug: true`; fehlt das Feld, ist er aus — keine Migration). Nur markierte Server erscheinen in der Serverwahl des Abschnitts und in `firstPugServer`; ist keiner markiert, zeigt der Abschnitt nur den Hinweis „Kein PuG-Server …“. Für einen nicht markierten Server liefert die Übersicht `notPugServer: true` (die Seite zeigt denselben Hinweis), Übernehmen antwortet 409 `not_pug_server`. Offene Kategorien, Einladungen und Partner-Listen hängen **nicht** am Schalter.
- **Wo:** Einstellungen › Discord-Server, je Server ein Abschnitt „Rollen & Onboarding“ (`pages/settings/PugOnboardingPart.tsx`). API `GET /api/discord/pug-onboarding?guildId=&categories=` (Übersicht; ohne `guildId` der erste markierte Server mit PuG-Kategorie, sonst der erste markierte Server; ist keiner markiert, der erste Server der Liste mit `notPugServer: true`) und `POST /api/discord/pug-onboarding { guildId, categoryIds, fingerprint }` (übernehmen), `src/web/apiRoutes/pugOnboarding.js`; Logik `src/services/discord/pugOnboarding.js`. `guildId` nur aus der Serverliste (`serverQuery.js`, sonst 400 `unknown_guild`).
- **PuG-Kategorien:** die eingestellten Raid-Kategorien (`botCheck.configuredRaidCategories`), die auf diesem Server liegen und für die sich **alle** anmelden dürfen (`signupAccess.accessRule` = `open`: keine Raider-Rolle, kein Roster). Kategorien mit Raider-Rolle oder Roster werden als „nicht betroffen“ aufgeführt. Die Version kommt aus `mainVersionFor`; ist weder für die Kategorie noch als Hauptversion eine eingestellt, gilt die Standardversion (`tbc`) — die Seite nennt solche Kategorien („keine Version eingestellt, gilt als …“). Je PuG-Kategorie ein Schalter (Standard an): nur die eingeschalteten gehen in Vorschau, Fingerabdruck und Übernahme; eine ausgeschaltete Kategorie bleibt in Discord, wie sie ist, und ihre Version fehlt dann in der Versionsfrage, wenn keine andere Kategorie sie hat.
- **Soll:** je Version mit PuG-Kategorie eine Rolle (Name = Label der Version, ohne Farbe, neu angelegt mit eigener Gruppe in der Mitgliederliste); je Klasse dieser Versionen eine Rolle (englischer Klassenname, Farbe aus `classes.js`, bleibt unter „Online“); zwei Fragen (Version Pflicht, Klasse freiwillig, beide Mehrfachauswahl, ohne Kanäle); je PuG-Kategorie: @everyone „Kanal ansehen“ verweigert, Versionsrolle, Orga-Rollen (Voll-Admin- und Orga-Rollen der Einstellungen, Manager des Rosters der Kategorie, nur Rollen dieses Servers) und Bot erlaubt. Unterkanäle, die mit der Kategorie synchronisiert sind, gleicht der Bot danach per `lockPermissions` an (sie bleiben synchron). Unterkanäle mit eigenen Rechten fasst er nicht an: sie bleiben für alle sichtbar, die Seite und die Vorschau nennen sie („In Discord mit Kategorie synchronisieren“).
- **Ist:** Rollen über die gespeicherte ID, sonst über den Namen (keine Integrationsrolle, nicht @everyone). Die IDs stehen im Settings-Store, `config.pugRoles[guildId] = { versions: { <versionId>: roleId }, classes: { <classId>: roleId }, appliedAt, appliedBy }` — nicht in `.env`, nicht über `PATCH /api/settings` schreibbar. Versionsrollen gelten auf der Rollen-Seite als „PuG-Versionsrolle“ (`selfRole.roleUses` → `pugVersion`) und lassen sich nicht über Rollen-Nachrichten verteilen.
- **Übernehmen:** erst alle Prüfungen, dann Rollen (anlegen / Name oder Farbe anpassen; IDs sofort gespeichert), dann die Rechte der Kategorien (Bot zuerst, damit er sich nie aussperrt), zuletzt das Onboarding. Nur was abweicht, geht an Discord. Pro Server läuft höchstens eine Übernahme (409 `busy`, Freigabe im `finally`). Der Fingerabdruck der Vorschau muss noch stimmen, sonst 409 `changed` („Inzwischen geändert – bitte neu laden“). Eine gefundene Rolle, die mehr freigibt als ihren Zweck (Discord-Rechte, Web-Rechte, Bot-Befehle, Raider-Rolle einer Kategorie, Rollen-Abgleich, Roster, ein freigeschalteter Kanal; bei der Versionsrolle zählt ihr eigener Zweck nicht), blockiert vor dem ersten Schreiben (409 `role_privileged`); die Vorschau zeigt sie als „Gesperrte Rollen“. Fehler: 409 `offline`, `not_pug_server`, `busy`, `changed`, `no_pug_category`, `no_community`, `missing_permissions`, `role_above_bot` (nur mit „Rollen verwalten“), `category_access` (Bot darf die Rechte einer Kategorie nicht ändern), `role_privileged`; 400 `no_category_selected`, `fingerprint_required`; 502 `onboarding_unreadable` (vor jedem Schreiben), `discord_failed` (die Meldung nennt den Schritt; was davor geschah, bleibt — die Seite lädt danach neu).

**Ergebnis der API-Prüfung (Okt 2026, discord.js 14.27, Discord-Doku „Guild Onboarding“):**

- `guild.fetchOnboarding()` (GET) und `guild.editOnboarding({ prompts, defaultChannels, enabled, mode, reason })` (PUT `/guilds/{id}/onboarding`). Es gibt **nur das Ganze**: PUT ersetzt alle Fragen. Darum schickt der Bot seine zwei Fragen und lässt fremde Fragen fallen — die Vorschau listet sie als „geht verloren“. IDs, Beschreibungen und Emojis bestehender Fragen/Optionen werden mitgeschickt; neue IDs per `SnowflakeUtil.generate()`. Fragentyp Multiple Choice = 0.
- **Rechte:** „Server verwalten“ **und** „Rollen verwalten“; Rollen, die eine Option vergibt, müssen unter der höchsten Rolle des Bots stehen (sonst blockiert `role_above_bot`).
- **Community-Server:** laut Discord-Support-Doku Pflicht (nicht in der API-Referenz); ohne `COMMUNITY` in `guild.features` schreibt der Bot nichts.
- **Einschalten:** ein aktives Onboarding braucht mindestens 7 Standard-Kanäle (Discord-Support-Doku). Der Bot sendet `enabled`, `mode` und `defaultChannels` **unverändert** zurück — einschalten und die Standard-Kanäle wählen macht die Orga in Discord (Server-Einstellungen › Onboarding).
- **Standard-Kanäle müssen für @everyone sichtbar sein:** Discord lehnt jeden Onboarding-PUT ab, solange ein Standard-Kanal @everyone verborgen ist (400 50035 `DEFAULT_CHANNEL_REQUIRES_EVERYONE_ACCESS`, live geprüft Okt 2026) — auch einen unveränderten. Weil die Rechte vor dem Onboarding geschrieben werden, prüft der Bot vorher: ist ein Standard-Kanal eine gewählte PuG-Kategorie oder ein synchroner Kanal darin, warnt die Vorschau (Voraussetzung `defaultChannels`) und das Übernehmen bricht vor dem ersten Schreiben mit 409 `default_channel_hidden` ab.
- **Onboarding-Rollen schalten nichts frei (#930):** Versions- und Klassenrollen aus `config.pugRoles` holt sich jeder selbst, darum lehnt jedes Speichern ab, das einer solchen Rolle ein Recht **neu** gibt: `PATCH /api/settings` (Voll-Admin-, Orga-, Offiziers-Rolle, Bereichsrechte, Bot-Befehle, Raider-Rollen einer Kategorie, Rollen-Abgleich) und Roster anlegen/ändern (Mitglieds-, Probe-, Manager-Rolle) antworten 409 `pug_onboarding_role`. Die Felder liest `selfRole.roleUses` — keine zweite Liste; Logik `src/services/discord/pugRoleGuard.js`. Erkannt wird nur über die gespeicherten IDs, nie über den Rollennamen. Ein Recht, das die Rolle schon vorher hatte, blockiert kein Speichern; solche Reste meldet der Bot-Check (`pugRolesGranting`, in System › Discord als „Hinweis“ mit Link zur Rollen-Seite). Bereichsrechte zählen je Stufe (lesen → schreiben ist neu), der Rollen-Abgleich je Paar (eine weitere Partner-Rolle ist neu). Ein Versionswechsel wird vor dem Speichern durchgespielt (`rosterVersionSwitch.rostersAfterSwitches`): die im Dialog gewählten Rollen des neuen Rosters und ihr Spiegel in `categoryRoles` zählen wie direkt gesetzte. Abgeschlossene Roster zählen nicht — weder beim Speichern noch im Bot-Check; ein wieder geöffnetes gilt als neu. Ein Roster eines anderen Servers zählt nicht. Raider-Rollen einer Kategorie werden ohne Discord-Cache nicht je Server unterschieden. Ohne `pugRoles` ändert sich nichts.
