# Mehrere Event-Server plus ein Talk-Server (event servers and talk server)

Endnutzer-Sicht: siehe [guide-discord.md#was-der-bot-sonst-noch-automatisch-macht](guide-discord.md#was-der-bot-sonst-noch-automatisch-macht).

The bot can work with several **Event-Discords** at once (#251, #361 — each with its own event channels, Raid-Helper, raids), plus one **Kommunikations-Discord** (sign-up per bot, pings). Each event server can independently post its own raid overview to a channel on **any** server the bot is on — the talk server, another event server, or itself. Nothing configured = the old one-server behaviour.

- **Stored (server network, #890 of epic #893)** as `config.discordServers = { servers, links, talkGuildId, talkPingChannelId, signupNoteChannelId, guildBankChannelId }`, normalised on every read by `configSchema.normalizeDiscordServers`:
  - `servers = [{ guildId, label }]` — every server of the network, equal in rank: `guildId` a snowflake or the entry is dropped, dedupe by `guildId` (first wins), at most 10 (`MAX_SERVERS`), `label` a free-text name ("PvE", "PvP", …).
  - `links = [{ from, to, channelId, lang, versions }]` — "server `from` shows its raids on server `to` in channel `channelId`". A link counts only when `from` and `to` are both in `servers` and `channelId` is set; `from = to` is allowed (the overview on its own server); a repeated `from:to` is dropped (first wins). Links are made by hand in the web only; there are no external entries.
    - `lang` — `"de"`, `"en"` or `""` (default): the language of the raid list on the target; `""` falls back to the server language (`serverLang`). Anything else is stored as `""`. Suggesting the target server's Discord language when a link is made comes with #891.
    - `versions` — game version ids from `config/gameVersions` (`VERSIONS`: `tbc`, `classic`, `forever`) the list shows; empty = every version. Unknown ids and duplicates are dropped.
    - Both are only normalised and stored for now; the overview reads them with #892. Migrated links get `lang: ""`, `versions: []`, so nothing changes visibly.
  - `talkGuildId` is a scalar next to them and is **added to `servers` when missing** (while fewer than 10 are listed). A server may hold raids and be the talk server at once — the old rule that cleared `talkGuildId` when it equalled an event server is gone.
  - **Migration on read, idempotent:** a block without a `servers` array is the old shape (`legacyServersAndLinks`): every `eventGuilds` entry becomes a server (label kept), its `overviewGuildId`/`overviewChannelId` the link `{ from: guildId, to: overviewGuildId, channelId }` (a foreign target server joins `servers` too), the talk server joins when missing; a config with no event server at all seeds `config.guildId` as the one server. A block that already has `servers` is only normalised — a second run changes nothing. The start migration (`settingsMigration`, `eventGuildId` → `eventGuilds`) skips blocks with `servers`. The output carries no `eventGuilds`.
  - `config.guildId` stays the **fallback**: `getConfig().guildId` reports the *first* server, and saving writes it into `guildId` too — so `auth.js`, `activeGuild.js` and everything else reading `guildId` follow without change.
- **Read** through `src/services/discord/guildRoles.js`: `serverIds()` (every server, falling back to `[config.guildId]`), `serverLabel(id)`, `links()` (the valid links), `linkedSources(id)` (links whose `to` is this server — whose raids show here) and `linkedTargets(id)` (links whose `from` is this server — where its raids show). `eventGuildIds()` = `serverIds()` (the talk server is a server like any other now, so loops over the event servers include it), `eventGuildId()` the first of those (kept for the call sites deliberately still scoped to "the primary event server", see below), `talkGuildId()`, `configuredGuildIds()` (servers ∪ talk), `guildRole(id)` (`"talk"` first, then `"event"` for any server, else `""`), `eventGuild()`/`eventGuildCards()`/`talkGuild()` (status cards: connected, member count, `permissions` from `discord.botPermissionsIn()` — null = not knowable, never "all missing"; `eventGuildCards()` additionally carries each entry's `label`, `overviewGuildId`/`overviewChannelId` from its first link and a best-effort `overviewGuildName`) and `memberOverlap()` (human members of the *first* server also on the talk server, via `fetchGuildMembersCached`; null when both are the same server; failures come back as `error`, never thrown).
- **One server as event and talk server:** a ping with target `both` goes to the event channel only (`pingDelivery.effectiveTarget` — otherwise the same people would be pinged twice on one server), the role sync does not run (`roleSync` reports „Event- und Talk-Server sind derselbe Server.“), `memberOverlap()` is null.
- **Transition until #891 (old settings dialog):** `GET /api/settings/discord-servers` still serves the old `eventGuilds` shape next to the new fields (`legacyDiscordServers` in `apiRoutes/settings.js`, built by `guildRoles.legacyEventGuilds`: the servers without the talk server, each with its first link as `overviewGuildId`/`overviewChannelId`); a PATCH that sends `eventGuilds` without `servers` re-derives `servers` and `links` from it (`configStore.saveConfig`); a link the dialog sends back with the same `from:to` keeps its stored `lang` and `versions` (`keepLinkExtras`), a new one gets `""`/`[]`. The settingsStore facade `normalizeDiscordServers` hands both shapes to the schema. All of it goes with #891.
- **Edited** in Einstellungen → Verbindungen → *Discord-Server* (`pages/settings/SettingsDiscordServers.tsx`, section `discordserver`, adminOnly + standalone): one card per configured event server (name, own label, connection state, its own raid-overview row once a target is set) plus the talk-server card, rights as "4 von 5" with the list in the tooltip, a "+ Event-Server hinzufügen" affordance, a dialog that PATCHes only this block — one row per event server (guild picker excluding every other picked server, a label field, its own target-server-and-channel picker), plus the unchanged talk-server fields. `GET /api/settings/discord-servers` serves the cards (`events: EventServerCard[]`, `talk`), overlap and every bot server with its text channels. `discordServers` is **full-admin-only** (`GUILD_KEYS` in `apiRoutes/settings.js`): the event servers decide whose roles count (see the admin-role check below).
- **The web server switcher stays** — it still offers every server the bot is on (the Kanäle page edits any of them through it) and only shows the role as an *Event*/*Talk* badge (`/api/session` tags `guilds[].role`).
- The Discord & Raid-Helper card no longer edits `guildId`; that moved into the dialog above, and names the *first* configured event server.
- **The admin-role check runs against every configured event server, not just one**: `auth.js`'s `computeAccess()` tries each of `guildRoles.eventGuildIds()` in turn — a member of any one of them with a qualifying role gets access (role permissions union across every server they belong to), not being a member of one is not fatal, only a `guild.fetch` failure on *every* configured server throws ("bot offline everywhere"). This is a pure broadening versus the old single-guild check: nobody who had access before loses it, but an admin who only holds a role on a *secondary* event server now gets in too, which used to be impossible.
- **Deliberately still scoped to the first/primary event server**, not generalised (#361 kept its blast radius narrow — extend these only if a real second use case shows up): role sync (`roleSync.js`), Raid-Helper retirement (`raidhelperRetirement.js`), an event series' default guild id fallback (`eventSeries.js`, only hit when no explicit guild id is already in context), the talk overview's own Raid-Helper sign-up fallback (`commands/signup/talkSignup.js`, `utils/signup/multiSignup.js`), and `memberOverlap()` above.

**Pings, reminders and role sync across the servers (#264).** Two Discord rules shape all three: a mention only notifies someone who is on the server it is posted on, and a role mention only works on the role's own server.

- **Ping targets** (`src/services/discord/pingDelivery.js`): "Fehlende pingen" and the Anmelde-Aufruf take `target` = `event` (default, the old single post — the route still calls `discord.postMissingPing`/`postAnnouncement` directly) | `talk` (the talk server's `talkPingChannelId`) | `both`. On the talk server raiders are mentioned one by one and only if they are there (`fetchGuildMembersCached`); an event role becomes its talk counterpart from `roleSync`, a role without one becomes user mentions. **Whoever is not on the talk server gets a DM (`sendDirectMessage`) — only for `talk`**: with `both` they were reached in the event channel already. The talk members are read *before* anything is posted, so a failure never leaves a half-delivered ping. The raid-detail payload carries `pingTargets` (`pingTargetInfo()`), and `pages/raid-detail/modals/TargetField.tsx` renders the "Wohin" segment only when a talk ping channel exists; the modal head says where it goes (`targetHint`).
- **Pings and their DMs are cards (Oct 2026, `utils/discord/card.js`, see docs/bot-commands.md).** `discord.postMissingPing` posts kind `warn` with the mentions as the card's **first line** (`mentions` — they notify from inside the container, tried on the dev server) and the text under them, `allowedMentions: { users }` for exactly the pinged users; many mentions are split over several cards under Discord's **4000** characters of text per card, every mention whole, the text on the last card. `editPingMessages` (a setup ping card of the time before) edits into the same cards with `allowedMentions: { parse: [] }` — an old plain-text ping turns into a card on its next edit. The same path carries „Invite callen“; **the setup ping is no card any more** but part of the setup message (docs/setup.md, „The ping is part of the setup message“). A DM (`pingDelivery.dmCard`) is kind `warn` without mentions: the raid as heading, the text, the start short (`<t:…:d> <t:…:t> · <t:…:R>`, never `:F`) and a link button „Zum Kanal“ in the reader's language. Reminder texts use the short start too.
- **„Fehlende pingen“ under the signup message** (`src/services/events/missingPingBot.js`, `commands/event/missingPingButton.js`, customIds `event-missing:<eventId>[:go|:no]`): the orga's button under the own event's signup message (before the deadline in a row of its own under the select — „Anmelden“ fills the status row —, after it at the end of the status row), drawn **only when the category has raider roles or a roster** (`config.categoryRoles`, `eventMessage.hasRaiderRoles` → `expectedRaiders.hasExpected`, #658) and only while signing up still makes sense (open or past the deadline, not started, not cancelled or closed). Everyone sees it — a component cannot be hidden per viewer —, the click is `/event`'s (`accessOf: "event"`, checked by `botAccess.guardInteraction` before the handler; a raider gets the router's refusal). An orga click answers **ephemerally** with a preview card: who is missing (`missingPing.findMissingRaiders` — the same derivation as the raid detail and Event verwalten: the expected raiders without a reaction — with a roster its core and trial members, else the role holders, `services/roster/expectedRaiders.js`), the count, the first 25 names and „+N weitere“, buttons *Jetzt pingen* / *Abbrechen*; nobody missing → an ok card „Alle haben reagiert“; no roles, started raid, unreadable member list → an error card with the reason. *Jetzt pingen* first replaces the preview by a card without buttons, then posts through `pingMissingRaiders(target "event")` (re-derived, so whoever signed up meanwhile is spared), logs `action: "ping"` on the event and says „N Raider gepingt“. **Against a double ping:** one ping per event at a time (in process), and a ping logged on the event (this button or Event verwalten) in the last 2 minutes refuses another one („Schon gepingt … von …“).
- **Reminders** (`src/web/events/reminders.js`, `startReminders()` every 5 min, started by `jobs.js`): `config.categoryReminders = { [categoryId]: { missingHours, signedHours, target } }` — hours 1–168, 0 = off, a category with both off is dropped (`normalizeCategoryReminders`). Every sweep loops **every configured event server** (`guildRoles.eventGuildIds()`), so a raid category on a secondary event server gets reminders exactly like one on the first; one server's events failing to load (Raid-Helper down there) never blocks the sweep on the others, and the sweep only reports an error when *every* server failed. *missing* goes `missingHours` before `event.signupDeadline` (EventHelper's own events, #254; `raidEventGroups` passes it through when an event has one) or, without one, before the start, to the expected raiders who have not reacted (a category with a roster: its core and trial members, #658; else the category's role holders); *signed* goes `signedHours` before the start to signed/late signups. **Never after the start**, a *missing* one never after the deadline. Exactly once: `reminderStore.js` (`data/settings/reminders-sent.json`) marks *before* sending, a failed send takes its mark back so the next sweep retries, a member list that cannot be read skips without marking; marks are pruned after 30 days (event ids are globally unique, so one store works across every server). Not guarded (`categoryReminders` is a plain settings key).
- **Setup proposal at the deadline** (same sweep, independent of `categoryReminders`): `runAutoSuggest()` in `reminders.js` — an own event with `autoSuggest` whose `signupDeadline` has passed, that has not started and has no `setup` yet gets `setupInput.proposeSetup([eventId])`, stored **only as a draft** through `eventStore.saveSetupDraft(eventId, proposal)` → `event.setup = { ...proposal, status: "draft", createdBy: "auto", createdAt }`. Already server-agnostic (`eventStore.listEvents("")` over every guild), unaffected by #361. Never approved here; an approved setup is never overwritten (`code: "approved"`). Marked once as kind `autoSuggest` in `reminderStore`, a failed proposal takes the mark back. ⚠️ The setup editor (#263) must store its drafts in the same shape (reuse `saveSetupDraft` or align both).
- **Role sync** (`src/services/discord/roleSync.js`): `config.roleSync = [{ eventRoleId, talkRoleId, direction: "toTalk" | "toEvent" | "both" }]`, **full-admin-only** (`ROLE_SYNC_KEYS`), scoped to the *first* configured event server and the talk server (not generalised, see above). Runs for the one member on `guildMemberUpdate` (only when the roles changed) / `guildMemberAdd` (`bot.js`), and over everyone every 10 min (`startRoleSync()`, first run a minute after boot). ⚠️ **It only ever calls `member.roles.add` — never a remove** (decided in #250/#264; `test/services/discord/roleSync.test.js` scans the source for it). Without "Rollen verwalten" on a target server (`botPermissionsIn`; unknowable counts as missing) it adds nothing there and reports `missingPermission`; a role above the bot's own is skipped. `roleSyncDrift()` lists who holds the synced role but no longer the source role (one-way entries only — with `both` the sync gives it straight back), **computed on read, nothing stored**.
- **Roster roles and the role sync (#656):** the rosters give and take their Discord roles (`services/discord/memberRoles.js`, the only module that removes a role, and only roster roles — docs/roster-profile.md "Roster und Discord-Rollen"). The role sync stays add-only, so **a roster role mirrored to the talk server is not removed there** when the tool takes it on the event server (it turns up in the drift list). The other way round, a roster role the sync *gives* from the other server comes back after the tool takes it, as long as the person holds the source role — and with it the person returns to the roster. `GET /api/rosters/sync` reports both cases per role as `mirrored` (`outgoing` / `incoming`) for the Abgleich tab's hint.
- **UI**: under the server cards, `SettingsRoleSync.tsx` (only with a talk server: one line per pair, add/edit in a modal, drift as a badge plus a fold-out with Discord profile links, a "Recht fehlt" line) and `SettingsReminders.tsx` (one line per event category across every configured event server with "24 h vor Schluss · 1 h vor Raid", details in a modal). `GET /api/settings/role-sync` (full admin) and `GET /api/settings/reminders` serve them (the latter names a category by its name on whichever configured event server actually has it); both save through `PATCH /api/settings`. Drift is also a dashboard task (`roleDriftTask`, full admins only, links to `?section=discordserver`).

**Wie aktuell die Mitgliederliste ist (Okt 2026).** Every page that needs "who is on the server / who holds role X" (raid detail attendance and „Fehlende pingen“, roster and its Discord sync view, member search, dashboard drift, settings overlap, bot command access) reads the full member list through `discord.fetchGuildMembersCached(guildId, guild)` — one `guild.members.fetch()` per guild, capped at 25 s. It is served **stale-while-revalidate**:

- under **60 s** old (`MEMBERS_CACHE_TTL_MS`): as it is;
- **60 s – 30 min** (`MEMBERS_STALE_MAX_MS`): at once, and one refresh starts in the background — the page never waits for Discord; a failed refresh is logged and the old list stays;
- older, or nothing yet: the caller waits. Parallel callers (the cold first fetch included) share one fetch per guild, so a burst of pages or the raid detail's parallel reads cost one.
- **`{ fresh: true }`** waits for a list fetched now (or joins the running fetch): only the two jobs that *write* roles from the list use it — the role-sync sweep (`roleSync.runRoleSync`) and the roster reconcile (`rosterRoleSync.reconcile`), both every 10 minutes, which keeps the shared list warm for the pages too. „Fehlende pingen“ deliberately does not: it must ping exactly the raiders the page just showed, and a second full fetch is what once pushed it past the proxy's 60 s.
- **What can be old:** role changes reach the cached members in place through the GuildMembers intent (`GUILD_MEMBER_UPDATE` patches the same `GuildMember` objects), so a role given or taken shows up within the gateway's lag. Joins and leaves show up with the next refresh: normally at the second page view after a minute, at worst 30 minutes later (no page view and no job). `guild.members.cache` itself is not served — after a reconnect or without the intent it silently holds a partial list.
- At **bot start** (`ClientReady` in `bot.js`) `discord.warmGuildMembers(configuredGuildIds())` fetches the configured event and talk servers in the background.

**Links in overviews (#537).** "Links dürfen nicht kaputt sein." Every link an overview writes goes through `src/services/discord/linkCheck.js`: `channelLink`/`messageLink`/`eventLink` (Discord), `webLink`/`webTarget(kind, id)` (web: `event`, `comp`, `calendar` only for an own event that exists, `raidplan` only for a published plan, `signup`, `setup`) and `externalLink` (sheet, softres: stored and `https?://`). Channel state: the bot's cache is authoritative while it is online (every guild channel is cached), else `checkChannel()` asks Discord (10003/10008/50001/404 = missing) and keeps the answer 5 min; **bot offline = the last state known in this process, nothing known = no link** (a missing link costs a click, a dead one trust). `src/services/discord/linkWatch.js` hooks `channelDelete` and the raw `MESSAGE_DELETE(_BULK)` packets (no `Partials.Message`, #430): a deleted channel is missing at once, its own events get the log entry "Kanal in Discord gelöscht", the overviews redraw (1.5 s); a deleted signup message is posted anew, a deleted setup post is forgotten, a deleted overview message is reposted by its sync. The web lists get `channelState` per row (`linkCheck.withChannelState`, raids, past raids, dashboard, history, raid detail) and `lib/discord/discordLinks.ts` links the post only on `"ok"`. The raid plan post follows its share (`syncRaidplanPost` after `POST /api/raidplan/publish`: new token in, withdrawn share out). `test/services/discord/linkCheck.guard.test.js` keeps `discord.com/channels/` out of every other file in `src/` (client: only `lib/discord/discordLinks.ts`). A missing channel of an own upcoming raid is a dashboard task with "Kanal neu anlegen" — see docs/channels.md.

**Each server's raid overview (#257, #361, #890).** One bot message per server that is the source (`from`) of a link, listing *that server's own* upcoming raids — both sources, via `loadEventGroups(entry.guildId)` — posted in the link's channel on its `to` server (the talk server, another server, or itself), so whoever reads that channel knows what is planned without opening the source server. Until #892 only the **first link per source** posts (`talkOverview.overviewEntries()` turns it into the old entry `{ guildId: from, label, overviewGuildId: to, overviewChannelId: channelId }`), and the store stays keyed by the source's guild id; `linkWatch` and `botMessages` read the same first links.

- **Built** by `src/services/talk/talkOverview.js`'s `buildOverviewMessage(groups, opts)` (pure, plain API JSON, called once per configured entry with that entry's own `groups`/guild): one embed field per category (only `config.categoryIds` when set; categories ordered by their soonest raid — `loadEventGroups()` already scopes every category to its own guild, so a category id belonging to a *different* event server can never leak into another server's overview, no extra guild check needed), one line per raid — `**Titel** · Do 17.09. 19:30 · 👥 15 signed up · [#kanal](https://discord.com/channels/<eventGuild>/<channel>) · Raid-Helper` (the marker only on Raid-Helper events; `15 signed up` = the single Discord accounts on signed + late, `capacity.accountCount` with `attendance.signupStatus` — an account with several entries counts once, and since #520 there is no „/size“). The link is a plain URL on purpose: `<#id>` does not resolve across servers. **Only a channel that exists is linked (#537):** the line asks `linkCheck.channelInfo()` (see "Links in overviews" below) — a deleted channel reads `channel missing` without a link, a channel nothing is known about yet (bot offline since the start) its bare `#name`; `currentPayload()` confirms every listed channel with `linkCheck.checkChannels()` before it builds. The title links the public event page and the three web buttons appear only with a real `PUBLIC_BASE_URL` (not the `http://localhost:<port>` fallback). Below: the buttons *Für alle Raids anmelden* / *Mehrere Raids wählen …* (`talk-signup-all` / `talk-signup-multi`, only while an EventHelper event is listed — see "Mehrere Raids auf einmal (Bot)" in docs/signups.md), the select `talk-signup` ("Einzelnen Raid wählen …", the next 25 raids) and three link buttons (Web-Übersicht `/raids`, Meine Anmeldungen `/signups`, Mein Profil `/profile`). Discord's limits are enforced in the builder: ≤25 fields, ≤1024 per field ("+N weitere"), ≤6000 per embed (footer "+N weitere Raids in der Web-Übersicht"), ≤25 options. Nothing time-dependent goes into the payload, so its sha1 (`payloadHash`) says whether anything changed.
- **Grouped per game version (#743):** TBC and Forever run on the same Discord server, so the version never comes from the server. `upcomingGroups()` splits every category by the stored version of each raid (`versionOfEvent`), orders TBC/Classic/Forever in rule-set order and names the version in the field title (`Forever · Montag`, short name from `events/versionTag.js`) as soon as more than one version is listed. Raids of a hidden version (`hideOtherVersions`) are left out; one overview per version in its own channel is not built (default: one overview, grouped). The same rule holds for reminders (`web/events/reminders.js`), "Fehlende pingen" (`events/missingPing.js`) and the subscription calendar (`web/pages/calendarFeed.js`, optional `?version=` on `/r/cal/user/<token>.ics`): hidden versions are skipped. Raid posts carry their version as a small label (event embed footer, `kicker` of the missing-ping and setup cards).
- **Synced** by `runSync({ repost, guildId })` (serialised — two triggers never post two messages on top of each other): with a `guildId`, only that one entry syncs, returning its single result; without one, every configured entry syncs in turn (`{ results: [...] }`) — one entry's failure never blocks another's. Per entry: unconfigured → nothing; unchanged hash → no edit; changed → `message.edit`; message deleted in Discord (10008) → posted anew; `repost` or a changed channel → the old message is deleted, a new one posted. When that server's event list could not be loaded completely (Raid-Helper down) its existing message is **left alone** rather than edited into a list without Raid-Helper events. Where each one sits lives in `src/stores/talkOverviewStore.js` (`data/settings/talk-overview.json`: `{ [guildId]: { channelId, messageId, hash, postedAt/editedAt/checkedAt, error } }`, one record per event server — an old flat-shape file migrates into the first guild that reads it, once) — deliberately not in the settings config, which a PATCH would race.
- **Triggers**: `startTalkOverview()` (started by `jobs.js`) — `onSignupsChanged` (debounced 3 s), a sweep every 5 min (Raid-Helper signups, raids that started; first run 30 s after boot), and `eventCreate.js` calls `scheduleOverviewSync()` after creating an event (35 s for a Raid-Helper event, which outlasts `raidEventGroups`' 30-s cache) — none of these pass a `guildId`, so every configured entry resyncs on every trigger; each entry's own hash check keeps the no-op case cheap, and the guild count is small.
- **The select** (`commands/signup/talkSignup.js`, `group: "signup"`, `defaultAccess: "everyone"`) opens the Discord signup dialog for an own event and links a Raid-Helper event into its event channel — see "Anmeldung (Bot)" in docs/signups.md. Still scoped to the first configured event server (see the "deliberately still scoped" bullet above).
- **Web**: each event-server card in Einstellungen → Discord-Server shows its own "Übersicht" row (`SettingsTalkOverview.tsx`, now a controlled component fed from one shared fetch in `SettingsDiscordServers.tsx` rather than fetching itself) once its own overview target is set — a badge "bearbeitet vor 3 Min." linking to the message, the times, any error and the target server/channel in its tooltip (`talkOverviewBadge` in `settingsLogic.ts`), and "Neu posten" (now takes that entry's `guildId`). `GET /api/settings/talk-overview` without a `guildId` returns every configured entry's status (`{ statuses }`, what the cards render); with `?guildId=` it returns one entry's status plus `preview` (the payload a sync would post now, a dry run; `?preview=0` skips it — currently unused by the frontend). `POST` requires `{ guildId, repost? }` and syncs just that one entry; both full-admin-only.

## Raid-Übersicht je Kategorie (`/createoverview`)

Eine Karte je Kategorie, die die kommenden Raids der Kategorie zeigt und sich selbst aktuell hält — die Kategorie-Variante der Talk-Server-Übersicht oben. Entwurf „C“ (Okt 2026), ohne Knöpfe.

- **Aufbau** (`src/services/events/raidOverviewPanel.js`, rein, ein Components-V2-Container in der Akzentfarbe): Überschrift = Kategoriename; darunter die Raids **gruppiert nach Raid-ID** (Sperrwoche Mittwoch bis Dienstag, `src/utils/time/raidId.js`): „Diese ID“ (laufende), „Nächste ID“, sonst „ID“, dazu die Spanne „Mi 14.10. – Di 20.10.“. Je Raid drei Zeilen: `Sa 18.10. · **Titel** · <t:…:t> · <t:…:R>`, dann `<#Kanal> · geleitet von <@Leiter>`, dann klein die Füllung: „17 / 25 angemeldet“, „10 / 10 voll · Warteliste offen“ (nur bei `overflow: waitlist`) oder „Anmeldung geschlossen“ (Anmeldung vom Orga geschlossen oder Frist vorbei); ohne Größe (Raid-Helper) nur „17 angemeldet“. Gezählt wird wie überall `talkOverview.attendingCount`. Abgesagte und schon begonnene Raids fehlen, Raids einer ausgeblendeten Spielversion auch. Grenzen: höchstens 3 IDs und 15 Raids (`MAX_IDS`, `MAX_RAIDS`), der Text bleibt unter 3700 Zeichen, der Rest steht als „+n weitere Raids“. Fuß: „Aktualisiert sich selbst · letzte Änderung <t:…:t>“.
- **Grafik (Entwurf „C2“):** jeder Raid ist eine *Section* mit dem Zonenbild als Thumbnail — das eigene Bild des Events (`lookOf(event).url`), sonst das Zonenbild der Instanzen wie in der Anmelde-Nachricht (`ruleSetLook(...).art`; Raid-Helper-Zeilen ohne `instanceIds` lesen sie aus dem Titel über `raidContentIds`). Ohne Bild (oder ohne https-Adresse) ein schlichter Text. Vor der Füllzeile ein Balken aus fünf App-Emojis (`eh_ui_barg`/`baro`/`barn`/`bare`): so viele Segmente gefüllt wie die Anmeldungen die Plätze füllen (mindestens eins, sobald jemand dabei ist), grau unter einem Drittel, grün dazwischen, orange wenn voll, der Rest leer; ohne Emojis 🟩🟧⬜▫️. Raid-Helper-Zeilen ohne Größe: kein Balken. Kleine Icons `eh_ui_time` vor der Uhrzeit, `eh_ui_leader` vor dem Leiter, `eh_ui_date` vor der ID-Überschrift. Die Emojis stehen im Hash — kommen sie später hinzu, zeichnet sich die Nachricht neu. **Komponenten:** eine Section mit Bild zählt 3 (Section, Text, Thumbnail), ein Raid ohne Bild 1; `raidOverviewPanel` zählt gegen Discords 40 mit und kürzt mit „+n weitere Raids“ (praktisch etwa 10 Raids mit Bild).
- **Wochenleiste als Bild (Entwurf „D“, Test, Okt 2026; Schalter `config.discordVisuals.overviewWeekStrip`, Standard an):** jede ID beginnt mit einem gezeichneten Bild statt ihrer Überschriftszeile (`src/services/events/raidWeekStrip.js`, rein, SVG): „NÄCHSTE ID“/„DIESE ID“/„ID“ mit Spanne, darunter sieben Tageskacheln Mi…Di (Wochentag kurz, Tageszahl groß, Sprache der Kategorie). Ein Tag mit Raid bekommt einen Rahmen in der Füllfarbe (grün, orange voll, grau unter einem Drittel — dieselbe Regel wie der Emoji-Balken), die Startzeit des ersten Raids, je Raid ein Kürzel aus den Instanz-Kurznamen („HYJAL + BT“, „KARA“; ohne Instanz der Titel in Großbuchstaben; ein langes Kürzel wird erst kleiner, dann mit „…“ gekürzt) und einen dünnen Füllbalken; zwei Raids am Tag stehen untereinander, ab dem dritten „+n“. In der laufenden ID sind vergangene Tage abgeblendet, heute ist violett markiert. Das Bild ist ein Components-V2-**Media-Gallery**-Eintrag `attachment://raid-id-<n>.png` mit Alt-Text (die Raids als Text, ≤ 1024 Zeichen); **ein Bild je ID** (höchstens 3), es kostet so viele Komponenten wie die ersetzte Überschriftszeile (2 mit Trenner), die 40er-Grenze ändert sich also nicht. Die klickbaren Raid-Zeilen darunter bleiben unverändert. Der **Hash** umfasst die SVGs (das Bild kann sich ändern, wenn der Text gleich bleibt — z. B. wandert die Heute-Markierung einmal am Tag); die Fußzeit steht nie im Bild. Gerendert wird nur bei geändertem Hash, das PNG je Nachricht im Speicher gehalten (`services/discord/discordImage.js`, siehe „Gezeichnete Bilder“ unten). Aus = die Textform von vorher beim nächsten Sweep.
- **Raid-ID-Zwilling:** `utils/time/raidId.js` ist das Backend-Gegenstück zu `src/web-client/src/lib/raids/raidId.ts` (Berlin, Reset-Stunde 5: ein Raid am Dienstag 23:30 oder Mittwoch 03:00 gehört noch zur Vor-ID). `test/utils/time/raidId.test.js` hält Konstanten und Logik gleich (es führt die TS-Funktionen aus und vergleicht zwei Jahre, Zeitumstellung inklusive).
- **Sprache:** die der Kategorie (`botLanguage.categoryLang`) — PuG-Kategorien englisch, sonst die Serversprache (Standard Deutsch). Katalog: `config/botText/de/raidOverview.js`.
- **Daten:** `loadEventGroups(guildId)` (beide Quellen, Raid-Helper nur über den zentralen Sync und seinen Cache, nie eine eigene Anfrage). Lässt sich die Liste nicht vollständig laden, bleibt die Nachricht unverändert.
- **Gemerkt** in `stores/raidOverviewStore.js` (`data/settings/raid-overviews.json`): `{ guildId, channelId, messageId, categoryId, hash, lastChange }`, mehrere je Kategorie (je Kanal eine). `/createoverview` (`commands/setup/createOverview.js`) postet die Karte und merkt sie; liegt im selben Kanal schon eine Übersicht dieser Kategorie, wird diese neu gezeichnet statt einer zweiten.
- **Aktuell halten** (`services/events/raidOverview.js`, Job `raidOverviews` in `jobs.js`): Sweep eine Minute nach dem Start und alle 5 Minuten, dazu ein Anstoß 5 s nach `eventStore.onEventsChanged` / `signupStore.onSignupsChanged` und nach jedem Raid-Helper-Sync (`raidhelperSync.js`). Bearbeitet wird nur, wenn sich der Inhalt geändert hat (`hash` über den Inhalt **ohne** die Zeit im Fuß; `lastChange` zeigt die letzte Änderung, sonst würde jede Zeichnung den Hash ändern). Eine in Discord gelöschte Nachricht („Unknown Message“) wird **vergessen, nicht neu gepostet** — die Nachrichten sind von Hand platziert. `linkWatch.js` meldet das Löschen sofort (`onOverviewMessageDeleted`), sonst fällt es beim nächsten Zeichnen auf. Ein anderer Fehler (Kanal weg, keine Rechte) bleibt im Store und wird einmal geloggt.
- **Alte Übersichten übernehmen:** einmal je Event-Server (`scannedGuilds` im Store) durchsucht `adoptExisting()` die Textkanäle unter einer Kategorie nach den letzten 50 Nachrichten, mit 1,5 s Pause je Kanal. Übernommen wird jede Nachricht des Bots, die von `/createoverview` stammt (`message.interaction.commandName` bzw. `interactionMetadata`) oder noch den Knopf `update-events` trägt; die Kategorie ist die des Kanals. Der nächste Lauf zeichnet sie neu. Ein Kanal, der sich nicht lesen lässt, wird übersprungen; ein Server gilt erst als durchsucht, wenn alle Kanäle gelesen wurden (sonst nächster Sweep wieder).
- **Alte Nachrichten:** der Knopf `update-events` einer alten Nachricht merkt und zeichnet genau diese Nachricht im neuen Entwurf (`adoptMessage`); die Module `show-signups`, `show-mysetups`, `show-allsetups` bleiben für alte Nachrichten bestehen. `/update-events` als Befehl zeichnet die Übersichten der Kategorie neu.

## Gezeichnete Bilder in Bot-Nachrichten (Test, Okt 2026)

Der Bot zeichnet Teile seiner Nachrichten als PNG: die Wochenleiste der Raid-Übersicht (oben, Entwurf „D“) und das Setup als Grafik ([setup.md](setup.md), Entwurf „F“). Der dritte Schalter derselben Gruppe, `eventCover`, gibt dem Discord-Event das Bild des Raids als Titelbild ([events.md](events.md), `discordEventCover.js`; kein gezeichnetes Bild).

- **Schalter:** `config.discordVisuals = { overviewWeekStrip, setupImage, eventCover }` (`configSchema.js`, `normalizeDiscordVisuals`: jeder an, solange nicht `false` gespeichert ist; `saveConfig` führt einzelne Schalter zusammen). Web: Einstellungen → Raid-Standardwerte → „Bilder in Bot-Nachrichten“ (`pages/settings/DiscordVisualsCard.tsx`, drei Schalter, im Entwurf der Seite, `PATCH /api/settings { discordVisuals }` nimmt nur bekannte Schlüssel als Boolean). Lesen: `discordImage.visualOn(config, key)`. Aus = die Textform ab der nächsten Neuzeichnung der Nachricht.
- **Zeichnen:** die Bauer liefern ein SVG als Text (rein, testbar), `src/utils/image/svg.js` (Escaping, Text, Rechtecke, dunkle Palette wie Discord: Grund `#1a1b26`, Flächen `#232533`, Text `#f2f3f5`/`#9aa0b4`, grün `#3ad07a`, orange `#f0b232`, violett `#8e7cf0`), Textbreiten aus der Schrift selbst (`src/utils/image/fontMetrics.js` liest `cmap`/`hmtx` der TTF), damit Namen vor dem Rand mit „…“ enden.
- **Rendern:** `src/services/discord/discordImage.js` mit `@resvg/resvg-js` (seit diesem Test eine Laufzeit-Abhängigkeit) und **nur der mitgelieferten Schrift** `assets/fonts/NotoSans-Regular.ttf` / `-Bold.ttf` (Noto Sans, SIL Open Font License, `assets/fonts/OFL.txt`; auf Latin + Latin-Erweiterungen gekürzt, Umlaute und Akzente drin), `loadSystemFonts: false` — der kleine Linux-Server zeichnet genau wie ein Entwicklerrechner. Ein Zeichen ohne Glyphe (Emoji im Namen) fällt weg. Je Schlüssel (Nachricht + Bildname) bleibt das letzte PNG mit dem Hash seines SVGs im Speicher (höchstens 60), die Renderzeit steht im Debug-Log (`[discordImage] … rendered in … ms`). Gemessen: Wochenleiste ~20 ms, Setup 25er ~40 ms, 40er ~60 ms.
- **Anhängen:** ein Bauer gibt `images: [{ name, svg }]` mit; `withImages(payload, { key })` macht daraus discord.js-`files` und `attachments: []` — beim Bearbeiten ersetzt das die alte Datei, statt eine zweite anzuhängen; ohne Bild entfernt es eine alte. Klappt das Rendern nicht (z. B. fehlt das resvg-Binary), wird die Nachricht in Textform gezeichnet und einmal gewarnt.

## Discord-Übersicht (Daten und API, Okt 2026)

Eine lesende Übersicht je Server-Seite (`side=event|talk`) für den Discord-Bereich im Web: wer neu ist oder gegangen ist, ob der Bot hat, was seine Funktionen brauchen, ob seine festen Nachrichten noch stehen, und wie aufgeräumt die Rollen sind. Hier stehen Daten und API; die Oberfläche ist der Reiter *Übersicht* unter *System › Discord* (docs/channels.md, `DiscordOverviewPage.tsx`).

- **API:** `GET /api/discord/overview?side=event|talk[&fresh=1]` (`src/web/apiRoutes/discordOverview.js`), Bereich `channels`, nur lesen; eine andere Seite → 400 `bad_side`. Antwort `{ side, guildId, online, members, botCheck, messages, hygiene }`, die Form steht im Kopf der Datei. Der Server der Seite kommt aus `guildRoles.eventGuildId` / `talkGuildId` (der erste Event-Server; weitere Event-Server sind noch nicht wählbar).
- **Neu und gegangen** (`members`): `guildMemberAdd` / `guildMemberRemove` in `bot.js` → `services/discord/memberActivity.js` → `stores/memberActivityStore.js` (`data/settings/member-activity.json`). Nur konfigurierte Server, keine Bots, der Listener wirft nie. Gemerkt: Server, Nutzer, Anzeigename, Zeit, `join`/`leave`, beim Gehen die Rollen (ohne @everyone). 14 Tage, höchstens 2000 Einträge (`KEEP_DAYS`, `MAX_ENTRIES`), aufgeräumt bei jedem Schreiben. Die API liefert die letzten 7 Tage, neueste zuerst, je Eintrag `relation`: offene Roster mit Status (`rosterStore`) und die Zahl der Charaktere (aus `memberRelation.js`: Profil, offene Roster und Zuordnungen aller Kategorien, je Spielversion und Name einmal — ein gleichnamiger TBC- und Forever-Charakter zählt zweimal, ein Name ohne Version nur, wenn er sonst fehlt; seit der Mitglieder-Seite zählen auch Roster-Charaktere, die nur im Roster stehen); wer `channels` lesen darf, sieht das (docs/permissions.md). Braucht den GuildMembers-Intent; ohne ihn kommen die Ereignisse nicht an. **Lücke beim Gehen:** der Bot hat kein `Partials.GuildMember` (und bekommt hier keins dazu) — wer geht, ohne im Mitglieder-Cache zu stehen (etwa kurz nach einem Neustart, bevor die Liste geladen ist), löst kein `guildMemberRemove` aus und fehlt in der Liste.
- **Bot-Check** (`services/discord/botCheck.js`): eine Tabelle `BOT_FUNCTIONS` „Funktion → Rechte“ (Kanäle, Posts, Reaktionen, Rollen, Mitglieder-Intent, Server-Events, Bewerbungs-Threads, Message-Content-Intent; die drei letzten nur auf der Event-Seite, sonst `not_needed`). Je Funktion `ok` / `missing` / `unknown` (Bot offline; Intents sind trotzdem bekannt) mit den einzelnen Rechten. Dazu die eingestellten Kanäle der Seite (Bewerbungen, Log-Kanäle, Talk-Pings, Gildenbank, Addon-Zentrale …) mit `ok` / `missing` (Rechte im Kanal fehlen, mit Namen) / `channel_missing` / `not_set` / `unknown`; ein Kanal zählt zu dem Server, auf dem er liegt — liegt er auf einem dritten Server (etwa einem zweiten Event-Server), fehlt er in beiden Seiten, statt als „Kanal fehlt“ zu erscheinen. Getrennt davon `rolesAboveBot`: Rollen, die der Bot vergibt (offene Roster, Probe-Rolle, Rollen-Abgleich, Rollen-Nachrichten der Seite, Ping-Rolle der Addon-Zentrale) und die auf oder über seiner höchsten Rolle stehen (`memberRoles.roleBelowBot`, also `comparePositionTo`) oder von einer Integration verwaltet werden. Die Rechte selbst bleiben in `REQUIRED_BOT_PERMISSIONS` (`discord.js`), die Tabelle liest nur.
- **Feste Bot-Nachrichten** (`services/discord/botMessages.js`): Orga-Zentrale, Raid-Zentrale, Raid-Übersicht, Raid-Übersicht im Talk (liegt auf dem Ziel-Server `to` des ersten Links der Quelle), Rollen-Nachrichten der Seite, Addon-Zentrale, Rekrutierung — je Eintrag Art, Titel/Kategorie, Kanal, Link und Status `ok` („steht“), `deleted`, `channel_missing`, `no_access` (dem Bot fehlt im Kanal „Kanal ansehen“ oder „Nachrichtenverlauf lesen“, vorab über `permissionsFor` geprüft, oder Discord antwortet 50001/50013/403), `unknown` (Bot offline, Zeitlimit, Discord antwortet nicht oder mit 5xx). Geprüft im Kanal des Bot-Caches (erst der Nachrichten-Cache, sonst `messages.fetch`, höchstens 4 gleichzeitig); der Link nur für eine stehende Nachricht über `linkCheck.messageLink`, eine gefundene Nachricht wird dort wieder verlinkbar (`linkCheck.messageFound`). Jede Antwort wird 10 Minuten **je Nachricht** gemerkt, `unknown` nie; eine neue Nachricht in der Liste wird sofort geprüft. Eine Prüfung endet nach 5 s (`CHECK_MS`), was bis dahin nicht geantwortet hat, ist `unknown`. `fresh=1` fragt Discord für jede Nachricht der Seite neu — der Knopf dafür ist also nicht kostenlos.
- **Rollen-Hygiene** (`services/discord/roleHygiene.js`), nur Zahlen: Rollen gesamt (ohne @everyone und Integrationsrollen), leer, über dem Bot, mit heiklen Rechten (Administrator, Server/Rollen/Kanäle verwalten, Bannen, Kicken, @everyone erwähnen, Webhooks, Timeout, Nachrichten/Spitznamen/Events/Threads verwalten, Audit-Log ansehen — die eine Liste `SENSITIVE`, die auch die Rollen-Seite nutzt; „Ausdrücke verwalten“ zählt bewusst nicht); „über dem Bot“ über `comparePositionTo` mit seiner höchsten Rolle. Es wird **nie** ein Member-Fetch gemacht (1 vCPU, siehe GuildMembers-Intent); „leer“ ist `null`, solange der Mitglieder-Cache nicht vollständig ist. Offline → `known: false`, alle Zahlen `null`.
- **Tests:** `test/stores/memberActivityStore.test.js`, `test/services/discord/memberActivity.test.js`, `botCheck.test.js`, `botMessages.test.js`, `roleHygiene.test.js`, `test/web/apiRoutes/discordOverview.test.js`, die Listener in `test/bot.test.js`.
