# Zwei Discord-Server (event server and talk server)

The bot can work with two servers (#251): the **Event-Discord** (event channels, Raid-Helper, the admin-role check) and the **Kommunikations-Discord** (raid overview, sign-up per bot, pings). Everything empty = the old one-server behaviour.

- **Stored** as `config.discordServers = { eventGuildId, talkGuildId, talkOverviewChannelId, talkPingChannelId }` (settingsStore's `normalizeDiscordServers`: snowflakes only, a talk server equal to the event server is cleared). `config.guildId` stays the **fallback**: `getConfig().guildId` reports the event server once one is set, and saving an event server writes it into `guildId` too — so `auth.js`, `activeGuild.js` and everything else reading `guildId` follow without change.
- **Read** through `src/web/guildRoles.js`: `eventGuildId()`/`talkGuildId()`/`configuredGuildIds()` (pure over a config), `guildRole(id)` (`"event" | "talk" | ""`), `eventGuild()`/`talkGuild()` (status cards: connected, member count, `permissions` from `discord.botPermissionsIn()` — null = not knowable, never "all missing") and `memberOverlap()` (human members of the event server also on the talk server, via `fetchGuildMembersCached`; failures come back as `error`, never thrown).
- **Edited** in Einstellungen → Verbindungen → *Discord-Server* (`components/SettingsDiscordServers.tsx`, section `discordserver`, adminOnly + standalone): two cards, the rights as "4 von 5" with the list in the tooltip, a dialog that PATCHes only this block. `GET /api/settings/discord-servers` serves cards, overlap and every bot server with its text channels. `discordServers` is **full-admin-only** (`GUILD_KEYS` in `apiRoutes/settings.js`): the event server decides whose roles count.
- **The web server switcher stays** — it still offers every server the bot is on (the Kanäle page edits both servers through it) and only shows the role as an *Event*/*Talk* badge (`/api/session` tags `guilds[].role`).
- The Discord & Raid-Helper card no longer edits `guildId`; that moved into the dialog above.

**Pings, reminders and role sync across both servers (#264).** Two Discord rules shape all three: a mention only notifies someone who is on the server it is posted on, and a role mention only works on the role's own server.

- **Ping targets** (`src/web/pingDelivery.js`): "Fehlende pingen" and the Anmelde-Aufruf take `target` = `event` (default, the old single post — the route still calls `discord.postMissingPing`/`postAnnouncement` directly) | `talk` (the talk server's `talkPingChannelId`) | `both`. On the talk server raiders are mentioned one by one and only if they are there (`fetchGuildMembersCached`); an event role becomes its talk counterpart from `roleSync`, a role without one becomes user mentions. **Whoever is not on the talk server gets a DM (`sendDirectMessage`) — only for `talk`**: with `both` they were reached in the event channel already. The talk members are read *before* anything is posted, so a failure never leaves a half-delivered ping. `postMissingPing` splits mentions over several messages under Discord's 2000-character limit. The raid-detail payload carries `pingTargets` (`pingTargetInfo()`), and `pages/raid-detail/modals/TargetField.tsx` renders the "Wohin" segment only when a talk ping channel exists; the modal head says where it goes (`targetHint`).
- **Reminders** (`src/web/reminders.js`, `startReminders()` every 5 min in `server.js`): `config.categoryReminders = { [categoryId]: { missingHours, signedHours, target } }` — hours 1–168, 0 = off, a category with both off is dropped (`normalizeCategoryReminders`). *missing* goes `missingHours` before `event.signupDeadline` (EventHelper's own events, #254; `raidEventGroups` passes it through when an event has one) or, without one, before the start, to the category's role holders who have not reacted; *signed* goes `signedHours` before the start to signed/late signups. **Never after the start**, a *missing* one never after the deadline. Exactly once: `reminderStore.js` (`data/settings/reminders-sent.json`) marks *before* sending, a failed send takes its mark back so the next sweep retries, a member list that cannot be read skips without marking; marks are pruned after 30 days. Not guarded (`categoryReminders` is a plain settings key).
- **Setup proposal at the deadline** (same sweep, independent of `categoryReminders`): `runAutoSuggest()` in `reminders.js` — an own event with `autoSuggest` whose `signupDeadline` has passed, that has not started and has no `setup` yet gets `setupInput.proposeSetup([eventId])`, stored **only as a draft** through `eventStore.saveSetupDraft(eventId, proposal)` → `event.setup = { ...proposal, status: "draft", createdBy: "auto", createdAt }`. Never approved here; an approved setup is never overwritten (`code: "approved"`). Marked once as kind `autoSuggest` in `reminderStore`, a failed proposal takes the mark back. ⚠️ The setup editor (#263) must store its drafts in the same shape (reuse `saveSetupDraft` or align both).
- **Role sync** (`src/web/roleSync.js`): `config.roleSync = [{ eventRoleId, talkRoleId, direction: "toTalk" | "toEvent" | "both" }]`, **full-admin-only** (`ROLE_SYNC_KEYS`). Runs for the one member on `guildMemberUpdate` (only when the roles changed) / `guildMemberAdd` (`bot.js`), and over everyone every 10 min (`startRoleSync()`, first run a minute after boot). ⚠️ **It only ever calls `member.roles.add` — never a remove** (decided in #250/#264; `test/web/roleSync.test.js` scans the source for it). Without "Rollen verwalten" on a target server (`botPermissionsIn`; unknowable counts as missing) it adds nothing there and reports `missingPermission`; a role above the bot's own is skipped. `roleSyncDrift()` lists who holds the synced role but no longer the source role (one-way entries only — with `both` the sync gives it straight back), **computed on read, nothing stored**.
- **UI**: under the two server cards, `SettingsRoleSync.tsx` (only with a talk server: one line per pair, add/edit in a modal, drift as a badge plus a fold-out with Discord profile links, a "Recht fehlt" line) and `SettingsReminders.tsx` (one line per event category with "24 h vor Schluss · 1 h vor Raid", details in a modal). `GET /api/settings/role-sync` (full admin) and `GET /api/settings/reminders` serve them; both save through `PATCH /api/settings`. Drift is also a dashboard task (`roleDriftTask`, full admins only, links to `?section=discordserver`).

**The raid overview on the talk server (#257).** One bot message in `talkOverviewChannelId` lists the event server's upcoming raids — both sources, via `loadEventGroups(eventGuildId)` — so the talk server knows what is planned without anyone opening the event server.

- **Built** by `src/web/talkOverview.js`'s `buildOverviewMessage(groups, opts)` (pure, plain API JSON): one embed field per category (only `config.categoryIds` when set; categories ordered by their soonest raid), one line per raid — `**Titel** · Do 17.09. 19:30 · 👥 15/25 · [#kanal](https://discord.com/channels/<eventGuild>/<channel>) · Raid-Helper` (the marker only on Raid-Helper events; `15/25` = signed + late against `size`, without a size just the count). The link is a plain URL on purpose: `<#id>` does not resolve across servers. Below: the buttons *Für alle Raids anmelden* / *Mehrere Raids wählen …* (`talk-signup-all` / `talk-signup-multi`, only while an EventHelper event is listed — see "Mehrere Raids auf einmal (Bot)" in docs/signups.md), the select `talk-signup` ("Einzelnen Raid wählen …", the next 25 raids) and three link buttons (Web-Übersicht `/raids`, Meine Anmeldungen `/signups`, Mein Profil `/profile`). Discord's limits are enforced in the builder: ≤25 fields, ≤1024 per field ("+N weitere"), ≤6000 per embed (footer "+N weitere Raids in der Web-Übersicht"), ≤25 options. Nothing time-dependent goes into the payload, so its sha1 (`payloadHash`) says whether anything changed.
- **Synced** by `syncOverview({ repost })` (serialised — two triggers never post two messages): unconfigured → nothing; unchanged hash → no edit; changed → `message.edit`; message deleted in Discord (10008) → posted anew; `repost` or a changed channel → the old message is deleted, a new one posted. When the event list could not be loaded completely (Raid-Helper down) an existing message is **left alone** rather than edited into a list without Raid-Helper events. Where it sits lives in `src/web/talkOverviewStore.js` (`data/settings/talk-overview.json`: channelId, messageId, hash, postedAt/editedAt/checkedAt, error) — deliberately not in the settings config, which a PATCH would race.
- **Triggers**: `startTalkOverview()` in `server.js` — `onSignupsChanged` (debounced 3 s), a sweep every 5 min (Raid-Helper signups, raids that started; first run 30 s after boot), and `eventCreate.js` calls `scheduleOverviewSync()` after creating an event (35 s for a Raid-Helper event, which outlasts `raidEventGroups`' 30-s cache).
- **The select** (`commands/signup/talkSignup.js`, `group: "signup"`, `defaultAccess: "everyone"`) opens the Discord signup dialog for an own event and links a Raid-Helper event into its event channel — see "Anmeldung (Bot)" in docs/signups.md.
- **Web**: the talk card in Einstellungen → Discord-Server shows one row "Übersicht" (`SettingsTalkOverview.tsx`) once an overview channel is set — a badge "bearbeitet vor 3 Min." linking to the message, the times and any error in its tooltip (`talkOverviewBadge` in `settingsLogic.ts`), and "Neu posten". `GET /api/settings/talk-overview` (status + `preview`: the payload a sync would post now, a dry run; `?preview=0` skips it) and `POST` with `{ repost: true }`, both full-admin-only.
