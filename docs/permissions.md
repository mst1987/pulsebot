# Role permissions (who may see/do what)

Endnutzer-Sicht: siehe [guide-web-admin.md#einstellungen](guide-web-admin.md#einstellungen).

Access is **per area** (one admin-menu section) and **per level** (`read` = open it, `write` = act in it; write implies read). The area list and all the pure logic live in `src/config/permissions.js` — the single source of truth shared by server and client (the client gets the list from `/api/session` and `/api/settings`).

- **Configured** in Einstellungen → *Berechtigungen*: per Discord role, a read and a write toggle per area, stored as `config.rolePermissions = { [roleId]: { [areaId]: { read, write } } }` (settingsStore). A member's rights are the **union** over all their roles.
- **Base access** sits above the roles in the same tab: `config.baseAccess = { [areaId]: { read, write } }` is what **every logged-in Discord account** gets — no role, no guild membership required — and is unioned into the role grants, so it only ever widens. Empty by default; the intended use is `loot: read`, so members can look up what dropped. Because it does not depend on Discord, it also holds when the member lookup says "not a member" or fails outright (`BASE_ACCESS()` in `services/discord/userAccess.js`).
- **Resolved** in `computeAccess(userId)` of `src/services/discord/userAccess.js` (moved out of `web/http/auth.js`, which requires and re-exports it, so the bot can ask too — `commands/` may not require from `web/`): `ADMIN_USER_ID` and the admin roles from the *Zugang* tab are full admins (every area at write); everyone else gets the base access unioned with `accessForRoles(...)`. The session carries `{ isAdmin, access }` and is re-checked in the background every 5 minutes, so permission changes apply without a re-login. `resolveAccess(userId)` falls back to the base access when Discord cannot be asked; `userMayAny(userId, areas, level)` answers one question with it.
- **Enforced** centrally in `src/web/http/apiAccess.js`, *before* `apiRouter.handle()` dispatches. The area of an endpoint is not a second list any more: it is the `area` of the route's own entry in its module's `routes` table (`src/web/apiRoutes/*.js`, collected by `src/web/http/routeTable.js` — see "Routen registrieren" in docs/web-admin.md), so path, handler and permission are one line. The level follows the HTTP method (GET = read, else write) unless the entry pins `level`. An entry may list **several** areas — any one of them at the required level opens the path. **The gate is fail-closed** — a route without `area` (not registered, or registered with neither `area` nor `auth`) is admin-only, so a new route can never leak; `test/web/http/apiAccess.test.js` insists such an entry says `adminOnly: true` out loud, and its golden master (`test/web/http/fixtures/apiAccess.golden.json`) holds every path's area as the hand-kept table had it (#421). The three special kinds — `auth: "none"` (`UNGATED`), `auth: "menu"` (`ANY_AREA`), `auth: "token"` (`TOKEN_AUTH`) — are route entries too; `apiAccess.js` still exports the sets, derived from the table. `AREA_BY_PATH` is likewise derived, for the tests and the docs.
- **Full admins only, by design:** a route that no area should ever open says `adminOnly: true` and is listed under `adminOnly` in the golden master — the first is `GET /api/system/status` (*Systemstatus*, [system-status.md](system-status.md)). Its menu entry carries `"adminOnly": true` with empty `areas` in `src/config/menu.json`; `mayOpen()` in `lib/app/menu.ts` shows it to full admins only, so neither a role holding every area nor "Ansicht als Rolle" sees it.
- **Escalation guard:** `adminRoleIds`, `rolePermissions` and `baseAccess` are full-admin-only (`ACCESS_KEYS` in `apiRoutes/settings.js`, `requireFullAdmin`). A role with write access to "Einstellungen" can edit the bot config but neither sees nor saves who has access. The same gate covers the credentials to foreign systems — `anthropic` and `warcraftlogsV2` (`CREDENTIAL_KEYS`, together `FULL_ADMIN_KEYS`): a limited settings user gets neither block from `GET /api/settings` and a PATCH carrying one is refused, so the client sends them only behind `canManageAccess`. No secret ever goes back to the browser — `publicConfig()` replaces the Battle.net/WCL client secrets and the Anthropic key with `hasClientSecret`/`hasApiKey`.
- The client mirrors this cosmetically: `Shell.tsx` hides tabs, `App.tsx`'s `Guard` hides pages, and the SettingsPage hides the *Zugang*/*Berechtigungen* tabs. It is never the actual gate — the API is.

**The menu itself is not gated.** Everyone who is logged in gets the shell — sidebar, breadcrumb and, above all, the **logout**; an account with nothing granted lands on a notice with the sidebar saying so, instead of a bare sentence on an empty page with no way back out. Only an anonymous visitor gets the login screen without a shell. `test/web-client/conventions/menuAccess.test.js` holds that line.

**`loot` is a second area on the history tab** — the read-only slice of *Historie & Loot*: the loot views (Vergaben, Items with its by-player switch, and under Raids only the loot per raid) plus the event- and character-loot pages, and nothing else. It exists because the base access should let a member look up loot without handing them the raid lists, the logs and the imports. Consequences to keep in mind when touching those pages:

- The shared endpoints list **both** areas (`["history", "loot"]`), and `getHistoryData()` answers a loot-only caller with `lootOnlyHistoryData()` — the same payload shape with the other fields empty, which also skips the Raid-Helper and Discord round-trips that caller has no use for.
- `HistoryPage.tsx` renders only the areas the visitor's areas cover (the inbox page needs `history`), and the write actions (import, delete, category select, manual item) are behind `canAccess(user, "history", "write")` on all three pages. Writing anywhere in the history always takes `history`, never `loot`.

**Rights can also go to one named account**, not just to a role: `config.userPermissions` is `{ [userId]: { [areaId]: { read, write } } }` — the same shape as `rolePermissions`, keyed by Discord user id, edited in Einstellungen → *Berechtigungen* under "Einzelne Konten" and unioned in exactly like the base access (it can only widen). It exists for areas that go to named people rather than to a group; inventing a Discord role for two players is a second list to keep in sync. Like the base access it is resolved **without Discord** (`BASE_ACCESS(userId)` in `userAccess.js`), so such a grant survives an offline bot, and it is full-admin-only (`ACCESS_KEYS`).

**`kader` (Kaderplaner) goes to named people only.** It is in no base access by default and should stay out of it: full admins have it, others get it through a role grant or — the intended way — a single-account grant under "Einzelne Konten". `read` shows the planner, `write` edits it ([kaderplaner.md](kaderplaner.md)).

**The start page opens with `dashboard` or `signup` (Oct 2026).** `GET /api/dashboard` lists both areas, and the menu entry „Übersicht“ (`menu.json`) and `App.tsx`'s index route follow it, so every raider with the base access lands on „Für dich“ (`web/dashboard/dashboardPersonal.js`: only the caller's own raids, attendance, profile and evaluation). What else the answer carries is decided inside the handler: the orga block (next raid, figures, last raids) only with `raids` **write** (full admins always) - `raids` read alone is no orga rank, raider roles often hold it; `raids` read opens no category in "Für dich" either — it lists the raids the caller may sign up for plus their own signups, the orga included (docs/signups.md „Which raids a member sees“); each open task only with the right it takes to do it (`cla` write for recommendations, `history` write for the addon inbox, `raids` write for sheet and log assignment); "Für dich" only with `signup`.

**`raidplan` (Raidplan) is its own area, not a part of `raids`.** It covers every `/api/raidplan…` route (the plan on an event, the templates with their tactic profiles, the catalog, the Raid-Helper switch), `POST /api/raids/post-raidplan` (posting the link publishes the plan) and the two pages *Raidplan-Vorlagen* / *Raidplan-Katalog* (sub entries of Raid-Events in `menu.json`, coloured like it, reached through the icon rail of Raid-Events' pages; without `raids` the menu shows *Raidplan-Vorlagen* as the line of that family and the rail offers only the two raid plan pages). The point is to hand the tactics to people who do not run the events, and to stop the event orga getting them for free — so `raids` implies nothing here, and the other way round. When the area came in, nothing was carried over: only full admins had it until someone granted it. Consequences:

- **The plan of one event lives on that event's page**, so opening it takes `raids` read *and* `raidplan` read. Without `raidplan` read the "Raidplan" tab is not there (`RaidDetailPage.tsx`, `hasPlan`); the editor's `canWrite` is `raidplan` write, whatever `raids` says — or the orga of the raid's category (#726, below).
- **The "Einteilungen" step** (posting the link) comes only with the right to post it: `GET /api/raids/detail` builds with `planPost = raidplanAccess.canWriteRaidplan(user, event)` (`raidplan` write, or the raid category's orga), which otherwise leaves out `raidplanPost` and the own event's `plan` step (`eventSteps(d, { plan: false })`) — no button that fails at the server.
- **The orga of a category plans its raids (#726):** the writes on one event's plan and `POST /api/raids/post-raidplan` are `orgaScoped` with `globalByWrite` — `raidplan` write stays the right for every raid **without an orga rank** (unlike the setup), a manager of the category's current roster gets the raids of that category. Templates, tactic profiles, the catalog and the default maps stay `raidplan` write only (`canWriteLibrary` in the editor's answer). Details: docs/raidplan/model.md "Permissions".
- **`/api/game-versions`** is `["raids", "raidplan"]`: the template and catalog pages show one game version at a time.

**Discord roles of a roster need more than `roster` write (#656).** Giving or taking a roster's Discord role from the web (`POST /api/rosters/roles`, and the member changes of `services/roster/rosterMembers.js` the member routes build on) passes the area gate with `roster` **write** and then asks `rosterAccess.canManageRosterLive`: only a full admin or a manager of **that** roster (`managers.userIds`, or a role in `managers.roleIds` on the roster's server) — everyone else gets 403 `not_manager`. Reading the Abgleich lists (`GET /api/rosters/sync`) is `roster` read; its `canManage` tells the page whether to show the buttons. Discord itself is the other way in: whoever may hand out a roster role in Discord changes the roster too (docs/roster-profile.md "Roster und Discord-Rollen").

**Roster members and settings (#655, #657)** follow the same two steps. Taking members in, changing status, characters, note or trial end and taking them out (`POST /api/rosters/members`, `…/members/remove`) is `roster` write plus `canManageRosterLive`, else 403 `not_manager`. Creating and deleting a roster (`POST /api/rosters/create`, `…/delete`) is for **full admins** only (403 `admin_only`, also for a roster writer). `POST /api/rosters/update`: a full admin changes everything; a manager of that roster only name, slots, `allowMultipleChars` and `signupOnly` — a changed manager list, role, category or version answers 403 `admin_only`; anyone else 403 `not_manager`. Reading (`GET /api/rosters/options`, `…/composition`, `…/member-search`) is `roster` read; the Kader in the options appear only for a reader of the area `kader`. A **closed** roster (#739, its category switched to another game version) is read only for everybody, full admins included: every member, role and settings write answers 409 `roster_closed`; its managers still read it as its orga, and a full admin may delete it. Where a right comes from "the roster of the category" (attendance by hand, a raid's orga), it is the roster of the **raid's version** — a manager of the closed TBC roster has no say over a Forever raid, and a closed roster grants no attendance edits. Details: docs/roster-profile.md "Mitglieder bearbeiten", "Roster anlegen und einstellen" and "Roster je Version".

**Bot commands are a separate axis.** Who may run which command in Discord is not an area and not a `read`/`write` level — it hangs on Discord roles per command (`config.botCommandAccess`, Einstellungen → Berechtigungen → *Bot-Befehle*, see "Who may run a command" in docs/bot-commands.md). Full admins are admins there too; everything else is configured apart from the web areas. **One exception asks the web areas:** the guild bank's orga buttons (`commands/signup/guildBank.js`, *Erledigt* / *Ablehnen …* under a request in the orga channel) let every click through the bot gate and then require `raids` **write** via `userAccess.userMayAny` — the orga that handles requests is the orga that runs the raids in the web (docs/signups.md, „Gildenbank“).

## Orga-Rollen und Orga-Bereiche (`config.orgaRoleIds`, `src/web/http/areaAudience.js`, `components/ui/OrgaZone.tsx`)

**Who is orga is set, not guessed from areas.** In Einstellungen → Berechtigungen every role row carries a toggle chip **Orga / Raider** (`config.orgaRoleIds`, full-admin-only like the other access keys, `ACCESS_KEYS`). A raider role ("Mo Raider", "Mi Raider") may still be handed any area — reading or even changing raids makes nobody orga.

- **`userIsOrga(user)`** (`config/permissions.js`): a full admin, or `user.isOrga`. `userAccess.computeAccess` sets `isOrga: true` (only then — the key is left out otherwise) when a non-admin holds an orga role on an event server; login and the 5-minute re-check store it on the session (`auth.js`); *Ansicht als* recomputes it from the viewed roles (`viewAs.accessAsRoles`), never keeping the admin's own. `GET /api/session` sends `user.isOrga` and `user.orgaRoles` (names, admin roles left out).
- **What the orga gets:** the dashboard's orga block (`/api/dashboard` `orga`; each task still needs its own right) and everybody's absences (`/api/availability/overview`, `…/overview/raider`: 403 `orga_only` for anyone else, whatever areas they hold — a raider sees "Meine Anwesenheit"). **Roster pages:** a raider with `roster` read sees the roster cards and the Komposition only; members, attendance, Discord sync, history, the all-characters list, claims and other people's profiles are orga (403 `orga_only`, or a trimmed view). A **manager of a roster counts as orga for that roster** (`rosterAccess.isRosterOrga`), not for the others. Details: docs/roster-profile.md "Orga und Raider im Roster". **Addons:** an addon marked `orgaOnly` (Einstellungen → Module → Addons, default: the EventHelper Sync tool) is for `userIsOrga` only — absent from `GET /api/addons` and `/addons` for everyone else, 403 `orga_only` on `GET /api/addons/download` (docs/addons.md).
- **`withUser({ orga: true })`** (`web/http/apiHandler.js`): 403 `orga_only` for a non-orga, before the write check — on `/api/dashboard/next-raid`. The routes that had it on events (every "Event verwalten" route, the raid detail's actions, the setup editor's writes) are `orgaScoped` since #725–#728 — the same orga gate plus the orga of the raid's category (see "Kategorie-Orga"); a raider role with `raids` write still gets 403 `orga_only` there.
- **Which raids a raider sees** (`services/signups/eventVisibility.js`, one rule for every read): the orga every raid; anyone else the categories they may sign up for (`signupAccess.canSignUp` for the raid's version, Discord roles best-effort, a failed lookup = no roles), the categories whose roster of the raid's version opened its raids (`roster.publicRaids` via `categoryRoster.rosterOfEvent`, seeing only — the signup keeps its rules) and every raid they signed up for. `GET /api/raids` and `/past` filter by it (the past rows lose their logs for a raider); `GET /api/raids/detail`, `GET /api/raids/setup` and `GET /api/raidplan` answer a hidden raid with the same 404 as an unknown one. `raids` read no longer opens every category (`/api/signups`, "Für dich"). Loot is never filtered by it.
- **The raid detail for a raider** (`web/events/raidDetailView.js` `forRaider`): no logs, no attendance lists or role ids, no other raiders' comments or "kann auch", no player summaries, no event log count, no steps, none of the dialogs' data (templates, roles, sheets, softres edit link). The client mirrors it with `isOrga(user)` and draws the orga's parts (steps, the roster's lists and actions, the Logs tab) in an `OrgaZone`.
- **Marks (design canvas Oct 2026, E + B):** `user.audience` per area the caller may open: `{ everyone, roles, writers, raiders, accounts }` — `everyone` = the base access **or any raider role** opens it; `roles`/`writers` = the orga roles that open it / change in it; `raiders` = the raider roles that open it. A page is orga (`lib/app/orgaArea.ts` `pageAudience`) when none of its areas is a raider area, or when it is adminOnly (Systemstatus). **`OrgaChip`** in the top bar of such a page (right after the breadcrumbs, `Shell.tsx`; the bar gets a thin teal edge, `.topbar.is-orga`): a teal chip "Orga-Bereich", the rest ("Raider sehen diese Seite nicht", "sichtbar für Admins · @Orga-Rolle …") in its tooltip and its accessible name (`role="note"`), for a full admin a small "So sieht es ein Raider" button beside it (*Ansicht als* with no role); on a phone (≤ 640 px) both shrink to their icons. **`OrgaDot`** in the menu (aria-hidden, the chip says it in words). **`OrgaZone`** around the orga's part of a page everybody sees (dashboard orga block, absence overview), naming the admins and the orga roles.

## Kategorie-Orga (`src/services/roster/categoryOrga.js`, #724, Epic #723)

**The managers of a category's roster are the orga of that category** — for its setup, raid plan, signups and events — beside the global orga (`userIsOrga`), who is the orga of every category. One helper answers it for the web, the Orga-Zentrale in Discord (`orgaHubBot.js`, `orgaHubLinks.js`) and the attendance overrides (`attendanceAccess.js`):

- **`isCategoryOrga(user, categoryId)`**: global orga, or a manager (`rosterAccess.canManageRosterLive`: account or role on the roster's server) of the roster the category plays **now** (`categoryRoster.currentRoster`). A category without roster has only the global orga. `isCategoryOrgaById(userId, categoryId)` does the same for a bare Discord id (rights via `userAccess.resolveAccess`).
- **`canOrgaEvent(user, event)`** (an id or a row): global orga, or a manager of the roster of the raid's category **in the raid's version** (`categoryRoster.rosterOfEvent`, #739 — the manager of the TBC roster has no say over a Forever raid). **The server's record always wins**, category and version alike: an own event (`eh-`) from the event store, a Raid-Helper event from its snapshot (`raidEventStore`) or the event groups (`loadEventGroups`) — a row's `categoryId` or `versionId` never overrules it, and an id the server does not know (an unknown `eh-` id included) is no raid: `false`. A row's `categoryId` counts only for a row **without** id ("a new event in category X", #728), in the version the category plays now. `managerOnly: true` leaves the global orga out (the category path of the gate).
- **Which roster gives the right — on purpose:** only the **current** roster (`categoryRoster.isCurrentRoster`: open, and of the version the category plays now) — for a raid as well as without one, so `canOrgaEvent` never says more than the gate's `isAnyCategoryManager` (#725 review). A closed roster (`closedAt`, #739: its category switched version) makes nobody orga, not for its old raids either; an open roster that is not current yet (e.g. a Forever roster prepared before the switch) gives no right until the category plays that version.
- **`orgaCategoryIds(user)`**: the categories whose current roster they manage (the global orga: every category with a roster); **`isAnyCategoryManager(user)`**: whether that list is not empty, the global orga not counted.
- **Discord roles once per request:** every question takes a `cache` (`requestCache(req)`, one per HTTP request, shared by gate and handler) and reads a member's roles at most once per server, at most `ROLE_FETCH_MS` (3 s) long; a failure or a timeout is "no role".
- **Attendance by hand** stays as it was: full admin or `raids` write, else a manager of the night's **open** roster (`managesRoster`, without the global orga).

**The gate — `orga: true` and `orgaScoped`** (`web/http/apiHandler.js`, `apiAccess.gate`):

| Mark on `withUser` | Global orga (admin, orga role) | Manager of a category's roster | Anyone else |
|---|---|---|---|
| none | area + `write` as always | area + `write` as always | area + `write` as always |
| `orga: true` | area + `write` | 403 `orga_only` | 403 `orga_only` |
| `orgaScoped: (body, query) => eventId(s)` | with the area and `write`: every raid, as `orga: true`; **without** them: the manager path (never less than a manager) | area gate passes, `write` is not asked, then **every** named event must be one of their categories (`canOrgaEvent`), else 403 `not_category_orga`; naming no event, or an empty entry in a list, refuses too | 403 `orga_only` (or the area refusal) |
| `orgaScoped` + `globalByWrite: true` (needs `write`) | with `write`: every raid; without it: the manager path | as above | with `write`: every raid, **no orga rank needed**; without it: 403 `forbidden` |

`globalByWrite` is for an area handed to people outside the orga — the raid plan (#726): there the `write` right alone is the global path, so a tactician without orga rank keeps every raid; everyone without it (a global orga too) takes the category path.

The two marks exclude each other (an error at load). The wrapper carries `handler.orgaScoped = true`; `routeTable.isOrgaScoped(route)` reads it, so the mark on `withUser` is the only place — the area gate (`apiRouter.handle` → `apiAccess.gate`) widens a 403 `forbidden` only on such a route **with areas** (never an `adminOnly` or area-less one), for a menu user who manages some current roster (a global orga without the area too), and only after `checkAccess` refused; it then marks the request's cache (`areaViaCategory`) so the handler takes the category path. Order in `withUser`: menu user → orga (global, or any category for `orgaScoped`) → `write` (skipped on the category path) → CSRF → body → the event check (`not_category_orga`) → `archived` (409) → handler — a raid of another category is "not yours" before it is "archived". The golden master (`test/web/http/fixtures/apiAccess.golden.json`, `orgaScoped`) lists every marked route — each one is a deliberate change. #725 marked the setup editor (every write route of `apiRoutes/setup.js`, `move-raid` with both raids; its `canWrite` per event, docs/setup.md); #726 the raid plan at the event (every write on one event's plan and `POST /api/raids/post-raidplan`, with `globalByWrite`; `canWrite` / `canWriteLibrary` per event, docs/raidplan/model.md "Permissions"); #727 the signups, #728 the events (below). The function gets `(body, query, req)` — `req` for what only the request knows (a new event's category needs its server).

**Signups (#727).** `orgaScoped` (by the body's / query's `event`): in `apiRoutes/eventManage.js` `POST /api/raids/manage/signups` (close/open), `GET /api/raids/manage/raider` (the add dialog's candidates), `POST /api/raids/manage/raider` and `…/raider/remove`; in `apiRoutes/raidDetail.js` `POST /api/raids/notify` (Anmelde-Aufruf), `/ping-missing` and `/invite-call`. A category orga's Anmelde-Aufruf goes into **the raid's own channel** (the server's record, `resolveEventForPost`) — a `channelId` in the body counts only for the global orga with `raids` write — and pings **only the raider roles of the raid's category** in the raid's version (`categoryRoles.expectedRoleIds`); any other role id refuses the whole call with 400 `role_not_allowed` (refused, not filtered: the dialog offers every role of the server, a silently shortened ping would reach other people than picked). The global orga with `raids` write pings any role, as before. The own signup's exemption `byOrga` (`PUT /api/signups`, `/bulk`) is the orga of that raid: `web/events/raidOrgaAccess.js` `canOrgaRaid` (global orga with `raids` write, else `canOrgaEvent` with `managerOnly` — the gate's rule; `setupAccess.canWriteSetup` is the same rule); `GET /api/signups` exempts the global orga only (its marks only show in „Alle Kategorien“). The raid detail still shows a category orga the raider view (`raidViewer`) — the buttons come with #729. **Discord:** the orga buttons at an event („Fehlende pingen“, „Invite callen“, the setup pings, Event verwalten) are judged by the `/event` command's right (`accessOf: "event"`, `botAccess.js`), not by the orga rank or a category — unchanged here; the Discord signup knows no orga exemption. **Deliberate, open for a decision (16.10.2026):** a category orga's „Raider eintragen“ offers every raider profile of the server as a candidate (helpers, PuGs), and adding a raider with a character missing from their profile writes that character into their global profile — before #727 both were the global orga's only.

**Events (#728).** `orgaScoped` with `write: "raids"` (no `globalByWrite`: the global path is the orga with `raids` write — a raider role holding `raids` write but no orga rank, which used to create events, edit them and keep series, now gets 403 `orga_only` there, as the client already hid those buttons from it):

- **Create** `POST /api/raids` by the new event's category (`web/events/eventCreateAccess.js` `newEventRow` → `{ categoryId }`, a row without id = the roster the category plays now): the category is the server's — the clone's source event, else the chosen channel's Discord parent, else the new channel's category (`eventCreate.requestedCategoryId`; never a `categoryId` the body claims). `createEvent`'s `guard` (`createGuard`) checks again on what the create really became, before any channel is made: their category (403 `not_category_orga`), the version the category plays **now** — a `versionId` of the request never counts, a different one is 409 `version_fixed` —, a template channel (`newChannel.templateChannelId`) and a voice channel of that category only (its preset / its schema's template, or a channel inside it; else 400 `channel_not_allowed`). The global orga keeps every category and every value of the request.
- **Edit** `PATCH /api/raids` by `id`: their raid, its version kept (409 `version_fixed`), a new voice channel of its category only. The setup editor's „Mehr → Raidgröße“ calls it, so `canEditEvent` in `GET /api/raids/setup` is the setup's `canWrite` (#725's rule).
- **The create dialog** `GET /api/raids/new` (area `raids` read): everyone but the global orga with `raids` write gets only the categories whose current roster they manage (`orgaCategoryIds` with `managerOnly`) and with them only those categories' text and voice channels (plus their voice presets), raids to repeat, leader candidates and an event to edit only when it is one of their raids — a raider none of it. `canSaveTemplate` (`raids` write) hides „Als Vorlage speichern“: raid templates stay global.
- **Event verwalten** (`apiRoutes/eventManage.js`): every route, by `event` — `GET /api/raids/manage` (state and log of the dialogs), the move preview and move, cancel, reopen, delete, recreate-channel. None of them changes a raid's category: a move keeps the channel in its category, an archived channel goes to the server's archive category, a recreated one into the raid's stored category.
- **Raid detail** (`apiRoutes/raidDetail.js`) by `event`: fill and post the sheet, post softres, create/link softres, the loot system and the softres item search (`GET /api/raids/softres/item-search?event=` — the picker names its raid; the global orga searches without one). Posts go to the raid's own channel, the server's record.
- **Series** (`apiRoutes/eventSeries.js`) by `categoryId` (`{ categoryId }`, the category's current roster): `PUT`, `DELETE`, `POST …/run` (a sweep of every series at once, without `categoryId`, is the global orga's) and the preview (`category`, no `write`). `GET /api/raids/series` lists the global orga every category (`canWrite` with `raids` write), the orga of a category theirs (`canWrite` true), anyone else none; `canRunAll` (the global orga with `raids` write) shows „Jetzt prüfen“, the sweep of every series.
- **Unchanged:** raid templates (`/api/raid-templates`) stay `raids` write; the channels page's quick create with events (`apiRoutes/channels.js`) stays area `channels`. **Discord:** the Orga-Zentrale's „Raid anlegen“ asks the `/event` command right *and* `isCategoryOrga` for the hub's category; the create flow it opens (`eventDraft.js`) and the „Event verwalten“ panels hang on the `/event` command right alone (`accessOf: "event"`), not on a category.

## Ansicht als Rolle (`src/web/http/viewAs.js`, `components/shell/ViewAs.tsx`)

A full admin can look at the whole menu **with the rights of one or more Discord roles**, like Discord's "View server as role" — to test what the permission matrix really opens up. The eye button in the top bar opens the role picker (roles of the permission server, marked *Admin* / *Rechte* / *ohne Rechte*); no role picked = only the base access. While it runs, a bar above every page names the roles and offers *Ändern* and *Beenden*.

- **One switch, every gate:** the session keeps the admin's own `isAdmin`/`access` and only gets `viewAs = { roleIds, at }`. `auth.getUser()` hands every reader `effectiveUser()` — a **copy** with what a member holding exactly those roles would get (an admin role → full admin; else `baseAccess` ∪ the roles' `rolePermissions`; single-account grants are left out, they belong to a person). So `apiAccess.checkAccess`, `requireAdmin`/`requireFullAdmin`, the SSR pages and the client's hidden tabs all show the role's view with nothing else to keep in sync. Actions still run under the admin's name, but only with the role's rights.
- **Safety:** only a real full admin can start a view (`auth.getRealUser`, re-checked when the 5-minute refresh demotes the account — the view is then ignored); `/api/session/view-as` is in `UNGATED` and checks the caller's **own** rights in its handler, so *Beenden* works even from a role that may open nothing (CSRF still required); a view older than 12 h (`MAX_AGE_MS`) ends by itself. Starting and stopping reload the menu from `/`.
- **API:** `GET /api/session/view-as` (roles), `POST /api/session/view-as { roleIds }` / `{ stop: true }`; `GET /api/session` carries `user.canViewAs` and, while a view runs, `user.viewAs { roleIds, roleNames, at }`. Bot commands in Discord are not affected.
- **The raid lists count with the viewed roles too:** „Für dich“ and „Anmeldungen“ ask `web/signups/viewerRoles.js`, which takes `user.viewAs.roleIds` instead of the admin's own Discord roles on the event server — otherwise an admin holding every raider role would preview every raid. A roster-only category counts a holder of the roster's roles as its member (a role has no roster membership), and the admin's own signups make no raid visible. Rows of a visible raid still show the admin's own status: the view is per role, not per person.
- **Tests:** `test/web/http/viewAs.test.js`, the flow in `test/web/http/auth.test.js`, the routes in `test/web/apiRoutes/session.test.js`, the client in `test/web-client/conventions/viewAs.test.js`; the raid lists in `test/web/apiRoutes/dashboard.forYou.test.js` and `test/web/apiRoutes/signups.test.js`.

## Public, token-guarded read routes (`UNGATED`)

Besides the session bootstrap, `UNGATED` holds `/api/raidplan/public`: the read view of a **published** raid plan (`/p/<token>`, docs/raidplan.md). It needs no session because the token in the address is the authentication; its handler answers only for the token of a published plan (unknown, withdrawn and orphaned all get the same 404), and a session, when there is one, only marks the viewer's own token. Every other `/api/raidplan…` path is area `raidplan` (see above).
