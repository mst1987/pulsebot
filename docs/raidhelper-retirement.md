# Umstieg von Raid-Helper (`src/web/events/raidhelperRetirement.js`, #291)

Endnutzer-Sicht: siehe [guide-discord.md#umstieg-von-raid-helper](guide-discord.md#umstieg-von-raid-helper).

The last package of #286: everything the EventHelper needs to replace Raid-Helper completely, and the switch that stops asking Raid-Helper. **Nothing is deleted and nothing flips silently.**

**Raid-Helper stays a supported source for as long as a server wants it.** This page is the way out for a server that wants to leave, not a plan to leave: features that work with Raid-Helper events keep working (the raid plan of a Raid-Helper event, docs/raidplan.md "Raid-Helper-Events", is a permanent mode and does not depend on this switch — switched off, it plans from the line-up it saved last).

- **Per Discord server (#927).** Raid-Helper is set **per server** in `config.serverSettings[guildId].raidhelper = { enabled, serverId, apiKey, envKey, at, byName }` (off by default), read only through `utils/raidhelper/servers.js` (`raidhelperOf(guildId)` resolves `{ enabled, serverId, apiKey, active }`, `activeRaidhelperGuilds()` lists the servers that sync). `serverId` is an optional override of the Raid-Helper server id (empty = the Discord server's own id) — needed for dev instances, whose `GUILD_ID` is the test server while Raid-Helper's events live under another id. The key is the server's own `apiKey`; `envKey: true` (set only by the migration for the server that used Raid-Helper before) lets it use `RAIDHELPER_API_KEY` from `.env` — the key is never copied into `config.json`. A server is **active** only when `enabled` and a key is there; an inactive server sends **no request at all** (its client answers like the switched-off one) and its categories offer **only EventHelper** for new events (`signupSourceFor` ignores a stored `raidhelper`). `categorySignupSource` stays per category.
  - **Settings:** Einstellungen › Server › Raid-Helper (`pages/settings/connections/SettingsRaidhelperServer.tsx`, full admins): switch, Raid-Helper server id, key as a password field. The client only ever gets `maskedRaidhelper` — `hasKey` and the **last 4 characters** (`keyLast4`), never the key. `PATCH /api/settings { raidhelper: { enabled?, serverId?, apiKey? } }` saves the active server's block: no `apiKey` keeps the stored key, `""` clears it, a bad value is 400 `invalid_raidhelper`. While the server is on, the sync card and the checklist sit under the form.
  - **Migration** (`settingsMigration.migrateRaidhelperServers`, once, while no server has a block): the server Raid-Helper ran for (old `raidhelperServerId` / `RAIDHELPER_SERVER_ID`, else the first server) gets `enabled` from the old global switch and `envKey`; every other server starts off. `raidhelper-events.json` and `raidhelper-budget.json` of before #927 move to that server (idempotent on every start). The old `raidhelperServerId` in Verbindungen › Discord is only read by this takeover now.
- **Default source.** `config.signupSourceDefault` is what a category without an entry in `categorySignupSource` gets — `"eventhelper"` for a fresh install. The map keeps **both** values now. A config from before #291 (no `signupSourceDefault` stored) gets every category it configured anything for (`categoryIds`, raider roles, template, loot addon, sheet, reminders) pinned to `"raidhelper"` on read (`settingsStore.signupSourcesOf`), and the next save writes that down — so only categories added later start on EventHelper. An old config without any category keeps `"raidhelper"` as its default. `eventSources.signupSourceFor(categoryId, config)` is the one reader; `GET /api/raids/new` hands the dialog every category already resolved, and the category list in Einstellungen shows an "n noch Raid-Helper" badge in its head (names in the tooltip).
- **The switch** is per server since #927: switching off writes `enabled: false` (with `at`, `byName`) into that server's `serverSettings[guildId].raidhelper`; the old global `config.raidhelperRetirement` is only read by the migration. It takes effect in `utils/raidhelper/client.js`, the single place every caller gets its client from: switched off, `createRaidhelperClient()` returns a client that asks raid-helper.xyz **nothing** — reads answer empty (`[]`, no raidplan, `getEvent` → `{}`), writes (`createEvent`, `signUpToRaid`) are refused with `code: "raidhelper_disabled"`. `raidEventScan` returns `{ disabled: true }` without a request. Every reader then behaves exactly as during an outage, minus the error: `loadEventGroups` with a lookback and `loadMatchableEvents` merge `raidEventStore`'s snapshots, so past Raid-Helper raids stay readable (detail page, logs, loot, attendance). Reversible at any time.
- **The checklist** (`buildChecklist` pure, `loadChecklist` gathers, computed on every read): `categories` (every event category on EventHelper, x / y, the rest named — **required**), `upcoming` (no upcoming Raid-Helper event, listed — **required**; a Raid-Helper that does not answer is `unknown` and does not block, "not reachable" is exactly when one wants to switch it off), `history` (spec history imported), `emojis` (app emojis, `appEmojis.appEmojisLoaded()` tells "missing" from "bot offline"), `discordevent` (#305: the categories that want a Discord event per raid and whether the bot has "Events verwalten" — `info`/"aus" while no category does, `bad`/"Recht fehlt" otherwise; a recommendation, never a blocker), `commands` (hint only: `npm run register`), `permissions` (`discord.botPermissionsIn` on that server). Each item carries `status` ok/mid/bad/unknown/info, `value`, `why` (one line), `detail[]`, `required` and a `link` into the menu, an `action` or a `hint` (command). `setRaidhelperDisabled(true)` refuses with `not_ready` + `blockers` while a required item is open; switching back on always works.
- **Spec history** (`src/web/events/raidhelperHistoryImport.js` + `src/stores/roster/specHistoryStore.js`, `data/settings/spec-history.json`): for the last N (default 10, max 50) Raid-Helper events **per category** — `raidEventStore` snapshots merged with the live `getPastEvents` (className and the signup's name), a switched-off or failing Raid-Helper leaves the snapshots — every signup's `className`/`specName` becomes a rule-set spec key through `eventSources.specKeyFromRaidHelper` (the reverse of `RH_SPEC_NAMES`, classlist aliases like `Destro`/`RestoSham`, a real class wins over an ambiguous name: "Holy" on a paladin is Paladin-Holy). Absences, Bench/Tentative pseudo specs and own events are skipped, unmapped names are counted. **No event is created or copied.** Stored per user and spec: `{ count, lastAt, lastEventId, character }`; **idempotent per event** (`importedEventIds`), so a second run only adds new raids. `planImport()` is pure and is what the dry run shows. Readers: `signupStore.lastSignupOf` falls back to it when the raider has no own signup (`imported: true`), and `joinPicker.defaultPick` then matches **by spec alone** (the main first), labelled "zuletzt" — never for an own signup. `GET /api/profile` carries the caller's own `specHistory` (nobody else's), and *Charakter hinzufügen › Von Hand* prefills class, specs and name from it (`lib/settings/raidhelperRetirement.ts`' `specSuggestion`, badge "aus Raid-Helper").
- **Where:** the checklist and the switch belong to the active server (#927). Script `node scripts/import-raidhelper-history.js [--dry-run] [--per-category n] [--guild id] [--no-live] [--dev]`; web: Einstellungen › Server › Raid-Helper, card "Umstieg von Raid-Helper" (`pages/settings/connections/SettingsRaidhelperRetirement.tsx`, rules in the strippable `lib/settings/raidhelperRetirement.ts`, CSS `rhr-` in `styles/settings.css`): one line per item (badge, label with why/detail/command/Pflicht in its tooltip, value, link), the switch in the foot (disabled with the reason until ready, asks first), "Importieren …" opens a dialog with the number per category, *Probelauf* first and *Importieren* only after a dry run found something. API (full admins, area `settings`): `GET /api/settings/raidhelper-retirement`, `POST … { disabled }` (409 `not_ready`), `POST /api/settings/raidhelper-history-import { perCategory, dryRun }` (dry run unless `dryRun: false`, on the first server).
- **Audit of the features with own events** (all covered by tests): Softres suggests from an own event's `instanceIds` (`softres.codesForRulesetInstances`) instead of guessing from the title; the dashboard counts an own event's **approved** setup (`setupCount`, never a draft) and takes its boss icon from its raids (`dashboardOverview.zoneForEvent`); loot import, addon inbox (`suggestMatch`), log auto-link, roster attendance, loot-council categories and `/raids`/`/raid` already read both sources through the adapters. `helper.getCategoryEvents`, `show-allsetups` and the setup lookups no longer fail completely when Raid-Helper does not answer — the own events stay.
- **Abgleich und Tageslimit (#608).** Raid-Helper allows **1000 requests per API key in 24 hours**; past that it answers HTTP 429 (`Rate limit encountered: 1000 / 24h`) to everything, a signup included. Pages, commands and jobs used to ask on every view and every tick and used the day up. Now:
  - **One job asks for the list — per active server (#927):** `services/events/raidhelperSync.js` (job `raidhelperSync` in `web/http/jobs.js`) runs once for every server in `activeRaidhelperGuilds()`, each with its own key and Raid-Helper server id, and fetches every event from `EVENT_LOOKBACK_DAYS` back on — upcoming ones included, signups too — with **one** request every 5 minutes into that server's slot of `stores/events/raidhelperEventsStore.js` (`{ servers: { [guildId]: … } }`), then runs the snapshot scan (`raidEventScan.scanAllGuilds({ probeSetups: true })`). A failed sync keeps the last list. A successful write through a client (`createEvent`, `signUp`) asks for a sync 5 s later.
  - **Everyone else reads the copy:** `createRaidhelperClient()` hands out a `Raidhelper` with `snapshot`, so every list read (`fetchEvents` and everything built on it: `getAllEvents`, `getPastEvents`, `getTemplates`, `getUserSignUps`, …) answers from the store and throws `NOT_SYNCED` before the first sync. Only the job and the history import use `{ live: true }`. Single reads (`getSetup`, `getEvent`) stay live but are kept 5 minutes per id (`cacheMs`); a page view's scan asks for no raidplan at all, a raid without one is probed again after 6 h at the earliest.
  - **The budget is the safety net:** `utils/raidhelper/budget.js` counts every attempt (retries too) per hour **and per server** in `stores/events/raidhelperBudgetStore.js` (`{ servers: { [guildId]: … } }`, survives restarts; every server has its own 1000 because every key does) and refuses before sending (`code: "raidhelper_budget"`, German message with the time it frees up): background (every job runs inside `runInBackground`, the async context carries to its timers) at 450, reads at 750, writes at 850 (`RAIDHELPER_BUDGET` in `config/constants.js`). A 429 that still comes back pauses **that server** for the hours Raid-Helper names plus one — the other servers keep going. Dev instances share the key: all of them get 100 and **no background requests** unless `RAIDHELPER_BACKGROUND=1` — use "Jetzt aktualisieren" or the fixture (`EVENTHELPER_RH_FIXTURE`).
  - **Errors say why:** a `status: "failed"` payload is thrown as an Error with Raid-Helper's `reason` (`Raid-Helper: Rate limit …`) instead of the bare object that made every page show "Events konnten nicht geladen werden (Raid-Helper API)".
  - **Where:** Einstellungen › Server › Raid-Helper, card "Raid-Helper-Abgleich" (the active server's numbers) (`pages/settings/connections/SettingsRaidhelperSync.tsx`): last sync, events, requests in 24 h, a pause, the last error and **Jetzt aktualisieren** (at most every 30 s). API (full admins, area `settings`): `GET /api/settings/raidhelper-sync`, `POST /api/settings/raidhelper-sync`.
- **Legacy bot commands:**

| Command | With own events |
|---|---|
| `/signup` | In an own event's channel it answers with the way that knows the rules (select under the event message, `/signups?event=`); Raid-Helper events as before |
| `/fillsetup` | `setup_id` optional: `eh-…` or empty (= the channel's own event) fills from the **approved** setup; a number is still a Raid-Helper raidplan |
| `/show-signups`, `/show-mysetups`, `/show-allsetups` | Both sources (`helper.getCategoryEvents`, `ownSignedUpEvents`, `ownApprovedSetup`); a failing Raid-Helper leaves the own events |
| `/createoverview`, `update-events` | The self-updating raid overview of a category (docs/discord-servers.md, "Raid-Übersicht je Kategorie"): reads `loadEventGroups` (both sources, Raid-Helper only through the central cached sync), no Raid-Helper request of its own |

Once every server has switched off Raid-Helper for good, `commands/setup/signup.js` (the legacy `/signup` above, which only ever spoke Raid-Helper), `show-*` (and the old `update-events` button) are candidates to remove together in one pass rather than one at a time — see #430. The one-off migration `scripts/import-raidhelper-history.js` (and its test `test/scripts/importRaidhelperHistory.test.js`) goes in the same pass: once Raid-Helper is gone there is nothing left to import (#418, `scripts/README.md`).
