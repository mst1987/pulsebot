# Umstieg von Raid-Helper (`src/web/raidhelperRetirement.js`, #291)

The last package of #286: everything the EventHelper needs to replace Raid-Helper completely, and the switch that stops asking Raid-Helper. **Nothing is deleted and nothing flips silently.**

- **Default source.** `config.signupSourceDefault` is what a category without an entry in `categorySignupSource` gets — `"eventhelper"` for a fresh install. The map keeps **both** values now. A config from before #291 (no `signupSourceDefault` stored) gets every category it configured anything for (`categoryIds`, raider roles, template, loot addon, sheet, reminders) pinned to `"raidhelper"` on read (`settingsStore.signupSourcesOf`), and the next save writes that down — so only categories added later start on EventHelper. An old config without any category keeps `"raidhelper"` as its default. `eventSources.signupSourceFor(categoryId, config)` is the one reader; `GET /api/raids/new` hands the dialog every category already resolved, and the category list in Einstellungen shows an "n noch Raid-Helper" badge in its head (names in the tooltip).
- **The switch** `config.raidhelperRetirement = { disabled, at, byName }` lives in `utils/raidhelperClient.js`, the single place every caller gets its client from: switched off, `createRaidhelperClient()` returns a client that asks raid-helper.xyz **nothing** — reads answer empty (`[]`, no raidplan, `getEvent` → `{}`), writes (`createEvent`, `signUpToRaid`) are refused with `code: "raidhelper_disabled"`. `saveRaid` still works: it talks to Pulse GDKP, not to Raid-Helper. `raidEventScan` returns `{ disabled: true }` without a request. Every reader then behaves exactly as during an outage, minus the error: `loadEventGroups` with a lookback and `loadMatchableEvents` merge `raidEventStore`'s snapshots, so past Raid-Helper raids stay readable (detail page, logs, loot, attendance). Reversible at any time.
- **The checklist** (`buildChecklist` pure, `loadChecklist` gathers, computed on every read): `categories` (every event category on EventHelper, x / y, the rest named — **required**), `upcoming` (no upcoming Raid-Helper event, listed — **required**; a Raid-Helper that does not answer is `unknown` and does not block, "not reachable" is exactly when one wants to switch it off), `history` (spec history imported), `emojis` (app emojis, `appEmojis.appEmojisLoaded()` tells "missing" from "bot offline"), `discordevent` (#305: the categories that want a Discord event per raid and whether the bot has "Events verwalten" — `info`/"aus" while no category does, `bad`/"Recht fehlt" otherwise; a recommendation, never a blocker), `commands` (hint only: `npm run register`), `permissions` (`discord.botPermissionsIn` on the event server). Each item carries `status` ok/mid/bad/unknown/info, `value`, `why` (one line), `detail[]`, `required` and a `link` into the menu, an `action` or a `hint` (command). `setRaidhelperDisabled(true)` refuses with `not_ready` + `blockers` while a required item is open; switching back on always works.
- **Spec history** (`src/web/raidhelperHistoryImport.js` + `src/web/specHistoryStore.js`, `data/settings/spec-history.json`): for the last N (default 10, max 50) Raid-Helper events **per category** — `raidEventStore` snapshots merged with the live `getPastEvents` (className and the signup's name), a switched-off or failing Raid-Helper leaves the snapshots — every signup's `className`/`specName` becomes a rule-set spec key through `eventSources.specKeyFromRaidHelper` (the reverse of `RH_SPEC_NAMES`, classlist aliases like `Destro`/`RestoSham`, a real class wins over an ambiguous name: "Holy" on a paladin is Paladin-Holy). Absences, Bench/Tentative pseudo specs and own events are skipped, unmapped names are counted. **No event is created or copied.** Stored per user and spec: `{ count, lastAt, lastEventId, character }`; **idempotent per event** (`importedEventIds`), so a second run only adds new raids. `planImport()` is pure and is what the dry run shows. Readers: `signupStore.lastSignupOf` falls back to it when the raider has no own signup (`imported: true`), and `joinPicker.defaultPick` then matches **by spec alone** (the main first), labelled "zuletzt" — never for an own signup. `GET /api/profile` carries the caller's own `specHistory` (nobody else's), and *Charakter hinzufügen › Von Hand* prefills class, specs and name from it (`lib/raidhelperRetirement.ts`' `specSuggestion`, badge "aus Raid-Helper").
- **Where:** script `node scripts/import-raidhelper-history.js [--dry-run] [--per-category n] [--guild id] [--no-live] [--dev]`; web: Einstellungen → Verbindungen, card "Umstieg von Raid-Helper" (`components/SettingsRaidhelperRetirement.tsx`, rules in the strippable `lib/raidhelperRetirement.ts`, CSS `rhr-` in `styles/einstellungen.css`): one line per item (badge, label with why/detail/command/Pflicht in its tooltip, value, link), the switch in the foot (disabled with the reason until ready, asks first), "Importieren …" opens a dialog with the number per category, *Probelauf* first and *Importieren* only after a dry run found something. API (full admins, area `settings`): `GET /api/settings/raidhelper-retirement`, `POST … { disabled }` (409 `not_ready`), `POST /api/settings/raidhelper-history-import { perCategory, dryRun }` (dry run unless `dryRun: false`, on the event server).
- **Audit of the features with own events** (all covered by tests): Softres suggests from an own event's `instanceIds` (`softres.codesForRulesetInstances`) instead of guessing from the title; the dashboard counts an own event's **approved** setup (`setupCount`, never a draft) and takes its boss icon from its raids (`dashboardOverview.zoneForEvent`); loot import, addon inbox (`suggestMatch`), log auto-link, roster attendance, loot-council categories and `/raids`/`/raid` already read both sources through the adapters. `helper.getCategoryEvents`, `show-allsetups` and the setup lookups no longer fail completely when Raid-Helper does not answer — the own events stay.
- **Legacy bot commands:**

| Command | With own events |
|---|---|
| `/signup` | In an own event's channel it answers with the way that knows the rules (select under the event message, `/signups?event=`); Raid-Helper events as before |
| `/fillsetup` | `setup_id` optional: `eh-…` or empty (= the channel's own event) fills from the **approved** setup; a number is still a Raid-Helper raidplan |
| `/saveraid` | Own event of the channel first (approved setup, refused without one), else the Raid-Helper post; clear error without any event |
| `/show-signups`, `/show-mysetups`, `/show-allsetups`, `/createoverview`, `update-events` | Both sources (`helper.getCategoryEvents`, `ownSignedUpEvents`, `ownApprovedSetup`); a failing Raid-Helper leaves the own events. The overview's successor is the raid overview on the talk server |
