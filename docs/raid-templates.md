# Spielversionen und Raid-Vorlagen

Endnutzer-Sicht: siehe [guide-web-admin.md#raid-vorlagen](guide-web-admin.md#raid-vorlagen).

## Spielversionen und Instanzen (`src/config/gameVersions/`)

One rule set per game version — `tbc.js` (TBC Anniversary), `classic.js` (Classic Era), `forever.js` (WoW Forever) — pure data plus pure functions in `index.js` (`rulesFor`, `instance`, `instanceById`, `roleOfSpec`, `buffsOf`, `defaultComposition`, `compositionFor`). Signup, raid templates, event creation and the setup suggestion (#250 ff.) read from here; **there are no custom raids**, the rule set is the only source of instances. Served as `GET /api/game-versions` (area `raids`, types `GameVersion…` in `api/raidTemplates.ts`).

### Hauptversion (#541)

Which version the guild plays is a **setting**, not a code constant: `config.mainVersion` (a version id, default `"tbc"`) and `config.categoryVersion = { [categoryId]: versionId }` for a category that plays another one (only those are stored; `normalizeMainVersion`/`normalizeCategoryVersion` in `configSchema.js` keep known ids only). Einstellungen → **Spielversion** edits both through `PATCH /api/settings` (area `settings`, write; the map is sent whole, a category on "Hauptversion" is left out); `GET /api/settings` carries `gameVersions` for the picker.

- **One resolver:** `src/services/events/mainVersion.js` — `mainVersionFor({ categoryId, config })` (category → global → `DEFAULT_VERSION`, an unknown id is skipped), `versionOfEvent(event)` / `rulesForEvent(event)` (the event's own known version, else its category's), `classesOfVersion(id)`. Without `config` it reads `configStore` directly (the `settingsStore` facade would close a require cycle through the template store); a route passes `settingsStore.getConfig()`.
- **Only a missing version is filled.** New event without version or template (`eventStore.normalizePlan`, `eventCreate.planFor` — the title's instances only when they belong to that version), a template body without version (`normalizeTemplate`), the bot's setup/signup/message/manage paths for an event without one (Raid-Helper). `DEFAULT_VERSION` is only the last fallback and the default parameter of the pure lookups in `index.js`, whose callers hand a version.
- **Stored records never move:** an event, a Raid-Helper template (`migrateLegacy`) or a raid plan link stored without a version is `LEGACY_VERSION` (`"tbc"`), whatever the main version is today.
- **To the client:** `GET /api/game-versions[?categoryId=]` and `GET /api/raids/new` send `defaultVersion` from the setting, `raids/new` also `categoryVersions`; the create dialog's empty plan starts in `categoryVersionOf(ctx, categoryId)` (`lib/eventPlan.ts`). `GET /api/signups` sends `classesByVersion` (the dialog takes the list of the event's version, `lib/signups.ts` `classesForRows`), `GET /api/profile` `mainVersion` + `classesByVersion`; `profile.js`' `pageContext({ versionId })` also sends `versions` (main version first, `lastName`) for the add dialog; characters carry their own version since #543 (docs/roster-profile.md).
- **Links, armory, softres and raidsheet per version** since #542: see "Einstellungen je Spielversion" below. The raid plan catalogue is #544.

### Einstellungen je Spielversion (#542)

Everything that points outside the app depends on the version: `config.versionSettings = { [versionId]: { blizzardRegion, blizzardRealmSlug, blizzardNamespace, armoryUrlTemplate, wclUrlTemplate, wowheadPath, softresEdition, raidsheetId } }`, one block for **every** version a rule set knows. Shape and normalisers are `src/stores/versionSettingsSchema.js` (only valid values survive: region eu/us/kr/tw, slugs `[a-z0-9-]`, templates http(s) with `{char}`, softres editions of `softresInstances.js`, raidsheet id); **an empty field means "not there for this version"** — the link is left out, the armory is not asked, no softres list, never a TBC fallback.

- **Migration** (`settingsMigration.migrateVersionSettings`, idempotent, logged once): a config without `versionSettings` gets its old single values as the TBC block — the realm fields of `config.blizzard` (a stored override wins, else the env/bootstrap `BLIZZARD_REGION`/`BLIZZARD_REALM`/`BLIZZARD_NAMESPACE`; an "auto" namespace is written out as `profile-classicann-<region>`), `APPLY_ARMORY_URL`/`APPLY_WCL_URL` (`config/defaults.js`), Wowhead `tbc`, softres `tbc`; Classic and Forever empty. `config.blizzard` keeps only `clientId`/`clientSecret` (one Battle.net application for all versions); the old realm fields are **removed**, not kept as a facade — every reader was switched. Until the migration ran, `normalizeConfig` reads the same TBC block from the old fields (`versionSettingsOf`); a fresh install (no file) is never written.
- **One helper, server** — `src/services/events/versionSettings.js`: `settingsForVersion(versionId, { config })` (the interface #543 calls with a character's version; unknown/missing id = the main version), `versionLinks(versionId)` → `armory(char)`, `wcl(char)`, `wowheadItem(id, params)`, `wowheadSpell(id)`, `wowheadPath`, `softresEdition`, `raidsheetId` — every URL through `linkCheck.externalLink` (#539), so a half-filled template is no link — and `blizzardFor(versionId)` → `{ client, reason, message }` ("version_not_configured": "Armory für WoW Forever nicht eingerichtet (Einstellungen → Spielversion)", no request at all).
- **One helper, client** — `lib/versionLinks.ts` (same rules, `blockProblems()` mirrors the server's validation for the form) and `lib/wowheadItems.ts`' `wowheadItemUrl(id, params, path)` ("" without a path). A page whose data names its version provides the server's `wowheadPath` through `WowheadPathProvider`; without one it is `LEGACY_WOWHEAD_PATH` ("tbc", stored data).
- **Which version a reader asks:** an event's (`versionOfEvent`: raid detail softres edition and catalogue, default raidsheet, raid plan), an import's event (`services/loot/lootVersion.js` relinks imported loot after the target event is known), the loot council's category (`mainVersionFor({ categoryId })`), a character's own since #543 (char page: `?version=` or its version, roster: the filtered version or the row's, profile: the character's; `services/characters/characterVersions.js`), the main version for what has no character (recruitment `/apply` links, dashboard kicker, Wowhead item search without edition). Log reports read TBC logs (tbcContent), so `web/report/widgets.js` links with the LEGACY (TBC) block.
- **Raidsheet:** `utils/setup/raidsheets.pickRaidsheet` — keyword match first, a sheet that is another version's `raidsheetId` never matches by keyword, else the version's own sheet.
- **Settings → Spielversion**, second card `VersionSettingsCard` (`pages/settings/SettingsGameVersion.tsx`): version switcher (starts on the main version), fields Armory (region, realm, namespace, link), Warcraft Logs link, Wowhead path, softres edition, raidsheet template, each error said at the field, a preview line with the three links for a sample name. Part of the page draft; `PATCH /api/settings` takes `versionSettings` (merged per version and field, a filled value the schema would drop → 400 `invalid_version_settings` naming version and field; an unknown raidsheet → 400). The Battle.net connection card keeps only client id/secret and shows the main version's realm.
- **Still fixed** (Phase 2/3 of #540): the WCL v1 applicant analysis (`utils/logcheck/applicant.js`, `APPLY_WCL_REALM`), report links `classic.warcraftlogs.com/reports/<id>` (WCL redirects across its sites), the `Blizzard` class' own defaults (only reached without explicit values), the TBC loot catalogue's Wowhead links (`web/loot/lootCatalog.js`, TBC content).

- **Classes/specs** (`classes.js`, shared by all three): spec key `"<Class>-<Spec>"` in WCL spelling (same as `casterSpecs.js`), `role` tank/healer/melee/ranged for placing a raider, `buffRole` in `raidBuffs.js`' vocabulary (a hunter is "melee" there — he wants Might), `canTank`/`canHeal`.
- **Instances** carry `sizes`, `defaultSize`, `icon`, `color` (#307: die Farbe, die Anmelde- und Setup-Nachricht ohne eigene Werte nehmen — jede Instanz hat eine), `bosses`, `finalBoss`/`finalBossNames` (EN + DE), `composition` (suggested tanks/healers per size) and `status`. **TBC is derived from `tbcContent.js`** (ids, labels, `encountersFor`, `FINAL_BOSSES`) — only size, icon and the suggestion are added in `tbc.js`. Instance ids are **unique across versions** (`ony` vs `forever-ony`, `hyjal` vs `forever-hyjal`), so a stored id never needs its version.
- **Boss order** is `BOSS_ORDER` in `tbcContent.js`, the order the raid actually meets the encounters (hand-kept): the raid plan tabs (`bossesForInstances`), the loot pick list (`lootCatalog.js`), the encounter grid of `raidProgress.js` and the raid plan auto-advance (docs/raidplan/sharing.md) all read it. Black Temple since #534: Naj'entus, Supremus, Akama, Gorefiend, **Reliquary of the Lost, then Gurtogg Bloodboil**, Shahraz, Council, Illidan. A saved plan keeps its boards (keyed by `<instance>/<boss slug>`), only the tab order follows.
- **`incomplete`** (all Forever raids until release): plannable, no bosses, no final boss — `raidProgress.js` therefore never blocks on them, and `compositionFor()` falls back to `defaultComposition(size)` (10 → 2/3, 20 → 2/5, 25 → 3/6, 40 → 4/10). Fill them in once the raids are out.
- **Buffs** (`buffs.js`) are derived from `raidBuffs.js` and `totems.js`, never kept twice: it only adds which spec brings a talent buff, party vs raid scope, and per version what does not exist (Classic: no Wrath of Air, Totem of Wrath, Commanding Shout). Shields and racial auras are left out.
- **Consumers so far:** `raidListing.js`' `raidSize()` takes the largest `defaultSize` of the night's contents (replaced `TEN_PLAYER`); `raidProgress.js` asks `tbcContent` first and the rule set second (Classic bosses, zones and final bosses). Raid-Helper's spec names (`Holy1`, `Destro`, …) are only an alias table in `config/classlist.js` (#428): each resolves to a rule-set key, and class, role and Raid-Helper's own names/emojis (`RAID_HELPER_NAMES`, plus the Death Knight in `RAID_HELPER_ONLY_CLASSES`, which no rule set plays) come from `gameVersions/classes.js` — so `setupView.roleOf` and the raidsheet fill read the rule set's roles.

## Raid-Vorlagen (`src/services/events/raidTemplates.js`, page `/raids/raid-templates`)

What an evening looks like (#266): `{ id, name, versionId, instanceIds, size, composition: { tank, healer, melee?, ranged? }, requiredBuffs, signupDeadline: { hoursBefore }, durationMinutes, fairness, wishes, overflow, lockAtLimit, color, image { mode, url } }` in `data/settings/raid-templates.json` (settingsStore). `color` und `image` sind das Aussehen der Anmelde-Nachricht (#307, leer = Regelsatz); im Editor eine Zeile „Aussehen“ hinter „Mehr“, mit kleiner Vorschau. Instances and buffs come **only** from the rule set above — `validateTemplate()` refuses anything else, plus tanks + healers (and the melee/ranged minimums) > size and a max below min. `durationMinutes` (#305) is 30–600 or `null` ("nicht gesetzt", the event then takes the default 180); an event inherits it like every other planning field.

- **Migration on read:** a pre-#266 entry `{ id, name }` (a bare Raid-Helper template) becomes `rh-<id>` with `raidhelperTemplateId`, no instance and `size: null` — badged "Größe ergänzen" — and is written back once. "Aus Raid-Helper laden" (`POST /api/raid-templates/import`) adds unknown Raid-Helper templates the same way and leaves linked ones alone.
- **Default per category:** `config.categoryRaidTemplate = { [categoryId]: templateId }`, a select on the category card in Einstellungen → Kategorien. It replaced `raidDefaults.templateId`: a config without the map hands the old global default to every `categoryIds` entry (`categoryRaidTemplateOf()`), and the next save persists it. `DELETE /api/raid-templates` answers **409** while a category uses the template.
- **API:** one path, `GET/POST/PATCH/DELETE /api/raid-templates` (area `raids`, level by method). GET decorates each template with `needsSize`, `incomplete` (an instance with "Infos fehlen") and `defaultFor`.
- **Client:** `pages/RaidTemplatesPage.tsx` (one row per template, version segment, editor as a `Modal` held in `?edit=`), linked from the Raid-Events head — no sidebar entry. The editor is built from the shared `components/RaidPlanFields.tsx` (`InstancePicker`, `SizePicker` — `size` may be null for a migrated template —, `RoleRanges`, `BuffPicker`, `NumberInput`, `SwitchRow`), the same the create dialog uses; `src/web-client/src/lib/raidTemplates.test.ts` keeps copies out of the page. Size change proposes tanks/healers (`lib/raidTemplates.ts`' `proposeComposition`, the same rule as the server's, `src/web-client/src/lib/raidTemplates.test.ts` compares them). `components/CompositionEditor.tsx` (tanks/healers ±, "n Plätze für DPS") is shared with the event creation (#261). For a Raid-Helper event the create dialog still sends a Raid-Helper template id: it offers the templates that link one and preselects the category default (`categoryTemplates` in `GET /api/raids/new`); an EventHelper event sends `raidTemplateId` and the plan instead.
