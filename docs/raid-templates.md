# Spielversionen und Raid-Vorlagen

Endnutzer-Sicht: siehe [guide-web-admin.md#raid-vorlagen](guide-web-admin.md#raid-vorlagen).

## Spielversionen und Instanzen (`src/config/gameVersions/`)

One rule set per game version — `tbc.js` (TBC Anniversary), `classic.js` (Classic Era), `forever.js` (WoW Forever) — pure data plus pure functions in `index.js` (`rulesFor`, `instance`, `instanceById`, `roleOfSpec`, `defaultComposition`, `compositionFor`). Signup, raid templates, event creation and the setup suggestion (#250 ff.) read from here; **there are no custom raids**, the rule set is the only source of instances. Served as `GET /api/game-versions` (area `raids`, types `GameVersion…` in `api/raidTemplates.ts`).

### Hauptversion (#541)

Which version the guild plays is a **setting**, not a code constant: `config.mainVersion` (a version id, default `"tbc"`) and `config.categoryVersion = { [categoryId]: versionId }` (`normalizeMainVersion`/`normalizeCategoryVersion` in `configSchema.js` keep known ids only). Since #738 **every active category has its own entry** and the main version is only the default for something new (see "Feste Version je Kategorie" below). Einstellungen → **Spielversion** edits both through `PATCH /api/settings` (area `settings`, write; the map is sent whole); `GET /api/settings` carries `gameVersions` for the picker.

- **One resolver:** `src/services/events/mainVersion.js` — `mainVersionFor({ categoryId, config })` (category → global → `DEFAULT_VERSION`, an unknown id is skipped), `versionOfEvent(event)` / `rulesForEvent(event)` (the event's own known version, else the version stored for its `id` — an own event's, a Raid-Helper snapshot's —, else its category's; see "Version fest an jedem Raid" below), `classesOfVersion(id)`. Without `config` it reads `configStore` directly (the `settingsStore` facade would close a require cycle through the template store); a route passes `settingsStore.getConfig()`.
- **Only a missing version is filled.** New event without version or template (`eventStore.normalizePlan`, `eventCreate.planFor` — the title's instances only when they belong to that version), a template body without version (`normalizeTemplate`), the bot's setup/signup/message/manage paths for an event without one (Raid-Helper). `DEFAULT_VERSION` is only the last fallback and the default parameter of the pure lookups in `index.js`, whose callers hand a version.
- **Stored records never move:** an event, a Raid-Helper template (`migrateLegacy`) or a raid plan link stored without a version is `LEGACY_VERSION` (`"tbc"`), whatever the main version is today.
- **Version fest an jedem Raid (#737).** Every raid has a stored version, and a switch of `mainVersion` or `categoryVersion` never changes which version an existing raid — or its loot, attendance, log or roster — belongs to. `mainVersionFor` names only the version of something **new**.
  - **Raid-Helper snapshots** (`raidEventStore.js`, `data/settings/raid-events.json`) carry `versionId`: `raidEventScan.js` hands in `mainVersionFor({ categoryId })` of the moment, `saveRaidEvents` keeps it like `firstSeenAt` — a later scan never overwrites it (it is in `SNAPSHOT_FIELDS`, so a snapshot without one is stamped by its next scan). `versionOfRaidEvent(id)` reads it without a copy (index per loaded file).
  - **Migration** (`settingsMigration.migrateStoredVersions`, idempotent, logged as `raid-events.json: n Raid(s) → "tbc" (#737)` and `rosters.json: n Roster → "tbc" (#737)`): every snapshot and every roster stored without a version gets the version its category plays that day (`categoryVersion`, else the main version — so TBC for everything before Forever). It runs at every start; it must have run once **before** the main version is switched the first time, which is why it ships with the first deploy of epic #736.
  - **One resolver:** `versionOfEvent(event)` reads `event.versionId`, then the version stored for `event.id` (an own event through the lookup `eventStore` registers with `registerOwnEventVersions` — `eventStore` requires `mainVersion.js`, so it cannot be required back —, a Raid-Helper snapshot through `raidEventStore.versionOfRaidEvent`), and only then the category's version of today (a coming Raid-Helper raid the scan has not stored yet). `services/events/storedVersion.js` answers by id alone, without that last fallback: `storedVersionOf(eventId)` ("" when nothing is stored) and `versionOfLog(log)` — a log has the version of its linked raid; a log without a raid belongs to no version ("", shown only under „nicht zugeordnet“, epic #736 part 5).
  - **Readers:** attendance (`rosterAttendance.buildAttendanceContext({ versionId })` filters nights with `versionOfEvent`), loot (`characterVersions.eventVersion`: the raid's stored version, TBC for loot without a stored raid — `lootStats`' awards and `lootAwards.listAwards` read it), the loot import's Wowhead links (`lootVersion.versionOfImport` passes the event id), the raid detail page (`raidDetailView.eventVersionSettings`) and the archive export (one rule for loot and attendance: the raid's stored version, else TBC).
  - **Rosters** (`rosterStore.js`) store `versionId` and no longer derive it from the live config on read: `createRoster`/`migrateCategories` stamp `mainVersionFor({ categoryId })` of the moment, a roster read without one is TBC until the migration above stamps it (`rosterStore.migrateVersions`, on the raw file).
  - **Guild bank:** a scan whose client names no version (`client.project`/`build`) is no longer filed under the main version — it goes to the bank already stored for its realm and guild (`guildBankStock.versionOfKnownBank`, one version only); otherwise it is refused (`GuildBankParseError`, 400 `parse_failed` to the sync tool, logged as `[guildbank] Scan abgelehnt: …`).
- **To the client:** `GET /api/game-versions[?categoryId=]` and `GET /api/raids/new` send `defaultVersion` from the setting, `raids/new` also `categoryVersions`; the create dialog's empty plan starts in `categoryVersionOf(ctx, categoryId)` (`lib/raids/eventPlan.ts`). `GET /api/signups` sends `classesByVersion` (the dialog takes the list of the event's version, `lib/signups/status.ts` `classesForRows`), `GET /api/profile` `mainVersion` + `classesByVersion`; `profile.js`' `pageContext({ versionId })` also sends `versions` (main version first, `lastName`) for the add dialog; characters carry their own version since #543 (docs/roster-profile.md).
- **Links, armory, softres and raidsheet per version** since #542: see "Einstellungen je Spielversion" below. The raid plan catalogue is #544.

### Feste Version je Kategorie, Umstellen = neuer Abschnitt (#738)

Every active category plays **one fixed version**; switching it is a deliberate step that starts a new section instead of re-reading the past. TBC and Forever categories run side by side on the same Discord server — nothing depends on the main version except the defaults (a category switched on just now, a new raid template, the profile).

- **Migration** (`settingsMigration.migrateCategoryVersions`, idempotent, logged as `config.json: Spielversion je aktiver Kategorie festgeschrieben (#738) - <id> tbc, …`): every category of the stored `categoryIds` without an entry gets the version it plays that day (the main version). Runs after #737's stored versions. A config without stored categories has nothing to pin; the settings page writes a version with the first save of its categories.
- **Settings API:** `PATCH /api/settings` answers **400 `category_version_missing`** ("Jede aktive Kategorie braucht eine Spielversion: …") when the body touches `categoryIds` or `categoryVersion` and an active category is left without a known version. The client (`lib/settings/categoryVersions.ts`) sends a category switched on just now with the draft's main version (`categoryVersionsToSave`); `toDraft` reads an active category stored without one as the saved main version.
- **Sections** — `config.categoryEras = { [categoryId]: [{ versionId, from, name }] }` (`normalizeCategoryEras`, oldest first): `from` = ms of the switch (0 = always), `name` = the Discord category name at the switch (`listKnownCategories` over every event server) — what the raids of a closed section are called after a rename (#744). A category never switched has no list. Helpers in `services/events/categoryEras.js`: `erasOf(categoryId)` (without a history: one section since always in today's version), `categoryEraAt(categoryId, time)` (seconds or ms; `current` says whether it is the open one), `currentEra(categoryId)`, `switchEras(stored, { fromVersion, toVersion, at, name })` (pure: a first switch writes the old section "since always", the open section is closed under today's name, the new one starts with it).
- **A switch** = a save whose `categoryVersion` gives a category that was active before (or already has sections) another version than it played (`categorySwitch.versionSwitches`): the route writes `categoryEras`, applies the dialog's series choice (`categorySwitchFixes = { [categoryId]: { series: "pause" | templateId } }`, `applySeriesFix`: pause, or a template **of the new version**), logs `[settings] Kategorie … : Spielversion tbc → forever, neuer Abschnitt (#738)` and answers `switchedCategories: [{ categoryId, fromVersion, toVersion, at, name, series }]`. Stored raids never move (#737): a coming raid of the old version keeps it (the orga may cancel it), loot, logs and attendance stay with their raid.
- **Hook for what follows a switch** (the roster of #739, names of #744): `categorySwitch.onCategoryVersionSwitch((sw, { config, user }) => …)` — called once per switched category **after** the settings were saved, awaited in order; a listener that throws is logged (`[categorySwitch] …`) and never fails the save. Returns its unregister function.
- **Templates of another version create no event** (`categoryEras.templateVersionProblem`): `eventCreate.planFor` refuses a raid template (the chosen one or the category default `categoryRaidTemplate`) whose version is not the category's with **409 `template_version_mismatch`** ("Die Raid-Vorlage „SSC + TK“ ist für TBC Anniversary, die Kategorie spielt WoW Forever. Kein Event angelegt – …") before any channel exists — the template used to win silently. A body that names `versionId` itself (the web create dialog) is a deliberate choice and still wins; then the template's instances are only taken when they are of that version. A series run therefore fails visibly (run mark `failed`, `seriesFailures`, the dashboard task), and `normalizeSeries` refuses to save a **running** series with an unfitting template ("… Bitte eine passende Vorlage wählen oder die Serie pausieren."); a paused one may keep it.
- **Dialog** — Einstellungen → Spielversion, card "Version je Kategorie" (`SettingsGameVersion.tsx`): one select per active category without a "Hauptversion" choice; a category switched on just now carries the badge „neu · startet mit …“, a switched one „seit <Datum>“. Picking another version for a saved category opens `pages/settings/CategorySwitchDialog.tsx` with `GET /api/settings/category-switch?categoryId=&versionId=` (area `settings`; `categorySwitch.switchPreview`: `from`/`to`, `eras`, `upcoming` = the category's coming raids of another version — own events not cancelled, Raid-Helper snapshots —, `series` and `defaultTemplate` with `fits`, `templates` of the new version). It says what happens (old raids, roster and quota stay readable under the old version; new raids get the new one; quota and roster start afresh), lists the coming raids with links, and offers a fix where the series or the default template no longer fits (series: "Serie pausieren" by default or a template of the new version; default: "keine" or a template). „Auf … umstellen“ only changes the page draft; the save bar makes it happen. Cancelling, or picking the saved version again, leaves nothing behind.

### Einstellungen je Spielversion (#542)

Everything that points outside the app depends on the version: `config.versionSettings = { [versionId]: { blizzardRegion, blizzardRealmSlug, blizzardNamespace, armoryUrlTemplate, wclUrlTemplate, wowheadPath, softresEdition, raidsheetId } }`, one block for **every** version a rule set knows. Shape and normalisers are `src/stores/versionSettingsSchema.js` (only valid values survive: region eu/us/kr/tw, slugs `[a-z0-9-]`, templates http(s) with `{char}` — `{region}` and `{realm}` may stand in for the block's own region and realm since #553, a template needing one the block has not set gives no link —, softres editions of `softresInstances.js`, raidsheet id); **an empty field means "not there for this version"** — the link is left out, the armory is not asked, no softres list, never a TBC fallback.

- **Migration** (`settingsMigration.migrateVersionSettings`, idempotent, logged once): a config without `versionSettings` gets its old single values as the TBC block — the realm fields of `config.blizzard` (a stored override wins, else the env/bootstrap `BLIZZARD_REGION`/`BLIZZARD_REALM`/`BLIZZARD_NAMESPACE`; an "auto" namespace is written out as `profile-classicann-<region>`), `APPLY_ARMORY_URL`/`APPLY_WCL_URL` (`config/defaults.js`), Wowhead `tbc`, softres `tbc`; the other versions get their standard values (below; Forever has none). `config.blizzard` keeps only `clientId`/`clientSecret` (one Battle.net application for all versions); the old realm fields are **removed**, not kept as a facade — every reader was switched. Until the migration ran, `normalizeConfig` reads the same TBC block from the old fields (`versionSettingsOf`); a fresh install (no file) is never written.
- **Standard values per version (#553)** live with the rule set: `config/gameVersions/<id>.js` `settingsDefaults` (namespace with `{region}`, armory/WCL templates with `{region}`/`{realm}`, Wowhead path, softres edition — **never a realm or a raidsheet**, those are the guild's). `versionSettingsSchema.defaultBlock(versionId, { region })` turns them into a block (region = the block's own, else the bootstrap `BLIZZARD_REGION`, else `eu`), `fillDefaults(block, versionId)` fills only empty fields. Checked values (Sept 2026): **Classic Era** — `profile-classic1x-<region>` (Blizzard's Era namespace; progression Classic is `profile-classic-`), `classic-armory.org/character/{region}/vanilla/{realm}/{char}`, `vanilla.warcraftlogs.com/character/{region}/{realm}/{char}` (Era and SoD live on the "vanilla" site), Wowhead `classic`, softres `classic`; realm empty until the orga sets it (then the armory/log links appear). **TBC** — the Anniversary values with placeholders (`profile-classicann-{region}`, `…/tbc-anniversary/{realm}/…`, `fresh.warcraftlogs.com`, `tbc`, `tbc`). **Forever** — only Wowhead `forever` (www.wowhead.com/forever, #750; item lookups, links and the guild bank use it); namespace, armory and log sites stay empty until the beta's values are known (Epic #540 phase 2), so the armory gear lookup stays off with a hint (`blizzardFor`). Add them to `settingsDefaults` and the next start fills them. The Anniversary re-issue aliases apply on the `tbc` path only.
  - **Migration** (`settingsMigration.migrateVersionDefaults`, idempotent): every version with defaults that `config.versionDefaultsApplied` does not list gets its *empty* fields filled and is added to the list — a value someone entered is never touched, a field cleared on purpose afterwards stays empty. A fresh install reads the defaults (`versionSettingsOf`) and counts them all as applied (`CONFIG_DEFAULTS.versionDefaultsApplied`).
  - **Button** „Standardwerte übernehmen" per version in the card: `GET /api/settings` sends `versionDefaults` (`defaultVersionSettings(config.versionSettings)`, in each block's own region); the button puts every field with a standard value into the draft (`lib/settings/versionLinks.ts` `defaultsDiff`/`applyDefaults`), realm and raidsheet stay; disabled when nothing would change or the version has none (Forever, tooltip says so). Saved with the save bar like any edit.
- **One helper, server** — `src/services/events/versionSettings.js`: `settingsForVersion(versionId, { config })` (the interface #543 calls with a character's version; unknown/missing id = the main version), `versionLinks(versionId)` → `armory(char)`, `wcl(char)` (`{region}`/`{realm}` from the block), `wclSite` (the origin of the WCL template when it is a `*.warcraftlogs.com` https address, else ""), `wclReport(id)`, `wowheadItem(id, params)`, `wowheadSpell(id)`, `wowheadPath`, `softresEdition`, `raidsheetId` — every URL through `linkCheck.externalLink` (#539), so a half-filled template is no link — and `blizzardFor(versionId)` → `{ client, reason, message }` ("version_not_configured": "Armory für WoW Forever nicht eingerichtet (Einstellungen → Spielversion)", no request at all).
- **One helper, client** — `lib/settings/versionLinks.ts` (same rules, `blockProblems()` mirrors the server's validation for the form) and `lib/wow/wowheadItems.ts`' `wowheadItemUrl(id, params, path)` ("" without a path). A page whose data names its version provides the server's `wowheadPath` through `WowheadPathProvider`; without one it is `LEGACY_WOWHEAD_PATH` ("tbc", stored data).
- **Which version a reader asks:** an event's (`versionOfEvent`, stored version first since #737: raid detail softres edition and catalogue, default raidsheet, raid plan), an import's event (`services/loot/lootVersion.js` relinks imported loot after the target event is known), the loot council's category (`mainVersionFor({ categoryId })`), a character's own since #543 (char page: `?version=` or its version, roster: the filtered version or the row's, profile: the character's; `services/characters/characterVersions.js`), an application's own since #553 (see "Bewerbungen je Version" below), the main version for what has no character (dashboard kicker, Wowhead item search without edition). Log reports read TBC logs (tbcContent), so `web/report/widgets.js` links with the LEGACY (TBC) block.
- **Raidsheet:** `utils/setup/raidsheets.pickRaidsheet` — keyword match first, a sheet that is another version's `raidsheetId` never matches by keyword, else the version's own sheet.
- **Settings → Spielversion**, second card `VersionSettingsCard` (`pages/settings/SettingsGameVersion.tsx`): version switcher (starts on the main version), fields Armory (region, realm, namespace, link), Warcraft Logs link, Wowhead path, softres edition, raidsheet template, each error said at the field, a preview line with the three links for a sample name, and the version's **colour** (#742: colour picker + hex field + "Zurücksetzen"; `color` in the block is `#rrggbb` or "" = the rule set's `color`, `stores/versionSettingsSchema.js` `defaultColorOf`/`colorOf`, `versionSettings.versionColor()` → `{ color, defaultColor, custom }`; the standard-values button never touches it). What the colour does: docs/web-admin.md, "Die Akzentfarbe folgt der Spielversion". Part of the page draft; `PATCH /api/settings` takes `versionSettings` (merged per version and field, a filled value the schema would drop → 400 `invalid_version_settings` naming version and field; an unknown raidsheet → 400). The Battle.net connection card keeps only client id/secret and shows the main version's realm.
- **Bewerbungen je Version (#553)** — an application is a Discord thread, not a record, so the version travels with it (`utils/recruitment/applyVersion.js`): a recruitment template and a tracked post carry `versionId` (a new template = the main version, the editor has a version switch; `recruitmentStore.migrateVersions` gives old ones `tbc`, a record without one also *reads* as `tbc`); the posted apply button is `apply:<versionId>` (the bare `apply` of an old message = TBC; `/createapplication` posts the main version; a scan reads the version off the button); `applyButton` puts it into the pending application, `applyModal` builds armory/WCL links with `versionLinks(versionId)`, writes an embed field `Version` (the label, read back by `parseApplicationEmbed`; none = TBC) and runs the log analysis through `applicant.applicantSource(versionId)`: realm/region/site of that version's block — `APPLY_WCL_REALM`/`APPLY_WCL_REGION` only fill an empty **TBC** realm/region —, parses from `<site>/v1/parses/…` (`WarcraftLogs.getParses(…, { site })`), the report link on the same site. A version without realm, region or `*.warcraftlogs.com` template gets "Keine Log-Analyse: für <Version> fehlen …" instead of a lookup on another realm. The Recruitment page shows each row's version (`VersionTag`) and filters all three tabs by the menu's content version (client-side, see "Content-Umschalter" below; `GET /api/recruitment` sends `gameVersions` + `mainVersion`).
- **Still fixed** (Phase 2/3 of #540): the report tables of the applicant analysis still come from the classic v1 host (`WarcraftLogs` baseURL; WCL answers across its sites), log report links `classic.warcraftlogs.com/reports/<id>` outside the applications (WCL redirects across its sites), the `Blizzard` class' own defaults (only reached without explicit values), the TBC loot catalogue's Wowhead links (`web/loot/lootCatalog.js`, TBC content).

- **Classes/specs** (`classes.js`, shared by all three): spec key `"<Class>-<Spec>"` in WCL spelling (same as `councilSpecs.js`), `role` tank/healer/melee/ranged for placing a raider, `buffRole` in `raidBuffs.js`' vocabulary (a hunter is "melee" there — he wants Might), `canTank`/`canHeal`.
- **Instances** carry `sizes`, `defaultSize`, `icon`, `color` (#307: die Farbe, die Anmelde- und Setup-Nachricht ohne eigene Werte nehmen — jede Instanz hat eine), `bosses`, `finalBoss`/`finalBossNames` (EN + DE), `composition` (suggested tanks/healers per size) and `status`. **TBC is derived from `tbcContent.js`** (ids, labels, `encountersFor`, `FINAL_BOSSES`) — only size, icon and the suggestion are added in `tbc.js`. Instance ids are **unique across versions** (`ony` vs `forever-ony`, `hyjal` vs `forever-hyjal`), so a stored id never needs its version.
- **Boss order** is `BOSS_ORDER` in `tbcContent.js`, the order the raid actually meets the encounters (hand-kept): the raid plan tabs (`bossesForInstances`), the loot pick list (`lootCatalog.js`), the encounter grid of `raidProgress.js` and the raid plan auto-advance (docs/raidplan/sharing.md) all read it. Black Temple since #534: Naj'entus, Supremus, Akama, Gorefiend, **Reliquary of the Lost, then Gurtogg Bloodboil**, Shahraz, Council, Illidan. A saved plan keeps its boards (keyed by `<instance>/<boss slug>`), only the tab order follows.
- **`incomplete`** (all Forever raids until release): plannable, no bosses, no final boss — `raidProgress.js` therefore never blocks on them, and Forever's instances carry an **estimated** `composition` (10 → 2/3, 20 → 2/5, 40 → 2/8) and the rule set a `composition` curve of its own, which `defaultComposition(size, versionId)` reads first (#751); other sizes fall back to the shared curve (10 → 2/3, 20 → 2/5, 25 → 3/6, 40 → 4/10). Fill them in once the raids are out.
- **Forever's buffs (#751)** are built in `forever.js` with `buildBuffs(classes, { exclude, scopes, sharedSlots })` from Classic's rule set (beta facts, 10.10.2026, to be checked on the server): the group buffs that reach the whole raid (Gift of the Wild, Arcane Brilliance, the Prayers) are raid buffs; Battle Shout, Windfury, Grace of Air, Strength of Earth and Leader of the Pack stay party buffs; the air totems share one slot (`sharedSlot`), so a second shaman in a party adds nothing (`setupEditor.partyBenefits`). `rules.sheetLayout` (TBC only) says the Google raid sheet fits the version — the "possible" of the feature `raidSheet` (#761, "Funktionen je Version" below): `versionCapabilities.sheetVersionRefusal` makes `/fillsetup` and `POST /api/raids/fill` answer 409 `no_sheet_layout` for other versions (`feature_off` when switched off), and the raid detail plans them with the raid plan (`sheetOffered`).
- **Buffs** (`buffs.js`) are derived from `raidBuffs.js` and `totems.js`, never kept twice: it only adds which spec brings a talent buff, party vs raid scope, and per version what does not exist (Classic: no Wrath of Air, Totem of Wrath, Commanding Shout). Shields and racial auras are left out.
- **Consumers so far:** `raidListing.js`' `raidSize()` takes the largest `defaultSize` of the night's contents (replaced `TEN_PLAYER`); `raidProgress.js` asks `tbcContent` first and the rule set second (Classic bosses, zones and final bosses). Raid-Helper's spec names (`Holy1`, `Destro`, …) are only an alias table in `config/classlist.js` (#428): each resolves to a rule-set key, and class, role and Raid-Helper's own names/emojis (`RAID_HELPER_NAMES`, plus the Death Knight in `RAID_HELPER_ONLY_CLASSES`, which no rule set plays) come from `gameVersions/classes.js` — so `setupView.roleOf` and the raidsheet fill read the rule set's roles.

### Funktionen je Version (#761)

What a game version **can** do and what it **does** is one source: `services/events/versionCapabilities.js`. A new version brings data (a rule set, a log rule set, version settings, catalog entries) — no feature code learns about it. The features are `config/versionFeatures.js` `VERSION_FEATURES`: `logcheck`, `lootCouncilBis`, `simulation`, `raidSheet`, `softres`, `armory`, `wowheadLinks`, `raidplanCatalog`.

- **`versionCapabilities(versionId, { config })`** → per feature `{ possible, enabled, on, reason, message, missing, also }`; `featureState(versionId, feature)` / `featureOn(...)` for one. **possible** = the data exists: the log rule set ready and a Warcraft-Logs site (`logcheckCapability`, `wclApiSite`: the log rule set's `apiSite` — TBC's classic host — else the settings' site), the rule set's `councilContent.bis` / `.sim` (TBC only), the rule set's `sheetLayout` (TBC only), a softres edition / armory region+realm+namespace / Wowhead path in the version's settings, a catalog entry whose `versions` names the version. **enabled** = not in the setting `config.versionSettings[<id>].disabled` (a list of feature ids, `normalizeDisabled`: known ids only, matrix order, kept only when not empty — so every stored config reads "all on" without a migration). **on** = both. `reason`: `""`, `disabled`, or why not possible (`unknown_version`, `no_rules`, `rules_not_ready`, `no_site`, `no_bis_data`, `no_sim_data`, `no_sheet_layout`, `no_softres_edition`, `armory_not_configured`, `no_wowhead_path`, `no_catalog_entries`), `message` its German text, `also` further reasons (logcheck: rules not ready **and** no site).
- **A feature switched off behaves like one that is not possible**, with its own hint ("… ist für TBC Anniversary ausgeschaltet (Einstellungen → Spielversion)."):
  - log check: `logVersion.logcheckSupported` asks the feature, `unsupportedMessage` names the switch;
  - loot council: `councilContent(versionId)` → `{ bis, tiers, itemTable }` follow "BiS-Listen", `sim` follows "Simulation", `off` + `simHint` for the page (route, `web/loot/lootCouncil.js`, `/council`);
  - raid sheet: `sheetOffered` (raid detail planning) and `sheetVersionRefusal` (409 `no_sheet_layout` / `feature_off` for `POST /api/raids/fill` and `/fillsetup`);
  - softres: the raid detail offers no edition (`softresOff` for the dialog's text), `POST /api/raids/softres` answers 409 `feature_off` / `no_softres_edition`;
  - armory: `blizzardFor` → `reason: "feature_off"` (no request; the character page and the council's refresh say so);
  - Wowhead links: `versionLinks().wowheadItem/wowheadSpell/wowheadPath` are empty, and so are the paths the council, the raid detail and the guild bank hand to the client (item lookups keep the setting's path — they are no links);
  - raid plan catalog: `catalogEnabled(versionId)` — a plan of that version gets no mobs and spells (`web/raidplan/raidplan.js catalogFor`), the suggestions pick classes by the built-in rules (`raidplanAssign`); a plan without a known version keeps the catalog.
- **Data instead of version lists:** the per-feature lists are gone — `LOGCHECK_VERSIONS` (now the log rule set's `apiSite`), the council's `CONTENT` map (now the rule set's `councilContent`), `ASSIGN_TYPE_VERSIONS` (now the rule set's `raidplanTypesLeftOut`), the guild bank's `FALLBACK_PATH` (now the rule set's `settingsDefaults.wowheadPath`). `test/services/events/versionCapabilities.guard.test.js` fails on a new map keyed by version ids (or a list of version ids) outside the rule sets, the log rule sets, the catalog defaults and the source, and on a raw check (`hasSheetLayout(`, `.councilContent`, `rules.ready`) outside the source. The source sits low in the require graph (data, the settings schema, the log rule sets, the catalog store, the config store late) — its readers require it, never the other way round (`test/web/noCycles.test.js`).
- **Settings** — Einstellungen → Spielversion, card **"Funktionen je Version"** (`pages/settings/VersionFeaturesCard.tsx`, before "Links und Armory"): features as rows, versions as columns; a cell is "an" / "aus" (a `ui/Switch`) or "nicht möglich" (no switch, a dash on a phone); the reason in the tooltip (`settings.versionFeatures.reason.<code>`, with `{count}` of what the log rules lack). `GET /api/settings` sends the matrix as `versionCapabilities` (`capabilityMatrix`, from the **saved** settings — a path typed into the draft counts after saving). The switches are part of the page draft (`versionDisabled`, `lib/settings/versionFeatures.ts`); the save bar sends them inside `versionSettings` (`withDisabled`, each version's list whole). `PATCH /api/settings` takes `versionSettings.<id>.disabled` as a list of known ids; anything else is 400 `invalid_version_settings` ("TBC Anniversary: unbekannte Funktion „x“.").

### Raid-Inhalte versionsbewusst erkennen (#749)

`config/raidContent.js` steht vor `tbcContent.js` und den Regelsätzen: `contentsForText`, `contentForInstance`, `contentForBoss`, `contentForLoot`, `sourceForItem` nehmen `{ versionId }` und suchen **nur in den Instanzen dieser Version**. TBC geht an `tbcContent` (Loot-Tabelle, Titel-Kürzel), jede andere Version an ihren Regelsatz (`zoneNames`, `bosses`, `bossHints`, Name ohne „(…)", `short` als ganzes Wort). So gehört „Hyjal Summit (Forever)" oder Archimonde in einem Forever-Raid zu `forever-hyjal`, nie zu TBC-`hyjal`. Ohne `versionId` gilt TBC, ein Text mit „Forever" gilt als Forever. `bossHints` (nur Forever) nennen Begegnungen, die einen Log einem noch unvollständigen Raid zuordnen, ohne ihn zum Endboss zu machen (der Wächter blockt weiter nie).

- **Aufrufer reichen die Version des Events durch** (`versionOfEvent`): `raidListing.raidContentIds({ …, versionId })` liest Titel/Kategorie/Kanal/Log-Zonen nur in ihr; **geplante `instanceIds` jeder Version gewinnen** vor dem Wortlaut. `dashboardOverview` nimmt Icons (`iconOf`), Größe (`defaultSize`) und Rollenziele (`compositionFor`, 20er 2/5/13, 40er 4/10/26) aus dem Regelsatz. `rosterAttendance.categoryInfo` liest Zonen/Titel in der Version der Kategorie. `analyzeRaidProgress(fights, { versionId })` und `analyzeFightTimeline(…, { versionId })` suchen Bosse/Zonen nur in der Version des Logs (ohne: wie bisher TBC zuerst).
- **Icons:** jede Instanz jeder Version hat `icon` im Regelsatz; der Client liest sie aus der einen Tabelle `lib/wow/raidIcons.ts` (`RAID_CONTENTS`, nach Instanz-ID, auch `forever-*`; ein Vitest-Test hält sie gleich mit dem Regelsatz), `LootBadges.contentIcon` und `RaidLoader` benutzen sie, `lib/raids/raidEmojis.ts` hat je Instanz eine eigene Zeile (kein Rückfall von `forever-hyjal` auf `hyjal`).

### Content-Umschalter und „Andere Versionen ausblenden" (#563)

One game version for the whole web admin instead of a version filter on every page (#545's `VersionFilter` is gone). Design: Epic #540, artboards "Kopfleiste", "Einstellung", "Archiv-Link", "Handy".

- **Which versions are offered:** `services/events/contentVersions.js` `contentVersions()` — the main version first, then every version with data or a category (`versionsWithData`: `categoryVersion`, own events, Raid-Helper snapshots by their stored version (#737), raid templates, profile characters, loot by its raid's stored version, loot without a stored raid = TBC). Sent as `content: { mainVersion, hideOtherVersions, versions }` with `GET /api/session` (menu users; `null` otherwise).
- **Client:** `components/shell/ContentVersionProvider.tsx` (in `Shell`, seeded from the session) holds it, `hooks/useContentVersion.ts` reads it (`version`, `mainVersion`, `hidden`, `versions`, `setVersion`, `refresh`), rules in `lib/app/contentVersion.ts` (default = main version; the pick in `localStorage` `eh-content-version`, read and written in try/catch, the main version stored as nothing; a pick no longer offered falls back to the main version). `components/shell/ContentSwitch.tsx` sits in `.top-actions` before the server select: a segment with a coloured dot per version (tokens `--ver-<id>`), on ≤ 700 px a chip that opens the segment in its own row; one version = no switch, hidden = the quiet hint `.cswitch-quiet`. Outside the shell (a page test) the version is "" = the server's main version; `src/web-client/src/test/render.tsx` `renderPage(…, { content })` renders the switch above the page.
- **Pages** send the version as `?version=` exactly as before (`resolveVersionQuery`): Raid-Events (kommend/vergangen), Übersicht, Roster, Loot-Council, Loot-Historie (`/api/history/loot-stats` and `/api/history/loot-awards` now take `?version=` too, the "Loot" buckets carry `versionId`), or filter client-side by it (Raid-Vorlagen, Recruitment, Raidplan-Vorlagen, Raidplan-Katalog, Historie Raids/Items/Charaktere). The Settings page calls `refresh()` after saving a changed main version or hiding.
- **Setting `config.hideOtherVersions`** (Einstellungen → Spielversion, `HideOtherVersionsCard`, default `false`, `normalizeConfig` keeps only a literal `true`; no migration needed). One helper set in `mainVersion.js`: `hidesOtherVersions`, `visibleVersions` (all, or `[main]`), `isVersionVisible` (unknown/missing = main), `visibleRows(rows, versionOf)`, `otherVersions`; `resolveVersionQuery` returns the main version whatever `?version=` asks while hidden, and `characterVersions.versionChoices` offers only visible versions. Lists that do not go through `?version=` filter with `visibleRows`: `/api/history` (raids, loot buckets, characters), `/api/raid-templates`, `/api/raids/new` (templates, reusable events, categories of a hidden version, rule sets), `/api/raidplan/templates` and `/catalog` (entries of a hidden version only, instances), `/api/recruitment`, `/api/signups`, the profile's add dialog (`versions`, `raidGroups`; the profile page shows only the main version's characters, nothing is removed). `GET /api/game-versions` stays complete (static rule sets an archived event still needs).
- **Archive = a direct link to an event of a hidden version** (`services/events/eventArchive.js`): `archiveOf(event)` → `{ versionId, label, short }` or null; `GET /api/raids/detail`, `GET /api/raidplan` (then `canWrite: false`) and `GET /api/raidplan/public` send it as `archived`, the client shows `components/raid/ArchiveBanner.tsx` and the raid page goes read only (no manage menu, no cockpit deeds, no loot-system dialog). **The server refuses writes itself:** `withUser({ archived: (body, query) => eventId(s) })` (`web/http/apiHandler.js`) answers 409 `archived` before the handler for every event write of `raidDetail.js`, `setup.js` (propose, save, approve, post, ping text, extra role, signup edit), `raidplan.js` (save, suggest, publish, groups, apply, link), `eventManage.js`, `PATCH /api/raids`, `PUT /api/signups`, `POST /api/signups/bulk`; `signupService.submitSignup` refuses too (code `archived`, English through `botEnglish`). **Discord:** the event buttons, the public selects (`eventButton`, `eventPick`, `eventJoin`, `eventSignup`, `talkSignup`) answer with the ephemeral embed `archivedNotice()` ("This raid is archived …").
- **Warning and export:** `GET /api/settings` sends `upcomingByVersion` (own events not cancelled and scanned Raid-Helper snapshots from now on, per version) and `dataVersions`; the card warns with count and dates while the draft switch is on. `GET /api/settings/archive-export?format=csv|json` (full admins, `withUser({ full: true })`) — loot and attendance (`listStoredEvents` signups), both by their raid's stored version (#737, TBC without one), of every version but the main one that has data; one CSV with a `type` column (UTF-8 BOM, formula signs defused), or JSON. Nothing is ever deleted; switching the setting off brings everything back.

## Raid-Vorlagen (`src/services/events/raidTemplates.js`, page `/raids/raid-templates`)

What an evening looks like (#266): `{ id, name, versionId, instanceIds, size, composition: { tank, healer, melee?, ranged? }, requiredBuffs, signupDeadline: { hoursBefore }, durationMinutes, fairness, wishes, overflow, lockAtLimit, color, image { mode, url } }` in `data/settings/raid-templates.json` (settingsStore). `color` und `image` sind das Aussehen der Anmelde-Nachricht (#307, leer = Regelsatz); im Editor eine Zeile „Aussehen“ hinter „Mehr“, mit kleiner Vorschau. Instances and buffs come **only** from the rule set above — `validateTemplate()` refuses anything else, plus tanks + healers (and the melee/ranged minimums) > size and a max below min. `durationMinutes` (#305) is 30–600 or `null` ("nicht gesetzt", the event then has no duration either — no planned end, see docs/events.md); an event inherits it like every other planning field, and the dialog pre-fills it from here.

- **Migration on read:** a pre-#266 entry `{ id, name }` (a bare Raid-Helper template) becomes `rh-<id>` with `raidhelperTemplateId`, no instance and `size: null` — badged "Größe ergänzen" — and is written back once. "Aus Raid-Helper laden" (`POST /api/raid-templates/import`) adds unknown Raid-Helper templates the same way and leaves linked ones alone.
- **Default per category:** `config.categoryRaidTemplate = { [categoryId]: templateId }`, a select on the category card in Einstellungen → Kategorien. It replaced `raidDefaults.templateId`: a config without the map hands the old global default to every `categoryIds` entry (`categoryRaidTemplateOf()`), and the next save persists it. `DELETE /api/raid-templates` answers **409** while a category uses the template.
- **API:** one path, `GET/POST/PATCH/DELETE /api/raid-templates` (area `raids`, level by method). GET decorates each template with `needsSize`, `incomplete` (an instance with "Infos fehlen") and `defaultFor`.
- **Client:** `pages/RaidTemplatesPage.tsx` (one row per template of the menu's content version — see "Content-Umschalter" above, #563; a new template starts in that version — editor as a `Modal` held in `?edit=`), linked from the Raid-Events head — no sidebar entry. The editor is built from the shared `components/raid/RaidFields.tsx` (`InstancePicker`, `SizePicker` — `size` may be null for a migrated template —, `RoleRanges`, `BuffPicker`, `NumberInput`, `SwitchRow`), the same the create dialog uses; `src/web-client/src/lib/raids/raidTemplates.test.ts` keeps copies out of the page. Size change proposes tanks/healers (`lib/raids/raidTemplates.ts`' `proposeComposition`, the same rule as the server's, `src/web-client/src/lib/raids/raidTemplates.test.ts` compares them). `components/raid/CompositionEditor.tsx` (tanks/healers ±, "n Plätze für DPS") is shared with the event creation (#261). For a Raid-Helper event the create dialog still sends a Raid-Helper template id: it offers the templates that link one and preselects the category default (`categoryTemplates` in `GET /api/raids/new`); an EventHelper event sends `raidTemplateId` and the plan instead.
