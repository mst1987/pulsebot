# Spielversionen und Raid-Vorlagen

Endnutzer-Sicht: siehe [guide-web-admin.md#raid-vorlagen](guide-web-admin.md#raid-vorlagen). Das Versionsmodell: [game-versions.md](game-versions.md).

## Spielversionen und Instanzen (`src/config/gameVersions/`)

One rule set per game version — `tbc.js` (TBC Anniversary), `classic.js` (Classic Era), `forever.js` (WoW Forever) — pure data plus pure functions in `index.js` (`rulesFor`, `instance`, `instanceById`, `roleOfSpec`, `defaultComposition`, `compositionFor`). Signup, raid templates, event creation and the setup suggestion (#250 ff.) read from here; **there are no custom raids**, the rule set is the only source of instances. Served as `GET /api/game-versions` (area `raids`, types `GameVersion…` in `api/events/raidTemplates.ts`).

Das Versionsmodell (Hauptversion, feste Version je Kategorie und Abschnitte, Version fest am Raid, Einstellungen und Funktionen je Version, Content-Umschalter und strenge Trennung, Umstieg auf eine neue Version) steht in [game-versions.md](game-versions.md). Hier bleiben die Regelsätze selbst und die Raid-Vorlagen.

### Regelsatz: Klassen, Instanzen, Buffs

- **Classes/specs** (`classes.js`, shared by all three): spec key `"<Class>-<Spec>"` in WCL spelling (same as `councilSpecs.js`), `role` tank/healer/melee/ranged for placing a raider, `buffRole` in `raidBuffs.js`' vocabulary (a hunter is "melee" there — he wants Might), `canTank`/`canHeal`.
- **Instances** carry `sizes`, `defaultSize`, `icon`, `color` (#307: die Farbe, die Anmelde- und Setup-Nachricht ohne eigene Werte nehmen — jede Instanz hat eine), `bosses`, `finalBoss`/`finalBossNames` (EN + DE), `composition` (suggested tanks/healers per size) and `status`. **TBC is derived from `tbcContent.js`** (ids, labels, `encountersFor`, `FINAL_BOSSES`) — only size, icon and the suggestion are added in `tbc.js`. Instance ids are **unique across versions** (`ony` vs `forever-ony`, `hyjal` vs `forever-hyjal`), so a stored id never needs its version.
- **Boss order** is `BOSS_ORDER` in `tbcContent.js`, the order the raid actually meets the encounters (hand-kept): the raid plan tabs (`bossesForInstances`), the loot pick list (`lootCatalog.js`), the encounter grid of `raidProgress.js` and the raid plan auto-advance (docs/raidplan/sharing.md) all read it. Black Temple since #534: Naj'entus, Supremus, Akama, Gorefiend, **Reliquary of the Lost, then Gurtogg Bloodboil**, Shahraz, Council, Illidan. A saved plan keeps its boards (keyed by `<instance>/<boss slug>`), only the tab order follows.
- **`incomplete`** (all Forever raids until release): plannable, no bosses, no final boss — `raidProgress.js` therefore never blocks on them, and Forever's instances carry an **estimated** `composition` (10 → 2/3, 20 → 2/5, 40 → 2/8) and the rule set a `composition` curve of its own, which `defaultComposition(size, versionId)` reads first (#751); other sizes fall back to the shared curve (10 → 2/3, 20 → 2/5, 25 → 3/6, 40 → 4/10). Fill them in once the raids are out.
- **Forever's buffs (#751)** are built in `forever.js` with `buildBuffs(classes, { exclude, scopes, sharedSlots })` from Classic's rule set (beta facts, 10.10.2026, to be checked on the server): the group buffs that reach the whole raid (Gift of the Wild, Arcane Brilliance, the Prayers) are raid buffs; Battle Shout, Windfury, Grace of Air, Strength of Earth and Leader of the Pack stay party buffs; the air totems share one slot (`sharedSlot`), so a second shaman in a party adds nothing (`setupEditor.partyBenefits`). `rules.sheetLayout` (TBC only) says the Google raid sheet fits the version — the "possible" of the feature `raidSheet` (#761, "Funktionen je Version" in [game-versions.md](game-versions.md)): `versionCapabilities.sheetVersionRefusal` makes `/fillsetup` and `POST /api/raids/fill` answer 409 `no_sheet_layout` for other versions (`feature_off` when switched off), and the raid detail plans them with the raid plan (`sheetOffered`).
- **Buffs** (`buffs.js`) are derived from `raidBuffs.js` and `totems.js`, never kept twice: it only adds which spec brings a talent buff, party vs raid scope, and per version what does not exist (Classic: no Wrath of Air, Totem of Wrath, Commanding Shout). Shields and racial auras are left out.
- **Consumers so far:** `raidListing.js`' `raidSize()` takes the largest `defaultSize` of the night's contents (replaced `TEN_PLAYER`); `raidProgress.js` asks `tbcContent` first and the rule set second (Classic bosses, zones and final bosses). Raid-Helper's spec names (`Holy1`, `Destro`, …) are only an alias table in `config/data/classlist.js` (#428): each resolves to a rule-set key, and class, role and Raid-Helper's own names/emojis (`RAID_HELPER_NAMES`, plus the Death Knight in `RAID_HELPER_ONLY_CLASSES`, which no rule set plays) come from `gameVersions/classes.js` — so `setupView.roleOf` and the raidsheet fill read the rule set's roles.

## Raid-Vorlagen (`src/services/events/raidTemplates.js`, page `/raids/raid-templates`)

What an evening looks like (#266): `{ id, name, versionId, instanceIds, size, composition: { tank, healer, melee?, ranged? }, requiredBuffs, signupDeadline: { hoursBefore }, durationMinutes, fairness, wishes, overflow, lockAtLimit, color, image { mode, url } }` in `data/settings/raid-templates.json` (settingsStore). `color` und `image` sind das Aussehen der Anmelde-Nachricht (#307, leer = Regelsatz); im Editor eine Zeile „Aussehen“ hinter „Mehr“, mit kleiner Vorschau. Instances and buffs come **only** from the rule set above — `validateTemplate()` refuses anything else, plus tanks + healers (and the melee/ranged minimums) > size and a max below min. `durationMinutes` (#305) is 30–600 or `null` ("nicht gesetzt", the event then has no duration either — no planned end, see docs/events.md); an event inherits it like every other planning field, and the dialog pre-fills it from here.

- **Migration on read:** a pre-#266 entry `{ id, name }` (a bare Raid-Helper template) becomes `rh-<id>` with `raidhelperTemplateId`, no instance and `size: null` — badged "Größe ergänzen" — and is written back once. "Aus Raid-Helper laden" (`POST /api/raid-templates/import`) adds unknown Raid-Helper templates the same way and leaves linked ones alone.
- **Je Server (#1076):** every template carries `guildId`; a server sees and changes only its own, the model is the raid plan library (#945, `web/http/libraryServer.js`). A read means `?guildId=` or the active server, a write the server the tab loaded (`libraryGuildId`, the GET's `guildId`): a tab left over from another server is **409 `server_switched`**, a template of another server **404**. Only a full admin reaches another server than the active one; the write right stays `raids` write. Store functions take the server first, an invalid server holds nothing and refuses a write. A new server starts empty, never from another server's data.
- **Readers:** every way to a template asks on the raid's server: create dialog, `POST /api/raids`, series, quick create, bot draft, setup, leader flags, roster options, loot council and addon sync (by the category's server, `guildOfCategory`). A reader of a raid whose category has no known server finds no template rather than another server's. Only the Einstellungen dialog falls back to the active server (`templateServerOf` in `web/apiRoutes/system/settings.js`: `guildOfCategory(categoryId) || activeGuildFor(req)`), because the admin choosing a default is on that server. `getRaidTemplate(guildId, id)` matches the exact id, then a copy's `originId`, so a stored old id (a raid, an unplaced reference) still finds **its server's** copy. Across servers only `allRaidTemplates()`, for the versions with data and the version launch.
- **Migration (`settingsMigration.migrateRaidTemplateServers`, at start):** the old global file goes once to `raid-templates.json.pre-1076`; each template stays with its id on the first server of the list, every further server gets a copy with a new id and `originId`. The backup goes through temp plus rename, the log line counts stamped originals and copies apart. A second run changes nothing. Then category defaults and series of a further server are set to their server's copy (the first server keeps its ids). **Proof of the server:** the name snapshot `category-names.json` first. A `guildId` on an event, raid event, roster or series can be a guess, so it only counts when the category is not older than that server by Snowflake; a server older than the category stays undetectable without a snapshot entry. A category nothing proves keeps its id, with one log line. **Once:** the references move once, marked `raidTemplateReferences` in `migrations.json`, set only after they moved: a crash between the files goes on at the next start, and later starts leave them alone. While global entries are left (a `WARNUNG` line) they wait and no mark is set; a run that copies again moves them again whatever the mark says. Without any server the file stays untouched with a `WARNUNG` line and the next start tries again.
- **Rückweg (back to global templates):** only together with deploying a version before #1076; with #1076 still deployed a restored file just migrates again at the next start (new copy ids, the references follow, the first backup stays). Stop the bot. Read the mapping `id → originId` from the current `raid-templates.json` first, as the backup does not hold it. In `config.json` (`categoryRaidTemplate`) and `event-series.json` (`raidTemplateId`) set every id of a copy back to its `originId`. Then copy `raid-templates.json.pre-1076` over `raid-templates.json`. Not covered: templates changed or created since the migration, and raids that name a copy's id. The mark may stay, the old version does not read it.
- **Default per category:** `config.categoryRaidTemplate = { [categoryId]: templateId }`, a select on the category card in Einstellungen → Kategorien, offering the templates of the category's server. It replaced `raidDefaults.templateId`: a config without the map hands the old global default to every `categoryIds` entry (`categoryRaidTemplateOf()`), and the next save persists it. A save resolves a changed entry on the category's server (a copy's old id becomes the copy's own, a foreign id is dropped); an unchanged entry stays. `DELETE /api/raid-templates` answers **409** while a category uses the template; a category of unknown server and a reference by `originId` count as using it, so a delete never takes a default away.
- **API:** one path, `GET/POST/PATCH/DELETE /api/raid-templates` (area `raids`, level by method), see „Je Server“. GET answers `{ guildId, templates, categoryNames }` and decorates each template with `needsSize`, `incomplete` (an instance with "Infos fehlen") and `defaultFor`. `POST /api/raid-templates/import` takes the templates into the tab's server.
- **Client:** `pages/RaidTemplatesPage.tsx` (one row per template of the menu's content version — see "Content-Umschalter" in [game-versions.md](game-versions.md), #563; a new template starts in that version — editor as a `Modal` held in `?edit=`), linked from the Raid-Events head — no sidebar entry. The editor is built from the shared `components/raid/RaidFields.tsx` (`InstancePicker`, `SizePicker` — `size` may be null for a migrated template —, `RoleRanges`, `BuffPicker`, `NumberInput`, `SwitchRow`), the same the create dialog uses; `src/web-client/src/lib/raids/__tests__/raidTemplates.test.ts` keeps copies out of the page. Size change proposes tanks/healers (`lib/raids/raidTemplates.ts`' `proposeComposition`, the same rule as the server's, `src/web-client/src/lib/raids/__tests__/raidTemplates.test.ts` compares them). `components/raid/CompositionEditor.tsx` (tanks/healers ±, "n Plätze für DPS") is shared with the event creation (#261). For a Raid-Helper event the create dialog still sends a Raid-Helper template id: it offers the templates that link one and preselects the category default (`categoryTemplates` in `GET /api/raids/new`); an EventHelper event sends `raidTemplateId` and the plan instead.
