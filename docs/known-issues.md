# Known Issues and Gotchas

- **The SPA fallback must never answer a file (#530).** `staticClient.js` used to hand *every* path it had no file for to `index.html` with 200 — also `/assets/RaidplanTab-<hash>.js` of the previous build that a tab opened before a deploy still asked for. The browser then refused the "module script" with MIME type `text/html`, `import()` failed with "Failed to fetch dynamically imported module" and the page went white. Only a path **without** a file extension is a page and falls back to `index.html`; a missing file is a `404 text/plain`. On that 404 the client reloads once (`lib/chunkReload.ts`, `lazyWithReload()` instead of `lazy()`), and `deploy.sh` keeps the previous build's assets for a while. A new lazy chunk that uses plain `lazy()` brings the white page back — `test/web-client/conventions/codeSplitting.test.js` refuses it. Reproduce: build, open a page in the browser, change a lazy module and build again, then open that lazy page in the old tab (docs/web-admin.md, "Nach einem Deploy").

- **Deleted channels leave dead links behind (#537).** On the dev server every event channel was deleted on 22.09.; `data/settings/events.json` kept pointing at them and the talk overview linked all seven ("You don't have access to this link", API 10003). The stores never learn about a deletion by themselves — a link is only safe through `linkCheck.js`, and a new overview that glues `discord.com/channels/` together itself is refused by `linkCheck.guard.test.js`. A copied `data/` on a dev instance points at channels of the dev server that may be long gone: expect "channel missing" and the dashboard tasks there, that is the check working.

- **dotenv path:** `bot.js` loads `.env.dev` when it exists next to `src/`, otherwise `.env` (both resolved from `src/`, so the working directory does not matter). The scripts read the env file relative to the **working directory** (`scripts/register-commands.js`: `.env`, or `.env.dev` with `--dev`), so always run them from the project root.
- **No validation on `interaction.channel.parent`:** Commands that need a category channel must guard against `parent` being null (top-level channels have no parent).
- **`console.log(data)` in `raidhelper.js`:** `getAllEvents()` logs the raw API response to stdout on every call in legacy code paths.
- **Past-event detail pages can lose an event once its Discord channel is gone:** `/api/raids/detail` resolves an event via `raidEventGroups.js`'s `loadEventGroups()`, which joins live Raid-Helper events against **live** Discord channels (`discord.getChannelCategoryMap()`). If a past raid's signup channel was later deleted/archived, the event silently drops out of that join (`if (!meta) continue;`) even though Raid-Helper's API still returns it — the detail page then errors with "Event nicht gefunden.". The "Vergangene Raids" **list** doesn't have this problem: it reads a separate persisted snapshot (`raidEventStore.js`, populated by `raidEventScan.js`) that keeps the channel/category name captured at scan time instead of re-joining live Discord state. `matchableEvents.js`'s `loadMatchableEvents()` (used by log→event assignment) has the same persisted-snapshot fallback for the same reason.
- **Never look an event up by scanning the window when you know its id.** Cloning a raid (`POST /api/raids` with `sourceEventId`) used to find its source in `loadEventGroups(guildId, { sinceSeconds })` — the same 60-day list the create dialog was filled from — and answered "Ausgangs-Event nicht gefunden" whenever it was not in it. That list can shrink between opening the dialog and pressing the button for reasons that have nothing to do with the event: a Raid-Helper hiccup, a Discord reconnect emptying the channel join, or the cache's five-minute bucket rolling over (the last-good fallback is keyed by request *shape* since then, not by that bucket, so an outage no longer starts with an empty fallback). `sourceChannelFor()` in `eventCreate.js` (an own source event comes straight from the store) asks Raid-Helper for that one event instead (`getEvent(id)`), then the snapshot, then the window scan — and says which of the two things went wrong, because "Raid-Helper antwortet gerade nicht" and "das Event gibt es nicht mehr" call for different reactions.
- **A branch name with "token" or "secret" fails `main` after its merge (and skips the deploy).** `GET /health` reports the running commit's subject, and `test/web/http/server.test.js` ("keeps paths and secrets out of /health") refuses those words in the whole response. On the branch the subject is the own commit message, so the PR's checks pass; the merge commit's subject is "Merge pull request #N from <owner>/<branch>", so a branch like `feature/raidplan-task-tokens` (#499) turns `main` red and CI skips "Deploy to Production". Name branches without those words (write "marker", "key", "credential"); if it happened, the next merge with a clean subject makes `main` green and deploys both.
- **Board lines only reach what stands on the map *as that reference*.** `assignmentLinks` (`lib/raidplan/assign.ts`) was written for placed slots and heal rows only; since the auto placement (tank rows, #498 task rows) most raiders and mobs stand on the map as **derived** objects (`deriveAuto`), not as slots or icons, so a "Heiler 1 -> Tank 1" row whose slots are only in the Besetzung drew nothing, and tank / kick rows never had a line at all (#507 - no regression between 6449f731 and #506, the same data drew the same lines on both). A new kind of map object must be resolvable by the line code too: hand the plan in (`assignmentLinks(board, me, plan)`), fall back from a slot to its raider's place, and cover it in the render test in `BoardWorkspace.test.tsx`.
