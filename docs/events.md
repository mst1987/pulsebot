# Eigene Events (Anlegen, Verwalten, Serien)

## Eigene Events (`eventStore.js`, `signupStore.js`, `eventSources.js`)

Events live in **two sources**: at Raid-Helper, and in the EventHelper's own store (`source: "eventhelper"`, #254). **One event has exactly one source** — nothing is imported, nothing is mirrored, nothing expires. A Raid-Helper event stays fully in use wherever one exists, also in a category whose new events are created in the EventHelper.

- **⚠️ Readers only know the common shape.** Every reader — `loadEventGroups()` (raid list, detail, history, ingest, dashboard modal, reminders), `loadMatchableEvents()` (log auto-link, CLA assignment), the stored-event list (past raids, dashboard, roster attendance, loot council, category names, player summaries, the channel page's event badges), `dashboardData.loadNextRaids()` and the bot's `helper.getCategoryEvents()` — gets both sources in the shape Raid-Helper events already had, plus `source`. The only file that knows there are two is `src/web/eventSources.js`: `ownEventGroupRows()` / `ownMatchableEvents()` / `ownUpcomingRaw()` merge the own events into the three existing lists, `listStoredEvents()` / `getStoredEvent()` are the drop-in for `raidEventStore.listRaidEvents()` / `getRaidEvent()` (Raid-Helper's snapshot plus own events that already started). **A new reader asks the adapter, never `eventStore` directly**, and a new Raid-Helper-only feature branches on `source`, not on the id.
- **Signups** (`data/settings/signups.json`, `eventId → userId → { character, spec, role, characters[], status, canAlso[], comment, at }`): `characters` (#293) are the raider's own characters `{ character, spec, role, status }` in priority order (`status` per character since the signup buttons: „Spät“/„Vielleicht“/„Bank“ on an existing signup move only the first; a character without one has the signup's, an absence stores none; the top-level `status` is the first character's, and a request without per-character statuses keeps them while the signup's status stays the same, else all take the new one — `signupCharacters.migrateSignup`, `signupService.withStatuses`; after the deadline/closing each character must keep its status or take an allowed one) — the first is the choice, the others "kann auch mit", at most `MAX_CHARACTERS` 3; the top-level character/spec/role **always mirror `characters[0]`**, so every reader that knows one character keeps working, and `canAlso` stays the roles without an own character. A signup stored before #293 gets `characters` on read (`signupCharacters.migrateSignup`, used by `listSignups`/`getSignup`; the pure part lives in `src/web/signupCharacters.js`). `toSignUpShape()` carries `characters` along; attendance and log matching still count per person. `spec` is a rule-set key (`"Priest-Shadow"`), `status` one of `attendance.js`' `SIGNUP_STATUSES`. `toSignUpShape()` hands them out as `{ userId, specName, className, status, … }` with `specName` mapped onto the Raid-Helper spec name (`RH_SPEC_NAMES`, a test holds every rule-set spec resolving through `setupView.specProfile`) and an absence as the pseudo spec `"Absence"` — so attendance, role fill, class counts and the bot's "not signed up" lists need no change.
- **Events** (`data/settings/events.json`): id with the prefix `eh-` (Raid-Helper ids are bare numbers — `isOwnEventId()`, and the client's `lib/discordLinks.ts` uses the same rule), guild, category, channel, title, description, leader, `startTime` (seconds), `versionId`, `instanceIds`, `size`, `composition { tank, healer, melee, ranged }` (melee/ranged = the minimum, 0 = no target), `compositionMax { melee, ranged }` (the optional maximum of a range, null = open — kept apart so every reader of a plain number still works), `requiredBuffs` (rule-set buff keys), `raidTemplateId` (where the values came from; the template is never written through the event), `signupDeadline`, `durationMinutes` (30–600, default 180 — #305; the end is `startTime + durationMinutes × 60`, the one rule is `utils/eventTime.js`' `eventEndTime()`, deliberately not in the store because half its readers mock it), `voiceChannelId` (#305, "" = none), `fairness`/`wishes`/`autoSuggest` ("Vorschlag bei Anmeldeschluss", for #262), `overflow`/`lockAtLimit` (the waiting list, #306), `announcedAt` (the create announcement went out, #306), `setup` (draft, approval and approved snapshot — see "Setup-Editor" in docs/setup.md), `message` (where the bot's post sits), `discordEvent` (the Discord event, see below). `normalizePlan()` validates against the rule set and fills what is missing: the biggest instance's `defaultSize`, its suggested tanks/healers. It takes melee/ranged as a number or `{ min, max }`, refuses minimums that add up to more than the size, a max below its min or above the size, and buffs the version does not have.
- **Which source a new event gets** is `config.categorySignupSource = { [categoryId]: "raidhelper" | "eventhelper" }` (missing = `config.signupSourceDefault`, EventHelper for a new category since #291 — see docs/raidhelper-retirement.md), edited as the one segment *Neue Events* on the category's card in Einstellungen → *Kategorien*. `src/web/eventCreate.js`'s `createEvent()` is the one way in (`POST /api/raids` and `/event anlegen`): it resolves, clones (`sourceChannelFor`, own source events read from the store) or creates the channel (`newChannel: { name, categoryId, templateChannelId }`, via `discordChannels.createFromTemplate`), reads the category's source (a body's `signupSource` overrides it for that one event), and either calls Raid-Helper as before or validates the plan **before** cloning a channel, stores the event (instances from the body, else from the title) and posts the event message. A message that cannot be posted is reported as `messageError`, never a failed create.
- **Raid-Helper-only things stay Raid-Helper-only:** the raidplan link (`raidplanUrl()` returns `""` for an own id, every caller renders no link then), `getSetup` (dashboard, raid detail, `utils/raidhelper.js`), the "Raidplan öffnen" primary action (`raidDetailSteps.js` — an own event's setup step opens its setup editor instead). `POST /api/raids/fill` fills an own event's sheet from its **approved** setup (`setupEditor.raidHelperSlots`), refused with `no_approved_setup` before an approval. The Discord post link of an own event opens its channel.
- **The raid plan works with both sources** (docs/raidplan.md, "Raid-Helper-Events"): an own event always has one; a Raid-Helper event gets one when the orga switches it on in its "Verwalten" menu (the only entry that menu has for a Raid-Helper event). Its players are then read from Raid-Helper (never written), instance/size/version live on the plan record, taken from the title. Neither source is the preferred one for planning — pick the source by how the signup should run, the plan follows.
- **The event message** (`src/web/eventMessage.js`): the Raid-Helper-style signup list with the public select `event-join:<eventId>` — see "Anmelder-Nachricht" in docs/signups.md. Posted on create; `startEventMessageSync()` (started in `server.js`) listens to `signupStore.onSignupsChanged` and edits it once per burst of changes, re-posting a message that was deleted in Discord. Messages posted before #287 still carry the button `event-signup:<eventId>`, whose handler `commands/signup/eventSignup.js` keeps opening the Discord signup dialog — see "Anmeldung (Bot)" in docs/signups.md.
- **`/event anlegen` in Discord (#260)** — `commands/event/event.js` (slash, group `raids`, default admins; the orga role gets it under Bot-Befehle), `eventCreateStep.js` (`event-new:<field>:<state>`: selects Kategorie / Raid-Vorlage / Kanal-Modus / Event bzw. Kanal, the source toggle, Zurück, Abbrechen) and `eventCreateModal.js` (`event-form:<state>[:<token>]`: "Weiter" and "Nochmal" open the modal **directly** — never after a defer —, the submit defers and replaces the message). All logic is `src/web/eventDraft.js`. **Nothing is stored between the steps:** the state `cat:tpl:mode:src:ref` rides in every customId (≤ 100 chars — ids are checked by regex, a template id over 24 chars is not offered) and is re-checked on submit against what exists now (event category, template, channel on the server, event server only). The modal has Titel, Datum (`24.09.2026`, `24.09.`, `24.9.` — `parseGermanDate` in `utils/date.js`, a yearless day long gone rolls into next year, a recent one is refused as past), Uhrzeit (`19:30`, `1930` — `parseClockTime`), `Größe/T/H` (only for EventHelper, prefilled from the template, e.g. `25/3/6`) and Beschreibung. Channel modes: *neu nach Schema* and *duplizieren* name the channel through `channelNaming.deriveChannelName()` (like the category's previous event channel resp. the duplicated one, else the stored/default schema — see docs/channels.md; step 1 and the confirmation say where the name came from) and refuse a taken name; *bestehender Kanal* is a Discord channel select. A Raid-Helper event needs a template with `raidhelperTemplateId`. Errors come back with „Nochmal" (the typed values kept in memory under a short token for 30 min, only for the same user) and „Zurück"; success shows *Zum Kanal*, *Im Web bearbeiten* and *Ankündigung pingen* (`/raids/detail?event=…&tab=actions`, the Anmelde-Aufruf dialog). Tests: `test/web/eventDraft.test.js`, `test/commands/event/event.test.js`.
- **The setup** is proposed by "Setup-Vorschlag" (it reads the event's own `requiredBuffs` and melee/ranged ranges; `autoSuggest` drafts a proposal at the deadline — see "Setup proposal at the deadline" in docs/discord-servers.md) and edited and approved in "Setup-Editor" in docs/setup.md.

## Event anlegen im Web (`components/RaidCreateDialog.tsx`, #261)

One guided dialog, **one step at a time**: *Vorlage* (segment "Letzte Events" / "Raid-Vorlagen", plus "Leer beginnen") → *Termin* (title, date, time, category; leader and description folded away) → *Raid* (**only for an EventHelper event**) → *Kanal & Anmeldung* → *Prüfen*. `lib/eventPlan.ts`' `stepsFor(editing, source)` decides the list; a Raid-Helper event keeps today's fields (its Raid-Helper template sits in the channel step).

- **The raid step stays calm:** version segment, instance chips with icon and "Infos fehlen" (`components/RaidPlanFields.tsx`, rt- classes shared with the template modal), size segment from the instances' allowed sizes plus "frei", tanks/healers large in the shared `CompositionEditor`, one badge "n / size verplant" or the problem. Melee/ranged ranges, required buffs and the three switches (Fairness, Wünsche, Vorschlag bei Anmeldeschluss) are behind "Mehr". A size change proposes tanks/healers, an added instance that does not come in the current size brings its own default size (`withSize` / `withInstance`).
- **The plan rules are pure and mirrored:** `lib/eventPlan.ts` is strippable like `lib/raidTemplates.ts`; `test/web-client/eventCreateDialog.test.js` runs `planProblem()` against the server's `normalizePlan()` and `schemaName()` against `utils/channelNames.renderChannelName()`, so the dialog words a problem exactly like the API.
- **Starts:** a raid template copies its values into the plan (`planFromTemplate`); repeating an event takes its category's default template, else the instances its title names; "Leer beginnen" the category default. The event keeps a copy — changing it never changes the template. **"Als Vorlage speichern"** (raid step) writes the plan into the template it came from or a new one through the ordinary `POST/PATCH /api/raid-templates` (`templateFromPlan`).
- **Channel:** "Neu nach Schema" creates a text channel in the chosen category (`newChannel: { name, categoryId }` → `discordChannels.createFromTemplate`, the same shape `/event anlegen` sends; an empty name is filled from the schema, the schema's template channel is used if one is stored), named like the category's previous event channel (`GET /api/raids/channel-name`, one `NamingBadge` under the field, #285; the local schema only as fallback) until the name is typed by hand, and created as a copy of that channel behind the previous date; "Klonen" only for a repeated event in its own category; "Vorhanden" lists the category's channels. A clone or new channel without a name is named by the schema on the server too (`schemaChannelName`). Discord refusing reads "Kanal konnte nicht angelegt werden: fehlende Rechte".
- **Source and deadline:** "Anmeldung über" is preset from `categorySignupSource` and sent as `signupSource` (it overrides the category for this one event). The deadline is "Stunden vor Start" (`signupDeadlineHours`), turned into seconds on the server from the Berlin start, so the browser's time zone never matters.
- **Context:** `GET /api/raids/new` also returns `categories`, `categoryRaidTemplates`, `raidTemplates` (with badges), `versions`/`defaultVersion`, `channelSchemas`/`defaultSchema` and, with `?event=<eh-id>`, `editEvent`.
- **Editing an own event** uses the same dialog (`editEventId`): from the raid detail's head, the first entry of the "Verwalten" menu (see "Event verwalten") for an EventHelper event and `raids` write. No start step, the channel and category stay. `PATCH /api/raids` (`eventCreate.updateEvent()`, area `raids`, write by method) takes `{ id, title, date, time, … plan fields }`, refuses a Raid-Helper id (`not_own_event`) and another server's event, re-validates the plan and edits the bot's message (`refreshEventMessage`, a failure is `messageError`). `createEvent()`'s signature is shared with the Discord modal (#260); an edit also re-syncs the talk overview (#257).

## Kalender-Link und öffentliche Event-Seite (`src/web/icsFeed.js`, `src/web/eventPublicPage.js`, #308)

> Öffentliche Event-Seite, ICS-Texte und Discord-Event sind für Raider und deshalb **Englisch** (siehe [signups.md](signups.md), „Sprache im Discord“). Die Seite schreibt Zeiten als englischen Text in Serverzeit („Thu 24 Sep 2026, 19:30“, `<html lang="en">`); die ICS-Zeiten bleiben UTC und der Kalender zeigt sie in der Zeitzone des Lesers.

Two paths an own event owns, both **server-rendered and reachable without a login**, both matched in `server.js` *above* the SPA fallback (like `/r/<id>`), both with an id pattern of `[A-Za-z0-9_-]+` only — no path can traverse:

- **`GET /r/cal/<eventId>.ics`** — one VEVENT, `text/calendar`, `Content-Disposition: attachment`. `buildIcs(event)` in `icsFeed.js` is pure and is the whole rule: CRLF endings, every line folded at **75 octets** (`foldLine` counts UTF-8 bytes and never splits a character; continuation lines start with one space), text escaped per RFC 5545 (`\` `;` `,` newline) and every time in **UTC** — a local time would need a VTIMEZONE block and the store keeps unix seconds anyway. `UID` is the event id, `DTSTAMP`/`SEQUENCE` come from the last change (`SEQUENCE` counts seconds since 2020, so it stays inside 32 bits), `DTEND` from the duration (#305, `utils/eventTime.js`; an event stored before it reads as the default 3 h), `LOCATION` is the event channel's Discord link, `URL` the public page, and a cancelled event is `STATUS:CANCELLED` with „Abgesagt" in the summary. An event without an id or without a start answers "" and the route 404s.
- **`GET /e/<eventId>`** — the page the bot links under every signup message, for everyone in the channel, with or without a menu account. `publicEventView(event, signups)` in `eventPublicPage.js` is pure and is the **only** thing the page renders from; `renderPublicEventPage()` puts it into `render.js`'s `layout()`. Head, three facts (Termin · Angemeldet n/size · Anmeldeschluss), the description, the two links, the signups as one block per class (the grouping is `eventMessage.rosterEntries`/`classesOf`/`rosterCounts`/`messagePhase`, so the page and the channel can never disagree), Spät/Vielleicht/Bank/Abgemeldet as their own blocks, and the **approved** setup. A cancelled or closed event says so; an unknown id is a 404.

⚠️ **Nothing personal leaves either of them, and `VIEW_KEYS` is the list.** The payload carries character name, spec (key, German label, icon) and status — and nothing else. Out, on purpose: Discord **user ids**, comments, wishes and wish partners, „kann auch mit", everything from the raider profile, and any setup **draft** (only `setupEditor.approvedSetupOf()` is read, and the approved snapshot's `userId`s and reasons are dropped again here). The page carries **no Discord link at all** — a link is an id, and a visitor need not be on the server; the `.ics` keeps `LOCATION` because a calendar entry wants a place. Whoever adds a field adds it to `VIEW_KEYS`, or `test/web/eventPublicPage.test.js` fails: it walks the payload against the list and searches payload *and* rendered HTML for every id, comment and draft of its fixture.

- **The links:** the signup message's line is `Event · Anmeldung · Setup · Kalender` (`eventMessage.js`; the calendar link defaults to the event's own `/r/cal/<id>.ics`, `icsUrl` still overrides it), and the web's signup dialog carries „In Kalender eintragen" / „Öffentliche Event-Seite" (`components/SignupDialog.tsx`, `.an-links`).
- Tests: `test/web/icsFeed.test.js` (folding, escaping, UTC, duration, cancelled, nothing personal), `test/web/eventPublicPage.test.js`, the routing in `test/web/server.test.js`, the message line in `test/web/eventMessage.test.js`, the dialog links in `test/web-client/signupsPage.test.js`.

### Kalender-Abo je Raider (`GET /r/cal/user/<token>.ics`, `src/web/calendarFeed.js` + `calendarTokenStore.js`, #312)

The third path of the same family: **one link per raider**, pasted into Outlook/Google/Apple once, carrying every raid they are signed up for — so a new raid turns up in the calendar by itself. Matched in `server.js` above the single-event file (and above the SPA), same `[A-Za-z0-9_-]+` pattern, GET only.

- **The token is the whole authentication**, so the store (`calendarTokenStore.js`, `data/settings/calendar-tokens.json`, prefix `ehc_`) follows `ingestTokenStore.js` to the letter: **sha256-hashed** on disk (never the secret; a 4-char `hint` tells two links apart), the plaintext handed out in exactly **one** answer and never retrievable, `verifyToken` comparing in constant time, revoking immediate. The one difference: a token belongs to **exactly one Discord account**, and `revokeToken(id, userId)` checks the owner itself so no caller can forget to — a foreign id reads as „not found". At most `MAX_PER_USER` (5) per raider.
- **⚠️ An unknown *or* a revoked token is a plain 404** — the same answer a path that never existed gets, never „Token ungültig". `feedFor()` verifies before it reads a single store.
- **What is in it:** `buildUserCalendar(entries)` in `icsFeed.js` (pure; `vevent()` is the VEVENT shared with `buildIcs`) — one VEVENT per raid with title, time, end, the channel link, the public page **and the reader's own status** („Deine Anmeldung: Spät"). Nothing else: no other raider's name, no comment, no „kann auch mit", no setup, no Discord user id. `test/web/icsFeed.test.js` walks the file against an **allowlist of property names** and hunts for every id, name and comment a careless caller might hand in.
- **An own absence stays in as `STATUS:CANCELLED`** instead of falling out. A silently missing VEVENT leaves the raid standing in every calendar that already fetched it; `CANCELLED` makes the client strike it (the summary then reads „Abgemeldet: …"). `TRANSP` is `OPAQUE` only for *Dabei* and *Spät* — a „Vielleicht" or a bench seat does not block the day in a free/busy view.
- **The signup's own change time rides along** (`changedAt`), so a status change raises `DTSTAMP`/`SEQUENCE`: a calendar client may ignore an update whose sequence did not grow.
- **Bounded and cached:** `collectEntries` asks `eventStore.listEvents` for **30 days back, 90 days forward** and stops at `MAX_EVENTS` (200); `feedFor` caches the built file **per token for five minutes** (`Cache-Control: private, max-age=300` — never a shared cache). A subscribed calendar polls forever from several clients, so `touchToken` only counts a real build: the disk stays quiet and the profile can still say „noch nie abgerufen". Only **own** events appear — a Raid-Helper event has no signup in our store. `signupStore.signupsOfUser(userId)` is the one pass over the signups.
- **Where it is minted:** Mein Profil → the folded line *Kalender-Abo* (`ProfilePage.tsx`'s `CalendarPart`, `.pf-cal*` in `styles/profil.css`) — a sentence that the link is secret, „Link erzeugen", the link once in a copy field badged „nur jetzt sichtbar", one line per link with created/last fetched and „Widerrufen". `GET/POST /api/profile/calendar` (area `signup`, the session's account only; `{ revoke: id }` on the POST revokes, like `/api/profile/characters`' `{ remove }`). Without `PUBLIC_BASE_URL` the part says so instead of offering a link.
- **Tests:** `test/web/calendarTokenStore.test.js`, `test/web/calendarFeed.test.js` (window, cache, unknown/revoked token, two raiders never crossing), the allowlist in `test/web/icsFeed.test.js`, the routing in `test/web/server.test.js`, the endpoints in `test/web/profileRoute.test.js`, the page in `test/web-client/profilePage.test.js`.

## Discord-Event, Dauer und Sprachkanal (`src/web/discordEvent.js`, #305)

Raid-Helper puts every raid into Discord's own event list; the EventHelper does too — **per category, off by default** — and a raid now says how long it takes and where it meets.

- **Die Dauer ist ein Planungsfeld** wie die Größe: `event.durationMinutes` (30–600, Default 180), geerbt von `raidTemplate.durationMinutes` (`null` = nicht gesetzt). Das Ende ist `startTime + durationMinutes × 60`. Die Regel steht in **`src/utils/eventTime.js`** (`clampDuration`, `eventEndTime`), nicht im `eventStore` — die Anmelder-Nachricht, das Discord-Event und der Setup-Editor lesen sie, und die Hälfte davon mockt den Store in ihren Tests; eine reine Rechnung darf nicht mitgemockt werden müssen. `eventStore` re-exportiert sie.
- **Der Sprachkanal** ist `event.voiceChannelId` ("" = keiner), vorbelegt aus `config.categoryVoiceChannel[categoryId]`; er steht als eigenes Kopf-Feld (`eh_ui_voice`) in der Anmelder-Nachricht und ist der Ort des Discord-Events. `discord.listVoiceChannels(guildId)` füttert beide Auswahlen (`GET /api/settings`, `GET /api/raids/new`).
- **Das Discord-Event** (`event.discordEvent = { id, guildId, at, error }`, `eventStore.setEventDiscordEvent`, gemergt wie `setupPost`): `createForEvent` · `syncForEvent` · `cancelForEvent` · `reopenForEvent` · `deleteForEvent`. **Alles best-effort** — jede Funktion antwortet `{ warning }` statt zu werfen, der Text landet über `warningOf()` in den `warnings` der Aktion und als `discordEvent.error` am Event. Ein fehlendes Recht („Events verwalten", `discord.botCanManageEvents` — `null` heißt *unbekannt*, nie *fehlt*) verhindert nur das Discord-Event, nie das Anlegen.
- **Der Ort:** ein Sprachkanal des Event-Servers (`entityType: Voice`, geprüft gegen den Channel-Cache — ein gelöschter Kanal fällt zurück), sonst `External` mit der Anmelde-Nachricht als `location`. **Ein External-Event braucht zwingend ein Ende** — deshalb ist die Dauer nicht optional.
- **Die Beschreibung sagt, dass die Anmeldung woanders läuft** (`SIGNUP_NOTE`: „Anmeldung nur über die Nachricht im Kanal – ‚Interessiert' hier zählt nicht."). Ohne den Satz hätte ein Raid zwei Roster, und keines wäre richtig — Discord kennt weder Spec noch Charakter.
- **Mitziehen:** `eventCreate.createEvent` legt es **nach** der Nachricht an (damit die Beschreibung sie verlinken kann), `updateEvent` und `eventManage.moveEvent` synchronisieren, `cancelEvent` sagt es ab (Status `Canceled`; wo Discord das verweigert, wird gelöscht — ein gelistetes Event zu einem ausgefallenen Raid ist schlimmer als keines), `reopenEvent` legt ein neues an (ein abgesagtes lässt sich nicht wiederbeleben), `deleteEvent` löscht es (`{ store: false }` — das Event ist da schon aus dem Store). Ein von Hand gelöschtes Discord-Event (404 / 10070) wird vergessen und, wenn es noch Sinn ergibt, neu angelegt.
- **Schalter:** `config.categoryDiscordEvent = { [categoryId]: true }` (Default aus, nur eingeschaltete Kategorien gespeichert) und `config.categoryVoiceChannel = { [categoryId]: channelId }` — beide in Einstellungen → Kategorien (`CategoryMatrix.tsx`), gemergt gespeichert (`false` bzw. `""` löscht den Eintrag), kein Full-Admin-Schlüssel.
- **Im Web:** die Dauer klein neben der Uhrzeit im Schritt *Termin* (mit „Ende 23:30" darunter), der Sprachkanal im Schritt *Kanal & Anmeldung*, beides auch in der Prüfen-Liste; die Vorlage hat die Dauer unter „Mehr". **In `/event anlegen`** trägt das Feld **`Größe/T/H/Dauer (Min.)`** die Dauer als vierten Teil (`25/3/6/240`) — ein Discord-Modal nimmt fünf Felder, und Titel, Datum, Uhrzeit und Beschreibung sind alle nötig; ohne den vierten Teil bleibt die Dauer der Vorlage.
- **Tests:** `test/web/discordEvent.test.js` (Aufbau, Voice vs. External, Anlegen/Ändern/Absagen/Löschen mit einem Fake-Client, 404, Schalter aus, fehlendes Recht), plus die Haken in `eventCreate`, `eventManage`, `eventStore`, `eventMessage`, `eventDraft`, `discord`, `settingsStore`/`settingsRoute` und `raidhelperRetirement`.

## Das Raid-Cockpit auf der Raid-Detailseite (`src/web/raidDetailSteps.js`, #319)

Ein Raid wohnt an sieben Stellen im Menü, die Frage der Orga ist aber immer dieselbe: **was ist bei diesem Raid als Nächstes zu tun?** Die Detailseite eines **eigenen** Events beantwortet sie oben als Strecke aus fünf Schritten — **Angelegt › Anmeldung › Setup › Freigabe › Nachbereitung** —, je Schritt ein Zustand, eine große Zahl und **höchstens eine Tat**. Darunter stehen die bekannten Tabs. **Ein Raid-Helper-Event behält die heutige Ansicht**: `steps` ist dann `null` und der Kopf zeigt weiter die Leiste von #219 (Anmeldung › Setup › Raidsheet › Softres › Loot › Logs) samt ihrer Haupt-Tat.

- **Die Regel ist rein und liegt an einer Stelle:** `eventSteps(d, { now })` in `raidDetailSteps.js` — keine Store- und keine Discord-Aufrufe, nur eine Funktion über das Detail-Payload, das die Seite ohnehin bekommt. Darum kann die Raid-Liste `/raids` später dieselbe Antwort benutzen (Entwurf B; die Liste ist nicht Teil von #319), und darum hängen die Regeln in plain Jest statt ungetestet im TSX. Je Schritt kommt `{ id, label, icon, state, value, unit, note, fill, hint, action }` heraus, dazu `{ current, action, cancelled, note }` — `action` ist die eine auffällige Tat (die des offenen Schritts, bei einem abgesagten Event der Weg zurück).
- **Woher die Daten kommen:** `event.*` (Kanal, Start, `size`, `signupDeadline`, `autoSuggest`, `status`, `signupsClosed` — die letzten drei über `manageState()`), `ownSignups` (Plätze und Warteliste), `ownSetup` (`setupSummary`), **`ownSetupPost`** (neu: Kanal, Nachricht, `version` und die DM-Zahlen der geposteten Setup-Nachricht, #290 — bewusst ohne `told`-Karte und ohne User-Ids) sowie `eventLogs` und `lootItems`. `size`, `signupDeadline` und `ownSetupPost` stehen nur an einem eigenen Event im Payload.
- **Wann ein Schritt fertig ist:** *Angelegt* immer · *Anmeldung*, sobald sie geschlossen ist oder der Anmeldeschluss vorbei (dann kommt niemand mehr von selbst dazu) · *Setup*, sobald ein **Entwurf** existiert · *Freigabe* nur mit **freigegebenem** Setup, das seit der Freigabe nicht verändert wurde · *Nachbereitung*, wenn ein Log **ausgewertet** *und* Loot **importiert** ist.
- **Genau eine Tat je Schritt**, und zwar die, an der es gerade hängt: *Anmeldung* → kein einziger Angemeldeter = „Anmelde-Aufruf posten“, Fehlende mit Raider-Rolle = „Fehlende pingen“, sonst „Anmeldung schließen“; *Setup* → „Setup vorschlagen“ bzw. „Setup öffnen“; *Freigabe* → „Setup freigeben“, und wenn die Nachricht im Kanal einen älteren Stand zeigt „Setup posten“; *Nachbereitung* → „Log zuordnen“ → „CLA/RPB auswerten“ → „Loot importieren“. Freigeben, Vorschlagen und Posten führen in den **Setup-Editor** — die Leiste baut keine zweite Logik daneben.
- **⚠️ „Übersprungen“ darf nicht wie „kaputt“ aussehen.** Ein Raid ohne Setup ist ein gewöhnlicher Raid (PuG, spontaner Abend), kein Fehler. Die Regel: **kein Entwurf, weniger als eine Stunde bis zum Start, und `autoSuggest` ist aus** (bzw. der Raid hat schon begonnen — dann kommt auch mit `autoSuggest` keiner mehr) ⇒ *Setup* und *Freigabe* stehen auf `skipped`, blasser statt rot, ohne Ton, ohne „fehlt“, und nichts ist mehr offen. Der Weg in den Editor bleibt trotzdem. Ein Entwurf, der nie freigegeben wurde und dessen Raid gelaufen ist, ist ebenfalls `skipped` („nie freigegeben“) — nachträglich ändert eine Freigabe nichts mehr.
- **Wo die Strecke anfängt:** vor dem Raid können nur *Anmeldung*, *Setup* und *Freigabe* „dran“ sein, **ein vergangener Raid fängt bei der Nachbereitung an** — niemand soll für einen gelaufenen Abend noch eine Softres-Liste anlegen. Was offen, aber nicht dran ist, steht auf `todo` („später“), nicht auf „offen“. **Ein abgesagtes Event zeigt nur „abgesagt“ und den Weg zurück**: jeder Schritt steht auf `cancelled` und trägt keine Tat, das Ergebnis nennt den Grund und „Absage zurücknehmen“.
- **Web:** `pages/raid-detail/StepBar.tsx` zeichnet nur — Zustände, Taten und Zahlen kommen vom Server, die Wörter drumherum rein aus `lib/raidSteps.ts` (`stepStateLabel`, `stepStateTone`, `stepPosition`, `stepSummary`, `stepTipSub`, `withoutDeeds`; strippable wie `lib/eventManage.ts`, `test/web-client/raidSteps.test.js` führt sie gegen die Server-Regel aus). Der offene Schritt ist markiert und trägt den **einzigen** auffälligen Knopf; jede andere Kachel ist ein stiller Knopf, der ihre Tat ausführt. **Der erklärende Satz und die abgeschnittene Randnotiz stehen im Tooltip**, nicht auf der Fläche, und `RaidDetailHero` lässt seine eigene Haupt-Tat weg, solange ein Cockpit da ist — dieselbe Tat zweimal im Kopf ist genau die Verdopplung, gegen die das Cockpit antritt. `RaidDetailPage`s `runDeed()` ist die **eine** Stelle, die eine Tat in Dialog, Tab, Menü-Aktion oder Auswertung übersetzt. Ohne `raids`-Schreibrecht zeigt `withoutDeeds()` dieselbe Leiste ohne jeden Knopf.
- **Mobil** (≤ 640 px) fällt die Leiste auf **eine Zeile** zusammen — „Schritt 2 von 5 · Anmeldung“ plus die offene Kachel mit ihrer Tat —, nie waagerechtes Scrollen (gemessen: 0 px Überhang). Zwischen 640 und 1100 px stehen die fünf Kacheln in zwei Reihen. Ist nichts offen, bleiben alle Schritte stehen (`:has(> li.is-current)`). CSS: `styles/raid-detail.css`, Präfix `rd-ck-`.
- **Was aus dem „Verwalten“-Menü gewandert ist** (`lib/eventManage.ts`): *Bearbeiten* → Schritt „Angelegt“, *Fehlende pingen* → „Anmeldung“, *Setup öffnen* → „Setup“/„Freigabe“. Dafür sind die drei Dialoge eingezogen, zu denen die alte Leiste der einzige Weg war: **Anmelde-Aufruf**, **Raidsheet**, **Softres-Liste**. Im Menü bleiben die seltenen Dinge: Verschieben, Anmeldung öffnen/schließen, Raider eintragen, Verlauf, Absagen, Löschen. *Anmeldung öffnen/schließen* steht bewusst weiter im Menü — es ist ein Schalter, der in **beide** Richtungen erreichbar sein muss, während der Schritt nur das Schließen anbietet, und nur im Moment, in dem es dran ist.
- **Tests:** `test/web/raidDetailSteps.test.js` (jede Lage: frisch angelegt, Anmeldung mit Warteliste, Anmeldeschluss vorbei, Entwurf, freigegeben, gepostet und veraltet, vergangen mit/ohne Log und Loot, abgesagt, übersprungen), `test/web/apiRouter.test.js` (Payload; ein Raid-Helper-Event bekommt `steps: null`), `test/web-client/raidSteps.test.js` (Client-Logik und Seitenaufbau), `test/web-client/eventManage.test.js` (was das Menü noch führt).

## Lootsystem je Raid (`src/web/lootSystem.js`, `eventLootSystemStore.js`)

Ein Loot-Council-Raid braucht keine Softres-Liste — also soll ihn auch nichts dazu drängen. Das **Lootsystem** (`softres` · `lootcouncil` · `gdkp` · `other`) entscheidet, ob ein Raid den Softres-Schritt, das Badge „Softres fehlt“ und den Menü-Eintrag „Softres-Liste“ bekommt.

- **Die Kategorie gibt den Standard vor:** `config.categoryLootSystem = { [categoryId]: system }`, in Einstellungen › Kategorien als Segment „Lootsystem“ (gemergt gespeichert, `""` = *automatisch* löscht den Eintrag). **Automatisch** heißt: Loot-Addon RCLootcouncil ⇒ Loot-Council, sonst Softres — so wie es war, bevor es die Einstellung gab.
- **Ein Raid kann abweichen:** `data/settings/event-loot-system.json` (`events[eventId] = { system, softres, at, by, byName }`), nach Event-Id, damit es für eigene **und** Raid-Helper-Events geht. `system: ""` = wie die Kategorie, `softres: true` = „Softres zusätzlich“ (z. B. BoEs bei einem LC-Raid). Ein Eintrag ohne beides wird gelöscht. Gesetzt über `POST /api/raids/loot-system { event, system, softres }` (Bereich `raids`, schreiben) aus dem Dialog „Lootsystem“ — geöffnet über den Chip neben der Kategorie im Kopf der Raid-Detailseite (nur mit `raids`-Schreibrecht ein Knopf).
- **Die eine Regel** ist `resolveLootSystem({ config, categoryId, override, softresList })` → `{ system, label, source (event|category|addon|default), categorySystem, categoryLabel, softresExtra, softres }`; `lootSystemOf(eventId, categoryId)` liest Config, Override und Softres-Liste dazu. **`softres` ist wahr bei System Softres, bei „Softres zusätzlich“ und immer, wenn schon eine Liste existiert** — ein Link verschwindet nie, nur weil das System nachträglich umgestellt wurde.
- **Wer es liest:** das Raid-Detail-Payload (`lootSystem`; `raidSteps()` lässt den Softres-Schritt weg, die Leiste hat dann fünf Spalten über `--rd-steps`), das Verwalten-Menü (`ManageState.softres`), die Übersicht (`nextRaid.lootSystem`: statt „Softres fehlt“ ein ruhiges Badge mit dem Lootsystem) und das Raid-Details-Modal.
- **Tests:** `test/web/lootSystem.test.js`, `test/web/eventLootSystemStore.test.js`, der Schritt in `test/web/raidDetailSteps.test.js`, Route und Payload in `test/web/apiRouter.test.js`, `settingsStore`, und clientseitig `eventManage`, `settingsLogic`, `uebersicht`.

## Event verwalten (`src/web/eventManage.js`, #288)

Everything the orga does with an **own** event after creating it: move it, close/open the signup, sign raiders up or off, ping the missing ones, cancel it (and take that back). **One service** (`eventManage.js`) for the web and Discord; every action refuses a Raid-Helper id (`not_own_event`) and another server's event, and every action is **logged on the event** (`eventStore.appendEventLog`: `event.log = [{ at, action, by, byName, detail }]`, newest last, capped at 100; labels in `ACTION_LABELS`). Editing through the create dialog logs too (`eventCreate.updateEvent({ …, user, byName })`, only the fields that really changed, named in German). Discord calls run **after** the store changed and are best-effort: a refused rename, a DM that does not arrive, an unpostable message come back as `warnings`, never as a rolled-back action.

- **State on the event** (`eventStore.setEventState`, apart from `updateEvent` so the plan is not re-validated): `status` `"active" | "cancelled"`, `signupsClosed`, `cancel { reason, at, by, byName, archived }`. `eventSources.planFields` hands `status`/`signupsClosed` to every reader.
- **Closed signup:** `signupService` lets a member only sign off (`WHEN_CLOSED`, code `closed`, 409), keeping an unchanged signup still works; `byOrga` is exempt. **Cancelled:** nothing at all — not even `byOrga` (`cancelled`); `allowedStatuses` is empty, so the web and Discord signup dialogs show it closed.
- **Move** (`movePlan` = preview, nothing changes; `moveEvent`): new Berlin start (past or unchanged refused), the deadline keeps its distance to the start, the reminder marks `missing`/`signed` are cleared. **The channel is renamed by #285's naming** — `deriveChannelName({ fromEventId, excludeChannelId, date })` — but only when its name follows a rule the old day is visible in: derived from its own name (`source: "previous"` with `fromChannelId` = its channel), or the category's stored schema *and* the channel still carries the old day's schema name. A hand-made name keeps its name, and the preview says why (`channel.reason`). `renameChannel` / `notify` switch the rename and the note: a post in the event channel mentioning everyone not signed off (`deliverUserPing` target `event`).
- **Raider eintragen** (`addRaider`): `submitSignup(…, { byOrga: true })` with a profile character; a character or spec the raider's profile lacks is **added to the profile first** (`raiderProfileStore.addCharacter`, a spec of another class is refused). `removeRaider` deletes the signup. `raiderCandidates` offers profiles ∪ holders of the category's raider roles ∪ signups, plus the rule set's classes for a new character.
- **Cancel** (`cancelEvent`): a reason is required (≥ 3 characters, it goes to the raiders); status cancelled + signup closed, the message is titled "Abgesagt: …" with the reason, red and without components (`eventMessage.messagePhase` reads `status` and `cancel.reason`; a closed signup is phase `closed`: a 🔒 line and the join select with only Abmelden), a DM with the reason to everyone not signed off (`pingDelivery.sendDms`, `notify`), and optionally the channel into the archive (`discordChannels.archiveChannel` + `channelArchiveStore.recordArchived`; no archive category = `no_archive` before anything happens). Reminders and the automatic setup proposal skip a cancelled event (`reminders.js`), the talk overview strikes it through (`~~Titel~~ · **ABGESAGT**`) and leaves it out of its signup select, the raid detail's steps show "abgesagt" and push no next step. `reopenEvent` takes it back (an archived channel stays in the archive, the message says so).
- **"Fehlende pingen"** is one function now, `src/web/missingPing.js` (`pingMissingRaiders`), used by `POST /api/raids/ping-missing` and the Discord button; a cancelled event is refused.
- **Löschen** (`deleteEvent`, also for a cancelled event): the stores first — `eventStore.deleteEvent`, `signupStore.deleteEventSignups`, `reminderStore.clearEvent` — so no sync reposts anything, then the signup message (`event.message`) and the setup message (`event.setupPost`) are deleted in Discord (a message already gone, 10008/10003, counts as deleted; anything else is a `warning`), and the talk overview re-syncs. **Both options are off by default** (mostly test or mistaken events are deleted): `archiveChannel` (like cancelling, `no_archive` without a category; the channel is never deleted) and `notify` (a short DM, only for a raid still ahead that was not cancelled — `deletionInfo().canNotify`). **A raid that already started** is refused with `409 started` („… 12 Anmeldungen und die Anwesenheit gehen verloren“) unless `confirmStarted` — its signups are its attendance. Linked **logs and loot stay untouched**: `logStore` keeps `eventId` + `eventLabel`, `lootStore` its `eventId` + `eventLabel`, so the CLA list and "Nach Raid" still name the raid. **A series never recreates the date** (#289): the date's run mark becomes `status: "deleted"` (when it was this event's mark, or the category has a series at all; a mark of another event that day stays), `dueDates` skips it and `planSeries` shows `deleted` („Event gelöscht — wird nicht neu angelegt“). The event's log goes with it, so **who deleted what is `console.log`ged** (`[eventManage] Event eh-… „Titel“ (Do 24.09. 19:30) gelöscht von Orga (id) · …`). `manageInfo` carries `deletion = deletionInfo(event)`: `{ started, cancelled, signups, recipients, messages, logs, loot, canNotify }`.
- **API** (`apiRoutes/eventManage.js`, area `raids` in `apiAccess.js`, level by method; the two GETs check write in the handler as well): `GET /api/raids/manage?event=` (state, counts, recipients with names, `archive.configured`, log newest first), `GET /api/raids/manage/move?event=&date=&time=` (the preview) · `POST` (move), `POST /api/raids/manage/signups { event, open }`, `GET /api/raids/manage/raider?event=` (candidates) · `POST { event, userId, character, spec, status }`, `POST /api/raids/manage/raider/remove`, `POST /api/raids/manage/cancel { event, reason, archiveChannel, notify }`, `POST /api/raids/manage/reopen`, `POST /api/raids/manage/delete { event, archiveChannel, notify, confirmStarted }` (all three only when sent as `true`). The raid detail payload carries `event.status/signupsClosed/cancelReason/cancelArchived/logCount` for an own event.
- **Web:** one ghost button **"Verwalten"** in the raid detail's head (only own event + `raids` write; it replaced the separate edit icon), a menu portalled into `<body>` (the head is a clipped panel) with one line per action saying what it does — Bearbeiten (the create dialog, #261), Verschieben, Anmeldung schließen/öffnen, Raider eintragen, Fehlende pingen, Setup öffnen, Verlauf, Absagen and Löschen (both red, last); a cancelled event offers only "Absage zurücknehmen", the history and Löschen, a past raid nothing time-bound but Löschen. ## Wiederkehrende Events (`src/web/eventSeries.js`, page `/raids/series`, #289)

A **series** per raid category — "Mo + Mi 19:30 · SSC + TK 25er · 6 Tage vorher" — makes the EventHelper create each date's event in time, with everything a hand-made one gets.

- **Stored** in `src/web/eventSeriesStore.js` (`data/settings/event-series.json`, kept out of the settings config because the scheduler writes on every creation): `series[categoryId] = { categoryId, guildId, enabled, weekdays (1 = Mo … 7 = So), time "HH:mm", raidTemplateId ("" = the category's default template, `categoryRaidTemplate`), daysBefore (1–28), title ("" = template name), skipDates ["yyyy-MM-dd"], leaderId, updatedAt/By/ByName }` and `runs[categoryId][date] = { status: creating | created | existing | failed, at, eventId, channelId, channelName, error, attempts, messageError }`. `normalizeSeries()` refuses no weekday, a bad time, days outside 1–28, an unknown template and "no template and no category default"; past skip dates are dropped.
- **Dates are Berlin wall-clock** (Luxon, `Europe/Berlin`): `occurrences()` walks calendar days, a start is `date + time` in Berlin (19:30 stays 19:30 across the DST switch), the creation moment is the start minus `daysBefore` **calendar days** at the same clock time. Tests cover both switches (25.10.2026, 28.03.2027) and several weekdays.
- **The sweep** (`startEventSeries()` in `server.js`: every 5 min, first run a minute after boot; `runSeries()`): only enabled series of a category whose `categorySignupSource` is `eventhelper` — a Raid-Helper category's series rests (`ignored`); nothing while the Discord client is not ready. `dueDates()` = window open, start ahead, not skipped, no mark (or a retryable failure). For each: a date that already has an event in the category (own via `eventSources.ownUpcomingRaw`, plus `loadEventGroups` — any source, **any status, a cancelled one included**) is only marked `existing`; otherwise the date is **claimed first** (`claimDate`, "creating") and then created through `eventCreate.createEvent({ body: { title, date, time, newChannel: { name: "", categoryId }, signupSource: "eventhelper", raidTemplateId } })` — so the channel is named and copied like the category's previous event channel (#285), the signup message is posted and the talk overview refreshed, with nothing series-specific. The event's log gets `series` ("Von Serie angelegt").
- **Never twice:** a claimed date is never claimed again (overlapping sweeps also stop at the `running` flag); marks **outlive a deleted series**, so setting it up anew repeats nothing; a date whose event was deleted (Event verwalten › Löschen) keeps a `deleted` mark and is never created again; marks are pruned 60 days after their date. **Failures:** `failed` with the message (`Kanal konnte nicht angelegt werden: fehlende Rechte`), retried at most `MAX_ATTEMPTS` 3 times, `RETRY_AFTER_MS` 10 min apart, then only by "Erneut versuchen" (`POST /api/raids/series/run { categoryId, retryDate }` clears the mark). A `creating` mark older than 15 min is **interrupted** (restart mid-create) — shown and reported, never retried on its own, because nobody knows whether its channel exists. `seriesFailures()` feeds the dashboard task `series` ("Serie konnte Event nicht anlegen: fehlende Rechte", `eventSeriesTask` in `dashboardOverview.js`, for users who can read `raids`, links to `/raids/series`).
- **API** (`apiRoutes/eventSeries.js`, area `raids`, level by method): `GET /api/raids/series` (one row per `categoryIds` entry plus categories that still have a series: `source`, `series`, `template`, `summary`, `upcoming` = the next 4 dates from `planSeries()` with `state` planned | due | creating | interrupted | created | existing | cancelled | failed | skipped | off, the channel it got or `previewName` + `naming` from `channelNaming.describeResult`, `lastCreated`; plus `templates`, `canWrite`, `limits`), `GET /api/raids/series/preview?category=&weekdays=&time=&daysBefore=&template=&skip=&enabled=&title=` (the modal's live preview, nothing stored), `PUT /api/raids/series` (409 `raidhelper_category` for a *new* series in a Raid-Helper category; an existing one can still be edited or switched off), `DELETE /api/raids/series { categoryId }`, `POST /api/raids/series/run { categoryId?, retryDate? }` ("Jetzt prüfen").
- **Web — why a page under Raid-Events and not the Kategorien card:** the card is already a dense grid saved as one settings form, while a series saves itself, has scheduler state to show and needs `raids` write (it creates events), not `settings`. So `pages/EventSeriesPage.tsx` (linked "Serien" in the Raid-Events head, beside Raid-Vorlagen) is **one line per category**: name, the summary line in mono, badges only for *aus* / *Raid-Helper* / *n Fehler*, and on the right "Nächster Termin Mi 23.09. #mi-23-09-ssc-tk" with one sentence what happens ("wird am Do 17.09. um 19:30 angelegt", "fehlgeschlagen: … · neuer Versuch folgt") plus "zuletzt angelegt: Mo 21.09. als #… (am Mi 16.09.)". A Raid-Helper category without a series shows the hint with a link to Einstellungen → Kategorien instead of a button. Everything else is the modal (`?edit=<categoryId>`): switch, weekday chips, time, days before, template (default named), title, the summary as it will read, and **"Nächste 4 Termine"** — each with its state badge, the channel name it will get with the `NamingBadge`, the sentence, an "überspringen" check box (saved with the series) and "Erneut versuchen" on a failure. Wording and date rules are pure in `lib/eventSeries.ts` (strippable). CSS `styles/serien.css` (`sr-`).
- **Tests:** `test/web/eventSeries.test.js` (DST, several weekdays, window, never twice incl. overlapping sweeps and a re-created series, existing/cancelled/skipped, Raid-Helper ignored, Discord not ready, retries and the dashboard task, interrupted, overview/preview), `test/web/eventSeriesRoute.test.js` (access + handlers), `test/web-client/eventSeries.test.js` (lines, draft, page shape, routing).

- **Event leader dropdown:** "More details" in the create dialog lists `leaderCandidates` of `GET /api/raids/new` (`apiRoutes/raids.js`): the creator first, then the current leader and the people signed up — for an event being edited its own signups, for a new one those of the guild's events from the lookback window on (max 60, names through `resolveUserNames`, the creator alone if Discord is offline). "Other Discord id …" shows the text field for anybody else.
