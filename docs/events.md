# Eigene Events (Anlegen, Verwalten, Serien)

Endnutzer-Sicht: siehe [guide-web-admin.md#raid-events](guide-web-admin.md#raid-events), [guide-web-admin.md#serien-wiederkehrende-events](guide-web-admin.md#serien-wiederkehrende-events), [guide-discord.md#event-verwaltung-nur-orga](guide-discord.md#event-verwaltung-nur-orga).

## Eigene Events (`eventStore.js`, `signupStore.js`, `eventSources.js`)

Events live in **two sources**: at Raid-Helper, and in the EventHelper's own store (`source: "eventhelper"`, #254). **One event has exactly one source** — nothing is imported, nothing is mirrored, nothing expires. A Raid-Helper event stays fully in use wherever one exists, also in a category whose new events are created in the EventHelper.

- **⚠️ Readers only know the common shape.** Every reader — `loadEventGroups()` (raid list, detail, history, ingest, dashboard modal, reminders), `loadMatchableEvents()` (log auto-link, CLA assignment), the stored-event list (past raids, dashboard, roster attendance, loot council, category names, player summaries, the channel page's event badges), `dashboardData.loadNextRaids()` and the bot's `helper.getCategoryEvents()` — gets both sources in the shape Raid-Helper events already had, plus `source`. The only file that knows there are two is `src/services/events/eventSources.js`: `ownEventGroupRows()` / `ownMatchableEvents()` / `ownUpcomingRaw()` merge the own events into the three existing lists, `listStoredEvents()` / `getStoredEvent()` are the drop-in for `raidEventStore.listRaidEvents()` / `getRaidEvent()` (Raid-Helper's snapshot plus own events that already started). **A new reader asks the adapter, never `eventStore` directly**, and a new Raid-Helper-only feature branches on `source`, not on the id.
- **Signups** (`data/settings/signups.json`, `eventId → userId → { character, spec, role, characters[], status, canAlso[], comment, at }`): `characters` (#293) are the raider's own characters `{ character, spec, role, status }` in priority order (`status` per character since the signup buttons: „Spät“/„Vielleicht“/„Bank“ on an existing signup move only the first; a character without one has the signup's, an absence stores none; the top-level `status` is the first character's, and a request without per-character statuses keeps them while the signup's status stays the same, else all take the new one — `signupCharacters.migrateSignup`, `signupService.withStatuses`; after the deadline/closing each character must keep its status or take an allowed one) — the first is the choice, the others "kann auch mit", at most `MAX_CHARACTERS` 3; the top-level character/spec/role **always mirror `characters[0]`**, so every reader that knows one character keeps working, and `canAlso` stays the roles without an own character. A signup stored before #293 gets `characters` on read (`signupCharacters.migrateSignup`, used by `listSignups`/`getSignup`; the pure part lives in `src/services/signups/signupCharacters.js`). `toSignUpShape()` carries `characters` along; attendance and log matching still count per person. `spec` is a rule-set key (`"Priest-Shadow"`), `status` one of `attendance.js`' `SIGNUP_STATUSES`. `toSignUpShape()` hands them out as `{ userId, specName, className, status, … }` with `specName` mapped onto the Raid-Helper spec name (`RH_SPEC_NAMES`, a test holds every rule-set spec resolving through `setupView.specProfile`) and an absence as the pseudo spec `"Absence"` — so attendance, role fill, class counts and the bot's "not signed up" lists need no change.
- **Events** (`data/settings/events.json`): id with the prefix `eh-` (Raid-Helper ids are bare numbers — `isOwnEventId()`, and the client's `lib/discord/discordLinks.ts` uses the same rule), guild, category, channel, title, description, leader, `startTime` (seconds), `versionId`, `instanceIds`, `size`, `composition { tank, healer, melee, ranged }` (melee/ranged = the minimum, 0 = no target), `compositionMax { melee, ranged }` (the optional maximum of a range, null = open — kept apart so every reader of a plain number still works), `requiredBuffs` (rule-set buff keys), `raidTemplateId` (where the values came from; the template is never written through the event), `signupDeadline`, `durationMinutes` (optional — #305: `null` = not set, no planned end; set it is 30–600; the end is `startTime + durationMinutes × 60`, the one rule is `utils/time/index.js`' `eventEndTime()` (0 without a duration) and `plannedEndOrDefault()` for the Discord event and the calendar only, deliberately not in the store because half its readers mock it — see „Discord-Event, Dauer und Sprachkanal"), `voiceChannelId` (#305, "" = none), `fairness`/`wishes`/`autoSuggest` ("Vorschlag bei Anmeldeschluss", for #262), `overflow`/`lockAtLimit` (the waiting list, #306), `announcedAt` (the create announcement went out, #306), `setup` (draft, approval and approved snapshot — see "Setup-Editor" in docs/setup.md), `message` (where the bot's post sits), `discordEvent` (the Discord event, see below). `normalizePlan()` validates against the rule set and fills what is missing: the biggest instance's `defaultSize`, its suggested tanks/healers. It takes melee/ranged as a number or `{ min, max }`, refuses minimums that add up to more than the size, a max below its min or above the size, and buffs the version does not have.
- **Which source a new event gets** is `config.categorySignupSource = { [categoryId]: "raidhelper" | "eventhelper" }` (missing = `config.signupSourceDefault`, EventHelper for a new category since #291 — see docs/raidhelper-retirement.md), edited as the one segment *Neue Events* on the category's card in Einstellungen → *Kategorien*. `src/services/events/eventCreate.js`'s `createEvent()` is the one way in (`POST /api/raids` and `/event anlegen`): it resolves, clones (`sourceChannelFor`, own source events read from the store) or creates the channel (`newChannel: { name, categoryId, templateChannelId }`, via `discordChannels.createFromTemplate`), reads the category's source (a body's `signupSource` overrides it for that one event), and either calls Raid-Helper as before or validates the plan **before** cloning a channel, stores the event (instances from the body, else from the title) and posts the event message. A message that cannot be posted is reported as `messageError`, never a failed create.
- **Raid-Helper-only things stay Raid-Helper-only:** the raidplan link (`raidplanUrl()` returns `""` for an own id, every caller renders no link then), `getSetup` (dashboard, raid detail, `utils/raidhelper/queries.js`), the "Raidplan öffnen" primary action (`raidDetailSteps.js` — an own event's setup step opens its setup editor instead). `POST /api/raids/fill` fills an own event's sheet from its **approved** setup (`setupEditor.raidHelperSlots`), refused with `no_approved_setup` before an approval. The Discord post link of an own event opens its channel.
- **The raid plan works with both sources** (docs/raidplan.md, "Raid-Helper-Events"): an own event always has one; a Raid-Helper event gets one when the orga switches it on in its "Verwalten" menu (the only entry that menu has for a Raid-Helper event). Its players are then read from Raid-Helper (never written), instance/size/version live on the plan record, taken from the title. Neither source is the preferred one for planning — pick the source by how the signup should run, the plan follows.
- **The event message** (`src/services/events/eventMessage.js`): the Raid-Helper-style signup list with the public select `event-join:<eventId>` — see "Anmelder-Nachricht" in docs/signups.md. Posted on create; `startEventMessageSync()` (started in `jobs.js`) listens to `signupStore.onSignupsChanged` and edits it once per burst of changes, re-posting a message that was deleted in Discord. Messages posted before #287 still carry the button `event-signup:<eventId>`, whose handler `commands/signup/eventSignup.js` keeps opening the Discord signup dialog — see "Anmeldung (Bot)" in docs/signups.md.
- **`/event anlegen` in Discord (#260)** — `commands/event/event.js` (slash, group `raids`, default admins; the orga role gets it under Bot-Befehle), `eventCreateStep.js` (`event-new:<field>:<state>`: selects Kategorie / Raid-Vorlage / Kanal-Modus / Event bzw. Kanal, the source toggle, Zurück, Abbrechen) and `eventCreateModal.js` (`event-form:<state>[:<token>]`: "Weiter" and "Nochmal" open the modal **directly** — never after a defer —, the submit defers and replaces the message). All logic is `src/services/events/eventDraft.js`. **Nothing is stored between the steps:** the state `cat:tpl:mode:src:ref` rides in every customId (≤ 100 chars — ids are checked by regex, a template id over 24 chars is not offered) and is re-checked on submit against what exists now (event category, template, channel on the server, configured raid server only). The modal has Titel, Datum (`24.09.2026`, `24.09.`, `24.9.` — `parseGermanDate` in `utils/time/index.js`, a yearless day long gone rolls into next year, a recent one is refused as past), Uhrzeit (`19:30`, `1930` — `parseClockTime`), `Größe/T/H` (only for EventHelper, prefilled from the template, e.g. `25/3/6`) and Beschreibung. Channel modes: *neu nach Schema* and *duplizieren* name the channel through `channelNaming.deriveChannelName()` (like the category's previous event channel resp. the duplicated one, else the stored/default schema — see docs/channels.md; step 1 and the confirmation say where the name came from) and refuse a taken name; *bestehender Kanal* is a Discord channel select. A Raid-Helper event needs a template with `raidhelperTemplateId`. Errors come back with „Nochmal" (the typed values kept in memory under a short token for 30 min, only for the same user) and „Zurück"; success shows *Zum Kanal*, *Im Web bearbeiten* and *Ankündigung pingen* (`/raids/detail?event=…&tab=actions`, the Anmelde-Aufruf dialog). **Templates of the category's version:** step 1 offers only the raid templates `categoryEras.templateVersionProblem()` accepts for the chosen category (the rule `createEvent` enforces with 409 `template_version_mismatch`); the category default is preselected when it fits, else the first that does, and a category change re-fits. **Template ranges:** the modal carries only minimums, so `buildBody` sends the template's melee/ranged maxima as `compositionMax` too (capped at the size) — the stored plan equals the web dialog's for the same template. **Time:** `Uhrzeit` is prefilled with the time the category's quick-create remembers (`schemas[categoryId].time`). **Kanal-Icon** (only where a channel is created — *neu* and *duplizieren*; `eventIcon.js`): a select "Wie zuletzt" (what deriving gives) / "Passt zu <Raid>" (`config/raidEmojis.js`) / "In dieser Kategorie" (lead emojis of the category's channels, most used first) / "Kein Icon", at most 25 options, no emoji twice, each with its emoji. The pick replaces the emoji the derived name starts with and keeps its separator; a name without one gets emoji + the category's usual separator (default `・`) — `utils/leadEmoji.js`, the backend twin of `lib/discord/emoji.ts` (`setLeadEmoji`, `emojiStyleOf`), held identical by `test/utils/leadEmoji.test.js` and `test/config/raidEmojis.test.js`. The choice rides in the customId as a short code (`""`, `x`, `r<n>`, `c<n>`; state is now `cat:tpl:mode:src:ref:ann:ico`) and is resolved against the current options on every click and on submit — an unknown code means "Wie zuletzt"; a template/category/source change drops it. A message holds five rows, so in *duplizieren* (which needs the event select) a button "Icon: …" cycles through the same options instead of the select. Step 1 shows `**Kanal-Icon:** 🐍 Passt zu SSC + TK · \`🐍・mi-…\``. **"Kanal umbenennen …"** (`eventRename.js` → `eventChannelRename.js`, `event-rename:<channelId>`): under the confirmation when a channel was created or duplicated; a modal with the channel's actual name, the submit renames through `discordChannels.editChannel` (name via `utils/channelNames.js`, a taken name is refused). Besides the `/event` rule (`accessOf`) it needs `channels` write (`userAccess.userMayAny`, like the web's PATCH /api/channels), and only a channel of an event category can be renamed. **"Kanalname anpassen …"** (button `event-new:n:<state>` in step 1, only where a channel is created): a raid that needs a new naming pattern gets it *before* the channel exists. The button opens a modal with one field, prefilled with the **pattern** of the name step 1 derived (`channelNaming` `patternText`: date and weekday as placeholders, the raid as `{raid}`, the icon pick applied — `🏔️👑》{raid}-{dd}-{mon}`); `{tag} {dd} {mm} {mon} {yy} {yyyy} {d} {m} {wochentag} {wday} {weekday} {raid}` are filled with the event's date and the template's raid tag (`utils/channelNames.js` `renderChannelName`, `PATTERN_KEYS`), an unknown `{word}` is refused, a pattern without placeholders is used literally, an empty submit goes back to the derived name. The submit (same customId) keeps the pattern and redraws step 1 (`Name \`…\` · von Hand angepasst`, button "Kanalname: von Hand …"). **Where it is kept:** not in the customId (the worst-case state already fills all 100 characters) but per user in memory (`eventDraft.js` `nameSlots`, 30 min), bound to the combination category / template / channel mode / duplicated event — choosing another drops it, "Abbrechen", a new `/event anlegen` or "Raid anlegen" and a successful create forget it; the slot also holds the pattern step 1 derived last, so the modal opens without a slow call. **Decision: a hand-typed name is final** — on create (`buildBody`) it is rendered with the event's date, normalised by Discord's rules and the icon select/button are gone while it is set (the icon belongs in the typed name); an empty result or an existing channel name is refused with the usual "Nochmal" path, which keeps the pattern. The next raid of the same kind inherits the new pattern on its own: `deriveChannelName` takes the category's latest channel (same raid first) and reads date, weekday and raid out of it again. In *duplizieren* with the source EventHelper the button row would hold six buttons: "Abbrechen" gives way there (the ephemeral message can be dismissed). **Acknowledge first (no "Interaction failed"):** Discord wants the answer within 3 s, so every step answers before it does anything else — selects and the form submit `deferUpdate()` as the very first act (the raid-server check follows and refuses with an edit), `/event anlegen` and `orga:new` `deferReply` first, the "Weiter"/"Kanalname anpassen …"/"Kanal umbenennen …" buttons open their modal directly. For the rename button that meant moving the `channels` right check (a role lookup at Discord) to the *submit*: the modal opens for everybody, nothing is renamed without the right. **Timing log:** `bot.js` `handleInteraction` runs `services/discord/ackTiming.js` `trackAck()` for every command, button, select and modal (it only watches `interaction.deferred/replied`, nothing is wrapped) and logs `[warn] [ack] Slow acknowledgement of <name>: N ms since Discord created it (arrival a ms, access guard b ms, handler until acknowledged c ms)` above 2000 ms — *arrival* is Discord → our handler (gateway lag, a blocked event loop), *access guard* `guardInteraction`, *handler* the rest up to the first answer. Grep the server log for `Slow acknowledgement` to see where the time goes. Tests: `test/services/events/eventDraft.test.js`, `eventDraft.icons.test.js`, `eventDraft.namePattern.test.js`, `test/commands/event/event.test.js`, `eventRename.test.js`, `test/services/discord/ackTiming.test.js`, `test/bot.test.js`.
- **Raid groups (#811):** `raidGroupId` (the first raid's id on every raid of the group, "" = none) and `raidGroupIndex` (1 = the first) — further raids of an overbooked evening that share the first raid's signup, created in the setup editor ("Weiteren Raid hinzufügen"). `listEvents` leaves the further raids out unless `{ siblings: true }`; the readers that know them, the rules for signup, messages, attendance and logs: "Raid-Gruppe" in docs/setup.md. The raid list shows them indented under the first raid, the raid detail head links them, the public page of every raid names "Raid 1 von 2" and links the others (`publicEventView(…, { group })`, keys `group`, `count`, `url`, `current` in `VIEW_KEYS`; a further raid's signups and signup link are the first raid's). Calendar (`.ics`) and raid plan stay per raid. Moving the first raid moves the further ones; deleting it is refused while further raids exist.
- **The setup** is proposed by "Setup-Vorschlag" (it reads the event's own `requiredBuffs` and melee/ranged ranges; `autoSuggest` drafts a proposal at the deadline — see "Setup proposal at the deadline" in docs/discord-servers.md) and edited and approved in "Setup-Editor" in docs/setup.md.

## Event anlegen im Web (`components/raid-create/RaidCreateDialog.tsx`, #261)

One guided dialog, **one step at a time**: *Vorlage* (segment "Letzte Events" / "Raid-Vorlagen", plus "Leer beginnen") → *Termin* (title, date, time, category; leader and description folded away) → *Raid* (**only for an EventHelper event**) → *Kanal & Anmeldung* → *Prüfen*. `lib/raids/eventPlan.ts`' `stepsFor(editing, source)` decides the list; a Raid-Helper event keeps today's fields (its Raid-Helper template sits in the channel step).

- **The raid step stays calm:** version segment, instance chips with icon and "Infos fehlen" (`components/raid/RaidFields.tsx`, rt- classes shared with the template modal), size segment from the instances' allowed sizes plus "frei", tanks/healers large in the shared `CompositionEditor`, one badge "n / size verplant" or the problem. Melee/ranged ranges, required buffs and the three switches (Fairness, Wünsche, Vorschlag bei Anmeldeschluss) are behind "Mehr". A size change proposes tanks/healers, an added instance that does not come in the current size brings its own default size (`withSize` / `withInstance`).
- **The plan rules are pure and mirrored:** `lib/raids/eventPlan.ts` is strippable like `lib/raids/raidTemplates.ts`; `src/web-client/src/lib/raids/__tests__/eventPlan.createDialog.test.ts` runs `planProblem()` against the server's `normalizePlan()` and `schemaName()` against `utils/channelNames.renderChannelName()`, so the dialog words a problem exactly like the API.
- **Starts:** a raid template copies its values into the plan (`planFromTemplate`); repeating an event takes its category's default template, else the instances its title names; "Leer beginnen" the category default. The event keeps a copy — changing it never changes the template. **"Als Vorlage speichern"** (raid step) writes the plan into the template it came from or a new one through the ordinary `POST/PATCH /api/raid-templates` (`templateFromPlan`).
- **Channel:** "Neu nach Schema" creates a text channel in the chosen category (`newChannel: { name, categoryId }` → `discordChannels.createFromTemplate`, the same shape `/event anlegen` sends; an empty name is filled from the schema, the schema's template channel is used if one is stored), named like the category's previous event channel (`GET /api/raids/channel-name`, one `NamingBadge` under the field, #285; the local schema only as fallback) until the name is typed by hand, and created as a copy of that channel behind the previous date; "Klonen" only for a repeated event in its own category; "Vorhanden" lists the category's channels. A clone or new channel without a name is named by the schema on the server too (`schemaChannelName`). Discord refusing reads "Kanal konnte nicht angelegt werden: fehlende Rechte".
- **Source and deadline:** "Anmeldung über" is preset from `categorySignupSource` and sent as `signupSource` (it overrides the category for this one event). The deadline is "Stunden vor Start" (`signupDeadlineHours`), turned into seconds on the server from the Berlin start, so the browser's time zone never matters.
- **Context:** `GET /api/raids/new` also returns `categories`, `categoryRaidTemplates`, `raidTemplates` (with badges), `versions`/`defaultVersion` (the main version from the settings) plus `categoryVersions` (#541, see docs/game-versions.md), `channelSchemas`/`defaultSchema` and, with `?event=<eh-id>`, `editEvent`.
- **Editing an own event** uses the same dialog (`editEventId`): from the raid detail's head, the first entry of the "Verwalten" menu (see "Event verwalten") for an EventHelper event and `raids` write. No start step, the channel and category stay. `PATCH /api/raids` (`eventCreate.updateEvent()`, area `raids`, write by method) takes `{ id, title, date, time, … plan fields }`, refuses a Raid-Helper id (`not_own_event`) and another server's event, re-validates the plan and edits the bot's message (`refreshEventMessage`, a failure is `messageError`). `createEvent()`'s signature is shared with the Discord modal (#260); an edit also re-syncs the talk overview (#257).

## Kalender-Link und öffentliche Event-Seite (`src/services/events/icsFeed.js`, `src/web/pages/eventPublicPage.js`, #308)

> Öffentliche Event-Seite und Discord-Event sprechen die **Sprache der Kategorie** des Events, ohne eigene die Server-Sprache des Bots (Standard Deutsch, siehe [bot-commands.md](bot-commands.md), „Sprache des Bots“). Die Seite schreibt Zeiten als Text in dieser Sprache in Serverzeit (`<html lang>` passend); die ICS-Zeiten bleiben UTC und der Kalender zeigt sie in der Zeitzone des Lesers.

Two paths an own event owns, both **server-rendered and reachable without a login**, both entries of `pageRoutes.js`, matched *above* the SPA fallback (like `/r/<id>`), both with an id pattern of `[A-Za-z0-9_-]+` only — no path can traverse:

- **`GET /r/cal/<eventId>.ics`** — one VEVENT, `text/calendar`, `Content-Disposition: attachment`. `buildIcs(event)` in `icsFeed.js` is pure and is the whole rule: CRLF endings, every line folded at **75 octets** (`foldLine` counts UTF-8 bytes and never splits a character; continuation lines start with one space), text escaped per RFC 5545 (`\` `;` `,` newline) and every time in **UTC** — a local time would need a VTIMEZONE block and the store keeps unix seconds anyway. `UID` is the event id, `DTSTAMP`/`SEQUENCE` come from the last change (`SEQUENCE` counts seconds since 2020, so it stays inside 32 bits), `DTEND` from the duration (#305, `utils/time/index.js`' `plannedEndOrDefault()`: a calendar entry needs a block, so an event without a duration — or stored before #305 — ends after the default 3 h), `LOCATION` is the event channel's Discord link, `URL` the public page, and a cancelled event is `STATUS:CANCELLED` with „Abgesagt" in the summary. An event without an id or without a start answers "" and the route 404s.
- **`GET /e/<eventId>`** — the page the bot links under every signup message, for everyone in the channel, with or without a menu account. `publicEventView(event, signups)` in `eventPublicPage.js` is pure and is the **only** thing the page renders from; `renderPublicEventPage()` puts it into `render.js`'s `layout()`. The count is the single Discord accounts (`counts.accounts`, no „/size“ since #520), the signups come as one block per class (the grouping is `eventMessage.rosterEntries`/`classesOf`/`messagePhase` and the counts `signupService.roleCounts`, so the page and the channel can never disagree), Spät/Vielleicht/Bank/Abgemeldet as their own blocks, and the **approved** setup. A cancelled or closed event says so; an unknown id is a 404. The page depends on who looks (sign-up button, own signup), so it goes out with `Cache-Control: private, no-store`.
  - **Look since #908 (Pilot C, model: a Raid-Helper/Wowhead detail page):** one narrow column (`.ev-wrap`, 760 px), the version colour (`<html data-version>`) as the only accent, all classes `.ev-*` in `PAGE_STYLE`, report tokens only, light and dark (theme toggle in the crumb bar). Order: crumb (EventHelper · the **category name** in the raid's version — `categoryNameAt` with the live Discord name, else `event.categoryName`, else „PuG-Raid“/„Gilden-Raid“ — · raids; no link) → title → date line → one meta line (Raidleitung = the leader's **own signup character name**, never an id; nothing when the leader has not signed up) → a phase or full note → the count block with **one number**, „**27** angemeldet“ (the accounts, as above — never „von 25“), and the role line from `roleCounts()`: „Tanks 1/2 · Heiler 1/6 · DPS 0/17“ with targets (from the composition, DPS = size − tanks − healers; a role under its target in `--medium`), else plain counts „1 Tank · 2 Heiler · 0 DPS“ (singular for one) — no targets for a raid group or without a composition → deadline → buttons → description → the class blocks as a `dl` (class colour rule, count, members with spec icons titled by spec).
  - **The sign-up button** (`actionsHtml`): only while the phase is `open` and the raid is not full with overflow `refuse`. In a raid group the **first raid** (`signupEventIdOf`) decides phase, `signupsClosed`, deadline and overflow — the raiders sign up there, so a further raid shows no button once the first one is closed. Logged in → green „Anmelden“ to `/signups?event=<signupEventIdOf>`; logged out → „Mit Discord anmelden“ to `/auth/login?returnTo=%2Fe%2F<id>` (`authLogin` runs `safeReturnPath`, so the visitor lands back here). Full exists only with a limit: overflow `none` is never full and shows no note; waitlist → „neue Anmeldungen kommen auf die Warteliste“ (button stays), refuse → „keine neuen Anmeldungen“, no button.
  - **Signed up already** (`ownSignupOf`, from `viewer.userId` that `pageRoutes.eventPage` passes): „Du bist angemeldet als <Char> (<Spec>)“ — the first character of the signup, a sign-off does not count — and instead of „Anmelden“ the button „Anmeldung ändern“ to the same target, also when a full `refuse` raid takes no new signups. It shows in the phases open, deadline and closed (`signupService` still allows „Spät“, absence or sign-off there), not once cancelled or started. The id only finds the signup — `renderEventPage` drops it before rendering, so it never reaches the HTML.
  - **PuG raids** (`openToAll(categoryId, {config, versionId})`; the crumb shows the category name, „PuG-Raid“ only as its fallback): with an `inviteUrl` the page adds the PuG server's invite — `viewer.isMember === false` → the notice „Zum Anmelden musst du zuerst auf dem PuG-Server sein.“ plus „PuG-Server beitreten“; membership unknown (`null`) → a small line „Noch nicht auf dem PuG-Server?“ with the link; a member sees nothing. **Wired in** `pageRoutes.eventPage` through `pugMembership.pugPageViewer(event, userId)`: only for an open PuG raid, `inviteUrl` = the general invite of the raid's server (`pugInviteUrl` → `pugInvites.generalInviteUrl`, "" while none is made — no join link then) and `isMember` from `discord.guildMembership` (with its time limit; `null` without a login or when Discord does not answer). Any other raid gets `isMember: null`, `inviteUrl: ""` and no Discord lookup. Viewer, login URL and invite are **render options**, never fields of the view.

⚠️ **Nothing personal leaves either of them, and `VIEW_KEYS` is the list.** The payload carries character name, spec (key, German label, icon) and status — and nothing else. Out, on purpose: Discord **user ids**, comments, wishes and wish partners, „kann auch mit", everything from the raider profile, and any setup **draft** (only `setupCore.approvedSetupOf()` is read, and the approved snapshot's `userId`s and reasons are dropped again here). The page carries **no Discord link at all** — a link is an id, and a visitor need not be on the server; the `.ics` keeps `LOCATION` because a calendar entry wants a place. Whoever adds a field adds it to `VIEW_KEYS`, or `test/web/pages/eventPublicPage.test.js` fails: it walks the payload against the list and searches payload *and* rendered HTML for every id, comment and draft of its fixture.

- **`GET /e/<eventId>/comp`** (#520) — the „Comp“ link of the signup message, one link for everybody that the server resolves per reader (`eventComp` in `pageRoutes.js`, route `event-comp`): logged in with write access in `raids` (`userHasMenuAccess` + `userCan(user, "raids", "write")` on `auth.getUser(req)`, the same check as `apiAccess`, so an admin viewing the menu „als Rolle“ is sent where that role would go) → 302 `/raids/detail?event=<id>&tab=setup` (the setup editor); not logged in or without the right → 302 `/e/<id>`; unknown id (Raid-Helper ids included — they have neither the page nor our message) → 404. `Cache-Control: no-store`, since the answer depends on who asks. The golden master `test/web/http/serverRoutes.test.js` records every case (anonymous, account without rights, raider with read only, admin „Ansicht als“ raider, orga with write, admin, unknown event, wrong method).

### Kalender-Abo je Raider (`GET /r/cal/user/<token>.ics`, `src/web/pages/calendarFeed.js` + `calendarTokenStore.js`, #312)

The third path of the same family: **one link per raider**, pasted into Outlook/Google/Apple once, carrying every raid they are signed up for — so a new raid turns up in the calendar by itself. An entry of `pageRoutes.js` above the single-event file (and above the SPA), same `[A-Za-z0-9_-]+` pattern, GET only.

- **The token is the whole authentication**, so the store (`calendarTokenStore.js`, `data/settings/calendar-tokens.json`, prefix `ehc_`) follows `ingestTokenStore.js` to the letter: **sha256-hashed** on disk (never the secret; a 4-char `hint` tells two links apart), the plaintext handed out in exactly **one** answer and never retrievable, `verifyToken` comparing in constant time, revoking immediate. The one difference: a token belongs to **exactly one Discord account**, and `revokeToken(id, userId)` checks the owner itself so no caller can forget to — a foreign id reads as „not found". At most `MAX_PER_USER` (5) per raider.
- **⚠️ An unknown *or* a revoked token is a plain 404** — the same answer a path that never existed gets, never „Token ungültig". `feedFor()` verifies before it reads a single store.
- **What is in it:** `buildUserCalendar(entries)` in `icsFeed.js` (pure; `vevent()` is the VEVENT shared with `buildIcs`) — one VEVENT per raid with title, time, end, the channel link, the public page **and the reader's own status** („Deine Anmeldung: Spät"). Nothing else: no other raider's name, no comment, no „kann auch mit", no setup, no Discord user id. `test/services/events/icsFeed.test.js` walks the file against an **allowlist of property names** and hunts for every id, name and comment a careless caller might hand in.
- **An own absence stays in as `STATUS:CANCELLED`** instead of falling out. A silently missing VEVENT leaves the raid standing in every calendar that already fetched it; `CANCELLED` makes the client strike it (the summary then reads „Abgemeldet: …"). `TRANSP` is `OPAQUE` only for *Dabei* and *Spät* — a „Vielleicht" or a bench seat does not block the day in a free/busy view.
- **The signup's own change time rides along** (`changedAt`), so a status change raises `DTSTAMP`/`SEQUENCE`: a calendar client may ignore an update whose sequence did not grow.
- **Bounded and cached:** `collectEntries` asks `eventStore.listEvents` for **30 days back, 90 days forward** and stops at `MAX_EVENTS` (200); `feedFor` caches the built file **per token for five minutes** (`Cache-Control: private, max-age=300` — never a shared cache). A subscribed calendar polls forever from several clients, so `touchToken` only counts a real build: the disk stays quiet and the profile can still say „noch nie abgerufen". Only **own** events appear — a Raid-Helper event has no signup in our store. `signupStore.signupsOfUser(userId)` is the one pass over the signups.
- **Where it is minted:** Mein Profil → the folded line *Kalender-Abo* (`ProfilePage.tsx`'s `CalendarPart`, `.pf-cal*` in `styles/profile.css`) — a sentence that the link is secret, „Link erzeugen", the link once in a copy field badged „nur jetzt sichtbar", one line per link with created/last fetched and „Widerrufen". `GET/POST /api/profile/calendar` (area `signup`, the session's account only; `{ revoke: id }` on the POST revokes, like `/api/profile/characters`' `{ remove }`). Without `PUBLIC_BASE_URL` the part says so instead of offering a link.
- **Tests:** `test/stores/calendarTokenStore.test.js`, `test/web/pages/calendarFeed.test.js` (window, cache, unknown/revoked token, two raiders never crossing), the allowlist in `test/services/events/icsFeed.test.js`, the routing in `test/web/http/server.test.js`, the endpoints in `test/web/apiRoutes/profile.test.js`, the page in `src/web-client/src/pages/profile/__tests__/ProfilePage.test.tsx`.

## Discord-Event, Dauer und Sprachkanal (`src/services/discord/discordEvent.js`, #305)

Raid-Helper puts every raid into Discord's own event list; the EventHelper does too — **per category, off by default** — and a raid now says how long it takes and where it meets.

- **Die Dauer ist ein optionales Planungsfeld:** `event.durationMinutes` ist `null` (= nicht gesetzt, **kein geplantes Ende**), solange niemand sie setzt — eine Raid-Vorlage mit Dauer belegt sie vor (`raidTemplate.durationMinutes`, `null` = keine), im Dialog kann man sie eintragen und wieder leeren (leeres Feld → `null`, auch beim Bearbeiten; beim Anlegen schlägt ein geleertes Feld die Dauer der Vorlage, `eventCreate.planFor`). Gesetzt gilt 30–600 Minuten. Gespeicherte Werte bleiben, wie sie sind (keine Migration); ein Event ohne Feld (vor #305) liest sich als „nicht gesetzt". Die Regel steht in **`src/utils/time/index.js`**, nicht im `eventStore` — die Hälfte der Leser mockt den Store in ihren Tests; eine reine Rechnung darf nicht mitgemockt werden müssen. `eventStore` re-exportiert sie:
  - `durationOf(raw)` — Minuten in den Grenzen oder `null`.
  - `eventEndTime(event)` — `startTime + durationMinutes × 60`, **0 ohne Dauer** („kein geplantes Ende"). Die öffentliche Event-Seite, der Dialog („Ende 23:00" nur mit Dauer) und *Prüfen* („offen – kein geplantes Ende") zeigen dann kein Ende.
  - `plannedEndOrDefault(event)` — das Ende oder `start + DEFAULT_DURATION` (180 Min.). **Nur dort, wo ein Ende technisch Pflicht ist:** das Discord-Event (`scheduledEndTime`, auch die „vorbei"-Prüfung in `createForEvent`) und der Kalender-Eintrag (`DTEND` in `icsFeed.js`). Nirgends sonst wird ein Ende erfunden.
- **Der Sprachkanal** ist `event.voiceChannelId` ("" = keiner), vorbelegt aus `config.categoryVoiceChannel[categoryId]`; er steht als eigenes Kopf-Feld (`eh_ui_voice`) in der Anmelder-Nachricht und ist der Ort des Discord-Events. `discord.listVoiceChannels(guildId)` füttert beide Auswahlen (`GET /api/settings`, `GET /api/raids/new`).
- **Das Discord-Event** (`event.discordEvent = { id, guildId, at, error }`, `eventStore.setEventDiscordEvent`, gemergt wie `setupPost`): `createForEvent` · `syncForEvent` · `cancelForEvent` · `reopenForEvent` · `deleteForEvent`. **Alles best-effort** — jede Funktion antwortet `{ warning }` statt zu werfen, der Text landet über `warningOf()` in den `warnings` der Aktion und als `discordEvent.error` am Event. Ein fehlendes Recht („Events verwalten", `discord.botCanManageEvents` — `null` heißt *unbekannt*, nie *fehlt*) verhindert nur das Discord-Event, nie das Anlegen.
- **Der Ort:** ein Sprachkanal des Raid-Servers (`entityType: Voice`, geprüft gegen den Channel-Cache — ein gelöschter Kanal fällt zurück), sonst `External` mit der Anmelde-Nachricht als `location`. **Ein External-Event braucht zwingend ein Ende** — ohne Dauer bekommt das Discord-Event (beider Arten, damit ein Wechsel nie ohne Ende dasteht) deshalb `plannedEndOrDefault()`, also Start + 3 h.
- **Die Beschreibung sagt, dass die Anmeldung woanders läuft** (`SIGNUP_NOTE`: „Anmeldung nur über die Nachricht im Kanal – ‚Interessiert' hier zählt nicht."). Ohne den Satz hätte ein Raid zwei Roster, und keines wäre richtig — Discord kennt weder Spec noch Charakter.
- **Mitziehen:** `eventCreate.createEvent` legt es **nach** der Nachricht an (damit die Beschreibung sie verlinken kann), `updateEvent` und `eventManage.moveEvent` synchronisieren, `cancelEvent` sagt es ab (Status `Canceled`; wo Discord das verweigert, wird gelöscht — ein gelistetes Event zu einem ausgefallenen Raid ist schlimmer als keines), `reopenEvent` legt ein neues an (ein abgesagtes lässt sich nicht wiederbeleben), `deleteEvent` löscht es (`{ store: false }` — das Event ist da schon aus dem Store). Ein von Hand gelöschtes Discord-Event (404 / 10070) wird vergessen und, wenn es noch Sinn ergibt, neu angelegt.
- **Schalter:** `config.categoryDiscordEvent = { [categoryId]: true }` (Default aus, nur eingeschaltete Kategorien gespeichert) und `config.categoryVoiceChannel = { [categoryId]: channelId }` — beide in Einstellungen → Kategorien (`CategoryMatrix.tsx`), gemergt gespeichert (`false` bzw. `""` löscht den Eintrag), kein Full-Admin-Schlüssel.
- **Im Web:** im Schritt *Termin* eine Zeile Datum · Uhrzeit · **„Dauer (optional)"** — leer mit Platzhalter „z. B. 180", die Einheit „Min." im Feld, ein kleines × leert es, „Ende 23:30" darunter nur mit Dauer; die Grenzen 30–600 werden nur geprüft, wenn etwas drinsteht. Der Sprachkanal im Schritt *Kanal & Anmeldung*, beides auch in der Prüfen-Liste; die Vorlage hat die Dauer unter „Mehr". **In `/event anlegen`** trägt das Feld **`Größe/T/H/Dauer (Dauer optional, Min.)`** die Dauer als vierten Teil (`25/3/6/240`) — ein Discord-Modal nimmt fünf Felder, und Titel, Datum, Uhrzeit und Beschreibung sind alle nötig. Das Feld ist mit der Dauer der Vorlage vorbelegt; wer den vierten Teil entfernt, legt das Event **ohne** Dauer an (`durationMinutes: null`), ein ganz leeres Feld überlässt den Plan der Vorlage.
- **Titelbild** (`discordEventCover.js`): das Bild des Raids — das eigene Event-Bild (`lookOf(event).url`), sonst die Zonengrafik der führenden Instanz (`ruleSetLook().art`, dasselbe Bild wie `raidArt` in der Anmelder-Nachricht). Discord nimmt das Cover als Bilddaten (`image`, hier als Data-URI), nicht als Link: nur absolutes https, 4 MB, 8 s Timeout, Bildtyp geprüft, Cache je URL im Speicher. Mitgesendet wird es beim Anlegen und beim Sync nur, wenn sich das Bild geändert hat (`discordEvent.coverKey` = URL des Bildes auf Discord), weil jede Änderung mit Bild ein Upload ist. Schalter `eventCover` des Event-Servers (`coverEnabled(config, event.guildId)`, eigener Schalter des Servers, sonst `discordVisuals.eventCover`, #961; aus nur bei genau `false`): aus = beim Anlegen kein Bild; ein vorhandenes Cover bleibt, die API kennt kein Entfernen. Best-effort: ein Fehler beim Laden heißt Event ohne Cover, nie ein Fehler. Discord empfiehlt etwa 16:9; die Zonengrafik (600×300, 2:1) wird zugeschnitten.
- **Tests:** `test/services/discord/discordEvent.test.js` (Aufbau, Voice vs. External, Anlegen/Ändern/Absagen/Löschen mit einem Fake-Client, 404, Schalter aus, fehlendes Recht) und `discordEventCover.test.js` (eigenes Bild vs. Zonengrafik, Schalter, Cache, unverändert nicht erneut, Fehler), plus die Haken in `eventCreate`, `eventManage`, `eventStore`, `eventMessage`, `eventDraft`, `discord`, `settingsStore`/`settingsRoute` und `raidhelperRetirement`.

## Das Raid-Cockpit auf der Raid-Detailseite (`src/web/events/raidDetailSteps.js`, #319)

Ein Raid wohnt an sieben Stellen im Menü, die Frage der Orga ist aber immer dieselbe: **was ist bei diesem Raid als Nächstes zu tun?** Die Detailseite eines **eigenen** Events beantwortet sie oben als Strecke aus sechs Schritten — **Angelegt › Anmeldung › Setup › Freigabe › Einteilungen › Nachbereitung** —, je Schritt ein Zustand, eine große Zahl und **höchstens eine Tat**. Darunter stehen die bekannten Tabs. **Ein Raid-Helper-Event behält die heutige Ansicht**: `steps` ist dann `null` und der Kopf zeigt weiter die Leiste von #219 (Anmeldung › Setup › Raidsheet › Softres › Loot › Logs, mit aktiviertem Raidplan zusätzlich *Einteilungen* nach dem Raidsheet) samt ihrer Haupt-Tat.

- **Die Regel ist rein und liegt an einer Stelle:** `eventSteps(d, { now })` in `raidDetailSteps.js` — keine Store- und keine Discord-Aufrufe, nur eine Funktion über das Detail-Payload, das die Seite ohnehin bekommt. Darum kann die Raid-Liste `/raids` später dieselbe Antwort benutzen (Entwurf B; die Liste ist nicht Teil von #319), und darum hängen die Regeln in plain Jest statt ungetestet im TSX. Je Schritt kommt `{ id, label, icon, state, value, unit, note, fill, hint, action }` heraus, dazu `{ current, action, cancelled, note }` — `action` ist die eine auffällige Tat (die des offenen Schritts, bei einem abgesagten Event der Weg zurück).
- **Wie schnell die Seite lädt (Okt 2026):** `buildRaidDetail()` (`src/web/events/raidDetailView.js`) schickt die vier Lesezugriffe nach außen **gleichzeitig** los (`Promise.all`): das Raid-Helper-Setup, die Mitgliederliste für „fehlt“ (Discord), die Namen der eigenen Anmeldungen (Discord) und die Log-Titel (Warcraft Logs) — die Seite wartet auf den langsamsten, nicht auf die Summe; nur `softresPart` wartet auf die Anwesenheit. Das gespeicherte eigene Event wird **einmal** gelesen (`getEvent`) und an Kopf, Setup-Stand und Setup-Post weitergereicht. Die Mitgliederliste kommt stale-while-revalidate (bis 30 min alt, siehe docs/discord-servers.md „Wie aktuell die Mitgliederliste ist“); `backfillLogTitles` fragt je Aufruf höchstens 3 Logs bei WCL an (ein fehlgeschlagener Report ruht 30 min), den Rest füllt der 10-Minuten-Lauf von `logAutoLink` (`backfillAllLogTitles`, höchstens 20 je Lauf).
- **Woher die Daten kommen:** `event.*` (Kanal, Start, `size`, `signupDeadline`, `autoSuggest`, `status`, `signupsClosed` — die letzten drei über `manageState()`), `ownSignups` (Plätze und Warteliste), `ownSetup` (`setupSummary`), **`ownSetupPost`** (neu: Kanal, Nachricht, `version` und die DM-Zahlen der geposteten Setup-Nachricht, #290 — bewusst ohne `told`-Karte und ohne User-Ids) sowie `eventLogs` und `lootItems`. `size`, `signupDeadline` und `ownSetupPost` stehen nur an einem eigenen Event im Payload.
- **Die Zahl im Schritt *Anmeldung*** ist seit #520 die der einzelnen Discord-Accounts auf „Dabei“/„Spät“ (`capacity.accountCount` über `ownSignups`), Einheit „angemeldet“ — kein „/ 25“ und kein „(+3)“ mehr; der Balken füllt sich weiter gegen die Größe. Die Leiste eines Raid-Helper-Events (#219) ist unverändert.
- **Wann ein Schritt fertig ist:** *Angelegt* immer · *Anmeldung*, sobald sie geschlossen ist oder der Anmeldeschluss vorbei (dann kommt niemand mehr von selbst dazu) · *Setup*, sobald ein **Entwurf** existiert · *Freigabe* nur mit **freigegebenem** Setup, das seit der Freigabe nicht verändert wurde · *Einteilungen*, sobald der Link zur Lese-Ansicht des Raidplans im Kanal steht (siehe unten) · *Nachbereitung*, wenn ein Log **ausgewertet** *und* Loot **importiert** ist.
- **Genau eine Tat je Schritt**, und zwar die, an der es gerade hängt: *Anmeldung* → kein einziger Angemeldeter = „Anmelde-Aufruf posten“, Fehlende mit Raider-Rolle = „Fehlende pingen“, sonst „Anmeldung schließen“ — **ist das Setup gepostet (= freigegeben), ist die Anmeldung erledigt, ohne geschlossen zu werden**: sie darf offen bleiben, damit jemand nachrücken kann, wenn ein Raider ausfällt; *Setup* → „Setup vorschlagen“ bzw. „Setup öffnen“; *Freigabe* → „Setup posten“ (Posten ist Freigeben), und wenn die Nachricht im Kanal einen älteren Stand zeigt „Setup posten“; *Nachbereitung* → „Log zuordnen“ → „CLA/RPB auswerten“ → „Loot importieren“. Freigeben, Vorschlagen und Posten führen in den **Setup-Editor** — die Leiste baut keine zweite Logik daneben.
- **⚠️ „Übersprungen“ darf nicht wie „kaputt“ aussehen.** Ein Raid ohne Setup ist ein gewöhnlicher Raid (PuG, spontaner Abend), kein Fehler. Die Regel: **kein Entwurf, weniger als eine Stunde bis zum Start, und `autoSuggest` ist aus** (bzw. der Raid hat schon begonnen — dann kommt auch mit `autoSuggest` keiner mehr) ⇒ *Setup* und *Freigabe* stehen auf `skipped`, blasser statt rot, ohne Ton, ohne „fehlt“, und nichts ist mehr offen. Der Weg in den Editor bleibt trotzdem. Ein Entwurf, der nie freigegeben wurde und dessen Raid gelaufen ist, ist ebenfalls `skipped` („nie freigegeben“) — nachträglich ändert eine Freigabe nichts mehr.
- **Wo die Strecke anfängt:** vor dem Raid können nur *Anmeldung*, *Setup* und *Freigabe* „dran“ sein, **ein vergangener Raid fängt bei der Nachbereitung an** — niemand soll für einen gelaufenen Abend noch eine Softres-Liste anlegen. Was offen, aber nicht dran ist, steht auf `todo` („später“), nicht auf „offen“. **Ein abgesagtes Event zeigt nur „abgesagt“ und den Weg zurück**: jeder Schritt steht auf `cancelled` und trägt keine Tat, das Ergebnis nennt den Grund und „Absage zurücknehmen“.
- **Web:** `pages/raid-detail/StepBar.tsx` zeichnet nur — Zustände, Taten und Zahlen kommen vom Server, die Wörter drumherum rein aus `lib/raids/raidSteps.ts` (`stepStateLabel`, `stepPosition`, `stepSummary`, `stepTipSub`, `withoutDeeds`; strippable wie `lib/raids/eventManage.ts`, `src/web-client/src/lib/raids/__tests__/raidSteps.test.ts` führt sie gegen die Server-Regel aus). Der offene Schritt ist markiert und trägt den **einzigen** auffälligen Knopf; jede andere Kachel ist ein stiller Knopf, der ihre Tat ausführt. **Der erklärende Satz und die abgeschnittene Randnotiz stehen im Tooltip**, nicht auf der Fläche, und `RaidDetailHero` lässt seine eigene Haupt-Tat weg, solange ein Cockpit da ist — dieselbe Tat zweimal im Kopf ist genau die Verdopplung, gegen die das Cockpit antritt. `RaidDetailPage`s `runDeed()` ist die **eine** Stelle, die eine Tat in Dialog, Tab, Menü-Aktion oder Auswertung übersetzt. Ohne `raids`-Schreibrecht zeigt `withoutDeeds()` dieselbe Leiste ohne jeden Knopf.
- **Einteilungen posten (#502)** — das Gegenstück zu „Sheet posten“ für den Raidplan: `POST /api/raids/post-raidplan { event, message? }` (Bereich `raidplan`, schreiben, CSRF; `src/services/raidplan/raidplanPost.js`) postet den Link zur Lese-Ansicht `/p/<token>` in den Event-Kanal; ein Entwurf wird dabei **freigegeben**, erneutes Posten **bearbeitet dieselbe Nachricht** (ist sie weg, kommt eine neue). Wohin gepostet wurde, merkt sich `raidplanPostStore.js` (`settings/raidplan-posts.json`), nicht der Sheet-Store — sonst sähe ein Raid mit geposteten Einteilungen aus, als hätte er ein Sheet. Das Payload trägt es als `raidplanPost` (`{ filled, published, publicPath, channelId, messageId, message, postedAt }`, `null` ohne Raidplan). Der Schritt *Einteilungen*: ohne gespeicherten Plan `todo` mit „Raidplan öffnen“, gefüllt und nicht gepostet `open` mit „Einteilungen posten“ (dran nach der Freigabe), gepostet `done` mit „am 27.09.“ — der Knopf bleibt fürs Aktualisieren —, nach dem Raid nie gepostet `skipped`. Wer den Raidplan nicht schreiben darf, bekommt den Schritt gar nicht (und `raidplanPost` ist `null`): `buildRaidDetail({ …, planPost })`, `eventSteps(d, { plan: false })`. Dialog: `pages/raid-detail/modals/RaidplanPostModal.tsx` (dieselbe Zeile und Nachricht-Eingabe wie beim Raidsheet); ein zweiter Weg ist der Knopf im Raidplan-Tab neben „Freigeben & teilen“. Details: [raidplan/sharing.md](raidplan/sharing.md#einteilungen-in-den-event-kanal-posten-502).
- **Aussehen (Redesign, Oktober 2026):** die sechs Schritte sind **eine Reihe gleich breiter Zellen, je zweizeilig** (Oktober 2026: Name oben, Wert darunter über die ganze Zellbreite, damit nichts abgekürzt werden muss) — je Schritt Icon, Name, ein kurzer Wert mit Wort (`stepShort`: „25 angemeldet“, „25 von 25“ statt „25 / 25“, „Stand 1“; ein Wert, der nur den Namen wiederholt, entfällt) und rechts ein Haken (erledigt) bzw. die Nummer (der offene Schritt farbig hervorgehoben). Darunter der Streifen **„Jetzt dran: <Tat>“** (`stepFocus`: der erklärende Satz `hint`, sonst die Randnotiz) mit dem einzigen auffälligen Knopf, voll sichtbar; der offene Schritt selbst ist kein Knopf mehr. Zustand und Randnotiz jedes Schritts stehen im Tooltip (und für Vorlesehilfen unsichtbar im Text).
- **Mobil** (≤ 640 px) fällt die Leiste auf **eine Zeile** zusammen — „Schritt 5 von 6 · Einteilungen“ plus der Streifen, sein Knopf über die volle Breite (44 px hoch) —, nie waagerechtes Scrollen (gemessen: 0 px Überhang). Zwischen 640 und 1100 px stehen die sechs Schritte in zwei Reihen zu je drei. Ist nichts offen, bleiben alle Schritte stehen, zwei je Reihe (`.rd-cockpit.has-focus`). CSS: `styles/raid-detail.css`, Präfix `rd-ck-`.
- **Der Kopf darüber** ist kompakt: ein farbiger Zurück-Knopf „← Raid-Events“ (`components/ui/BackButton`, derselbe wie im Kaderplaner), Datumskachel, Titel, eine Zeile „17:57 Uhr · in 7 Tagen · Kategorie“; rechts der Zustand des Kanals als Badge („Kanal fehlt“, nie klickbar) mit eigenem Knopf **„Kanal anlegen“** (eigenes Event, `raids` schreiben; dieselbe Aktion wie die Aufgabe auf der Übersicht, `POST /api/raids/manage/recreate-channel`, docs/channels.md) und „Verwalten ▾“ (auf dem Handy nur sein Icon oben rechts). Unter den Tabs steht kein Karten-Kopf, der den Tab wiederholt: der Tab „Anmeldungen“ (id `roster`) beginnt mit einer Zeile — links, warum der Rollen-Abgleich nicht läuft (Badge „keine Raider-Rollen“ plus Knopf „Rollen festlegen“ → Einstellungen › Kategorien), rechts „Fehlende pingen“ und „Raider eintragen“. Auf dem Handy bleiben die Tabs eine waagerecht scrollende Reihe.
- **Raidplan oder Sheet, nie beides:** jede Raid-Kategorie plant entweder mit dem Raidplan oder mit einem Google-Sheet (Einstellungen → Kategorien → *Setup & Planung*). Gespeichert ist nur eine getroffene Wahl, `config.categoryPlanning = { [categoryId]: "raidplan" | "sheet" }`; ohne Wahl gilt `planningOf()` (`src/services/events/planning.js`): Kategorie mit festem Sheet (`categorySheets[cat].url`) = `"sheet"`, sonst `"raidplan"`; ein Event ohne Kategorie plant mit dem Raidplan. **Damit keine Kategorie ihr Werkzeug verliert,** schreibt die Migration beim Start (`settingsMigration.migrateCategoryPlanning`) jeder Raid-Kategorie (`categoryIds`) ohne Wahl die Planung fest, die sie wirklich benutzt hat: festes Sheet → Sheet, sonst das zuletzt Genutzte — eine gefüllte Sheet-Kopie (`event-sheets.json`, `filledAt`) oder ein Raidplan mit Boards (`raidplans.json`, `updatedAt`) —, sonst Raidplan; geloggt als `[settings] Migration: config.json: Planung je Raid-Kategorie …`, eine getroffene Wahl bleibt unberührt. Was daran hängt:
  - `resolveEventSheetLink()` (`configStore`) liefert für eine Raidplan-Kategorie **keinen Link** — auch keine gefüllte Kopie. Damit fallen der „Sheet“-Link der Anmelde-Nachricht, der Sheet-Link auf dem Dashboard und auf der Raid-Seite weg.
  - Das Detail-Payload trägt `planning`. ## Orga-Zentrale je Raid-Kategorie (`src/services/events/orgaHub.js`, Okt 2026)

Eine Bot-Nachricht je Raid-Kategorie **für die Orga** (Design „A · Liste je Raid“, Canvas https://claude.ai/artifact/TSeVnhEjaRsvRuzyBSLWuz), gepostet in einen Kanal, den nur die Orga sieht — wer den Kanal sieht, regeln die Kanalrechte in Discord. Das Gegenstück zur Raid-Zentrale der Raider (docs/signups.md, „Raider-Organizer“).

- **Aufbau** (`orgaHubPanel.js`, rein): ein Components-V2-Container in Türkis (`--orga-teal` des Webs) — Überschrift „Orga-Zentrale · <Kategorie>“, darunter „<n> Raids in den nächsten 4 Wochen“ und die Status-Zeile je Status mit Icon („1 Setup offen · 1 geändert · 1 in Arbeit · 1 gepostet“, nur was vorkommt); die Knöpfe **Raid anlegen**, **Alle Raids im Web** (`/raids`) und **Links …**, darunter die Link-Zeile der Orga (siehe unten); dann je Raid ein Abschnitt: Titel fett, `<t:…:d> <t:…:t> · <t:…:R> · <#Kanal>`, Status-Icon + Status + kurzes Detail, rechts der Link ins Web. Fuß: „Aktualisiert sich selbst · vergangene Raids fallen raus · höchstens 10 Raids, der Rest steht im Web“. Orga-Text, also Deutsch.
- **Welche Raids:** nur **eigene** Events der Kategorie (eine Store-Abfrage, nie Raid-Helper), Start in den nächsten 4 Wochen und noch nicht begonnen, einer sichtbaren Spielversion (`visibleRows`), nach Datum; höchstens 10 (`MAX_RAIDS`, 7 + 3 je Raid + 2 Komponenten bleiben unter Discords 40; mit Links weniger, siehe „40-Komponenten-Grenze“), der Rest steht als Zahl im Fuß. **Abgesagte bleiben bis zu ihrem Datum** durchgestrichen und ohne Link stehen; die Überschrift zählt nur die nicht abgesagten.
- **Status, abgeleitet, nie von Hand gesetzt** (`orgaStatus.js`, rein): *Anmeldung läuft* (niemand eingeteilt, Anmeldeschluss noch nicht erreicht, Anmeldung offen und Raid mehr als 3 Tage entfernt) · *Setup offen* (niemand eingeteilt, aber Schluss vorbei, Anmeldung geschlossen oder Raid unter 3 Tagen) · *Setup in Arbeit* (eingeteilt, nie freigegeben; „x von y im Setup“) · *Freigegeben* (freigegeben, nicht gepostet — oder die Nachricht zeigt einen älteren Stand) · *Gepostet* („x von y bestätigt“ aus den Bestätigungen der geposteten Aufstellung) · *Geändert seit Freigabe* (der Entwurf weicht von der Freigabe ab, **oder** Eingeteilte der Freigabe haben sich danach abgemeldet bzw. „Absagen“ gedrückt — „2 Absagen nach der Freigabe“) · *Abgesagt*. Wo das Setup steht, liest **`setupCore.setupPhase`** — dieselbe Funktion, die der Schritt *Freigabe* des Raid-Cockpits liest, damit beide nie auseinanderlaufen (`setupSummary` liegt dafür jetzt in `setupCore.js`; `setupEditor` reicht es weiter).
- **Der Link je Raid** richtet sich nach dem Status: *Raid* (Anmeldung läuft → `/raids/detail?event=<id>`), *Setup bauen* (offen), *Setup* (in Arbeit, gepostet), *Setup posten* (freigegeben), *Setup prüfen* (geändert) — alle außer *Raid* mit `&tab=setup`. Absolut über `PUBLIC_BASE_URL`; ohne sie gibt es keine Link-Knöpfe (Discord nimmt keine relativen).
- **Icons:** sieben eigene UI-Emojis `eh_ui_orga<status>` (`appEmojis.UI_ICONS`, gezeichnet in `scripts/render-ui-emojis.js`), Form **und** Farbe verschieden: hohler Kreis grau, voller Kreis orange, halb gefüllt blau, grüner Ring mit Haken, grün gefüllter Haken, oranges „!“, graues „×“. Der Bot lädt sie beim Start selbst hoch; bis dahin stehen Unicode-Zeichen da (⚪ 🟠 🔵 ☑️ ✅ ❗ ✖️).
- **„Raid anlegen“** (`orga:new:<categoryId>`, `commands/event/orgaHubButton.js` → `orgaHubBot.js`): öffnet ephemer den Ablauf von `/event anlegen` (`eventDraft.stepMessage(guildId, initialState(guildId, categoryId))`) mit der Kategorie vorgewählt. Darf, wer `/event` darf (`accessOf: "event"`, wie die Auswahlen des Ablaufs) **und** Orga dieser Kategorie ist: globale Orga (Admin oder Orga-Rolle, `permissions.userIsOrga`) oder Manager ihres aktuellen Rosters (`rosterAccess.isRosterOrga`); alle anderen bekommen ephemer „Dafür fehlt dir das Recht.“ Wie `/event anlegen` nur auf einem Raid-Server der Liste — **der Orga-Kanal muss auf einem Raid-Server liegen**, sonst antwortet der Knopf „Events legst du auf einem Raid-Server an.“
- **Posten** im Web unter Einstellungen → Kategorien → Details → *Discord-Zentralen* → **Orga-Zentrale**: Kanal wählen, *Posten* (`POST /api/orga-hub { categoryId, channelId }`, `GET /api/orga-hubs`, `DELETE /api/orga-hub { categoryId }`, Bereich `settings`, `apiRoutes/orgaHub.js`). Neu posten — in denselben oder einen anderen Kanal — löscht die frühere Nachricht. Gespeichert in `stores/orgaHubStore.js` (`settings/orga-hubs.json`).
- **Links der Orga-Zentrale** (bis zu 5 je Kategorie, `{ label, url }` in `orga-hubs.json` unter `links`, `orgaHubStore.getLinks/setLinks`): als Link-Knöpfe in einer eigenen Zeile unter *Raid anlegen*; ohne Links gibt es die Zeile nicht. Geprüft wie die Links der Raid-Zentrale (`availabilityStore.checkLinks`: https, Name höchstens 40 Zeichen, höchstens 5) plus: dieselbe Adresse nicht zweimal. Getrennt von den Raider-Links, weil die Orga etwas anderes braucht (WCL-Gilde, Raid-Sheet …). Neben *Raid anlegen* steht der Knopf **Links …** (`orga:links:<categoryId>`). Er antwortet ephemer mit einer Karte: die Links, **Link hinzufügen** (Formular Name + Adresse), die Auswahl **Link bearbeiten …** (Formular mit dem Link vorbefüllt) und **Link entfernen …**; bei 5 Links ist *Hinzufügen* gesperrt, die Fußzeile sagt warum. **Emoji:** das Formular hat ein drittes, optionales Feld *Emoji vor dem Namen* (leer = keins; das Formular hat damit drei von höchstens fünf Eingaben, ein Format wie „📊 WCL“ im Namensfeld wäre mehrdeutig und wird nicht geraten); die Karte zeigt das Emoji vor dem Namen, es gehört zum Hash des Links. Regeln und Web-Eingabe wie bei der Raid-Zentrale (docs/signups.md, „Emoji je Link“). Alles unter dem Präfix `orga` (`orga:ladd|ledit|lsave|ldel:<categoryId>`, `orgaHubLinks.js`): Quittung zuerst, Orga-Prüfung danach (gleiche Regel wie *Raid anlegen*, `isCategoryOrga`; sonst „Dafür fehlt dir das Recht.“). Ein Formular muss die direkte Antwort auf den Klick sein, deshalb öffnen *Link hinzufügen* und *Link bearbeiten …* es sofort; die Prüfung folgt beim Absenden (`deferUpdate`, dann ersetzt die Karte die Absage). Die Kategorie-ID aus der customId gilt als unvertraut: es muss eine Kategorie mit gepostetem Hub **auf diesem Server** sein. Ein Link wird über Index + kurzen Hash seines Inhalts angesprochen (`ledit`/`ldel`/`lsave`), eine veraltete Karte ändert nie den falschen Link. Jede Änderung geht durch `orgaHub.saveLinks`, das den Hub **sofort** neu zeichnet (statt auf die 5-Minuten-Runde zu warten); dasselbe tut `PUT /api/orga-hub/links { categoryId, links }` des Webs (`GET /api/orga-hubs` liefert `links` und `maxLinks` mit; Editor `OrgaLinksEditor.tsx` unter der Orga-Zentrale in den Kategorie-Einstellungen).
- **40-Komponenten-Grenze mit Links:** Kopf 9 feste Komponenten (Container, Überschrift, Knopfzeile mit 3 Knöpfen, Trenner, Fuß-Trenner und -Text), die Link-Zeile 1 + 1 je Link, 3 je Raid. `orgaHubPanel.raidCapacity(n)` rechnet daraus, wie viele Raids neben `n` Links passen: 10 ohne Links, 9 bei 1–3, **8 bei 4–5**; der Rest steht wie bisher als „+n weitere“ im Fuß (der Fuß nennt die tatsächliche Zahl).
- **Teile ein-/ausschalten** (#969): je Kategorie *Raid anlegen* (`newRaid`), *Links* (`links`: Knopf *Links …* samt Link-Zeile) und die Status-Zeile (`summary`); die Raid-Liste und *Alle Raids im Web* bleiben immer. Gespeichert in `orga-hubs.json` unter `features: { [categoryId]: { <Teil>: false } }` (fehlender Schlüssel = an, nur `false` wird gespeichert, keine Migration). Ohne Knöpfe entfällt die Knopfzeile ganz, der Leertext heißt dann nur „Noch kein Raid geplant.“; `raidCapacity(linkCount, features)` gibt den Platz ausgeschalteter Knöpfe und der Link-Zeile der Raid-Liste (höchstens 10). `PUT /api/orga-hub/features { categoryId, features }` (Bereich `settings`; unbekannter Teil oder unbekannte Kategorie → 400) geht über `orgaHub.saveFeatures`, das sofort neu zeichnet; `GET /api/orga-hubs` liefert `features` und `featureKeys`. Ein Knopf einer älteren Nachricht (`orga:new`, `orga:links`) antwortet ephemer „Diese Funktion ist in dieser Orga-Zentrale ausgeschaltet.“ (`orgaHubBot.SWITCHED_OFF`, Orga-Text, Deutsch).
- **Neu zeichnen:** jede Zentrale merkt sich einen Fingerabdruck (`hash`). Der Job `orgaHubs` zeichnet eine Minute nach dem Start und danach **alle 5 Minuten**, was sich geändert hat (ein begonnener Raid fällt raus, Text nach einem Deploy), und **5 Sekunden nach jeder Änderung** eines eigenen Events (`eventStore.onEventsChanged`: anlegen, bearbeiten, verschieben, absagen, Setup speichern/freigeben/posten) oder einer Anmeldung (`signupStore.onSignupsChanged`) — gleicher Hash = kein Discord-Aufruf. Eine in Discord gelöschte Nachricht wird gleich danach im selben Kanal neu gepostet (`linkWatch.js` meldet sie `orgaHub.onHubMessageDeleted`, das den Fingerabdruck vergisst; das Bearbeiten scheitert dann an „Unknown Message“ und postet neu); ein verschwundener Kanal wird einmal je Prozess geloggt.

## Lootsystem je Raid (`src/services/loot/lootSystem.js`, `eventLootSystemStore.js`)

Ein Loot-Council-Raid braucht keine Softres-Liste — also soll ihn auch nichts dazu drängen. Das **Lootsystem** (`softres` · `lootcouncil` · `gdkp` · `other`) entscheidet, ob ein Raid den Softres-Schritt, das Badge „Softres fehlt“ und den Menü-Eintrag „Softres-Liste“ bekommt.

- **Die Kategorie gibt den Standard vor:** `config.categoryLootSystem = { [categoryId]: system }`, in Einstellungen › Kategorien als Segment „Lootsystem“ (gemergt gespeichert, `""` = *automatisch* löscht den Eintrag). **Automatisch** heißt: Loot-Addon RCLootcouncil ⇒ Loot-Council, sonst Softres — so wie es war, bevor es die Einstellung gab.
- **Ein Raid kann abweichen:** `data/settings/event-loot-system.json` (`events[eventId] = { system, softres, at, by, byName }`), nach Event-Id, damit es für eigene **und** Raid-Helper-Events geht. `system: ""` = wie die Kategorie, `softres: true` = „Softres zusätzlich“ (z. B. BoEs bei einem LC-Raid). Ein Eintrag ohne beides wird gelöscht. Gesetzt über `POST /api/raids/loot-system { event, system, softres }` (Bereich `raids`, schreiben) aus dem Dialog „Lootsystem“ — geöffnet über den Eintrag **„Lootsystem“ im „Verwalten“-Menü** der Raid-Detailseite (nur mit `raids`-Schreibrecht; `lib/raids/eventManage.ts`' `lootSystemEntry`, bei einem Raid-Helper-Event neben dem Raidplan-Schalter). Wer nur lesen darf, liest das Lootsystem als Text in der Zeitzeile des Kopfs.
- **Softres-Liste aus dem Kanal (`services/loot/softresDetect.js`):** Legt die Raidleitung die Liste selbst auf softres.it an und postet den Link in den Raid-Kanal, verknüpft der Bot ihn mit dem Raid (`setEventSoftresLink`), und "Softres fehlt" verschwindet. Live über `messageCreate` (`onMessage`: Link in Text oder Embeds; eigene Bot-Nachrichten und DMs zählen nicht), nachgeholt von `backfill` (einmal kurz nach dem Start, dann alle 30 Minuten: je Kanal eines kommenden Softres-Raids ohne Liste die letzten 50 Nachrichten; Job `softresDetect`). Zum Kanal gehört der früheste Raid, der noch nicht vorbei ist (Start ≥ Nachricht − 6 h), aus den eigenen Events **und** der gesyncten Raid-Helper-Liste (`raidhelperEventsStore`, nie ein Raid-Helper-Aufruf). Ein vorhandener Eintrag mit URL wird nie überschrieben (das Menü gewinnt); bei eigenen Events steht im Verlauf "Softres-Liste aus dem Kanal verknüpft".
- **Die Softres-Karte mit Zähler (Okt 2026, `services/loot/softresStatus.js`):** „Softres posten“ (`POST /api/raids/post-softres`, `postSoftresCard()`) postet die Liste als Karte in der Sprache des Events (`eventLang`): softres.it-Icon als Thumbnail, Titel „Softres“, eine Zeile mit den Instanzen (" · "), Fakten *Start*, *SR je Spieler N*, *Eingetragen 14 / 25*, Knöpfe „Softres öffnen“ (Link) und „Wer fehlt?“, Fußnote „Zuletzt geändert <t:…:R>“. Ein zweites Posten liest frisch und editiert die alte Nachricht (fehlt sie, wird neu gepostet).
  - **Gelesen** wird `GET https://softres.it/raid/{raidId}[?adminToken=…]` (`utils/loot/softres.js` `fetchRaid`: HTML, darin das Inertia-JSON in `div#app data-page`, `props.raid` mit `reserves[]`, `hide_reserves`, `reserve_limit`, `instances`, `isManager`). Der Admin-Token geht nur mit, wenn er gespeichert ist, und wird nie ausgegeben.
  - **Erwartet** sind die Slots des freigegebenen Setups, ohne Setup die aktiven Anmeldungen (ohne Abmeldung, Bank, Abwesenheit; Tentative/Late zählen), je Raider einmal (`expectedRaiders`). Bei Raid-Gruppen (#811) ohne freigegebenes Setup gibt es noch keine Aufteilung: dann werden alle Angemeldeten der Gruppe beim ersten Raid erwartet. **Abgleich** (`matchReserves`) in drei Durchgängen, damit ein Konto, das für andere mit einträgt, deren Reserve nicht belegt: erst Discord-Id **und** Charname, dann der Charname allein, dann die Discord-Id allein. Verglichen wird gegen alle Chars des Raiders in der Version des Events (Anmeldung + Profil, `charactersOfVersion`); Groß-/Kleinschreibung, Akzente, Leerzeichen und Realm-Anhang zählen nicht (`nameKey`). Jedes Reserve zählt einmal.
  - **Kurz-Cache:** `readStatus` hält den Abruf je Liste 60 Sekunden (`fetchRaidCached`, geteilte Promise, ein Fehler wird nicht gemerkt) — 25 Klicks auf „Wer fehlt?“ sind ein Abruf bei softres.it.
  - **Kein Zähler** (Fakt und Knopf fallen weg, die Karte wird trotzdem gepostet), wenn die Reserves versteckt sind und der Bot nicht Manager ist (`hidden`), softres.it nicht antwortet (`fetch_failed`), niemand erwartet wird oder keine Liste existiert. Bei `fetch_failed` bleibt die Karte, wie sie ist; auch ein erneutes Posten behält dann den zuletzt bekannten Zähler und den Knopf.
  - **Job `softresStatus`** (`web/http/jobs.js`, alle 10 Minuten): alle geposteten Karten von Raids, die in den nächsten 7 Tagen starten oder höchstens 2 h zurückliegen, nacheinander; editiert wird nur, wenn sich Zähler oder fehlende Namen geändert haben (`status` in `event-softres.json`: `filled`, `expected`, `missingKey`, `checkedAt`). „Zuletzt geändert“ ist der letzte Lesezeitpunkt mit Änderung — nicht der letzte Lesezeitpunkt überhaupt, darum heißt die Fußnote so. Raid-Helper wird dabei nie abgefragt (`raidhelperEventsStore`).
  - **„Wer fehlt?“** (`softres-missing:<eventId>`, `services/loot/softresMissingBot.js`, Zugriff wie die Anmeldung: jeder Raider): defer, frisch lesen, Hauptkarte nachziehen, ephemere Karte „N fehlen noch“ mit den Namen (max. 25, dann „+N weitere“) und **„Jetzt pingen“** (`softres-ping:<eventId>`, Zugriff wie „Fehlende pingen“: `/event`-Recht, also die Orga). Die Liste geht an genau eine Person, darum hängt „Jetzt pingen“ nur dran, wenn der Klickende die Regel des Ping-Knopfs erfüllt (`mayPing`: `ruleFor`/`resolveBotAccess` aus `botAccess`, wie der Router); Raider bekommen stattdessen die Fußnote „Pingen kann nur die Orga.“. Der Router (`guardInteraction`) prüft den Klick trotzdem als zweite Sicherung. Der Ping geht in den Event-Kanal mit den Mentions und „Bitte Softres eintragen: <Link>“ (Sprache des Events); Schutz: die Knöpfe verschwinden sofort, je Event läuft ein Ping gleichzeitig, ein zweiter innerhalb von 2 Minuten wird abgelehnt (nur im Prozessspeicher); scheitert ein Ping nach dem ersten Teil, zählt er trotzdem als Ping (`sentMessageIds` am Fehler von `postMissingPing`). Die Antworten an die Orga sind deutsch, die Fehlerkarte auf „Wer fehlt?“ spricht die Sprache des Events.

## Event verwalten (`src/services/events/eventManage.js`, #288)

Everything the orga does with an **own** event after creating it: move it, close/open the signup, sign raiders up or off, ping the missing ones, cancel it (and take that back). **One service** (`eventManage.js`) for the web and Discord; every action refuses a Raid-Helper id (`not_own_event`) and another server's event, and every action is **logged on the event** (`eventStore.appendEventLog`: `event.log = [{ at, action, by, byName, detail }]`, newest last, capped at 100; labels in `ACTION_LABELS`). Editing through the create dialog logs too (`eventCreate.updateEvent({ …, user, byName })`, only the fields that really changed, named in German). Discord calls run **after** the store changed and are best-effort: a refused rename, a DM that does not arrive, an unpostable message come back as `warnings`, never as a rolled-back action.

- **State on the event** (`eventStore.setEventState`, apart from `updateEvent` so the plan is not re-validated): `status` `"active" | "cancelled"`, `signupsClosed`, `cancel { reason, at, by, byName, archived }`. `eventSources.planFields` hands `status`/`signupsClosed` to every reader.
- **Closed signup:** `signupService` lets a member only sign off (`WHEN_CLOSED`, code `closed`, 409), keeping an unchanged signup still works; `byOrga` is exempt. **Cancelled:** nothing at all — not even `byOrga` (`cancelled`); `allowedStatuses` is empty, so the web and Discord signup dialogs show it closed.
- **Move** (`movePlan` = preview, nothing changes; `moveEvent`): new Berlin start (past or unchanged refused), the deadline keeps its distance to the start, the reminder marks `missing`/`signed` are cleared. **The channel is renamed by #285's naming** — `deriveChannelName({ fromEventId, excludeChannelId, date })` — but only when its name follows a rule the old day is visible in: derived from its own name (`source: "previous"` with `fromChannelId` = its channel), or the category's stored schema *and* the channel still carries the old day's schema name. A hand-made name keeps its name, and the preview says why (`channel.reason`). `renameChannel` / `notify` switch the rename and the note: a post in the event channel mentioning everyone not signed off (`deliverUserPing` target `event`).
- **Raider eintragen** (`addRaider`): `submitSignup(…, { byOrga: true })` with a profile character; a character or spec the raider's profile lacks is **added to the profile first** (`raiderProfileStore.addCharacter`, a spec of another class is refused). `removeRaider` deletes the signup. `raiderCandidates` offers profiles ∪ holders of the category's raider roles ∪ signups, plus the rule set's classes for a new character.
- **Cancel** (`cancelEvent`): a reason is required (≥ 3 characters, it goes to the raiders); status cancelled + signup closed, the message is titled "Abgesagt: …" with the reason, red and without components (`eventMessage.messagePhase` reads `status` and `cancel.reason`; a closed signup is phase `closed`: a 🔒 line and the join select with only Abmelden), a DM with the reason to everyone not signed off (`pingDelivery.sendDms`, `notify`), and optionally the channel into the archive (`discordChannels.archiveChannel` + `channelArchiveStore.recordArchived`; no archive category = `no_archive` before anything happens). A cancelled past raid shows no "Keine Logs"/"Kein Loot" badges.
- **"Fehlende pingen"** is one function now, `src/services/events/missingPing.js` (`pingMissingRaiders`, on top of `findMissingRaiders` — who of the category's role holders has not reacted), used by `POST /api/raids/ping-missing`, the Event-verwalten button and the orga's button under the signup message (preview first, see docs/discord-servers.md); a cancelled event is refused.

## Wiederkehrende Events (`src/web/events/eventSeries.js`, page `/raids/series`, #289)

A **series** per raid category — "Mo + Mi 19:30 · SSC + TK 25er · 6 Tage vorher" — makes the EventHelper create each date's event in time, with everything a hand-made one gets.

- **Stored** in `src/stores/eventSeriesStore.js` (`data/settings/event-series.json`, kept out of the settings config because the scheduler writes on every creation): `series[categoryId] = { categoryId, guildId, enabled, weekdays (1 = Mo … 7 = So), time "HH:mm", raidTemplateId ("" = the category's default template, `categoryRaidTemplate`), daysBefore (1–28), title ("" = template name), skipDates ["yyyy-MM-dd"], leaderId, updatedAt/By/ByName }` and `runs[categoryId][date] = { status: creating | created | existing | failed, at, eventId, channelId, channelName, error, attempts, messageError }`. `normalizeSeries()` refuses no weekday, a bad time, days outside 1–28, an unknown template and "no template and no category default"; past skip dates are dropped. Since #738 it also refuses a **running** series whose template (own or default) is of another version than the category plays; a paused one may keep it. The sweep never creates a wrong-version event: `eventCreate` answers 409 `template_version_mismatch`, the date is `failed` and shows up in `seriesFailures` (docs/game-versions.md, "Feste Version je Kategorie").
- **Dates are Berlin wall-clock** (Luxon, `Europe/Berlin`): `occurrences()` walks calendar days, a start is `date + time` in Berlin (19:30 stays 19:30 across the DST switch), the creation moment is the start minus `daysBefore` **calendar days** at the same clock time. Tests cover both switches (25.10.2026, 28.03.2027) and several weekdays.
- **The sweep** (`startEventSeries()`, started by `jobs.js`: every 5 min, first run a minute after boot; `runSeries()`): only enabled series of a category whose `categorySignupSource` is `eventhelper` — a Raid-Helper category's series rests (`ignored`); nothing while the Discord client is not ready. `dueDates()` = window open, start ahead, not skipped, no mark (or a retryable failure). For each: a date that already has an event in the category (own via `eventSources.ownUpcomingRaw`, plus `loadEventGroups` — any source, **any status, a cancelled one included**) is only marked `existing`; otherwise the date is **claimed first** (`claimDate`, "creating") and then created through `eventCreate.createEvent({ body: { title, date, time, newChannel: { name: "", categoryId }, signupSource: "eventhelper", raidTemplateId } })` — so the channel is named and copied like the category's previous event channel (#285), the signup message is posted and the talk overview refreshed, with nothing series-specific. The event's log gets `series` ("Von Serie angelegt").
- **Never twice:** a claimed date is never claimed again (overlapping sweeps also stop at the `running` flag); marks **outlive a deleted series**, so setting it up anew repeats nothing; a date whose event was deleted (Event verwalten › Löschen) keeps a `deleted` mark and is never created again; marks are pruned 60 days after their date. **Failures:** `failed` with the message (`Kanal konnte nicht angelegt werden: fehlende Rechte`), retried at most `MAX_ATTEMPTS` 3 times, `RETRY_AFTER_MS` 10 min apart, then only by "Erneut versuchen" (`POST /api/raids/series/run { categoryId, retryDate }` clears the mark). A `creating` mark older than 15 min is **interrupted** (restart mid-create) — shown and reported, never retried on its own, because nobody knows whether its channel exists. `seriesFailures()` feeds the dashboard task `series` ("Serie konnte Event nicht anlegen: fehlende Rechte", `eventSeriesTask` in `dashboardOverview.js`, for users who can read `raids`, links to `/raids/series`).
- **API** (`apiRoutes/eventSeries.js`, area `raids`, level by method): `GET /api/raids/series` (one row per `categoryIds` entry plus categories that still have a series: `source`, `series`, `template`, `summary`, `upcoming` = the next 4 dates from `planSeries()` with `state` planned | due | creating | interrupted | created | existing | cancelled | failed | skipped | off, the channel it got or `previewName` + `naming` from `channelNaming.describeResult`, `lastCreated`; plus `templates`, `canWrite`, `limits`), `GET /api/raids/series/preview?category=&weekdays=&time=&daysBefore=&template=&skip=&enabled=&title=` (the modal's live preview, nothing stored), `PUT /api/raids/series` (409 `raidhelper_category` for a *new* series in a Raid-Helper category; an existing one can still be edited or switched off), `DELETE /api/raids/series { categoryId }`, `POST /api/raids/series/run { categoryId?, retryDate? }` ("Jetzt prüfen"). **Who (#728):** the global orga (with `raids` write for the writes) every category; the orga of a category (a manager of its current roster) sees and writes only the rows of their categories — the writes and the preview are `orgaScoped` by `categoryId`, a run without `categoryId` (every series) is the global orga's; anyone else (a raider role with `raids` write too) sees no row.
- **Web — why a page under Raid-Events and not the Kategorien card:** the card is already a dense grid saved as one settings form, while a series saves itself, has scheduler state to show and needs `raids` write (it creates events), not `settings`. So `pages/EventSeriesPage.tsx` (linked "Serien" in the Raid-Events head, beside Raid-Vorlagen) is **one line per category**: name, the summary line in mono, badges only for *aus* / *Raid-Helper* / *n Fehler*, and on the right "Nächster Termin Mi 23.09. #mi-23-09-ssc-tk" with one sentence what happens ("wird am Do 17.09. um 19:30 angelegt", "fehlgeschlagen: … · neuer Versuch folgt") plus "zuletzt angelegt: Mo 21.09. als #… (am Mi 16.09.)". A Raid-Helper category without a series shows the hint with a link to Einstellungen → Kategorien instead of a button. Everything else is the modal (`?edit=<categoryId>`): switch, weekday chips, time, days before, template (default named), title, the summary as it will read, and **"Nächste 4 Termine"** — each with its state badge, the channel name it will get with the `NamingBadge`, the sentence, an "überspringen" check box (saved with the series) and "Erneut versuchen" on a failure. Wording and date rules are pure in `lib/raids/eventSeries.ts` (strippable). CSS `styles/series.css` (`sr-`).
- **Tests:** `test/web/events/eventSeries.test.js` (DST, several weekdays, window, never twice incl. overlapping sweeps and a re-created series, existing/cancelled/skipped, Raid-Helper ignored, Discord not ready, retries and the dashboard task, interrupted, overview/preview), `test/web/apiRoutes/eventSeries.test.js` (access + handlers), `src/web-client/src/lib/raids/__tests__/eventSeries.test.ts` (lines, draft, page shape, routing).
- **A deactivated category's series rests (#744):** `runSeries` skips a series whose category is not active (`categoryLifecycle.isCategoryActive`, counted as `inactive` in the sweep summary); the stored series keeps `enabled`, so switching the category on again resumes it. `seriesOverview` marks the row `inactive: true` and plans its dates as `off`; the page shows the badge *Kategorie inaktiv*.

## Kategorien umbenennen, deaktivieren, abschließen (`src/services/events/categoryLifecycle.js`, #744)

Everything about a raid category keys on its **Discord id** — settings maps, series, reminders, rosters, Loot-Council profiles, Kader attendance, raids. A name is display only.

- **Renaming a role** changes nothing: rights (`rolePermissions`, `adminRoleIds`, `orgaRoleIds`), the role sync between the servers, rosters (`roleIds`) and `categoryRoles` hold role ids; pages read the name live (`discord.listRoles`). `test/services/discord/roleRename.test.js` holds it. The raider-role picker of a category (`lib/settings/categoryLifecycle.ts` `raiderRoleOptions`) offers every role whose name says "raid" **plus every role a category already uses, by id** — a raider role renamed to "Kern" stays offered.
- **Renaming a category:** raids of a **closed section** (#738, `categoryEras`) show the name the category had then, raids of the current section the live Discord name. One rule, `categoryEras.categoryNameAt(categoryId, startTime, liveName)`, applied centrally: `eventSources.withEraName` (every stored row: `listStoredEvents`, `getStoredEvent`, `toStoredShape`, `toMatchableShape`), `raidEventGroups.loadEventGroups` (each row gets its own `categoryName`; the group keeps the category's **live** name — taken from the channel map, so a group opened by an old snapshot row is named right too) and `matchableEvents`. Readers that used the group's name for a single raid (`raidListing`, `eventLookup`, `raidDetailView`, `apiRoutes/raids.js`, `dashboardData`) prefer the row's. A plain rename without a version switch keeps one section: all its raids show the new name. Channel names never follow a category name (docs/channels.md): a rename renames no channel and creates none twice.
- **Active** = in `config.categoryIds`; `activeCategoryIds(config)` / `isCategoryActive(id, config)` are the one reading. **An empty list still reads as "every category"** (what an install that never picked one always did). So the settings **refuse to save an empty list while raids exist** (`PATCH /api/settings` → 400 `categories_empty`, `emptyListBlocked`; only when categories were active before — an install that never picked one keeps working), and the pitfall cannot be reached from the menu. Chosen over a new explicit setting because every reader of the old `!cats.length ||` pattern stays correct without a migration.
- **Deactivating** (switching a category off and saving) deletes nothing: its **series rests** (above), its **reminders stop** (`reminders.runReminders` skips the category; the rule stays, `GET /api/settings/reminders` marks it `active: false`, the reminders card says *pausiert*), the **Kaderplaner** (`kaderSource.listRaidCategories`), the **roster dialog** (`rosterOptions.rosterCategories`: a deactivated category stays only while a roster names it, `active: false`) and **`/anwesenheit`** (`attendanceLookup.characterAttendance`) offer only active categories. Archive and history (raid lists, loot, logs, roster pages) keep showing it. Before the save the page opens `pages/settings/categories/CategoryDeactivateDialog.tsx` (`GET /api/settings/category-deactivate?next=<ids>` → per category taken out: series, reminders, coming own raids; `emptyBlocked`); the save answers `deactivatedCategories` and the page toasts each.
- **Which server a category belongs to (#926, prod incident 2026-10-27):** `config.categoryIds` and the per-category maps are **one list for every Discord server**. `services/events/categoryGuild.js` knows two owners per id: the **proof** owner — live in any usable guild the bot is on, else the stored snapshot (`storedCategoryGuilds`) — and the **display** owner, which also takes its events, raid snapshot or rosters (their `guildId` is often guessed: a roster takes the active web server, the migration the first server — so they only decide where a category is shown, never that it is deleted). `categoryState()` judges the proof owner: `live`, `missing` (bot online, the proof owner is a **configured, cached and available** server that lists at least one category, and the category is gone there) or `unknown` (`offline`, `no_server`, `server_not_configured`, `server_unreachable` — also a cached server with `available === false` during a Discord outage, see `discord.isGuildAvailable()` — and `server_empty`: the server lists no category at all). **Only `missing` is "deleted"**; a server absent from `discordServers.servers` (prod: Pulse Fresh missing, its categories read as deleted and `closeCategory` wiped their settings) makes its categories `unknown`, never deleted. The settings page is per server (`activeGuildFor(req)`): `GET /api/settings` adds `serverCategoryIds` (active ids on this server, plus unproven ones on the first server), `unprovenCategoryIds`, `otherServerCategoryIds` and `missingCategories` of this server only; the client (`api/settings.ts` `forServer`) narrows `config.categoryIds` to `serverCategoryIds`, so the matrix, the saved comparison and the deactivate preview only see this server. `PATCH` merges (`mergeServerCategoryIds`): a save on A never removes or adds a category of B. The merge takes the server from the tab, not from the session: the client always sends `serverSettingsGuildId` (the server the page loaded, `""` without one) with `categoryIds`, `serverSettingsTarget` checks it and answers 409 `server_switched` without saving anything when the session switched in another tab (without an active server it falls back to the first server); `GET /api/settings/category-deactivate` takes the same id as `guild` and refuses the same way. An available server where the last category really was deleted (`server_empty`) cannot be closed: its rows stay *Server unklar*. `unprovenCategoryIds` covers every configured id shown on this server (not only the active ones) whose display owner is not a listed server or whose state is `unknown`; such a category shows the badge *Server unklar* and no close button. `serverListed: false` (the active server is not in `discordServers.servers`) shows a warning on the page: a save there keeps no activation, the merge puts unlisted servers' categories on the first server.
- **Deleted in Discord:** `missingCategories({ config, nameOf, guildId, ctx })` = every configured id (active list, the settings maps of `SETTINGS_KEYS`, a series, a Loot-Council profile entry) Discord does not have, each with `closePreview()`; `GET /api/settings` hands it out as `missingCategories`. The gateway's `channelDelete` of an active category logs a warning (`linkWatch.js`) — only on a configured event server. Einstellungen → Kategorien shows the row under its last known name with the badge *in Discord gelöscht* and **„Kategorie abschließen“** (`CategoryCloseDialog.tsx`; disabled while the page has unsaved changes).
- **Closing** (`POST /api/settings/category-close { categoryId }`, area `settings` write, CSRF; 409 `category_exists` while Discord has it, 503 `bot_offline` while offline, 409 `category_server_unknown` without a proven server, 409 `category_other_server` for a category of another server than the active one) → `closeCategory()`: deletes the series (`eventSeriesStore.deleteSeries`; its run marks stay, so nothing is ever created twice), removes the category from `categoryIds` and every map in `SETTINGS_KEYS` incl. `categoryReminders` (`configStore.dropCategoryEntries` — `saveConfig` merges most maps and cannot drop a key), its `council-profiles.json` category entry and its place in every Kader's `attendanceCategories` (`services/kader/kaderCategories.js`, the door for this; nothing of a Kader's players leaves). `SETTINGS_KEYS` includes `categoryLootSystem` (else the closed category would stay a Loot-Council target) and `categoryAttendance` (else the settings list would keep it as an unknown row). **Kept on purpose:** `categoryVersion`, `categoryEras` (the version and name its raids read under) and `category-names.json` (its name for the history). Raids, loot and logs are untouched. **Rosters:** every roster of the category (one per game version) is closed with it — `rosterStore.closeRoster(id, { reason: "category_closed", actor })`, #739: readable under its version, no Discord role sync, nobody loses a role, a full admin can still delete it (docs/roster-profile.md "Roster je Version"). A roster an earlier switch closed stays as it is. The dialog lists them with a link ("schon abgeschlossen" for those) and says they will be closed; the answer's `rosters` carry `closed`.
- **Tests:** `test/services/events/categoryLifecycle.test.js`, `test/services/events/raidEventGroups.eras.test.js`, `test/web/apiRoutes/settings.categoryLifecycle.test.js`, `test/services/kader/kaderCategories.test.js`, `test/services/discord/roleRename.test.js`, the pause cases in `eventSeries.test.js` / `reminders.test.js`, `src/web-client/src/pages/settings/categories/__tests__/CategoryLifecycleDialogs.test.tsx` and the flows in `SettingsPage.sections.test.tsx` / `CategoryMatrix.test.tsx`.

- **Event leader dropdown:** "More details" in the create dialog lists `leaderCandidates` of `GET /api/raids/new` (`apiRoutes/raids.js`): the creator first, then the current leader and the people signed up — for an event being edited its own signups, for a new one those of the guild's events from the lookback window on (max 60, names through `resolveUserNames`, the creator alone if Discord is offline). "Other Discord id …" shows the text field for anybody else. **The dialog never waits for Discord:** `resolveUserNames(…, { waitMs: LEADER_NAMES_WAIT_MS })` (400 ms) answers with what it has, a name not known by then shows the character the raider signed up with, and the lookup finishes in the background into the member cache. Ids Discord did not return (left the server, signed up from elsewhere) are not asked for again for 30 min (`ABSENT_MS` in `discord.js`, 5 min after a failed lookup) — before, every open of the dialog (and every page listing such raiders) waited for them again, up to `NAME_FETCH_MS` (5 s).
