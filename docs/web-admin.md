# Web Admin (`src/web/`, `src/web-client/`)

Endnutzer-Sicht: siehe [guide-web-admin.md#übersicht--dashboard](guide-web-admin.md#übersicht--dashboard).

The bot ships its website as a **single React SPA** — `src/web-client/` (Vite + TypeScript), built to `dist/` and served as static files by `src/web/http/staticClient.js` **from the site root**. The SPA talks to `src/web/apiRoutes/*.js` (`/api/*`, JSON, dispatched by `apiRouter.js`) for everything — there is no server-rendered admin UI anymore.

**Why the root, and what that means for routing.** The menu used to live under `/admin` (and `/admin2` before that), but members open it to look up loot — a link reading `/admin/history` told them they were somewhere they should not be. So `server.js` (through `pageRoutes.js`) matches the paths that own themselves first (`/api/*`, `/auth/*`, `/health`, the public `/r/<id>` report pages) and hands **everything else** to `staticClient.js`; `/admin/*` and `/admin2/*` 302-redirect to the same path at the root, so old bookmarks and links already posted in Discord keep working. Consequences worth knowing:

- A new **server-side** path gets an entry in `PAGE_ROUTES` (`src/web/http/pageRoutes.js`, #424): `server.handle()` only dispatches over that list — the first entry whose method and path fit answers, and whatever finds none is the client (GET) or a 405. Order matters (`/r/<id>/p/<n>` before `/r/<id>`). `test/web/http/serverRoutes.test.js` pins every path's status, headers and body against `fixtures/serverRoutes.golden.json`.
- An unknown GET no longer 404s on the server — it reaches the SPA, whose `path="*"` route renders the "not found" page inside the shell. The server's 404 is left for a missing `dist/` and for an unknown report id.
- `staticClient.js` takes the request path unprefixed now, so its path-traversal guard is the only thing between `/../../.env` and the filesystem (`test/web/http/staticClient.test.js` covers it).
- Vite's `base` and the router's basename are both `/` — don't reintroduce either. Links in the SSR report chrome (`adminChrome.js`) point at the root paths too, so they don't take a redirect hop.

- **Tests of the client** run in Vitest inside `src/web-client` (`npm test` there, also in CI): logic and components next to their module as `*.test.ts(x)`, rendered with Testing Library and a mocked `api/`; only structural conventions stay as source scans in `test/web-client/conventions/` (Jest). How to write one: docs/testing.md, "Web-Client (Vitest)".
- **Must be built before it's reachable.** Run `cd src/web-client && npm install && npm run build` — the built `dist/` is what `staticClient.js` serves. In production this now happens automatically via `deploy.sh`. See "Local test instances" in CLAUDE.md for the worktree workflow.
- Page components live in `src/web-client/src/pages/`, one per admin section, routed in `App.tsx` (see "Where client code lives" below for the folders), shelled by `components/Shell.tsx` (sidebar nav + topbar with the server/guild switcher and theme toggle). Every page, the shell, the public plan page and the raid detail's `RaidplanTab` are loaded with `lazy(() => import(…))` (one chunk each, the shell's `<Suspense>` shows the `RaidLoader` meanwhile), `vite.config.ts` splits react/router (`vendor-react`) and `lucide-react` (`vendor-icons`), and only German is bundled — English is fetched as `i18n-en` when chosen (#436, guarded by `test/web-client/conventions/codeSplitting.test.js`); so a new page gets its own `lazy` line in `App.tsx`, never a static import.
- Backend route handlers live in `src/web/apiRoutes/*.js`, grouped by domain the same way the pages are. Each file also exports its **`routes` table**, which is where a route gets registered — see "Routen registrieren" below.
- **Wo ein Raid steht, entscheidet der Server, nicht die Seite.** Die Schritt-Leiste im Kopf der Raid-Detailseite (`RaidDetailPage`) kommt fertig aus `src/web/events/raidDetailSteps.js` — `raidSteps()` für ein Raid-Helper-Event, `eventSteps()` als fünfschrittiges Cockpit für ein eigenes (#319). Beides ist rein über dem Payload, das die Seite ohnehin bekommt: so hängen die Regeln in Jest statt im TSX, und später kann die Liste `/raids` dieselbe Antwort nutzen. Einzelheiten in [docs/events.md](events.md), Abschnitt „Das Raid-Cockpit auf der Raid-Detailseite“.
- **Die API des Clients liegt in `src/web-client/src/api/`, eine Datei je Bereich (#437)** — `client.ts` (`get`, `send`, `sendRaw`, `ApiError`, `pollJob`), `csrf.ts`, dann `session`, `dashboard`, `channels`, `settings`, `discordServers`, `raidhelperRetirement`, `botCommands`, `roster`, `raids`, `raidTemplates`, `notifyTemplates`, `raidDetail`, `raidManage`, `eventSeries`, `recruitment`, `history`, `loot`, `cla`, `lootcouncil`, `profile`, `signups`, `setup`, `raidplan`; die Typen stehen bei ihren Funktionen. `index.ts` re-exportiert alles, eine Seite importiert weiter aus `"../api"`; `canAccess`/`canAccessAny` wohnen in `lib/access.ts` (übergangsweise auch über `api` erreichbar). Eine neue Funktion kommt in die Datei ihres Bereichs, eine neue Datei in `index.ts` — `test/web-client/conventions/apiSplit.test.js` prüft beides und hält die Exportliste gegen `fixtures/apiExports.json`.
- **Der CSRF-Token wird nicht mehr durchgereicht.** `getSession()` legt ihn in `api/csrf.ts` ab, `send()`/`sendRaw()` setzen den `X-CSRF-Token`-Header von dort (`mutatingHeaders()` ist die reine, getestete Regel). Keine API-Funktion nimmt ihn als Parameter, kein Component als Prop, der `ShellContext` trägt nur den `user` — `test/web-client/conventions/csrf.test.js` bricht, sobald `csrfToken` außerhalb von `api/csrf.ts` und dem `Session`-Typ wieder auftaucht. Guild-Wechsel und „Ansicht als“ laden die Seite neu (also die Session), der Server hält einen Token je Session.
- **Laden geht über `hooks/useApi(fn, deps, { enabled?, initial? })`** → `{ data, error, loading, reload, setData }`. `fn` läuft beim Mount und bei jeder Änderung der `deps` (die Eingaben des Requests: Event-Id, Filter), `reload()` nach einer gespeicherten Änderung; der jüngste Aufruf gewinnt immer (eine ältere Antwort, eine nach Wechsel der Eingaben oder nach Verlassen der Seite wird verworfen — die Regel ist rein in `lib/asyncState.ts` und dort getestet). Ein fehlgeschlagener `reload` behält die Daten und merkt sich den Fehler, ein erfolgreicher löscht ihn; `setData` ändert die geladenen Daten an Ort und Stelle (optimistisch, oder mit der Antwort eines Speicherns). `enabled: false` schickt nichts (ein Request, der auf einen anderen oder ein Recht wartet), `initial` zeigt eine von früher behaltene Antwort bis zur frischen. Gezeichnet wird der Zustand mit **`components/ui/AsyncView`** (`state`, `loading`-Fallback, `error`-Zeile, `children(data)`) oder — wo nach dem Laden noch Hooks folgen — mit den beiden Guards `if (x.error) …; if (!x.data) …;` in derselben Reihenfolge. Ein eigenes `useState<ApiError | null>` hat nur noch, wer über `useJobs().run()` lädt (Loot-Council, Drop-Check); `test/web-client/conventions/useApi.test.js` hält die Liste. Ein bewusst stilles `.catch(() => undefined)` trägt einen Kommentar, warum der Fehler nicht gezeigt wird.
- **Was die Raid-Detailseite liest, baut `src/web/events/raidDetailView.js`** (#424): `buildRaidDetail({ guildId, eventId })` setzt die Antwort von `GET /api/raids/detail` aus je einem Teil-Builder zusammen (Event finden, Setup mit Snapshot-Rückfall, Anwesenheit, eigenes Event, Softres/Ziel, Logs, Kopf, Spieler-Übersicht) und liefert `{ body }` oder `fail(...)`; die Route in `apiRoutes/raidDetail.js` ist nur noch `sendResult`. Die Reihenfolge der äußeren Aufrufe (Raid-Helper, dann Discord-Mitglieder, dann Namen, dann Log-Titel) ist die des alten Handlers. Tests: `test/web/events/raidDetailView.test.js`.
- **Waiting looks the same everywhere: `components/ui/RaidLoader.tsx`** — four class icons with their names going at a random TBC end boss, one line saying what is being loaded. A page body renders it plain, a card `compact`, and `components/PageLoader.tsx` (the overlay of a long operation, e.g. the Loot-Council's first load) puts the same scene on a panel over the dimmed page. It is decorative: the icons are the ones the menu already mirrors (class icons plus the raid icons of `lib/raidIcons.ts`, so no unchecked icon name ever enters), the party and the boss are drawn once per mount, and nothing moves under `prefers-reduced-motion`. **A page must not go back to its own `<div class="empty">Lade…</div>`** — `test/web-client/conventions/raidLoader.test.js` scans every `.tsx` for that.

## Wo ein Backend-Modul hingehört (#425)

`src/web/` ist die HTTP-Seite des Bots, nicht mehr seine Domänenschicht. Die Ordner:

| Ordner | Inhalt |
|---|---|
| `src/stores/` | alle JSON-Stores (`*Store.js` auf `jsonStore.js`), `configStore`, `configSchema`, `settingsMigration`, die Fassade `settingsStore` |
| `src/services/<bereich>/` | Domänenlogik, die Befehle, utils **und** das Web brauchen: `discord/` (Bot-Client, Rollen, Pings, App-Emojis, Rollen-Abgleich, Befehlsrechte), `events/` (Anlegen, Verwalten, Event-Nachricht, Quellen, Raid-Listen, Vorlagen), `signups/`, `setup/` (Editor, Setup-Nachricht, Pings, Invite-Call, Suche), `raidplan/` (Board, Einteilungen, Katalog-Standard), `loot/` (Loot-System, Statistik, Gear), `characters/` (Charakter-Infos, Anwesenheit), `logcheck/` (Log-Kanal, Log-Zuordnung, Report-Liste), `talk/` (Raid-Übersicht) |
| `src/web/http/` | Server, Router, Routen-Tabelle, Zugriff, Body/Antwort/Ergebnis-Helfer, Seitenrouten, Login, aktiver Server, Ansicht-als, Client-Auslieferung, Version, Deploy-Stand, Hintergrundjobs |
| `src/web/apiRoutes/` | ein Modul je API-Bereich (unverändert) |
| `src/web/report/`, `src/web/pages/`, `src/web/static/` | serverseitig gerenderte Seiten: der Log-Report (samt `render.js`, `charts.js`, `adminChrome.js`), `/docs`, die öffentliche Event-Seite, der Kalender-Feed |
| `src/web/<bereich>/` | was nur das Web liest: `events/` (Raid-Detail, Serien, Erinnerungen, Raid-Helper-Umstieg), `signups/`, `setup/`, `raidplan/`, `loot/` (Loot-Council, BiS, Import), `characters/` (Roster, Profil), `logcheck/`, `dashboard/`, `channels/`, `recruitment/` |

**Die Regel:** `src/commands/` und `src/utils/` laden nie aus `src/web/`; `src/services/` und `src/stores/` auch nicht, bis auf `web/http/apiResult.js` (die `fail(status, code, message)`-Form, die einige Services ihrer Route zurückgeben). `test/docs/layering.test.js` prüft das, `test/web/noCycles.test.js` dazu, dass nirgends ein Ring entsteht. Braucht ein Befehl ein Modul aus `src/web/<bereich>/`, zieht es nach `src/services/<bereich>/` um (samt Test, gespiegelt).

## Routen registrieren (`src/web/http/routeTable.js`, `apiRouter.js`, #421)

Es gibt **eine** Liste aller `/api/*`-Routen, und sie steht bei den Handlern: jede `src/web/apiRoutes/*.js` exportiert `routes = [{ method, path, handler, area | auth | adminOnly, level? }]`. `routeTable.js` sammelt die Tabellen aller Module (`MODULES` dort — eine neue Datei kommt in diese Liste, `test/web/http/routeTable.test.js` merkt es, wenn sie fehlt), prüft sie beim Laden (Methode, `/api/`-Pfad, Handler-Funktion, kein Eintrag doppelt) und stellt `find(method, path)` und `methodsFor(path)` bereit. `apiRouter.handle()` schlägt darin nach und ruft **immer** `await handler(req, res, url)`; `apiAccess.js` liest den Bereich aus **derselben** Tabelle (docs/permissions.md). Eine Route steht damit genau einmal — Pfad, Methode, Handler und Berechtigung nebeneinander.

- **Ein Eintrag** nennt entweder `area` (eine Bereichs-Id oder eine Liste — jede davon auf der nötigen Stufe öffnet den Pfad; Stufe = GET liest, alles andere schreibt, es sei denn `level` legt es fest), oder `auth: "none" | "menu" | "token"` (ohne Login / jeder Menü-Nutzer / Bearer-Token, siehe permissions.md), oder `adminOnly: true`. **Ohne alles ist eine Route Voll-Admin-only** (fail-closed) — und `test/web/http/apiAccess.test.js` verlangt, dass das dann ausdrücklich dasteht.
- **Pfade sind exakt**; Parameter stehen in Query und Body (`/api/raids/detail?event=<id>`), nie im Pfad. Bekannter Pfad mit falscher Methode antwortet **405** (`method_not_allowed`, mit `Allow`), unbekannter Pfad 404 — beides erst nach dem Bereichs-Gate, damit ein Fremder aus dem 405 nicht lernt, welche Pfade es gibt.
- **Handler-Präambel:** `withUser({ full?, write?, csrf?, body? }, async ({ user, body, query, url, req, res }) => { … })` aus `src/web/http/apiHandler.js` erledigt Menü-Nutzer (`requireAdmin`; `full: true` = `requireFullAdmin`), Schreibrecht auf einem Bereich (403), CSRF-Header und JSON-Body (immer ein Objekt) in genau dieser Reihenfolge; die gewrappte Funktion behält die Signatur `(req, res, url)`, Tests rufen sie also weiter direkt auf. Nur die Session-Routen mit `getRealUser` (Ansicht als Rolle) und die Token-Routen (`ingest.js`) machen ihre Prüfung selbst.
- **Fehler:** nach außen gibt es eine Form, `{ error: { code, message } }` (`apiResponse.error`, der Client liest `body.error`). Innen liefert `src/web/http/apiResult.js` `fail(status, code, message)` für Services, die den Status selbst kennen (`sendResult(res, result)` antwortet damit), `sendFailure(res, { code, error })` für die Kurzcodes von setupEditor/signupService/raidplan-Stores mit der einen Tabelle `HTTP_BY_CODE`, und `AppError(code, status, message)` zum Werfen — `apiRouter.handle()` fängt ihn und antwortet mit seinem Status statt 500 `internal_error`. Ein Handler braucht also kein eigenes try/catch, das nur loggt und 500 sendet.
- **Query und Body lesen:** `q.str / q.int / q.bool / q.snowflake` aus `src/web/http/apiParams.js` (`q.str(query, "event")`, `q.str(body, "reportId")`) statt `String(body.x || "").trim()`; `cla.js`, `raidDetail.js` und `eventManage.js` machen es vor.
- **Tests:** `test/web/http/routeTable.test.js` (Tabelle vollständig, Golden-Master der Dispatch-Liste), `test/web/http/apiRouter.test.js` (Dispatch, 404/405, AppError, Area-Gate), je Route-Modul `test/web/apiRoutes/<name>.test.js`, `test/web/http/apiHandler.test.js` (401/403/CSRF/Body), `test/web/http/apiResult.test.js`, `test/web/http/apiParams.test.js`.

## Stores (`src/stores/jsonStore.js`, `src/config/paths.js`, #419)

Jeder `*Store.js` hält seinen Stand in einer JSON-Datei unter `data/` — und alle gehen dafür über **eine** Basis statt eigener `readAll`/`writeAll`-Kopien.

- **`DATA_DIR`** kommt aus `src/config/paths.js`: `<repo>/data`, oder `EVENTHELPER_DATA_DIR`, wenn gesetzt (Docker-Volume, zweite Instanz mit eigenen Daten; ein relativer Wert gilt ab Repo-Wurzel). Pfade immer über `dataPath(...)` bzw. `settingsPath(name)` bauen, nie selbst per `__dirname` + `"data"`.
- **`createJsonStore({ file, defaults, normalize, cache, space })`** liefert `read()`, `write(value)`, `update(fn)`, `remove()`, `ensureDir()` und `useFile()`. `read()` gibt `normalize(Datei)` zurück; fehlt die Datei, ist sie kein JSON oder wirft `normalize`, gibt es `defaults`. Ein Store behält seine öffentlichen Funktionen und reicht intern nur durch (`readAll = () => store.read()`, `writeAll = (events) => store.write({ events })`).
- **Geschrieben wird atomar**: erst eine versteckte Temp-Datei im selben Verzeichnis (`.<name>.<pid>.<id>.tmp`), dann `renameSync` darüber. Ein Absturz oder eine volle Platte mitten im Schreiben lässt die alte Datei heil, statt eine halbe zu hinterlassen, die der nächste Start als „leer“ liest. Windows verweigert das Umbenennen kurz, solange ein anderer Prozess (Virenscanner, Editor) die Datei offen hält: `EPERM`/`EACCES`/`EBUSY` werden bis zu fünfmal wiederholt. Für Stores mit einer Datei je Datensatz (`reportStore`) gibt es `writeJsonAtomic`/`readJsonFile` einzeln.
- **`cache: true`** merkt sich den normalisierten Wert und liest die Datei erst wieder, wenn sich `mtime`, Größe oder Inode ändern (auch eine Änderung von Hand zählt); jeder Aufruf bekommt eine Kopie, eine Änderung am Ergebnis landet also nie im Cache. Eingeschaltet für `config.json` (`getConfig()`, fast jeder Request) — mit der ganzen Schema-Normalisierung als `normalize`, sie läuft also nur, wenn die Datei eine neue Version hat (siehe unten).
- **Tests**: `store.useFile(tempStoreFile("x.json"))` richtet einen Store auf eine eigene Datei, `useFile(null)` zurück auf die Vorgabe — das ist der eine Hook (früher gab es daneben `_setFileForTests`). Wer gar nicht auf die Platte will, mockt `fs` mit `test/helpers/memoryFs.js` (`jest.mock("fs", () => require("../helpers/memoryFs").memoryFs())`); der kennt auch `renameSync` und `statSync`, die das atomare Schreiben und der Cache brauchen.

### Die Einstellungen unter `data/settings/` (#420)

`src/stores/settingsStore.js` war früher ein Store für fünf Sammlungen. Heute ist es nur noch eine **Fassade**, die alle bisherigen Exporte unverändert weiterreicht — die ~50 Importeure und die vielen `jest.mock(".../settingsStore")` in Tests laufen ohne Änderung weiter. **Neuer Code importiert den Fach-Store**, den er braucht:

| Datei | Inhalt |
|---|---|
| `recruitmentStore.js` | Recruitment-Vorlagen (`recruitment.json`) und gepostete Nachrichten (`recruitment-posts.json`); `useFile(templates, posts)` |
| `raidTemplateStore.js` | Raid-Vorlagen (`raid-templates.json`); Form und Regeln bleiben die reinen Funktionen in `raidTemplates.js` |
| `notifyTemplateStore.js` | Anmelde-Aufruf-Vorlagen (`notify.json`) |
| `raidsheetStore.js` | Google-Sheets-Ziele — die Liste `raidsheets` in `config.json`, liest und schreibt über `configStore` |
| `configStore.js` | `getConfig()`, `saveConfig()`, `resolveEventSheetLink()`, dazu `readStored()`/`writeStored()` für die Datei, wie sie liegt |
| `configSchema.js` | `CONFIG_DEFAULTS`, `normalizeConfig()` und die `normalize*`-Funktionen — rein, ohne Datei |
| `settingsMigration.js` | `migrateSettings()`: einmalige Umstellung alter Dateien beim Start |

- **`getConfig()` ist gecacht**: `configStore` hängt `normalizeConfig` als `normalize` an die Basis mit `cache: true`. Normalisiert wird nur, wenn die Datei eine neue Version hat (`mtime`/Größe/Inode), jedes Schreiben verwirft den Cache, jeder Aufrufer bekommt eine eigene Kopie — wer das Ergebnis verändert, verändert nie den Cache (heute tut das auch kein Aufrufer). Eine fehlende Datei liest sich als `normalizeConfig({})`, einmal berechnet.
- **Keine Migration mehr im Lesepfad.** `bot.js` ruft beim Start einmal `migrateSettings()` auf. Die stellt um: alte Raid-Helper-Einträge `{ id, name }` in `raid-templates.json` → Vorlage ohne Größe (`rh-<id>`); einen alten Server-Block (`discordServers.eventGuildId`/`talkOverviewChannelId` ohne `eventGuilds`) → ein Eintrag in `eventGuilds`; den alten globalen `raidDefaults.templateId` → `categoryRaidTemplate` für jede Raid-Kategorie. Sie ist idempotent, schreibt nur bei einer Änderung, loggt jede Änderung als `[settings] Migration: …` und wirft nie (ein Fehler wird geloggt, der Start läuft weiter). Beim zweiten Start: keine Zeile, kein Schreiben. Danach normalisiert `getConfig()` nur noch das Schema. Die Fassade behält für `normalizeDiscordServers`/`normalizeEventGuilds` das alte Verhalten (alter Block zählt mit), `configSchema` kennt ihn nicht.
- `signupSourcesOf()` (#291) bleibt bewusst im Schema: es hängt nur an der Datei selbst und wird mit ihr gecacht.
- **Tests**: je Store `test/stores/<name>.test.js`; `test/stores/configSchema.test.js` ist ein Golden Master — `test/fixtures/configSchema/golden.json` ist die Ausgabe von `getConfig()`/`listRaidTemplates()` für die Stände in `cases.json`, eingefroren *vor* dem Umbau. Wer das Schema ändert, ändert bewusst auch `golden.json`.

## Hintergrundjobs (`src/web/http/jobs.js`, #424)

`server.js` ist reines HTTP. Alles, was periodisch läuft oder eine Discord-Nachricht aktuell hält (Raidsheet-Aufräumen, Raid-Event-Scan, Log-Zuordnung, Event-Nachrichten, Erinnerungen, Rollen-Abgleich, Talk-Übersicht, Serien, verwaiste `/apply`-Bewerbungen), steht als Liste `JOBS = [{ name, start, stop }]` in `jobs.js`. `bot.js` ruft `startJobs(client)` direkt nach `startWebServer(client)`; das Log sagt einmal `Background jobs started: …`. `startJobs` ist idempotent, `stopJobs()` beendet alle in umgekehrter Reihenfolge (jedes Job-Modul hat dafür ein `stop…()`, das auch den verzögerten ersten Lauf abräumt). Ein neuer Job kommt in diese Liste, nicht nach `server.js`. Tests: `test/web/http/jobs.test.js` (Reihenfolge, genau einmal), `test/web/http/jobs.timers.test.js` (mit den echten Modulen: nach `stopJobs()` kein Timer mehr).

## Welcher Stand läuft (`src/web/http/version.js`, `src/web/http/deployStatus.js`, #314)

Acht PRs (#292–#313) galten als fertig, während das Deployment bei jedem Merge still scheiterte (`missing server host`) — nichts im Menü hätte es verraten. Seitdem sagt der Bot selbst, auf welchem Commit er läuft.

- **`version.js` liest einmal pro Prozess** `git log -1 --format=%H%n%cI%n%s` im Projektverzeichnis, sonst `GIT_COMMIT` aus der Umgebung (Docker, Tarball), und liefert `{ commit, short, committedAt, subject, startedAt }`. ⚠️ **Nichts davon darf je werfen**: kein git, kein Repo, hängendes git, kaputte oder leere Ausgabe — jeder Fall lässt die Felder leer und den Bot laufen (`stdio: ["ignore","pipe","ignore"]`, Timeout, sha-Prüfung per Regex). Der Pfad des Verzeichnisses wird nirgends gemeldet.
- **`GET /health`** antwortet JSON `{ status, commit, committedAt, subject, startedAt }` — ohne Login erreichbar und deshalb bewusst ohne alles Vertrauliche (kein Pfad, kein Token). `test/web/http/server.test.js` hält beides fest.
- **`deployStatus.js`** vergleicht gegen `https://api.github.com/repos/mst1987/pulsebot/commits?sha=main` — öffentliches Repo, **kein Token** (ein Deploy-Stand ist keine Zugangsdaten wert), Antwort **10 Minuten gecacht**, Fehlschlag inklusive. `compare()` ist die reine Hälfte: gefunden an Index n = n Commits zurück, `behindSince` ist das Datum des **ältesten fehlenden** Commits; nicht gefunden, kein Commit oder GitHub stumm = `status: "unknown"` („nicht prüfbar“), nie ein Fehler. In Tests ist axios gemockt — **kein Test darf ins Netz**.
- **`GET /api/version`** (Bereich `settings` in `apiAccess.js`) liefert dasselbe plus Abstand. Der Commit selbst ist über `/health` ohnehin öffentlich; der Vergleich bleibt bei denen, die etwas daran ändern können — und ein Mitglieder-Seitenaufruf löst so keinen GitHub-Abruf aus.
- **Im Menü** eine ruhige Zeile unten in der Seitenleiste (`Shell.tsx`' `DeployLine`, `.side-version`, Texte rein in `lib/deployVersion.ts`): „Server läuft auf `a1b2c3d` vom 12.09. · main ist 9 Commits weiter“, höchstens zwei Zeilen, alles Weitere im Tooltip; ein Fehlschlag lässt die Zeile ganz weg statt einen Fehler zu zeigen.
- **Dashboard-Aufgabe** `deployTask()` in `dashboardOverview.js`: steht **ganz oben** in der Liste (alles andere darunter könnte über Code reden, der gar nicht läuft), gelb ab dem ersten Commit, rot ab sieben Tagen Rückstand, Link auf `docs/deployment.md`. „Nicht prüfbar“ erzeugt **keine** Aufgabe — eine Aufgabe, die niemand schließen kann, ist Lärm.
- **Das Deployment selbst**: `ci.yml` hat einen Schritt „Secrets prüfen“, der mit klarer Meldung abbricht, statt still grün zu werden; das Zielverzeichnis steht nur noch einmal da (Repository-Variable `DEPLOY_DIR`, Vorgabe `/var/www/pulsebot`), und `deploy.sh` nimmt `DEPLOY_DIR`, sonst sein eigenes Verzeichnis. Secrets, Variable und das Deployen von Hand stehen in `docs/deployment.md`.

| Folder | What goes there |
|---|---|
| `pages/<Name>Page.tsx` | a page small enough for one file (`DashboardPage`, `RaidsPage`, `ChannelsPage`, `SignupsPage`, …) |
| `pages/<area>/` | a page split into parts, with everything only it uses: `recruitment/`, `cla/`, `history/` (Übersicht, Event, Inbox, Charakter and the loot tabs and dialogs), `profile/`, `settings/` (every settings section), `roster/`, `lootcouncil/`, `raid-detail/` (tabs, `setup/` for the setup editor, `raidplan/` with `raidplan/workspace/` for the board's hooks and parts, `manage/`, `modals/`). The page itself is `<Name>Page.tsx` in its folder, its Vitest files beside it |
| `components/<area>/` | components several pages share, by domain: `loot/`, `signup/`, `roster/`, `settings/` (`settingsUi`), `raid-create/` (the "Neues Event" dialog: `useRaidCreateForm.ts` holds the state, one file per step), `channels/`, `profile/`, `raidplan/` |
| `components/ui/` | the UI kit (`Button`, `Modal`, `Popover`, `Field`, `Badge`, `DataTable`, …) — see below |
| `components/*.tsx` | the shell and cross-cutting building blocks (`Shell`, `Jobs`, `icons`, `SortTh`, `Pager`, `SectionNav`, `ListSection`, `HoverPanel`, `RaidPlanFields`, …) |
| `hooks/` | React hooks without a component: `useApi`, `useDismiss`, `useBoardView`, `useOnFocus`, `useViewPrefs` |
| `lib/` | pure logic, tested in Vitest beside it; `lib/raidplan/` holds the raid plan's libs (`assign`, `autoPlace`, `steps`, `multiSelect`, …) and the board logic, split by topic (`model`, `players`, `objects`, `geometry`, `labels`, `besetzung`, …) behind one import, `lib/raidplan` (`index.ts`) |
| `styles/<module>.css` | a module's stylesheet, named in English after the page (`settings.css`, `channels.css`, `dashboard.css`, `signups.css`, `series.css`, …), its classes under one prefix (`test/web-client/conventions/cssNamespaces.test.js`) |

A component moves into `components/<area>/` once a second page uses it, and into the page's folder while only one does. Convention scans that walk "every page and component" read the top level of `pages/` and `components/` plus the folders listed in `SPLIT_FOLDERS` (`test/web-client/clientSource.js`); a new folder of that kind goes on that list, and `read()` there takes a folder as one source.

## Sprache (i18n): Deutsch / Englisch (`src/web-client/src/i18n/`)

Das Menü spricht Deutsch und Englisch, pro Nutzer umschaltbar; umgeschaltet wird oben rechts in der Kopfzeile (`components/LangToggle.tsx`, eine kleine Pille „DE | EN“, die aktive Sprache hervorgehoben — auch schon auf der Login-Seite). Ohne Wahl gilt Deutsch. Gespeicherte Werte (Status-Ids, Rollen, Spec-Schlüssel, Kanalnamen …) bleiben unverändert; übersetzt wird nur die Anzeige. Keine Bibliothek: ein kleines eigenes Modul reicht für zwei Sprachen, Parameter und Plural.

- **Wo die Texte stehen:** `i18n/locales/<de|en>/<namespace>.json`, verschachteltes JSON; der Schlüssel ist `<namespace>.<pfad>` (`locales/en/shell.json` `{ "menu": { "raids": … } }` → `shell.menu.raids`). Eine neue Namespace-Datei wird per `import.meta.glob` von selbst geladen.
- **Einen Text hinzufügen:** Schlüssel in **beide** Dateien (`de` und `en`) eintragen, dann im Component `const t = useT();` und `t("ns.key", { name })`. Platzhalter `{name}`; Plural als Objekt `{ "one": "{count} Raid", "other": "{count} Raids" }` (optional `"zero"`), gewählt über `params.count`. In einer Lib-Funktion, die beim Rendern aufgerufen wird, das einfache `t` aus `i18n/index.ts` importieren — **nie** `t()` auf Modulebene (`const LABELS = { … t(…) }`), das friert die Sprache beim Laden ein. Für Schlüssel aus Daten (`wow.class.${id}`) `tOr(key, fallback)`.
- **Ein neuer Text, Schritt für Schritt:** (1) den Namespace des Bereichs wählen — je Seite/Bereich einer (`channels`, `settings`, `history`, `lootcouncil`, `roster`, `recruitment`, `cla`, `series`, `notifyTemplates`, `raidTemplates`, `raidDetail`, …), Knopf- und Statuswörter, die überall gleich lauten („Abbrechen“, „Schließen“, „Hinzufügen“, „Löschen“, „Bearbeiten“, „Übernehmen“, „Speichert …“), stehen in `common` und werden nur genommen, wenn der deutsche Text **genau** gleich ist; (2) den Schlüssel mit deutschem und englischem Text in `locales/de/<ns>.json` und `locales/en/<ns>.json` eintragen; (3) im TSX `t("ns.key")` — nie ein deutsches Literal, der Wächter (unten) prüft **jede** Quelldatei des Clients; (4) hat die Seite einen Render-Test, gehört ein englischer Fall dazu (`switchLang("en")`). Ein Zähler als einziges Kind eines Elements (`<Badge>{tParts("ns.open", { count })}</Badge>`) nimmt `tParts` statt `t`: es liefert die Stücke „2“ + „ offen“ als eigene Textknoten, so zeichnet der Browser ihn genau wie früher `{count} offen` (ein Text in einem Knoten liegt einen Subpixel anders). Server-Labels mit fester Id aus dem Spiel: `specClassLabel` (Loot-Council-Specs), `slotLabel` (WCL-Slot), `contentName` (Raid der Loot-Historie) in `lib/wowNames.ts`. Englische Begriffe folgen den vorhandenen Dateien: Anmeldung = signup, Kanal = channel, Vorlage = template, Vergabe = award, Bedarf = need, Aufruf-Vorlagen = call templates.
- **Was nicht übersetzt wird:** Texte, die der Server schickt (Fehlermeldungen, Labels ohne feste Id), gespeicherte Inhalte (Vorlagen, Post-Texte, Kanalnamen) und Protokollwerte wie das Bestätigungswort „LÖSCHEN“ der Sammel-Löschung.
- **WoW-Begriffe:** `lib/wowNames.ts` (`classLabel`, `specLabel`, `roleLabel`, `instanceName`) übersetzt die stabilen Ids, die der Server neben seinen deutschen Labels schickt (Priest, BeastMastery, healer, bt) — Texte in `locales/*/wow.json`. Kennt das Wörterbuch eine Id nicht, bleibt das Label des Servers stehen.
- **Server-Labels mit fester Id** (Wochentage und Gear-Stufen im Profil, Status, Loot-Werkzeug) werden genauso über `tOr("ns.key.${id}", serverLabel)` angezeigt, damit ein neuer Wert nie leer erscheint.
- **Datum/Zahlen:** jedes Datum und jede Uhrzeit läuft über `lib/format.ts` (#440): `DISPLAY_TZ` (`Europe/Berlin`, die Zeitzone der Gilde) und `locale()` (`de-DE` bzw. `en-GB`) stehen nur dort. Bausteine: `formatWith(ms, opts)` für jede Kombination, `formatTime` („19:30“), `formatDayMonth` („17.09.“ / „17/09“), `formatWeekday`, `formatDayDate` („Do 17.09.“ / „Thu 17/09“), `formatDateTime`, `isoDay` (Kalendertag als Schlüssel, nie angezeigt), dazu `formatDate`, `fmtMs`, `formatEventTime`. Deutsch sieht damit aus wie vorher; Englisch zeigt das britische Format, wie `formatEventTime`/`fmtMs` es schon taten. Kein `"de-DE"` und kein `"Europe/Berlin"` außerhalb von `lib/format.ts` und `i18n/` — das prüft `test/web-client/conventions/i18n.test.js`. Zahlen: `toLocaleString(locale())`.
- **Fallback und Wächter:** fehlt ein englischer Schlüssel, erscheint der deutsche Text (im Dev-Build mit `console.warn`); fehlt er ganz, steht der Schlüssel selbst auf der Seite. `src/web-client/src/i18n/core.test.ts` (Vitest) bricht, sobald `de` und `en` verschiedene Schlüssel oder Platzhalter haben, ein Text leer ist, ein englischer Text einen Umlaut trägt oder eine Seite `t("…")` mit einem unbekannten Schlüssel ruft. Client-Tests nutzen den echten `t` (Deutsch), für Englisch `switchLang("en")`/`inLang("en", …)` aus `src/web-client/src/test/i18n.ts` (docs/testing.md, „Web-Client“). `test/web-client/conventions/i18n.test.js` scannt **alle** Quelldateien des Clients (ohne Tests, `*.fixture.ts` und die Wörterbücher) auf hart codierte deutsche Texte: kein Umlaut/ß in einem String oder JSX-Text, keine deutsche Wortgruppe als JSX-Text; Kommentare zählen nicht. Soll ein Literal bleiben, kommt es mit Begründung in `ALLOWED`, eine Datei, die deutsche Eingaben liest (`lib/raidplan/steps.ts`, `assign.ts`), in `ALLOWED_FILES`; der Test schlägt auch an, wenn eine Ausnahme nicht mehr gebraucht wird.
- **Texte prüft ein Test gerendert oder über `t(key)`** in Vitest — nicht über den deutschen Satz im TSX. Konventionstests unter `test/web-client/conventions/` lesen nur Quelltext und die JSON-Wörterbücher (`dictionary()` aus `test/web-client/clientSource.js`).
- **Gespeichert wird die Wahl** sofort im Browser (`localStorage` `eh-lang`) und für angemeldete Menü-Nutzer am Konto: `POST /api/session/lang` → `src/stores/userPrefsStore.js` (`data/settings/user-prefs.json`), zurück kommt sie als `user.lang` in `GET /api/session` und gewinnt beim Laden — so folgt sie auf ein anderes Gerät. `<html lang>` wird mitgesetzt; beim Umschalten wird der Seiteninhalt neu aufgebaut (`key={lang}` in `Shell.tsx`).
- **Stand (Phase 2 abgeschlossen, #440):** das ganze Menü ist übersetzt. Phase 1 brachte Shell/Menü, Login, Übersicht, Raid-Liste, Raid-Detail mit Cockpit, allen Tabs/Dialogen/Verwalten und Setup-Editor, Event anlegen/bearbeiten, Anmeldungen und „Mein Profil“; Phase 2 Kanäle, Einstellungen, Historie & Loot (samt Inbox und Charakter-Seite), Loot-Council mit Drop-Check, Roster, Recruitment, Log-Auswertung (CLA), Serien, Aufruf- und Raid-Vorlagen. Deutsch bleibt Standard und Rückfall; offen sind nur Texte, die der Server fertig schickt.
- **Phase 2 (offen):** Loot-Council, Roster, Historie & Loot, Log-Auswertung, Recruitment, Kanäle, Einstellungen, Raid-/Aufruf-Vorlagen und Serien; alle **Texte, die der Server fertig schickt** — API-Fehlermeldungen und Toasts (`message`), die Texte der Fortschrittsleiste/Schritte von Raid-Helper-Events, Kanalnamen-Herkunft (`naming.label`), Gruppen-Labels des Raidplans, Instanznamen außerhalb von TBC/Classic — und die Report-Seiten (`src/web/report/`). Für Server-Texte braucht es entweder feste Ids/Codes, die der Client übersetzt, oder die Sprache des Kontos im Request.

## How a page with many sections is laid out

Two pages outgrew a single tab row and are organised in two levels instead — the upper level says *what kind* of thing a section is, the lower *which one*:

- **Einstellungen** uses a section column (`components/SectionNav.tsx`) whose entries and groups are declared in `src/web-client/src/lib/settingsSections.ts`: *Zugang* (who gets in), *Verbindungen* (Discord/Raid-Helper, Battle.net, Loot-Sync tokens — every foreign system and its credentials), *Raid-Kategorien*, *Module* (one feature's behaviour). Two flags on a section carry real consequences: `adminOnly` keeps it out of a limited settings user's menu (mirroring `ACCESS_KEYS`/`requireFullAdmin` on the server), and `standalone` marks a section that saves itself, so the page's shared save button is not rendered under it. The open section is in the url as `?section=<id>`, so a hint on another page can link straight at it.
- **Historie & Loot** has three areas as a segment — *Loot* (Vergaben · Items · Gründe · Nach Raid), *Raids & Logs* (Raids · Warcraft Logs), *Charaktere* (`AREAS` in `HistoryPage.tsx`, design issue #225). The open area follows from the open view, so there is only one thing to persist and `?tab=items` still opens the right place. Import and inbox are not views: *Loot importieren* is a dialog from the page head (`pages/history/ImportLootDialog.tsx`, with a preview from `POST /api/history/import-preview` → `web/loot/lootImportPreview.js`, which stores nothing), the *Addon-Inbox* its own page `/history/inbox` (`HistoryInboxPage.tsx`, area `history` only). The old `?tab=import` / `?tab=inbox` links open the dialog resp. redirect. Who got an item, when and why is one dialog (`pages/history/ItemAwardsDialog.tsx`, rows open it; single awards deletable with write access) instead of a hover panel per recipient. The module's CSS is `src/web-client/src/styles/historie-loot.css`.
- **Everything configured per raid category** lives in one place, Einstellungen → *Kategorien* (`pages/settings/CategoryMatrix.tsx`): whether it is an event category, its raider roles, its loot addon and its fixed sheet — one card per category, saved with the page's form. It used to be four tabs each re-listing the same categories. A category that is switched off shows nothing but its switch.

## Editing a collection: list first, one editor at a time

Anything the admin keeps several of — raidsheets, Aufruf-Vorlagen, Recruitment-Vorlagen, gepostete Nachrichten — uses one shared pattern instead of stacking a form per entry (or parking a permanent "create" form under the list):

- `lib/collectionEditor.ts`'s `useCollectionEditor(param)` holds which editor is open in the url as `?<param>=<id|new>`: `""` = the list, `"new"` = creating, anything else = that entry's id. It **keeps the page's other params** (the settings section, the recruitment tab), and `editId` is `""` while creating, so no request ever asks the server to load an entry called "new".
- `components/ListSection.tsx` renders either the list (a heading row with the section's one "new" button, `ListHeader`) or the editor **in the list's place** (`EditorPanel`, with the way back where the new-button was). An id that no longer exists falls back to the new-editor rather than to a blank page.
- The forms themselves stay dumb: no own heading (the panel titles them) and an always-present *Abbrechen* that closes the editor. Two collections on one page need two params — Recruitment uses `edit` for templates and `editpost` for posted messages; sharing one would make the two editors close each other.
- **Recruitment opens its editors as modals over the list** instead (design #215): same url params, but the editor is a `Modal` with the live Discord preview (`pages/recruitment/DiscordPreview.tsx`, markdown parsed by `lib/discordMarkdown.ts`, whose regexes are held identical to the JS twin `test/web-client/support/discordMarkdown.js` (test support until the Vitest suite of #435 tests the `.ts` directly)) beside the fields, so the other templates stay in view. `?editpost=new` is the "Nachricht posten" dialog. A post remembers the `templateId` it was posted from; an application's `status` ("neu" = younger than 7 days, nothing stored) and class/spec icons come from `src/web/recruitment/recruitmentApplications.js`.

`test/web-client/conventions/listSection.test.js` holds the line, including a scan that no page renders `entries.map(e => <SomethingForm …/>)` again.

## Bausteine für Popups, Felder, Badges und Tabellen (#439)

Wer im Client etwas Aufklappbares, ein Formularfeld, ein Badge oder eine Tabelle baut, nimmt diese Bausteine statt einer eigenen Kopie — jeder hat einen Wächter-Test unter `test/web-client/`.

- **Schließen bei Klick außerhalb und Escape: `hooks/useDismiss(targets, open, onClose, { event, capture, escape })`.** `targets` sind Refs oder Elemente, die als „innen“ gelten (Panel und meist der Knopf, der es öffnet). Standard ist `mousedown` ohne Capture mit Escape; die Picker nehmen `click` ohne Escape, der Raidplan `pointerdown` in der Capture-Phase. Die reine Logik steht in `lib/dismiss.ts`. `useDismiss.test.js` bricht, sobald eine Datei wieder selbst einen `mousedown`/`click`-Listener mit `contains()` anlegt.
- **Schwebende Boxen: `components/ui/Popover`.** Anker (Ref/Element), Portal nach `<body>` (oder mit `host="dialog"` in den offenen Modal-Dialog), Platzierung per `place` aus `lib/popoverPosition.ts` (`tipPlacement`, `belowEndPlacement`, `panelPlacement`, `pointPlacement`, alle mit Viewport-Clamping), bei Scroll/Resize schließen oder mitlaufen (`follow`), Schließen über useDismiss, wenn es ein `onClose` hat. Darauf bauen `RichTip` (Loot-Council), `HoverPanel`, `ManageMenu` und das Kontextmenü des Raidplans; der globale `TipLayer` nutzt dieselbe `tipPosition`. Der Raidplan-Flyout behält seine eigene Positionierung (Seitenpanel/Bottom-Sheet) und schließt über useDismiss. Nur rendern, solange offen: `{open && <Popover …/>}`.
- **Formularfelder: `components/ui/Field`** — `Field` (Label mit Info-Tooltip, Steuerelement, `hint`, `error`), dazu `FieldLabel` und der runde `InfoTip`. Die Wrapper-Klassen der Module (`field`, `set-field`, `dlg-field`, …) bleiben und kommen als `className`; `.field-label`, `.field-error` und `.info` stehen in `index.css`.
- **Icons: eine Quelle, `components/icons.tsx`.** Kein Icon des gemeinsamen Satzes wird anderswo noch einmal definiert (`icons.test.js`). Der Raidplan zeichnet mit `lucide-react`; eine Umstellung aller Icons darauf steht aus.
- **Badges und Chips:** `ui/Badge` hat `tone`, `size="sm"` (kompakt) und `onRemove` (kleines ×, z. B. aktive Filter). `ui/Chip` ist der größere, klickbare Badge: Umschalter (`pressed` + `onClick`) oder entfernbar (`onRemove`), mehrere in einer `.chip-row`.
- **Tabellen: `components/ui/DataTable`** — Spalten als Daten (`label`, `sortKey`, `tip`, `width`, `className`, `actions`), Sortierung über `useTableSort`/`SortTh`, `empty` statt einer Tabelle ohne Zeilen, `pageSize` blendet den `Pager` ein (Seitenlogik in `lib/dataTable.ts`). Tabellen- und Wrapper-Klasse bleiben die des Moduls. Erster Einsatz: die Vorlagen im Recruitment; die übrigen Tabellen ziehen nach und nach um.

## The help page `/docs` (`src/web/pages/docsPage.js`)

`/docs` is server-rendered (`render.js` layout, reachable without a login, linked from the topbar). Its content is **not** read from `docs/guide-discord.md` / `docs/guide-web-admin.md`: `DISCORD_GROUPS` and `WEB_GROUPS` in `docsPage.js` are a third, hand-written copy of the same outline (shorter, HTML strings). A change a raider or the orga should see belongs in the guide **and** in `docsPage.js`. `test/web/pages/docsPage.test.js` checks that every slash command the page names is registered (the loader test does the same for the Discord guide); nothing checks the rest of the text against the guides.
